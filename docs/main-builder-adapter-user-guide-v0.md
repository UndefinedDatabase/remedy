# Main Builder Adapter — User Guide v0

## What is a main builder adapter?

A main builder adapter is Remedy's way of connecting to an external coding tool (Claude Code,
Pi.dev, OpenCode, or any CLI builder) to generate fix candidates for test failures and review
findings. Remedy does not generate fixes itself — it creates a structured request package, tracks
the builder session, and evaluates the builder's output through multiple safety gates.

## Why Remedy does not hardcode one provider

Remedy is a modular Baukasten (building-block system). Different projects may prefer different
builders:

- **Claude Code** for complex multi-file reasoning
- **Pi.dev** for web-based collaborative sessions
- **OpenCode** for open-source CLI workflows
- **Generic CLI builders** for custom or specialized tools
- **Ollama/local models** for cheap, small, repetitive tasks (future)

All adapters share the same lifecycle, the same safety gates, and the same intake path.

## How it works

1. **Repair Loop identifies what needs fixing** — a test failure or review finding becomes a
   repair work item with a token-aware context pack.

2. **Remedy creates a request package** — a minimal, redacted description of what the builder
   should fix, what constraints apply, and what output format is expected. No raw logs, diffs,
   or secrets are included.

3. **The operator selects and launches a builder** — Remedy does not start the builder
   automatically in v0. The operator chooses which adapter to use and launches it.

4. **The builder produces output** — a proposed patch or candidate. This output is recorded
   as a reference (not raw content) in the session record.

5. **Output goes through safety gates**:
   - External Builder Sandbox (quarantine)
   - Provider Trust Gate
   - Candidate Quality evaluation
   - Human review
   - Apply proof (approval required)
   - Re-test (bounded, failing blocks)

6. **Only after all gates pass** is the repair considered done.

## Why output is untrusted until verified

Builder output is generated by an external tool. Remedy cannot trust that the output:
- Is correct (it may introduce bugs)
- Is safe (it may contain secrets or harmful changes)
- Is complete (it may miss edge cases)
- Does what it claims (self-claims are not evidence)

The safety gates ensure that every candidate is independently verified before it can be applied.

## Why token-aware request packages matter

External builders charge tokens. Remedy tracks estimated token costs and:
- Prevents blind expensive routing (unknown cost → human decision)
- Prefers local/cheap routes for small tasks
- Requires human approval for expensive sessions
- Reduces context to the minimum needed (safe summaries, not raw dumps)

## Why local/Ollama may be better for small tasks

Not every fix needs a full external builder session. Small, well-understood fixes can often be
handled by a local model (Ollama) at much lower cost. Remedy's token economy and routing
recommendations help the operator choose the right tool for the job. This is a future capability —
not built in this block.

## What is not automated yet

- **Builder execution**: The operator must launch the builder manually in v0.
- **Real adapter configuration**: All real adapters are disabled by default. No secrets or
  API keys are stored by Remedy.
- **Auto-apply**: Candidates are never applied automatically. Human approval is required.
- **Ollama/local model integration**: Future block, not this one.
- **External memory (MemPalace)**: Future external adapter, not Remedy core.
