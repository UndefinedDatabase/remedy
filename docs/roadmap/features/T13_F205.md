# T13_F205 — Multi-repo missions
**Tier 13 · Depends on: F056, F146/F148 · Blocks/used by: F206/F207; systems instead of single repos**

## Goal & Done
See ROADMAP.md F205; the Done criterion there is binding.

## Context (existing code & prior features)
F056 missions chain jobs of ONE project; project identity (F146) and leak discipline (F148) are the guardrails.

## Design
mission_state extended: a mission may lead jobs across multiple pids; a mission manifest ~/.remedy/missions/<mid>.json {goal, repos:[{pid, root, objective}], jobs:[{pid, jid}]} - evidence/cards/ledger stay STRICTLY project-local; the mission holds references only. The orchestrator loop (F070) switches project context per job (detect by root, F146). Cockpit: the mission thread shows repo chips per chain link; clicking loads that project's cockpit (?project=pid&job=jid).

## Task slicing
T001 manifest + mission_state extension + context switching in the loop + tests (2 fixture repos). T002 the UI chain band with repo chips + an F148 leak regression run over mission data.

## Acceptance & tests
The fixture mission: 3 chained jobs across 2 repos, the thread clickable; the leak property stays green (the mission API returns references + titles only, never foreign evidence to the unauthorized - the F185 coupling).

## Risks / anti-goals
No global evidence store (the reference architecture is deliberate); a mission fails honestly if a repo access is missing (no partial muddling-through without a note).
