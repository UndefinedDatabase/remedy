# T3_F106 — Session resume instead of rebuild
**Tier 3 · Depends on: F003 session ids · Blocks/used by: repair cost**

## Goal & Done
Repair rounds stop resending the world: where the provider supports
resuming a session, repair calls resume the original session and send
only the findings delta — with an honest, automatic fallback to full
context when the session is gone, flagged in evidence. DONE when a
fixture repair chain shows measured token reduction with resume versus
without, an expired-session fixture falls back seamlessly with
resume_used=false, and correctness never depends on resume working.

## How it fits (inspect current shape before building)
Session identifiers are already captured in call evidence (verify the
exact field and which provider adapters populate it). The repair loop
and the diff-repair feature define what a repair sends; this feature
changes the TRANSPORT framing (resume + delta) per provider capability.
Capability is per adapter: a small capability flag on the provider
adapter surface (inspect its current shape) — providers without it are
untouched.

## Design (suggested shape)
- Provider adapter surface gains supports_resume + a resume parameter
  on the call entry (additive; adapters that ignore it are honest
  no-ops with the flag false).
- Repair path: when the previous round's session id exists and the
  adapter supports resume → send resume reference + findings delta
  (the diff-repair prompt without the re-shown regions the session
  already contains — the hunk selection shrinks accordingly); record
  resume_used, session_ref, and the token actuals as always.
- Failure semantics: a resume attempt that errors or clearly lost
  context (provider signals or validation failure of the response)
  falls back ONCE to the full-context path within the same round —
  fallback is a normal, evidenced event, never a task failure by
  itself.
- Measurement: the benchmark and stats can compare resume_used
  true/false token profiles — no separate reporting machinery here.

## Task slicing
- **T001** adapter capability + resume parameter + evidence fields +
  unit tests (unsupported adapter → honest false, zero behavior
  change).
- **T002** repair-path integration + delta prompt shrinking + expired
  fallback + fake-provider tests (resume happy path; expiry →
  fallback with correct flags; both rounds' evidence complete).
- **T003** a measured fixture comparison recorded into evidence
  (resume vs full token counts) + docs.

## Acceptance
- Fixture chain: second repair round resumes, tokens measurably below
  the full-context baseline, evidence flags correct. Expiry fixture:
  fallback within the round, task outcome identical. Providers without
  support: byte-identical behavior (regression suite untouched).

## Edge cases & assumption defaults (A9)
- Resume across a process restart: only if the session id persisted in
  evidence and the adapter accepts it — otherwise fallback; never
  cache session state outside evidence. Mixed models in a failover
  chain: resume only within the same model+provider pair (a resumed
  session on a different model is undefined — guard it).

## Orchestrator brief
T001 first and small. Gate T002 on diff-repair being merged (the delta
framing builds on it). Demand the fallback-once rule verbatim in the
T002 order.

## Do not touch
Failover policy, provider adapter internals beyond the additive
surface, prompt content rules. Suggested tests:
tests/orchestration/test_session_resume.py.

## Scope note (F075 candidate routing, 2026-08-06)
The orchestrator move schema has no `resume` kind: a paused job's only
forward path is re-dispatch, and a job that ended `max_cycles_reached`
cannot be continued (F075 R5/R6 evidence, routed from
.agent/candidates.md by F079 R1 as R-0201). When F106 is claimed,
treat "resume a job/mission from its persisted state" as in-scope
territory alongside provider-session resume — the two halves of the
same promise that an interruption is not a restart.

## Built State — what F106 delivered

T001–T003 built provider-session resume for repair rounds only; the
job/mission-resume half of the Scope note above is deferred out of this
closure by DECISION F106 D2.

- `packages/orchestration/pingpong_provider.py` — every concrete adapter
  (`FakeProvider`, `ClaudeProvider`, `ClaudeCliProvider`) exposes
  `supports_resume: bool` and an additive `resume: str | None = None` on
  `build`/`review`; `BuilderOutput`/`ReviewerOutput` default
  `resume_used`/`resume_session_ref` to `False`/`""`. Only `FakeProvider`'s
  test-only constructor override ever returns `True` — no adapter resumes
  in production yet (T001).
- `packages/orchestration/pingpong_loop.py` — a repair round's primary
  Builder and Reviewer calls each resume the prior round's own session,
  gated on `is_repair`, `supports_resume` and a captured prior session id
  (T002a/T002b-i); a resume attempt that errors falls back ONCE to
  `resume=None` within the same round, recorded on `resume_fallback`
  (T002c); and when a round is actually resuming, `compose_builder_prompt`/
  `compose_reviewer_prompt` take a `resume_hunks_text` parameter — rendered
  by `packages/orchestration/diff_repair.py`'s `select_repair_hunks`/
  `render_repair_hunks` (the module F111 built, reused here for
  prompt-content shrinking only, never diff-apply; DECISION F106 D1) —
  that replaces the full-diff prompt segment (T002b-ii).
- T003's measured comparison
  (`tests/orchestration/test_session_resume.py::TestT003MeasuredTokenReduction`)
  compares `PreparedCallInput.prompt_len_bytes`
  (`packages/orchestration/call_identity.py`) on a resumed vs full-context
  repair round: Builder round 2 1331 vs 1384 bytes (~3.8%), Reviewer round 2
  2208 vs 2270 bytes (~2.7%), measured at commit `177dada4`.

Tests: `tests/orchestration/test_session_resume.py`, 27 tests across all
