# T4_F120 — Automatic card harvesting
**Tier 4 · Depends on: F117, F063 mechanics · Blocks/used by: knowledge inflow**

## Goal & Done
Knowledge stops evaporating after runs: a post-job harvest pass turns
repeated review findings, postmortem patterns and correction signals
into card CANDIDATES — proposed, evidence-referenced, never
self-approving — flowing through the same human gate as ideas. DONE
when seeded fixtures yield exactly the expected candidates per
source, every candidate's evidence resolves at creation, approval
materializes a card through the gated store path, and the harvest
never blocks or fails the job it follows.

## How it fits (inspect current shape before building)
This is the idea engine's sibling for MEMORY: same post-terminal
funnel, same never-block discipline, same proposal/approval
mechanics — candidates are ideas of kind card_candidate (additive
kind) so denial memory, provenance typing and the queue CLI are
inherited whole (A6). Sources already exist as structured data:
review findings live in verdict evidence (repeat detection needs
finding identity — rule id + normalized message; verify what the
verdict schema captures and extend additively if identity is
missing), postmortem patterns come from the miner feature (consume
its detector, don't re-mine), and ownership corrections are noted
for later (that signal source lands with its own feature — the
harvester's source interface makes adding it trivial).

## Design (suggested shape)
- `harvesting.py`: on_terminal(job) → run source extractors →
  candidates {proposed card: type, title, draft body, scope derived
  from the evidence locations, evidence_refs typed} → the idea
  queue with kind card_candidate; per-job candidate cap (config).
- Sources v1: repeated_finding (same finding identity ≥2 within the
  job or across a window → a convention/lesson card draft quoting
  the rule, scoped to the offending paths), failure_pattern
  (delegating to the postmortem miner's detection over the window —
  emits lesson/risk drafts where the miner's pattern threshold is
  met but a playbook is too heavy: the split rule is documented —
  patterns with mechanical countermeasures → playbook proposals;
  observations without one → risk cards).
- Approval: approving a card_candidate writes the card via the
  store API with origin=harvest and the refs carried over — the
  ONLY automatic path into the store, and it still required a
  human.
- Draft bodies are honest: they quote evidence and describe the
  observation; they do not generalize beyond it (the prompt/template
  rule, tested on goldens).

## Task slicing
- **T001** finding-identity groundwork (verify/extend the verdict
  schema additively) + the repeated_finding extractor + table tests.
- **T002** failure_pattern delegation + the playbook/card split rule
  + goldens.
- **T003** the funnel hook + queue integration + approval
  materialization + never-block tests + the end-to-end (seeded job
  → two candidates → approve one → card exists with origin harvest,
  deny one → suppressed forever).

## Acceptance
- Seeded fixtures produce exactly the expected candidates with
  resolvable refs; caps respected; drafts match the honesty goldens.
  Approval is the only write path (fence + grep guards hold). The
  job's terminal handling is timing-unchanged when harvesting is
  disabled (config, default on) and unaffected by harvest failures.

## Edge cases & assumption defaults (A9)
- Candidate duplicating an existing ACTIVE card (scope+title
  similarity): suppressed with a counted "already known" log — the
  hygiene feature owns deeper dedupe. Cross-job windows use the
  ledger's clock, UTC, config length.

## Orchestrator brief
Gate on idea provenance + the miner. T001's schema verification is
the opening deliverable. Keep the playbook-vs-card split rule
verbatim in T002's order — it prevents the two knowledge stores from
blurring.

## Do not touch
Card value, selection, ownership signals (later), self-approval of
anything. Suggested tests: tests/orchestration/test_harvesting.py.
