# T8_F152 — Worker config isolation
**Tier 8 · Depends on: F151 · Blocks/used by: neutrality of every run; F156 certificate**

## Goal & Done
See ROADMAP.md F152; the Done criterion there is binding.

## Context (existing code & prior features)
Workers start inside the target repo's worktree; host configs (.claude/, global agent settings) can silently leak in. A finding from the skills discussion, enforced nowhere yet.

## Design
Per adapter a declared isolation() method: (a) a documented CLI flag/env of the tool (preferred), (b) a cleaned env whitelist + a throwaway HOME with a neutral minimal config, (c) a sandbox profile (F162) as reinforcement. The call builder logs the effective method as the evidence field worker_isolation {method, home, env_digest} per run. `remedy doctor` gains an isolation check. A MANDATORY research task per adapter: verify the tool's current isolation mechanism and pin it in an ADR (tools change flags).

## Task slicing
T001 isolation interface + claude_cli implementation (research+ADR) + env-whitelist builder + tests. T002 the A/B proof test: a host with a poisoned config (a skill that would inject marker text) vs. clean -> identical prompts/results; the doctor check.

## Acceptance & tests
String assertion on the call per adapter; A/B yields bit-equal prompt-trace digests; the evidence field exists in every run.

## Risks / anti-goals
Isolation must not break provider auth (keys passed explicitly, tested); never continue silently without isolation - misconfiguration is a hard infra fail (F010 class).
