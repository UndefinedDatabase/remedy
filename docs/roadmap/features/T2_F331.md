# T2_F331 — No job stays running with nothing running it
**Tier 2 · Depends on: F324 (unattended jobs stay unattended), F328 (an unattended job raises its budget once) · Blocks/used by: the improve run's orders over remedy-chat**

> Registered 2026-10-29 by the operator order beweis on the orchestrator's order, in Package 3
> because it comes from the runs of 2026-10-29: the gap F330's check of job d1a8b318952f4b04 found.

## Goal & Done
A job that a dead order walk left `running` without a run record is, when the server starts, either resumed, when it runs unattended, its order is still live and it is within its caps, or else ended with the stop reason `orphaned_after_restart` and a plain stop text, so no job ever stays „läuft“ with nothing running it.

## What it rests on
- Job d1a8b318952f4b04 of 2026-10-29, which read `running` in the app for hours after its walk had ended; the supervisor's start resumed only runs it had a record of and ended only jobs under a cancel request.

## Acceptance
- At the supervisor's start, an orphaned unattended job of a live order within its caps is resumed.
- An attended one, one whose order is gone or cancelled, one past its caps and one whose start is refused end `stopped` with `orphaned_after_restart` and a sentence why.
- A job a process still runs, a job under a cancel request and a job that is not `running` are left alone.
- Contract 1.34 names the stop reason.

## Built state (2026-10-29)
Built on branch feature/beweis. New `packages/orchestration/job_orphans.py`: `settle_orphaned_running_jobs(paths, launcher)` runs in `serve_daemon.run_supervisor` right after `RunLauncher.resume_registered`, in place of the call of `settle_orphaned_job_cancels`, which it makes first (so the supervisor's start function does not grow). It reads every job record; a job that reads `running`, has no cancel request and that `serve_runs.job_runner_alive` says no supervisor process can still run is resumed with `launcher.start` when it runs unattended, the supervisor holds its order and that order has no cancel request, and `budget_stop.job_within_caps` (new: none of the four limits reached by its saved actuals, no passed deadline) says it is within its caps. Every other such job, and one whose start is refused, ends `stopped` (the light stop the walk already uses for `shape_failed`, so `remedy job resume` continues it) with `stop_reason` `orphaned_after_restart`, `stop_source` `supervisor`, `stopped_at` and the stop text in metadata `stop_text`, which `job_stop`, the story's `stop` and the order jobs' `stop_text` say. A job no supervisor process ever ran (no run record, no order) stays alone, because a run in a terminal may hold it. The supervisor has no periodic sweep, so none was added: a walk that dies while the server keeps running leaves its job to the next start. Contract 1.34: a line in "What changed from 1.33 to 1.34" and the paragraph "A job nothing runs any more ends or runs again" under "Orders" of `docs/system/public-http-api-v1.md`, and the release matrix. Tests: `tests/orchestration/test_job_orphans.py` (9). No new dependency.

Decision: the job ends `stopped`, not `failed`, because its work is not wrong, only unattended by any process; `stopped` keeps its pending work for `remedy job resume`, and its stop text says so.
