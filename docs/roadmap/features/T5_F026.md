## Goal & Done
Course correction without restarting the world: edit_task on nodes
that are waiting, paused or failed (goal/prompt notes, scope hints,
acceptance criteria) creates spec v2 with full versioning, old runs
stay in the graph as a history fan, and the NEXT run provably carries
the edit — visible in the prompt trace. DONE when an edited failed
task re-runs with the new spec (trace asserted), in-progress and
completed tasks refuse edits with the state named, and the version
chain renders in the UI and evidence.

## How it fits (inspect current shape before building)
This extends the plan-editing backend (transactional apply,
revalidate, edit log) beyond the pre-approval window with a
STATE-GATED rule: editable states are exactly waiting | paused |
failed (the pre-start editor covered the approval window; this
feature covers the run). A task edit bumps a per-task spec version
(additive on the task model), archives the prior spec in evidence,
and resets a failed task to pending-with-new-spec (the rerun
machinery's attempt fan applies — the subtree-rerun feature deepens
fans; here the single task's history is enough). Prompt assembly
reads the task's CURRENT spec — the trace proves delivery.

## Design (suggested shape)
- Command edit_task {task_id, fields} (catalog schema; the editable
  field set mirrors the plan editor's per-task fields); effect: the
  editing backend with the state gate + DAG revalidation (scope/
  dependency edits can invalidate — same transactional refusal).
- Versioning: task.spec_version++, prior spec archived
  (task_specs/T004.v1.json pattern in evidence), the edit log entry
  carries actor + diff; the graph node gains a version chip per the
  design reference; L2 popover lists versions with diffs on click.
- Failed-task edit implies intent to retry: the task returns to the
  ready pool (state pending, attempt counter intact) — stated, so
  the human's mental model matches the machine's.
- Prompt-trace assertion: the next run's evidence must contain the
  v2 content (an automated test greps the trace — the feature's
  proof).

## Task slicing
- **T001** state gate + versioned apply + archive + revalidation +
  unit tests per state (three editable, others refused).
- **T002** channel command + audit + failed→pending semantics + the
  trace-proof test on a fake run.
- **T003** UI: version chip, popover version list, edit affordance
  on eligible nodes only + the end-to-end (fail → edit acceptance →
  rerun passes with v2 in trace, fan visible).

## Acceptance
- Editable-state matrix exact; refusals name the state. Version
  chain complete and renderable; prior specs immutable. The v2
  prompt-trace grep passes; a v1 remnant in the new trace fails the
  test. Revalidation refusals change nothing.

## Edge cases & assumption defaults (A9)
- Editing acceptance after partial DoD compilation: the DoD's
  traceability rule re-syncs on next compile — the edit log notes
  the pending re-sync (honesty over silent drift). Concurrent edits:
  the plan editor's revision-conflict discipline applies per task.

## Orchestrator brief
Gate on plan editing. The trace-proof test is the acceptance heart —
verbatim into T002's order. Keep the editable-state set closed;
extensions are future features, not favors.

## Do not touch
Clarification immutability, attempt semantics beyond the reset,
subtree rerun mechanics. Suggested tests:
tests/orchestration/test_task_edit_runtime.py.

## Built State (F026, 2026-09-25)

What exists on disk at the close of F026, built in five rounds of its first session on

**T001 — the state gate and the versioned apply.** `packages/orchestration/task_edit_runtime.py`
edits one task of an approved plan while no run holds the job's record, and the edit IS the plan
editor's own `plan_edit_task`: `apply_edit` and `revalidate` refuse exactly what they refuse before
approval, one entry joins the same `_edits` log, so `replay_edits` still reconstructs the plan, and
the plan's `_version` rises. The gate `runtime_edit_state` admits three states and no other —
`waiting` (a pending task not paused), `paused` (a pending task with a pause file, or in a paused
job) and `failed` (a task `failed` or `blocked`) — and refuses a running or terminal job, an open or
rejected approval, and every other task status, each refusal naming the state. The task entry is
updated in place and keeps its id, its runs and its pause files; `TaskEntry.spec_version` rises by
one and is the conflict check; the prior spec is archived create-only at
`task_specs/<planned id>.v<n>.json` in the evidence export before the record is written; the
approval's hash follows the edit; and a failed task returns to `pending` in the same write together
with every later task its block skipped (DECISION F026 D1).

**T002 — the channel, the CLI and the trace proof.** `job.edit-task` is a catalog command, a CLI
verb in `apps/cli/commands/job_plan_cmd.py` that takes a task by its id in the job or in the plan
and a required `--spec-version`, and a clause of the write door answered by `task_edit_refusal`;
`job plan-show` prints each task's spec version and status (DECISION F026 D2).
`TestTracePreservesTheEdit` in `tests/orchestration/test_task_edit_runtime.py` fails a planned
task under the fake provider, edits it, relaunches, and reads the new run's prompt trace and its
evidence-export copy: the edited text is there and the old is not. `run_job` now clears a stale job
error when a relaunch starts running (R-1059).

**T003 — the page and the end-to-end.** The dashboard's `task_specs` section carries each plan
task's spec, version chain and runtime editability; an edited task shows a `v<n>` chip beside its
graph node and in the detail popover; the popover's Versions list opens the fields each version
changed (DECISION F026 D3). The popover offers an "Edit task" form only for a task the dashboard
marks editable, sent through `apps/ui/src/api/taskEditSend.ts` with only the changed fields, and it
scrolls within the window (DECISION F026 D4). `tests/ui_server/test_task_edit_e2e_live.py` fails a
planned job through `python3 -m apps.cli.main job run`, edits it through a live server's door,
relaunches it through the CLI, and reads the edit in the new trace and two `task_run_started`
frames for the task in the live server's `events-since`, the run fan the graph draws.
