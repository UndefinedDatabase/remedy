## Goal & Done
Work can be queued per project and consumed unattended: `remedy queue add`
enqueues goals, a consumer claims entries atomically (two consumers never
claim the same entry), and the multi-cycle executor drains the queue when
told to. DONE when a two-process claim test shows zero double-claims, queue
state survives restarts, and the queue is honestly listable at all times.

## How it fits (deliberate deviation from an earlier draft)
An earlier draft placed the queue in SQLite — but in STATUS order this
feature lands BEFORE the SQLite token ledger introduces that dependency,
and the codebase today persists everything as atomic per-entity JSON
files. So v1 is FILE-BASED, matching the existing storage and decision
patterns: one JSON file per queue entry under a project-scoped queue area
of the data root, claims via atomic create-if-absent claim markers (the
same O_EXCL/rename discipline the stop-file and storage layers already
use). If the later scheduler feature outgrows this, migrating to the
then-existing SQLite is its decision — note this in the module docstring.

## Design (suggested shape)
Module `job_queue.py`:
- Entry record: id, project id, goal text or a path reference to a goal
  file, priority (small int, default 0), created_at, status
  (queued|claimed|done|failed), claimed_by (consumer id: host+pid),
  claimed_at, result_job_id.
- `enqueue(project, goal, prio)`; `claim_next(project, consumer_id)` —
  scan queued entries in (priority, created_at) order and atomically
  create `<entry-id>.claim`; creation failure means someone else won:
  move on. `release`, `complete(entry, job_id)`, `fail(entry, reason)`.
- Stale claims: a claim older than a configured TTL whose consumer no
  longer exists may be re-offered — but only via an explicit
  `remedy queue reclaim` command (P2: no silent takeovers in v1).
- CLI: `remedy queue add <text|path> [--prio]`, `list` (scoped by the
  project-scoping rules, statuses visible), `rm <id>` (only unclaimed).
- Executor binding: an opt-in flag/config lets the multi-cycle executor
  pull the next entry when idle; each entry becomes a normal job through
  the golden-path machinery (intake → plan → approval rules unchanged —
  a queued entry does NOT bypass plan approval unless run with --yes).

## Acceptance
- Zero double-claims across repeated concurrent runs; priorities and FIFO
  within a priority respected.
- Restart safety: kill a consumer after claim, entry visible as claimed
  with owner; reclaim re-offers it only on explicit command.
- Queue listing always works, even with corrupt entry files (skipped and
  counted honestly, same pattern as job listing).

## Edge cases & assumption defaults (A9)
- Duplicate goal text is allowed (two entries) — deduplication is a human
  judgment, not the queue's. rm on a claimed entry → refusal with the
  owner shown.

## Built State (2026-07-27)

What exists, as proven by the tests named below. Nothing here claims
behavior beyond what those tests exercise.

**The store.** `packages/orchestration/job_queue.py` — one JSON file per
entry at `<data_root>/queue/<project_id>/<entry_id>.json`, with the claim
marker `<entry_id>.claim` beside it. `data_paths.queue_dir()` resolves the
area like every other storage area; directories are 0700, files 0600, and
every read and write goes through identity-verified directory descriptors,
so a symlinked `queue`, project or entry is refused rather than followed.
The record carries id, project_id, goal text OR goal_path, priority,
created_at, status (queued|claimed|done|failed), claimed_by (host#pid),
claimed_at, result_job_id and failure_reason, behind a schema version.

v1 is FILE-BASED on purpose: in STATUS order this feature lands before the
SQLite token ledger (F103), and the codebase persists every entity as an
atomic per-entity JSON file today. Migrating is a later scheduler feature's
decision, and the module docstring says so.

**The claim, reused not rewritten.** `secure_fs.write_file_atomically(...,
create_only=True)` (`packages/common/secure_fs.py:532`) — an `os.link`
publication over an `O_EXCL` temp file with `fsync`, returning `False`
instead of clobbering. It is the same primitive F011's stop request uses at
`safe_points.py:372`; no second atomic-create path was introduced. Losing
the race is not an error and not a retry: that entry belongs to someone
else, so the consumer moves on to the next candidate. Because the marker is
created BEFORE the record is rewritten, an entry whose file still reads
`queued` while its marker exists is already spoken for.

**Ordering (A9).** Higher priority value first, FIFO by `created_at` within
equal priority, `id` as the same-microsecond tie-break. Duplicate goal text
is allowed and makes a second, independently claimable entry — dedup is a
human judgment, not the queue's.

**Honest listing.** `list_entries_safe` returns `(entries, degraded,
skipped_files)` — the same shape `storage.list_jobs_safe` uses for jobs. An
entry file that will not parse, or whose record version is unknown, is
skipped and COUNTED; a corrupt entry never blocks claiming.

**CLI.** `remedy queue add <text|path> [--prio N] [--path]`, `list`, `rm`,
`reclaim`, scoped by the F148 rules (`--project` / `REMEDY_PROJECT` / cwd).
`add` treats its argument as a goal file only when that file EXISTS, so a
sentence containing a slash stays goal text; `--path` forces it. `rm`
refuses a claimed entry and names its owner, deleting nothing.
`--all-projects` widens the LISTING only, over the project directories on
disk — including queues whose project was unregistered, because hiding work
that exists would be dishonest. There is still no cross-project queue.

**Reclaim is explicit, and doubly gated (A9).** `remedy queue reclaim <id>`
re-offers a claim only when BOTH hold: the claim is older than
`queue.reclaim_ttl_minutes` (default 60), AND the owner is verifiably gone —
the owner id names THIS host and its pid is dead. The refusals are
deliberate: an owner on another host is never declared gone, because a pid
says nothing about a machine we cannot probe; `PermissionError` from
`kill(pid, 0)` counts as alive under another user; an owner id that does not
parse as `host#pid` and a `claimed_at` that does not parse as a time both
refuse, because an age that cannot be proven is not an old age. No code path
anywhere reclaims on a timer (P2 — no silent takeovers).

**Executor binding, opt-in.** `queue.executor_binding` (default **false**).
With it off, `long_run_executor.run_cycles` does exactly what it did before
the queue existed and `to_json()` carries the same keys; the `queue_pull`
key appears only when something was actually pulled. With it on, a run that
ends at an IDLE terminal (`all_green`, `blocked`) claims the next entry for
its OWN project and turns it into a normal job — the same thing `job create`
+ `job plan` produce — which STOPS at PLANNED. No task is executed and
nothing implies `--yes`, so a queued goal meets the operator's approval gate
exactly like a typed one. A failing pull marks the ENTRY failed with the
reason rather than leaving it claimed by a consumer that has moved on; both
outcomes emit a `queue_pull` ledger event.
