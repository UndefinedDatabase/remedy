## Goal & Done
The scope guard tells three kinds of order apart and refuses a plan only for the kind that drew a
fence. DONE when `split_order_scope` (`packages/orchestration/order_scope.py`), and the task-plan
guard that reads it (`do_scope.out_of_scope_task_ids`, called by
`do_sequence._deliverable_task_plan`), distinguish:
1. **An order that names files** — its files are the deliverable and its fence holds; a task that
   delivers another file is a violation, as today.
2. **An order with a fence and no files** ("only the README") — the fence holds against the files
   it names in words, as today.
3. **An order with no file name and no fence** — the files of the planner's plan are the
   deliverable, and the guard only checks that no task delivers a mere checking artifact
   (`order_scope.is_checking_only`).

"Super, jetzt mach ein schickes design" and "Bring die webseite auf prototyp niveau und füge
funktionalität hinzu" are the third kind and give a plan, not a failure. The kind is read from the
person's ORDER, never from a text a planner wrote on the way (a milestone's job outline). When an
order of the third kind leads the planner to a rejected plan twice, Remedy asks the operator a
question (a `task_decision` asking which files are meant) instead of planning a third time.

## Why this exists
On 2026-10-20 the operator's second lab order, "Super, jetzt mach ein schickes design" (review
report `rr-20261020T130335Z`, order `4a4af8f164bb4d659b5634a8e1d66f13`), failed after five planner
calls and 226 seconds without a single job: "task plan rejected: every task delivers a file the
order did not ask for (T002, T003)". The order names no file; for such an order the files the
planner proposes are the delivery, and the guard read a valid order as a violation and burned
7,423 tokens of planning on a local model where a planner call takes 40 to 76 seconds (R-1369).

Read on the code at `8ee02682d`: the person's order alone carries no fence
(`do_scope.order_has_scope_fence` is false and `order_scope_files` is empty for both lab orders),
and `out_of_scope_task_ids` returns nothing for an unfenced text. The walk took the `milestones`
shape, and `_step_shape` (`do_sequence.py:796`) hands `plan_order_job` each milestone's job
outline as its `order`; `_deliverable_task_plan(fp_result.plan, mission, ...)` then judges the
task plan against that planner-written outline, which can name files and fence them. The guard
mixed up two cases: an order that names files and draws a fence (where a foreign file is a
violation) and an order that names no file (where there is nothing for a file to violate). The
first round confirms from the records of the job planned before the failure (`ee8c1df67ef94353`)
and the failed one which outline text drew the fence.

- T001, the three kinds. `do_scope.order_scope_kind` reads an order's kind from its text alone:
  `names_files` when it spells a file path, else `fenced` when it carries a fence of
  `order_scope`'s one vocabulary, else `open`. The task-plan guard `out_of_scope_task_ids` answers
  as before for the first two kinds, and for an open order only the tasks that make nothing but a
  checking artifact the order never asked for. `plan_order_job` takes the person's order as
  `scope_order`, and `_step_shape` passes it for every job, so a milestone's job outline still
  shapes its job's work but never fences it (DECISION F312 D2). Step (2) of `plan_order_job`'s
  boundary on the structure ledger, `_first_pass_task_plan`, came first, and `plan_order_job`
  fell from 249 to 165 lines.
- T002, the question after two refusals. An open order whose task plan is refused gets one more
  planner call with the same prompt; a second refusal saves the job stopped with the stop reason
  `scope_question`, keeps the prompt traces of both calls, raises one task decision asking which
  files the order means with the planner's proposed files as its options and no safe default, and
  ends the walk's shape step `stopped` with the answering command as its next line
  (`packages/orchestration/scope_question.py`, DECISION F312 D3). An answer naming files, through
  either answer door, makes them the job's tasks and the job `planned`, so `remedy job resume`
  runs it with no planner call; an answer naming no usable file changes nothing (DECISION F312
  D4). `do_job_task_listing` moved to `packages/orchestration/do_summary.py` to keep
  `do_sequence.py` under the file limit.

  file (the D3 addendum).
