# T4_F125 — Card scopes & inheritance
**Tier 4 · Depends on: F117, F146 · Blocks/used by: multi-project knowledge**

## Goal & Done
Knowledge can outgrow one project without losing precision: GLOBAL
cards live under the data root's global memory area and apply to
every project, project cards override on collision, and `remedy
memory promote <id>` moves a card project→global with its history
intact. DONE when the selector resolves the documented priority
(path-scoped > project > global) deterministically, promotion
preserves provenance and archives a project-side pointer, and
per-project opt-out of global memory exists (a project can be an
island).

## How it fits (a placement correction versus an earlier draft)
An earlier sketch put global cards in a home-directory dotfile; the
codebase's actual convention is the data root — global cards live at
`<data_root>/memory/global/cards/` (machine-scoped, like all
cross-project state), NOT in the repo (they don't belong to any one
repo) and NOT in ~/.remedy (which doesn't exist as a convention).
Consequence stated honestly: global cards do not travel with a repo
— teams share them via export/import (a small command pair here) or
later sync features; the store API grows a scope dimension rather
than a second store implementation (A6).

## Design (suggested shape)
- Store: scope parameter (project|global) on the existing CRUD; ids
  unique per scope; listing/CLI gain --global and merged views with
  a scope column.
- Resolution priority at selection time (documented in the selector,
  one rule): when a project and a global card collide on slug OR are
  flagged duplicates, the project card wins and the global one is
  excluded FOR THAT PROJECT with the exclusion in the funnel's
  near-miss evidence (visible override, not silent shadowing);
  otherwise both compete normally through scope/relevance/value
  (global cards have no paths → they match project-wide, which the
  scope stage already supports).
- `remedy memory promote <id>`: copies to global (new scope, same
  content, provenance + promoted_from), archives the project card
  with a pointer note; demote is the mirror. `export/import
  <file>` round-trips global cards for sharing (validation on
  import, collisions become proposals).
- Config [memory] use_global (default true) — false makes the
  selector project-only; the funnel evidence says so.

## Task slicing
- **T001** store scope dimension + global area + CLI views + tests
  (id uniqueness per scope, merged listing).
- **T002** selector priority + override evidence + opt-out + goldens
  (collision fixture: project wins, near-miss records the global).
- **T003** promote/demote with history + export/import + collision
  proposals + the end-to-end.

## Acceptance
- Collision fixture resolves per priority with the override visible.
  Promotion preserves everything and leaves the pointer; demote
  mirrors. Opt-out yields project-only funnels (evidence asserted).
  Import validates and never overwrites silently (collision →
  proposal).

## Edge cases & assumption defaults (A9)
- Global staleness checks: liveness against paths is per-project by
  nature — global cards should carry path-free scopes; the hygiene
  loop flags path-scoped globals as smells (proposal to narrow or
  demote). Value is per-scope in v1 (a global card's value is
  global — per-project value splits are a later refinement, noted).
