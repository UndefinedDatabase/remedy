## Goal & Done
The daily multi-repo reality gets a home: a home grid of project
cards with mini digests — active jobs, last result, cost today, open
decisions — a project switcher in the header, and deep links that
carry ?project= so every URL is shareable across the whole cockpit.
DONE when the grid renders fixture multi-project states with each
card's numbers traceable to their scoped sources, switching projects
re-scopes every panel without stale bleed-through, deep links restore
project+view state exactly, and single-project users see a sensibly
degraded (grid-free) experience.

## How it fits (inspect current shape before building)
Scoping is solved (the project-scoping feature's selector and
scoped listings) — the cockpit UI adopts it: one client-side
project context derived from ?project= (default: the resolution
precedence's answer served by the backend), threaded through every
data hook (jobs, decisions, stats, memory) so re-scoping is one
context flip; the mini digests reuse the digest endpoint per project
(composition, not new aggregation) plus a cheap per-project summary
endpoint (active counts, cost today from the ledger, decision
counts). SSE subscriptions are per job already — the home grid
subscribes to a light project-events summary or polls the summary
endpoint (measure; the calm view may not need push, honesty over
architecture astronautics).

## Design (suggested shape)
- Home grid per the reference: project cards (slug, repo hint,
  active-jobs chip, last result line with state color, cost today
  basis-labeled, decisions chip with urgency peak); click → the
  project's cockpit; empty-state invites `remedy init`.
- Header switcher: current slug, dropdown from the registry,
  keyboard-friendly (the palette feature indexes it too — note the
  contract).
- ?project= on every route; the client context provider reads it,
  every hook keys caches by project (stale bleed = the bug class to
  test for: switch during in-flight fetches).
- Orphan/unscoped honesty inherited from the scoping rules
  (legacy jobs' rendering rules apply in the UI too).
- CLI unaffected (its scoping shipped earlier) — parity means the
  UI matches ITS semantics.

## Task slicing
- **T001** the summary endpoint (per-project counts/cost/decisions,
  scoped, cheap) + contract tests.
- **T002** the client project context + hook re-keying + the
  switcher + stale-bleed tests (switch mid-fetch fixtures).
- **T003** the home grid + cards + empty/degraded states + deep-link
  restoration tests + the end-to-end (two fixture projects: grid
  numbers exact, switch, every panel re-scopes, URL round-trips).

## Acceptance
- Card numbers equal scoped-source queries per fixture. Switch
  leaves zero stale data (the mid-fetch fixtures). Deep links
  restore project+view (zoom focus included). Single project skips
  the grid to the cockpit with the switcher hidden. Cost-today
  carries its basis.

## Edge cases & assumption defaults (A9)
- Projects on unreachable repos (moved): cards render with the
  registry's warning state and the attach fix-it (the identity
  feature's message reused). Dozens of projects: grid paging like
  the collection; the switcher gets type-ahead.

## Orchestrator brief
Gate on scoping + digest. T002's stale-bleed fixtures are where
multi-project UIs rot — enumerate them in the order (switch during
stream, during fetch, with open panels). One context provider is
the architecture line.

## Do not touch
Scoping rules/semantics, registry mechanics, per-job SSE contracts.
Suggested tests: tests/ui_contract/test_multi_project.py.
