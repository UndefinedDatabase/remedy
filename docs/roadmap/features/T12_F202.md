# T12_F202 — Backup/restore & schema migrations
**Tier 12 · Depends on: F146 data model, F103 · Blocks/used by: upgrade safety; the F221 gate; F245 kinship**

## Goal & Done
See ROADMAP.md F202; the Done criterion there is binding.

## Context (existing code & prior features)
Data stores grew without version fields; F166 exports for compliance - this is the OPERATIONS view.

## Design
A data_v version field in config.toml + ledger.sqlite (user_version pragma) + job state files. packages/telemetry/migrate.py: a migration chain per store (up/down); `remedy migrate [--dry-run]` with a plan display; startup refuses when data_v > code version (clear message). `remedy backup create [--project|--all]` -> tar.zst with a manifest (store list + hashes + data_v); `remedy backup restore <file> [--into]` verifies the manifest BEFORE writing and restores atomically (staging + rename).

## Task slicing
T001 version fields + the migrate framework + a first no-op migration + up/down round-trip tests. T002 backup/restore + manifest verify + a fresh-machine test (restore -> doctor green -> a job runs).

## Acceptance & tests
The fresh-machine restore is hash-equal on defined stores and a fake job passes afterward; dry-run changes nothing (an fs-diff is empty); a future data_v aborts cleanly.

## Risks / anti-goals
No auto-migrate at startup (an explicit command; the daemon shows a pending hint); backups hold no plaintext secrets (F171 provider references stay references - tested).
