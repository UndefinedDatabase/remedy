# T2_F104 — Hard budget enforcement
**Tier 2 · Depends on: F103, F018 · Blocks/used by: cost safety for self-build**

## Goal & Done
Budgets grow teeth and foresight: a money budget (`--max-cost-usd`) joins
the existing limits, counters can read the queryable ledger, and a
PREDICTIVE stop halts BEFORE a task that would likely breach the limit —
checkpoint plus decision instead of overrun. DONE when a fixture with the
limit just under the next task's expected cost stops predictively with an
honest estimate label, and reactive enforcement still catches everything
prediction misses.

## How it fits (inspect current shape before building)
The budget guard, safe points, stop path and decision entries all exist —
this feature extends the guard's inputs (ledger-backed cost actuals, a
usd limit) and adds one pre-task check. Until per-task-class calibration
exists (a later tier), expected costs come from documented class defaults
and are labeled estimate_basis=class_default (P6) — predictions may be
wrong; the label and the reactive backstop make that safe.

## Design (suggested shape)
- Additive budget field max_cost_usd (flag + config, same precedence
  rules); cost actuals aggregate from the ledger where rows carry cost,
  with the unmeasured/unpriced notation propagating into budget output.
  Manifest note (R-0225, 2026-08-09): `max_cost_usd` must also be
  admitted to the CLOSED budget schema in `run_manifest.py`
  (`_BUDGET_ALLOWED_KEYS`) with its own strictly-positive finite-float
  validation. A budget field that `JobBudgets` accepts but the F012
  manifest rejects makes the limit unable to finalize a stop at all —
  the job is left running with the stop request still pending.
- Predictive check at the task-dispatch safe point: expected =
  band→tokens class default × configured price basis; if spent +
  expected > limit → the standard stop path with reason
  predicted_budget_exhausted:<limit> + a decision entry carrying the
  arithmetic (spent, expected, basis) so the human sees WHY.
  DECISION F104 D3 (2026-08-09): a JobTask carries no band field, so
  the band is DERIVED at the safe point from
  token_economy.estimate_task_token_band() over the next task's context
  estimate; a task whose band cannot be derived takes the A9 path below.
  DECISION F104 D4 (2026-08-09): the price basis has NO default. With
  none configured the predictive path is inert and labels itself
  estimate_basis=no_price_basis — Remedy invents no price (P6), and an
  invented one would make every prediction a fabrication.
  DECISION F104 D6 (2026-08-09): the context estimate feeding that band
  derivation comes from the task's OWN text (title, body, acceptance) plus
  the token counts of prior task proof summaries — NOT from
  `_build_task_prompt`. Building the prompt before the safe point would move
  work ahead of the stop-consumption guarantee the safe point exists to
  provide. The estimate is therefore a floor, which is the conservative
  direction: it can only under-predict cost, and the reactive check in
  `evaluate_budget` remains the backstop for everything it misses. Reverse
  this decision by moving the prompt build above the safe point and passing
  its `tokens_estimated`.
- Reactive checks continue unchanged after every call — prediction never
  replaces the backstop.
- Config: budget table gains price basis + class-default bands; all
  documented as provisional until calibration.
- `remedy job budget` shows spent, remaining, next-task expectation with
  its basis label.

## Task slicing
- **T001** usd limit + ledger-backed aggregation + notation propagation
  + tests (priced, unpriced-mixed fixtures).
- **T002** the predictive check + stop reason + decision arithmetic +
  the just-under fixture; a prediction-wrong fixture proves the reactive
  backstop still catches an overrun mid-task.
- **T003** display + docs + estimate labels everywhere a prediction
  surfaces (grep-style test for the basis label).

## Acceptance
- Just-under fixture: stops BEFORE dispatch, checkpointed, decision
  carries the arithmetic, nothing executed. Wrong-prediction fixture:
  reactive stop fires as today. No usd limit set → predictive path
  inert (regression: prior budget tests green unmodified).

## Edge cases & assumption defaults (A9)
- Tasks without a band (legacy plans): expected = the largest class
  default (conservative) — over-stopping beats overspending; the
  decision text says the band was missing. Extending after a predictive
  stop reuses the existing extend/abandon decision semantics.

## Orchestrator brief
Gate on the ledger. T002 is the substance — write both fixtures into the
order (just-under, prediction-wrong). Insist every user-facing predicted
number carries its basis label; that is an acceptance criterion, not
polish.

## Do not touch
Calibration from history, per-task-class caps, burn-rate anomaly
detection. Suggested tests:
tests/orchestration/test_predictive_budget.py.

## Built State
_As built and reviewed on branch `feature/f104-hard-budget-enforcement` (T001–T003)._

- **`max_cost_usd`** joins the F018 limits in `JobBudgets`, resolved by
  `budget_resolution.resolve_job_budgets` under the same CLI > env > TOML > no-limit
  precedence, exposed as `--max-cost-usd`, and admitted to the CLOSED F012 manifest
  budget schema (`run_manifest._BUDGET_ALLOWED_KEYS`) with its own strictly-positive
  finite validation. Reported in `_LIMIT_ORDER` position between `max_total_tokens`
  and `max_wall_clock_minutes`.
- **Cost actuals come from the F103 SQLite ledger** via
  `budget_guard.collect_ledger_cost_for_job`, read at the safe point by
  `run_job._build_budget_counters` and — read-only — by `remedy job budget`. The
  unpriced notation survives the trip: `measured_cost_usd` stays `None` and is never
  coerced to `0.0` (P6). `BudgetCounters` carries `priced_call_count` alongside
  `unpriced_call_count`; the cross-source token/cost check that made R-0224 is gone
  (DECISION F104 D5).
- **The predictive stop** runs at the task-dispatch safe point in `run_job`, only
  after the operator stop and the reactive check both decline. It derives the next
  task's band with `derive_next_task_token_band` from the task's own text plus prior
  proof-summary token counts — never from the assembled prompt (DECISION F104 D6),
  which makes the estimate a FLOOR — then `predict_next_task_cost` compares with a
  strict `>`. On breach it persists the arithmetic to `job.budget_prediction` and
  stops with reason `predicted_budget_exhausted:max_cost_usd`, zero provider calls
  made. The reactive check in `evaluate_budget` is unchanged and remains the backstop.
- **Estimates are labelled, always.** `VALID_ESTIMATE_BASES` is the closed vocabulary
  (`class_default`, `class_default_missing_band`, `no_price_basis`, `no_cost_limit`,
  `unpriced_spend`); the label also appears inside the one-line `arithmetic`. The price
  basis has NO default, so an unconfigured basis makes the path inert rather than
  inventing a price (DECISION F104 D4). Class-default token bands are documented and
  provisional; calibration is deliberately not built.
- **`remedy job budget`** shows the money limit, spend, remaining (a CEILING, `<= `,
  when the spend is only a floor), the next task's expected cost with its
  `estimate_basis` and arithmetic, and any recorded stop prediction. `--json` adds
  `prediction`, `recorded_prediction` and `cost_read_error`. The command writes
  nothing — pinned by a byte-identity assertion on `job.json`. A failed ledger read
  logs at ERROR and says so via `cost_read:` / `cost_read_error`, so it stays
  distinguishable from a genuinely unpriced job (R-0227).
- **`select_next_predictable_task`** (`pingpong_job.py`) is the single source of the
  "which task runs next, with what prior context" rule, pinned against what the LIVE
  `_stop_check` receives so the read-only inspector and the runner cannot drift.
- **Ist-doc:** `docs/system/job-budget-enforcement-v0.md` (DECISION F104 D8).
- **Deliberately not built:** calibration from run history, per-task-class caps,
  burn-rate anomaly detection.
