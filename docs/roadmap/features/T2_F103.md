# T2_F103 — Token ledger (SQLite)
**Tier 2 · Depends on: F003, F146 · Blocks/used by: F074, F115, F116, F150, F158**

## Goal & Done
Token and cost actuals become QUERYABLE: every provider call lands as a
row in a per-project SQLite ledger, and `remedy stats cost` answers
per-job, per-role and per-period questions from it. DONE when the writer
sits in the provider path without slowing it perceptibly, historical
file-based actuals can be backfilled once, and every cost figure names
its basis (P6).

## How it fits (this feature INTRODUCES SQLite — first and only place so far)
Actuals capture exists file-based (per call); this feature adds the
queryable store, NOT a second capture path: the writer consumes the same
records the actuals feature produces. The database lives under the data
root in the project's area, keyed by the registry UUID (the identity
feature's canonical rule) — an earlier draft's home-directory path is
superseded by the actual data-root convention. Python's bundled sqlite
module suffices; no ORM, no new dependency.

## Design (suggested shape)
- One DB per project: `<data_root>/projects/<uuid>/ledger.sqlite`,
  schema-versioned via a meta table; table calls{call_id, job_id,
  task_id, role, model, ts_utc, tokens_in, tokens_out, cache_read,
  cache_write, cost_usd, cost_basis (provider_reported | price_table |
  unknown), evidence_ref} + covering indexes for the query patterns
  (job_id; ts; role+model). Views (or query helpers) per job and per
  role/model/day.
- Writer `token_ledger.py`: an `record_call(...)` hook at the same seam
  where actuals are finalized; failures to write NEVER fail the run —
  log loudly, count misses, and let a `remedy stats verify-ledger`
  command reconcile the file evidence against rows (the files stay the
  source of truth; the DB is a mirror — state that in the docstring).
- Backfill: `remedy stats backfill-ledger` scans existing actuals
  evidence into rows, idempotent by call_id.
- CLI `remedy stats cost [--since] [--job] [--by role|model|day]
  [--json]` reads the current project's DB; `--all-projects` aggregates
  read-only across project DBs.
- Concurrency: WAL mode, short transactions, one writer per process —
  the queue/scheduler world may add writers later; keep transactions
  tiny now.

## Task slicing
- **T001** schema + migrations bootstrap + writer + never-fail-the-run
  discipline + unit tests (miss counting; concurrent-read during write).
- **T002** backfill + reconcile command + idempotence tests on fixture
  evidence.
- **T003** stats CLI + aggregation + basis labeling + cross-project
  read-only aggregation + tests.

## Acceptance
- A fake-provider job yields exactly its calls as rows with correct
  role/model/basis; rerunning backfill adds nothing. Reconcile reports
  zero drift on a clean fixture and finds an injected missing row.
- Writer failure (read-only DB fixture) does not fail the job; the miss
  is counted and reconcile heals it later. Query results match file
  evidence on a golden fixture.

## Edge cases & assumption defaults (A9)
- Calls without reported usage: rows with nulls and basis unknown — the
  stats output carries the unmeasured notation, consistent with budgets.
  Price tables for cost_usd: only if one already exists in config;
  otherwise cost stays null rather than inventing prices.

## Orchestrator brief
T001 first; require the "files remain source of truth" sentence in the
module docstring and a test for the never-fail rule. T002/T003 parallel
after. Reject any diff adding an ORM or a second capture path.

## Do not touch
Estimation/calibration (later features), budgets' counting (they read
actuals directly today; switching them to the ledger is a later,
explicit change), provider parsing. Suggested tests:
tests/orchestration/test_token_ledger.py, tests/cli/test_stats_cost.py.

## Scope note — provider credit pools (amendment amend0805-v3, 2026-08-05)
Budget accounting must model provider credit pools, not only tokens:
since 2026-06-15, non-interactive `claude -p` on subscription plans
draws from a monthly Agent SDK credit (separate from interactive
limits) before falling through to API rates. Context: the F075
campaigns ran tokens-unmeasured because the local provider reports no
ledger usage — F103's ledger closes that gap for every provider that
does report.

## Row granularity — ruling (DECISION D16, 2026-08-08)
A ledger ROW is one FINALIZED TASK RUN, not one HTTP request, and its
`call_id` is the deterministic `"<job_id>:<task_id>"`. The Design above
says the writer consumes the same records the actuals feature produces,
and what that feature puts on disk is
`task_runs/<task_id>/provider_evidence.json` — a per-task-run record
carrying `provider_call_count` and aggregated usage counters. No
per-HTTP-request record exists on disk, so backfill has nothing finer to
read, and synthesising one row per counted call would fabricate ids,
timestamps and a usage split no file records. Remedy deliberately does
NOT do that: an unmeasured split stays unmeasured (the F075 lesson).
When a per-request evidence record exists, change
`call_id_for_task_run` and the backfill scan to read it — `call_id` is
already the primary key, so no schema migration is needed.

## Built State (accepted 2026-08-08, R1–R6)

Built and reviewed on branch feature/f103-token-ledger:

- **Store & writer** (packages/orchestration/token_ledger.py, T001):
  `SCHEMA_VERSION = 1` recorded in a `meta` row, migrations as numbered
  steps rather than an if-ladder. One database per project at
  `token_ledger_path_for(project_id)` =
  `<data_root>/projects/<uuid>/ledger.sqlite` (`LEDGER_FILENAME`);
  `open_ledger` sets `PRAGMA journal_mode=WAL` plus a busy timeout and
  migrates on open. Table `calls` is keyed by `call_id` and carries the
  three covering indexes the Design names (job_id; ts_utc; role+model).
  `record_call` NEVER fails the run: any failure returns False and
  increments the counter `ledger_miss_count()` reads, so a miss is
  counted rather than silently dropped. The module docstring carries the
  mandated sentence verbatim — "The file evidence remains the source of
  truth and the database is a mirror." Python's bundled `sqlite3` only:
  no ORM, no new dependency. This is the FIRST and so far ONLY use of
  SQLite in Remedy, and the docstring says so where a reader would look.
- **Row granularity** (DECISION D16): a row is one FINALIZED TASK RUN,
  its key `call_id_for_task_run(job_id, task_id)` = `"<job_id>:<task_id>"`.
  No per-HTTP-request record exists on disk, and synthesising one would
  fabricate ids, timestamps and a usage split no file records — the F075
  tokens-unmeasured lesson. Remedy deliberately does not do that.
- **Data layer** (T002): `call_record_from_evidence` derives a row from
  `task_runs/<task_id>/provider_evidence.json` through `token_truth`'s
  own canonical aliases — imported, never re-parsed, so the feature adds
  no second capture path. `backfill_ledger` scans an evidence tree, is
  idempotent by `call_id`, and its counters satisfy
  `scanned == recorded + skipped + failed` on every path.
  `verify_ledger` compares CONTENT, not presence (finding R-0219): it
  re-derives each row from its own evidence through the same builder the
  live hook uses and reports field-level mismatches in `drifted_rows`.
- **Live mirror** (packages/orchestration/job_evidence.py, R6, finding
  R-0220): `_resolve_job_ledger_project_id` resolves the target ONCE per
  export, read-only, and `export_job_evidence` threads it and the job id
  through `_write_task_run_evidence` into the writer's keyword-only
  `ledger_*` opt-in. A real job therefore yields its task runs as rows
  with nobody passing a `ledger_*` argument by hand, which is what makes
  the acceptance criterion true of the built system rather than of a test
  that armed the hook itself. An absent `repo_path` returns None instead
  of letting `Path("")` become the process CWD, so evidence export can
  never escape into the wrong project.
- **Queries & CLI** (T003): `query_cost` and `merge_cost_reports` bucket
  by role, model or day and aggregate read-only across projects;
  `apps/cli/commands/stats_ledger_cmd.py` adds `stats.cost`,
  `stats.backfill-ledger` and `stats.verify-ledger` to the existing
  `stats` group, in human and `--json` output, every figure labelled with
  its basis (`provider_reported` | `price_table` | `unknown`; nothing in
  Remedy writes `price_table`, so cost stays NULL rather than inventing a
  price). P6 holds in code, not only in prose: there is no `COALESCE` in
  the queries, so a sum over all-unmeasured rows stays NULL and never
  renders as a measured zero, while COUNTS use `COUNT` because 0 is their
  honest empty value. Reads open with `mode=rw` plus
  `PRAGMA query_only=1`, which refuses to create a database and rejects
  every write at the driver without leaving `-wal`/`-shm` sidecars beside
  a ledger it merely read.
- **Measured cost** (finding R-0218): the mirror costs a median
  **+1.386 ms per finalized task run** at `write_evidence_bundle`
  (0.587 ms inert vs 1.973 ms active), independently reproduced by the
  reviewer at +1.395 ms with a row count of 330/330. The Goal's "without
  slowing it perceptibly" criterion is therefore met with a number rather
  than a claim, on a path whose sibling work is a provider call measured
  in seconds.
- **Tests**: tests/orchestration/test_token_ledger.py and
  tests/cli/test_stats_cost.py — 115 together. Integration gate (R5):
  16121 passed, 19 skipped, zero branch-only failures, re-run
  independently by the reviewer.

## Operator finding (2026-08-25, dogfooding)

A job path run never records a cost. Two real `claude-cli` calls with
measured usage ran under `remedy do job-run` (jobs `edbbc42bba4c4b00` and
`e984ec1943bb422f`, project `ce213ce0-e6d0-44ea-9eb3-00de0aac554c`), and
`remedy stats cost` afterwards reported `0 ledger(s) read` and "No ledger on
disk for this scope — nothing has been recorded yet". The scope was right and
the report was honest: `<data_root>/projects/<project-id>/ledger.sqlite` did
not exist.

This is a DESIGN GAP, not the R-0220 wiring class, and it is not a defect of
the built T001-T003 slices. The live mirror is armed in exactly one place,
`job_evidence._resolve_job_ledger_project_id`, and it is reached only from
`export_job_evidence`. Two commands call that: `remedy do job-evidence` and
`remedy do job-flow`. `remedy do job-run` completes a job, writes its
`task_jobs/<id>/job.json` and its run log, and touches no ledger — so a run
that is never exported has no cost row, and `remedy stats backfill-ledger`
cannot help either, because it mirrors an evidence DIRECTORY that was never
written. Everything the built feature promises holds for the paths it named;
the job runner was simply never one of them.

The seam is per-FINALIZED-TASK-RUN by DECISION D16, and evidence export is
where a task run is finalized, so the fix is not "call `record_call` from the
loop". Three shapes are worth weighing, and the choice is a design decision
this feature has not made:

- Arm the mirror at the end of `remedy do job-run` by exporting the same
  per-task evidence the exporter writes — cost truth for free, at the price of
  making every run write an evidence bundle.
- Give `remedy stats backfill-ledger` a second source that reads
  `task_jobs/<id>/` directly, so an un-exported run can be reconciled after the
  fact. Keeps the run cheap; keeps the ledger empty until someone asks.
- Record at the finalized-call seam (`on_call_finalized`) instead of at the
  evidence seam, which would change D16's row granularity and needs that
  ruling reopened.

Cost truth is what this feature exists for, and it explicitly extends to the
job path: a run whose money nobody can see is the P6 failure in another dress.
The operator's dogfooding is the first time the gap was visible, because it is
the first time real money was spent on this path.
