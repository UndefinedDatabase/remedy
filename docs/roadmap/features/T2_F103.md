# T2_F103 — Token ledger (SQLite)
**Tier 2 · Depends on: F003, F146 · Blocks/used by: F074, F115, F116, F150, F158**

## Goal & Done
Token and cost actuals become QUERYABLE: every provider call lands as a
row in a per-project SQLite ledger, and `remedy stats cost` answers
per-job, per-role and per-period questions from it. DONE when the writer
sits in the provider path without slowing it perceptibly, historical
file-based actuals can be backfilled once, and every cost figure names
its basis (P6).

## How it fits (this feature INTRODUCES SQLite — first and only place so far)
Actuals capture exists file-based (per call); this feature adds the
queryable store, NOT a second capture path: the writer consumes the same
records the actuals feature produces. The database lives under the data
root in the project's area, keyed by the registry UUID (the identity
feature's canonical rule) — an earlier draft's home-directory path is
superseded by the actual data-root convention. Python's bundled sqlite
module suffices; no ORM, no new dependency.

## Design (suggested shape)
- One DB per project: `<data_root>/projects/<uuid>/ledger.sqlite`,
  schema-versioned via a meta table; table calls{call_id, job_id,
  task_id, role, model, ts_utc, tokens_in, tokens_out, cache_read,
  cache_write, cost_usd, cost_basis (provider_reported | price_table |
  unknown), evidence_ref} + covering indexes for the query patterns
  (job_id; ts; role+model). Views (or query helpers) per job and per
  role/model/day.
- Writer `token_ledger.py`: an `record_call(...)` hook at the same seam
  where actuals are finalized; failures to write NEVER fail the run —
  log loudly, count misses, and let a `remedy stats verify-ledger`
  command reconcile the file evidence against rows (the files stay the
  source of truth; the DB is a mirror — state that in the docstring).
- Backfill: `remedy stats backfill-ledger` scans existing actuals
  evidence into rows, idempotent by call_id.
- CLI `remedy stats cost [--since] [--job] [--by role|model|day]
  [--json]` reads the current project's DB; `--all-projects` aggregates
  read-only across project DBs.
- Concurrency: WAL mode, short transactions, one writer per process —
  the queue/scheduler world may add writers later; keep transactions
  tiny now.

## Task slicing
- **T001** schema + migrations bootstrap + writer + never-fail-the-run
  discipline + unit tests (miss counting; concurrent-read during write).
- **T002** backfill + reconcile command + idempotence tests on fixture
  evidence.
- **T003** stats CLI + aggregation + basis labeling + cross-project
  read-only aggregation + tests.

## Acceptance
- A fake-provider job yields exactly its calls as rows with correct
  role/model/basis; rerunning backfill adds nothing. Reconcile reports
  zero drift on a clean fixture and finds an injected missing row.
- Writer failure (read-only DB fixture) does not fail the job; the miss
  is counted and reconcile heals it later. Query results match file
  evidence on a golden fixture.

## Edge cases & assumption defaults (A9)
- Calls without reported usage: rows with nulls and basis unknown — the
  stats output carries the unmeasured notation, consistent with budgets.
  Price tables for cost_usd: only if one already exists in config;
  otherwise cost stays null rather than inventing prices.

## Orchestrator brief
T001 first; require the "files remain source of truth" sentence in the
module docstring and a test for the never-fail rule. T002/T003 parallel
after. Reject any diff adding an ORM or a second capture path.

## Do not touch
Estimation/calibration (later features), budgets' counting (they read
actuals directly today; switching them to the ledger is a later,
explicit change), provider parsing. Suggested tests:
tests/orchestration/test_token_ledger.py, tests/cli/test_stats_cost.py.

## Scope note — provider credit pools (amendment amend0805-v3, 2026-08-05)
Budget accounting must model provider credit pools, not only tokens:
since 2026-06-15, non-interactive `claude -p` on subscription plans
draws from a monthly Agent SDK credit (separate from interactive
limits) before falling through to API rates. Context: the F075
campaigns ran tokens-unmeasured because the local provider reports no
ledger usage — F103's ledger closes that gap for every provider that
does report.
