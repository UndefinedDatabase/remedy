## Goal & Done
The chat panel in the right column (per ux_design.png) becomes the
cockpit's control stand — grounded, never hallucinating: the read
path answers questions in two scopes (node scope from that node's
evidence only; project scope only from the defined evidence set)
with citation chips anchoring every claim, uncited claims rendering
'unsupported'; the write path parses intent into EXISTING channel
verbs presented as confirmable action cards. DONE when the canary
test (asking about absent facts) reliably yields "not in evidence",
citation chips deep-link into artifacts, intent dispatch produces
correct action cards for the covered verbs and executes nothing
without confirmation, and the full spec document remains the
binding contract.

## How it fits (the spec is written — build against it)
docs/roadmap/design/grounded-chat-spec.md is the filed contract
(read it first; this file summarizes, the spec binds): project
scope's evidence set = project brain aggregate, progress ledger,
decision queue state, roadmap position from STATUS.md, latest
reports — the F071 dossier and F103 ledger views join the set now
that they exist (update the spec's set list in the same PR, a
reviewed contract change). Node scope = that node's trace, verdicts,
diff. Delivery is CLI-first (`remedy chat`) per the spec, the panel
wires the same backend. Routing: cheap/mid per the routing table
(chat classes declared there). Intent dispatch maps to the channel's
EXPOSED verbs only — the chat never grows a private verb.

## Design (binding specifics, spec-derived)
- Read: retrieve scope evidence → answer with inline citation chips
  [1][2] anchored {kind, ref} into artifacts (the deep-link
  contracts); the renderer marks any claim sentence lacking a chip
  as 'unsupported' (visible styling per reference) — the honesty is
  mechanical, not prompted-only; the canary suite (absent-fact
  questions per scope) must yield "not in evidence" answers.
- Write: intent parse (schema: {verb, args, confidence}) → an
  ACTION CARD rendering the verb, args, and the evidence triple
  where the underlying decision would carry one; confirm sends the
  real channel command (nonce, audit — the chat is a client, not a
  backdoor); low confidence → the card asks, never guesses.
- Steering interplay: focused-node context routes "tell the builder
  X" intents to steer_task (the F030 verb) — one delivery
  mechanism.
- CLI parity: `remedy chat [--node Txxx]` REPL with the same
  citations as text refs and confirm prompts as y/N lines
  (tty-honest per the preview feature's rules).

## Task slicing

## Acceptance
- Canary green in both scopes. Every rendered claim carries a chip
  or the unsupported mark (a DOM audit test). Verb coverage exact
  to the exposed list; unknown intents get the honest "I can't do
  that yet — available: ..." card. Nothing executes unconfirmed
  (audit diff proves). Spec-file conformance review recorded.

## Edge cases & assumption defaults (A9)
- Questions mixing scopes: node scope wins when focused; the answer
  says which scope it used (a header chip). Long answers: the
  citation density rule from the spec applies (no chip-free
  paragraphs). Local-model capability: the routing table decides;
  the chat degrades to read-only if no capable model is configured
  (honest banner).

## Built State (F038, 2026-09-28)

What exists on disk at the close of F038, built in thirteen rounds over three sessions on
`feature/f038-grounded-chat`, cut from `main` at `fec08a5b`. The chat reads the job's and the
project's own records and changes none of them; it acts only by sending a confirmed card through
the cockpit's one write door. Every DECISION named lives in `.agent/decisions.md`; every round's
verdict in `.agent/live_review.md` or, once rotated, its archive.

**T001 — the evidence and the grounded answer.** `packages/orchestration/chat_evidence.py` builds
an answer's evidence as numbered items, each a `ChatEvidenceItem(kind, ref, text)`: one fact on
one line of at most 400 characters, redacted before it is folded and cut, anchored by its kind and
ref (DECISION F038 D1). The node scope of one task holds its record (`node`), each round of its
latest run (`round`), each prompt of that run's trace by its metadata and never its text
(`prompt`), each file of its own diff (`diff`) and its run-log events newest first (`event`). The
project scope of one registry project holds its record (`project`), its repository's roadmap
position (`roadmap`), its linked jobs' open decisions (`decision`), the patterns across them
(`pattern`), its missions' dossiers (`dossier`), the token ledger's totals (`ledger`) and one
digest line per linked job (`job`), in that order (DECISION F038 D3). A source with nothing
recorded is one item saying so, which is the fact an absent-fact answer cites. The composer keeps
the items in order under a 4000-token estimate and counts the rest as omitted.
`packages/orchestration/chat_answer.py` checks an answer sentence by sentence: a sentence is
supported only when it cites `[n]` numbers the set holds and states no URL, backtick span or
number its cited items do not hold; "Not in evidence." with no citation is supported, because it
claims an absence (DECISIONS F038 D4 and D5). The mechanical answer restates the items that best
match the question's keywords, at most five, each ending in its citation, and answers "Not in
evidence." when none matches. The summary model writes the answer instead only when the operator
switches on `chat.model_written` (environment variable `REMEDY_CHAT_MODEL_WRITTEN`, off by default,
listed in `docs/guides/environment.md`), through `chat_call_fn()` and the `summary` role; its reply
passes the same check, and a failed call or a reply with no supported sentence falls back to the
mechanical answer, labelled with the reason. `chat_generator_line` turns that label into one
plain sentence saying how the answer was written (DECISION F038 D13).

**T002 — the request, the card and the door.** `packages/orchestration/chat_intent.py` reads a
line as a question, an action or unknown: a line ending in `?` or starting with a question word
is a question; otherwise its first word chooses stop, pause, resume, a note to the builder, veto
or rerun, each mapped to the write door's own command and argument names (DECISION F038 D6). A
card states the job, the task, the message or reason it carries, what is still missing and the
command it would send, and is confirmable only when nothing is missing; an unknown request gets
the card "I can't do that yet", naming what is available. `packages/orchestration/chat_intent_model.py`
asks the summary model about a line the mechanical parse calls unknown, only while
`chat.model_written` is on; it may also choose answering an open decision or adding a task, and
every argument it returns is filtered, the task always the focused one and a decision id only one
the job holds open, so a low-confidence or unusable reply stays unknown (DECISION F038 D8).
`packages/orchestration/chat_door.py` posts a confirmed card to the running cockpit's write door
over the loopback connection, with the bearer token, `X-Remedy-CSRF` and a fresh `chat-` nonce, so
the door's token check, replay check, rate limit and audit line apply to the chat unchanged
(DECISION F038 D7). `packages/orchestration/chat_turn.py`'s `run_chat_turn` is the one chat turn
both doors call: it answers a question from the focused task's node scope, or the project scope of
the project owning the job's repository, or an empty set when none owns it, and turns anything
else into a card, sending nothing; `chat_turn_view` is its one wire shape (DECISIONS F038 D9 and
D11).

**T003 — the command line, the route and the cockpit tab.** `remedy chat ask <job_id> "<text>"
[--task <task id>] [--yes] [--json]` runs one turn: a question prints its scope, how the answer was
written, the checked answer and one `[n] kind ref` line per evidence item; a card prints its title
and lines and is sent through the job's newest live cockpit, which `live_ui_session_for_job` in
`apps/cli/commands/ui.py` finds without writing, only when it is complete and confirmed by `--yes`
or a `y` typed at a terminal; it exits 3 when no cockpit runs or none answers, 1 when the cockpit
refuses the card, and 2 for a task id that names no task (DECISION F038 D10). The bare
`remedy chat` still records a steering message. `GET /api/jobs/<job_id>/chat?text=<line>&task=<task id>`
answers one turn in `chat_turn_view`'s shape behind the read token and sends nothing; a blank line
or an unknown task is data at 200, and no POST route was added (DECISION F038 D11). The evidence
panel's Chat tab, `apps/ui/src/components/graph/EvidenceChatTab.tsx`, replaces the placeholder
that promised this feature: a line asks about the focused run's task, or the whole project when
its box is ticked; an answer shows a scope chip, how it was written, each sentence with numbered
chips linking to its evidence items listed below or a dashed "unsupported" mark, and a button
opening the diff or the prompt trace for an item of that kind; a card shows its title and lines
and a Confirm button only while it is complete and not already sent, which sends it through the
write door once. `apps/ui/src/api/chatTurn.ts` holds every rule the tab applies: the decoder that
refuses a body whole, the sentence marks, the plain lines and the card's own refusal sentences
(DECISION F038 D12). The design reference's assumption log records the tab.
