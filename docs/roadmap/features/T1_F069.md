# T1_F069 — Mission compiler
**Tier 1 · Depends on: F013, F014, F061 · Blocks/used by: F070**

## Goal & Done
A long prose goal compiles into a MissionPlan — ordered milestones, each
with its own compiled DoD and draft job outlines — so the orchestrator
loop has a structured route instead of improvising. DONE when three long
fixture goals compile into sensible milestone plans, every milestone
carries a DoD reference, and draft jobs NEVER autostart.

## How it fits (inspect current shape before building)
This is the mission-level sibling of intake+plan: same schema discipline
(versioned model, validate-response, parse retry, honest deterministic
fallback), same provider-call surface, evidence in per-call directories.
Missions exist as records (previous feature); the DoD compiler exists —
milestone DoDs are compiled through it, not by a second mechanism (A6).

## Design (suggested shape)
- Schema `MissionPlan` (versioned "mission_plan_v1"): milestones[], each
  {id, goal, rationale, dod_ref (filled after DoD compilation),
  depends_on (milestone DAG, same validator discipline as task DAGs),
  jobs_draft[] — outline entries {title, goal, est_band}, explicitly NOT
  runnable jobs}; risks[]; assumptions[] (same conservative-default rules
  as clarifications).
- Module `mission_compiler.py`: compile(mission) → MissionPlan via
  provider call with the mission goal + project facts; then for each
  milestone invoke the DoD compiler and store the reference; persist the
  plan on the mission record; render a mission_plan.md next to the
  mission's evidence.
- Draft jobs become real jobs only through explicit continuation (the
  mission continue command or the orchestrator loop under its own rules)
  — the compiler itself has zero execution side effects.
- Fallback without a provider: one milestone wrapping the whole goal,
  labeled deterministic — the loop can still function degraded.
- CLI: `remedy mission plan <id>` compiles/recompiles (recompile keeps
  prior versions like flight-plan replans and is refused once any
  milestone is in progress).

## Task slicing
- **T001** schema + DAG validation + compiler + fallback + three
  long-goal fixtures with golden milestone structures.
- **T002** DoD hand-off per milestone + persistence + rendering + the
  no-autostart guarantee (negative test: compile leaves zero jobs).
- **T003** CLI + recompile versioning + in-progress refusal + tests.

## Acceptance
- Three goldens compile with coherent milestone DAGs; every milestone has
  a dod_ref after compilation. Compiling creates no jobs, starts nothing,
  touches no worktree. Recompile before progress versions; after progress
  refuses with a clear message.

## Edge cases & assumption defaults (A9)
- More milestones than plausible (validator cap ~12) → rejected as
  hallucinated scope, parse-class failure. Milestone goals must be
  outcome-phrased; the prompt mandates it and a lint-style validator
  rejects obvious task-lists-as-milestones (starts with an imperative
  verb list — heuristic, documented).

## Orchestrator brief
Sequential; ship T001's schema early — the orchestrator loop is built
against it next. Reuse the intake/plan prompt-building helpers; if a
worker copies one, require extraction into a shared helper instead.

## Do not touch
Execution, job creation, dossier maintenance, loop policy. Suggested
tests: tests/orchestration/test_mission_compiler.py.
