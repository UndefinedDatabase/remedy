# T4_F266 — remedy study (repo comprehension pass)

## Goal & Done
The three-step `remedy init` → `remedy study` → `remedy teach` on an ARBITRARY
repository.

`study` runs a bounded comprehension pass over the repository — structure, core
modules, conventions, entry points — and files the result, per D-C below,
automatically as APPROVED memory cards with provenance `machine-study`.
`teach` can then teach about that repository on that basis.

Harness and model are selectable per role (`role_config` role `study`, or reuse
of the `teacher` role — the choice is made IN this feature and recorded as a
dated DECISION). Budget-capped. Read-only against the repository.

DONE when the three-step runs through on a foreign example repository and
`teach ask` afterwards answers questions about that repository out of the
`study` cards.

## Why this exists
The teacher can already narrate a job it watched. It cannot say anything about
a repository it has not watched being built — which is every repository the
operator did not build with Remedy. Comprehension is the missing first step: a
teacher with no cards about a codebase can only read files on demand, once, per
question, at full token cost. `study` pays that cost once, deliberately, under
a cap, and leaves something reusable behind.

## DECISION D-C (2026-08-31, operator order amend0831-vocab-registrations)
Memory cards produced by `study`/`teach` are created AUTOMATICALLY as
**approved**, carrying the provenance field `machine-study`. The user may
afterwards edit, re-rank or delete them, but for THIS PROVENANCE CLASS there is
NO per-card approval duty — explicitly not during mission runs either.

This deliberately loosens the existing card-approval rule, and only for this
class. A card with any other provenance keeps its approval duty unchanged.
Reverse this decision by deleting this paragraph, at which point every
`machine-study` card falls back under the ordinary approval rule.

## Design
- `study` is a bounded job, not an open-ended crawl: it runs under the existing
  budget machinery with a cap, and it stops at the cap with an honest partial
  result rather than silently truncating.
- The cards it writes carry `provenance: "machine-study"` as a first-class
  field, so D-C's carve-out is a data property and not a code path. Anything
  that enforces approval reads the field.
- Read-only against the target repository. `study` writes cards; it never
  writes to the repository it is studying, and a test proves it.
- The role question (`study` as its own `role_config` role, versus reusing
  `teacher`) is settled inside this feature by a dated DECISION, with the
  reasoning written down. A separate role means a separate budget pot; reusing
  `teacher` means one pot for reading and one for lessons.
- What `study` produces is CARDS, not a report. A report would be read once;
  cards are what `teach ask` retrieves from.

## T001 — The comprehension pass
The bounded run: structure, core modules, conventions, entry points. Ships the
cap and the honest partial-result behaviour.

## T002 — Cards with provenance
Card writing with `provenance: "machine-study"`, auto-approved per D-C, and the
approval-check path taught to read the field.

## T003 — The three-step on a foreign repository
`init` → `study` → `teach ask` proved end to end against an example repository
that is not this one.

## Acceptance
- The three-step runs through on a foreign example repository.
- `teach ask` answers a question about that repository from `study` cards —
  proved by a fixture whose answer is only derivable from a card.
- Every card written carries `provenance: "machine-study"` and is approved
  without a per-card prompt, including inside a mission run.
- `study` writes nothing to the studied repository.
- Hitting the budget cap yields a partial result that says it is partial.

## Do not touch
The approval duty for cards of ANY other provenance — D-C is scoped to
`machine-study` and widening it is out of scope. Also: the scope-fence deny
list (F017) and the teacher's existing read-only stance.

## Orchestrator brief
T002 is the slice that touches an existing safety rule and should be settled
first in DESIGN even though it lands second — the approval path must read the
provenance field before any auto-approved card exists. T001 is the largest
slice and the budget risk. T003 is the acceptance harness and needs a real
foreign repository fixture, which is a setup cost worth planning for.
