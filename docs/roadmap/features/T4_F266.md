## Goal & Done
The three-step `remedy init` → `remedy study` → `remedy teacher` on an ARBITRARY
repository.

`study` runs a bounded comprehension pass over the repository — structure, core
modules, conventions, entry points — and files the result, per D-C below,
automatically as APPROVED memory cards with provenance `machine-study`.
`teacher` can then teach about that repository on that basis.

Per DECISION amend0905-vocab D8 (2026-09-05) `study` is invoked EXACTLY ONCE by
`remedy do` (F268) when the repository is non-empty and has never been studied;
it records `studied_at` and `studied_head` on the project record (no such
fields exist today; this feature adds the write, `do` reads them), and
afterwards runs only by hand. Its cards are auto-approved per D-C below.

Harness and model are selectable per role (`role_config` role `study`, or reuse
of the `teacher` role — the choice is made IN this feature and recorded as a
dated DECISION). Budget-capped. Read-only against the repository.

DONE when the three-step runs through on a foreign example repository and
`teacher ask` afterwards answers questions about that repository out of the
`study` cards.

## Why this exists
The teacher can already narrate a job it watched. It cannot say anything about
a repository it has not watched being built — which is every repository the
operator did not build with Remedy. Comprehension is the missing first step: a
teacher with no cards about a codebase can only read files on demand, once, per
question, at full token cost. `study` pays that cost once, deliberately, under
a cap, and leaves something reusable behind.

## DECISION D-C (2026-08-31, operator order amend0831-vocab-registrations)
Memory cards produced by `study`/`teacher` are created AUTOMATICALLY as
**approved**, carrying the provenance field `machine-study`. The user may
afterwards edit, re-rank or delete them, but for THIS PROVENANCE CLASS there is
NO per-card approval duty — explicitly not during mission runs either.

This deliberately loosens the existing card-approval rule, and only for this
class. A card with any other provenance keeps its approval duty unchanged.
Reverse this decision by deleting this paragraph, at which point every
`machine-study` card falls back under the ordinary approval rule.

## Design
- `study` is a bounded job, not an open-ended crawl: it runs under the existing
  budget machinery with a cap, and it stops at the cap with an honest partial
  result rather than silently truncating.
- The cards it writes carry `provenance: "machine-study"` as a first-class
  field, so D-C's carve-out is a data property and not a code path. Anything
  that enforces approval reads the field.
- Read-only against the target repository. `study` writes cards; it never
  writes to the repository it is studying, and a test proves it.
- The role question is settled by operator ruling 2026-09-11 (DECISION
  amend0911-feedback D2): `study` is its OWN `role_config` role with its own budget
  pot. Reading and explaining have different budgets, and a reader may be a cheap
  model. Its default model is what the F110 routing policy assigns to the cheapest
  task class capable of reading a repository (measured once in this feature and
  written into the config default with the measurement); the operator can override
  it per project like every other role. The feature records the measured default as
  a dated DECISION; the role itself is not open for debate.
- What `study` produces is CARDS, not a report. A report would be read once;
  cards are what `teacher ask` retrieves from.

## Decisions

## DECISION F266 D1 — the `study` role and its measured default model (2026-09-18, F266 R1)
`study` is its own `role_config` role with tier `summarize` — the cheapest task class capable of
reading a repository. F110 deliberately does not map a tier to a concrete model id; every role
resolves to the same provider-aware default except when overridden. `study`'s default model is
therefore the standard default (`ollama-default` or `claude-flagship`), measured once in this
feature and identical to every other role's default, operator-overridable as usual. See
`.agent/decisions.md` for the full text.

## DECISION F266 D2 — `provenance` on `MemoryEntry` and auto-approval (2026-09-18, F266 R1)
Cards carry a plain-string `provenance` field defaulting to `"human"`. `store_memory()` gains a
keyword-only `provenance` parameter; approval is derived from provenance at creation time (`True`
when `provenance == "machine-study"`, `False` otherwise). This makes D-C's auto-approval carve-out
a data property, not a separate code path. Explicit `approved=` arguments always override the
derived default, preserving existing caller behaviour. See `.agent/decisions.md` for the full text.

## Acceptance
- The three-step runs through on a foreign example repository.
- `teacher ask` answers a question about that repository from `study` cards —
  proved by a fixture whose answer is only derivable from a card.
- Every card written carries `provenance: "machine-study"` and is approved
  without a per-card prompt, including inside a mission run.
- `study` writes nothing to the studied repository.
- Hitting the budget cap yields a partial result that says it is partial.

## Do not touch
The approval duty for cards of ANY other provenance — D-C is scoped to
`machine-study` and widening it is out of scope. Also: the scope-fence deny
list (F017) and the teacher's existing read-only stance.

## Orchestrator brief
T002 is the slice that touches an existing safety rule and should be settled
first in DESIGN even though it lands second — the approval path must read the
provenance field before any auto-approved card exists. T001 is the largest
slice and the budget risk. T003 is the acceptance harness and needs a real
foreign repository fixture, which is a setup cost worth planning for.

## Built State (F266, 2026-09-18)

What exists on disk at the close of F266.

**T001 — the bounded comprehension pass.** `packages/orchestration/study.py` walks a repository (bounded by `DEFAULT_MAX_ENTRIES = 2000`, `_walk_repo`), heuristically detects four categories (`STUDY_CATEGORIES = ("structure", "core_modules", "conventions", "entry_points")`), optionally narrates each through an injectable `call_fn` bounded by `max_provider_calls` (default 4) and the existing `should_stop`/`evaluate_budget` machinery, and writes one memory card per category via `store_memory(..., provenance="machine-study")`. `study_call_fn()` bridges the `study` `role_config` role (registered in `role_config.KNOWN_ROLES`, tiered `summarize` in `model_routing.ROLE_TASK_CLASSES`, DECISION F266 D1) to a real callable through `make_structured_call_fn`, honestly returning `None` when no provider is reachable — never crashing.

**T002 — provenance and auto-approval.** `MemoryEntry` (`packages/memory/local_gateway.py`) carries a plain `provenance: str = "human"` field; `store_memory()`'s `approved` parameter, when left `None`, is derived from `provenance` (`True` for `"machine-study"`, `False` otherwise — DECISION F266 D2). Every downstream approval gate reads `.approved` alone and needed no change.

**CLI wiring.** `apps/cli/commands/study_cmd.py` exposes `study.run` (`remedy study run`), registered as an advanced/internal group (`user_facing=False`, DECISION F266 D3) in `apps/cli/command_catalog.py`, wired into `collect_all_handlers()`, and proven reachable through the real CLI dispatch (`tests/cli/test_study_cmd.py::TestStudyCommandReachability`). It resolves its project scope the same way `teacher ask` does (`resolve_scope(project_flag=project, all_projects=False, cwd=target)`), so both commands agree on a repository's registered project id.

**T003 — the three-step, end to end.** `apps/cli/commands/teacher_cmd.py::_cmd_teacher_ask` fetches every `machine-study` card for the resolved project, deduplicates by key keeping the newest value, and renders them as a `[study]` grounding-source block (`packages/orchestration/teacher_qa.py`'s `SOURCE_STUDY`, fourth in `GROUNDING_SOURCES`). `tests/cli/test_study_teacher_e2e.py` proves the full `init` → `study run` → `teacher ask` chain against a foreign repository fixture carrying a distinctive marker directory name, asserting the model is shown that name only through the `study:structure` card it wrote — the Acceptance criterion "answered ... from `study` cards, proved by a fixture whose answer is only derivable from a card."
