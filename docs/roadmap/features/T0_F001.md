# T0_F001 — Adaptive Provider-Timeouts + Retry
**Tier 0 · Abhängigkeiten: keine · Blockiert: alle Self-Runs, F075**

## Ziel & Done
Timeouts werden pro Rolle/Taskgröße berechnet statt hart kodiert; vor final
`provider_unavailable` laufen bis zu 2 Retries mit Backoff. Done: 10 Self-Runs ohne
Timeout-Block; Retry-Zähler in Evidence.

## IST-Bezug
- `packages/orchestration/pingpong_provider.py`: harte Defaults (120–300 s) — Hauptursache
  des T007-Blocks (Job 743f20d7) und der r2–r5-Retry-Kaskaden (Steps 5481–5510).
- `pingpong_loop.py` reicht Timeout durch; CLI-Flag `--timeout-sec` existiert.

## Design
Neues Modul `packages/orchestration/provider_timeouts.py`:
```python
@dataclass(frozen=True)
class TimeoutProfile:  # fast | normal | patient
    builder_base_s: int = 600; reviewer_base_s: int = 300
    per_allowed_file_s: int = 60; cap_s: int = 2400
def compute_timeout(role: str, allowed_files: int, profile: TimeoutProfile) -> int: ...
```
- CLI: `--timeout-profile fast|normal|patient` ersetzt `--timeout-sec` (Alias bleibt, deprecated-Warnung).
- Retry in `pingpong_provider.call()`: Backoff 30 s → 120 s, nur bei Timeout/Prozess-Exit≠0,
  NICHT bei Review-Reject. Evidence-Felder: `timeout_s_effective`, `retries_used`,
  `retry_reasons[]` in provider_evidence.json.
