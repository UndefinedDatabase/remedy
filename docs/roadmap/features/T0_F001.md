# T0_F001 — Adaptive provider timeouts + retry
**Tier 0 · Depends on: none · Blocks/used by: all self-runs, F075**

## Goal & Done
See ROADMAP.md F001; the Done criterion there is binding.

## Context (existing code & prior features)
pingpong_provider.py uses hard 120-300s defaults - the root cause of the historic T007 block and the r2-r5 retry cascades. The CLI flag --timeout-sec exists.

## Design
New module `packages/orchestration/provider_timeouts.py`:
```python
@dataclass(frozen=True)
class TimeoutProfile:  # fast | normal | patient
    builder_base_s:int=600; reviewer_base_s:int=300
    per_allowed_file_s:int=60; cap_s:int=2400
def compute_timeout(role:str, allowed_files:int, profile:TimeoutProfile) -> int: ...
```
CLI: `--timeout-profile fast|normal|patient` (old flag stays as a deprecated alias). Retry inside provider.call(): backoff 30s then 120s, ONLY on timeout/nonzero process exit, NEVER on review rejects. Evidence fields: timeout_s_effective, retries_used, retry_reasons[].

## Task slicing
T001 module + unit tests (bounds, cap). T002 provider integration + flag migration + evidence fields. T003 self-run smoke with an artificially slow fake provider.

## Acceptance & tests
3 profiles x roles x file counts yield expected seconds; a dying-once fake provider passes with retries_used=1; a review reject triggers NO retry (negative test); every attempt is a separate ledger entry (F003/F103).

## Risks / anti-goals
No new gate or taxonomy (A6). Retries must never hide token costs.
