## Goal & Done
Every event the UI server sends for a builder attempt, a review, a check, a test run and a repair
round carries the attempt id, the task id and the result; a plan-approved event exists; and prompts
become their own node kind in the live graph, so the prompt dots leave the simple view. Every
consumer of the stream is updated in the same feature. DONE when the live graph shows a node for
every kind the simple view shows, and the reducer's tests prove that test-run and repair nodes
appear.

## Why this exists
F019 built the live graph from the event messages as they are, because its plan forbade changing
the message format (operator question Q2). As a result the tasks appear only when the task list
appears, test runs and repair rounds have no nodes, and the prompt dots stay in the simple view
because the graph's data model has no prompt node (operator question Q3). The operator accepted
both as interim states and asked for the missing fields and the prompt nodes as their own feature.

## Task slicing
- T001 — the event fields: attempt id, task id and result on every builder, review, check, test and
  repair event, and a new plan-approved event, with every reader of the event vocabulary updated
  (the UI contracts, the humanized labels, the command line and the tests).
- T002 — the live graph reducer: test-run and repair nodes, and tasks appearing at plan approval,
  proven by the reducer's tests.
- T003 — prompt nodes: a prompt node kind in the graph's data model and its look, so the prompt
  dots are reachable in the live picture with the mouse and the keyboard.

## Acceptance
- Every builder, review, check, test and repair event carries the attempt id, the task id and the
  result, and a plan-approved event is sent when a plan is approved.
- The reducer's tests show test-run and repair nodes appearing from the stream.
- The live graph shows a node for every kind the simple view shows, prompts included.

## Do not touch
The simple view, which stays one click away; the graph's rule that it never draws a node its data
model does not hold.

**T001 — the event fields and the plan-approved event.** An attempt is one execution of a task.
`run_job` in `packages/orchestration/pingpong_job.py` mints its attempt id with `mint_run_id()`
before `task_run_started` and hands it to `run_pingpong` through the new keyword `run_id`, so the
attempt id is the run id every prompt of that execution names. For each round it writes
`task_round_repaired` when the round repaired and `task_round_tested` when its test ran, before
`task_round_completed`, each carrying the task id, the attempt id and its result as `outcome`
(DECISION F288 D1). The run-next path in `apps/cli/commands/job.py` mints its attempt id the same
way; a test run of `packages/orchestration/test_execution_service.py` is an attempt whose id is its
test run id, and its events carry the task id and their result; the long-run executor's cycle
events carry `cycle-<index>` as their attempt id (DECISIONS F288 D2 and D3).
`announce_plan_approval` in `packages/orchestration/job_plan.py` writes `plan_approved` with the
plan's task ids and the approval mode, after a human approval and after both unattended ones.
`_safe_event_summary` in `packages/orchestration/ui_server.py` adds `attempt_id` to the envelope of
the 19 kinds of `ATTEMPT_EVENT_KINDS` and a `plan` block to `plan_approved`'s, and every other
kind's frame stays byte-identical. `EVENT_NAMES`, `STREAM_EVENT_CATALOG`, `NARRATED_EVENTS`,
`remedy event timeline` and `docs/system/architecture.md` name the new events.

**T002 — the live graph reducer.** `feedRowOf` in `apps/ui/src/api/feedRow.ts` gives every row
`attemptId` and `planTaskIds`. `applyBrainEvent` in `apps/ui/src/components/graph/brainReducer.ts`
births the plan's tasks at `plan_approved`, a `test_run` from `task_round_tested` and from a test
service event that names a task, and a `repair_run` from `task_round_repaired`, each a child of its
task, in the state its outcome table gives, with its attempt id in its meta; `plan_approved` and
`task_round_tested` mark the planning and test phases of the timeline (DECISION F288 D3). The demo
recording `apps/ui/src/components/graph/brainDemoRecording.ts` was captured again from the widened
stream and every reader of it brought to it (DECISION F288 D4, finding R-1075).

**T003 — prompt nodes.** A prompt is a `synapse` node. `withPromptNodes` in
`apps/ui/src/components/graph/promptNodes.ts` composes the dashboard's prompt trace onto the live
model only, one node per prompt whose task the model holds, a child of that task in its state with
the attempt in its meta, drawn at graph_spec §4's radius of 2; a click selects the prompt item
itself through `selectionIdOf` in `brainView.ts` (DECISION F288 D5). The keyboard reaches the
prompts through `PromptNodeList`, a `nav` of native buttons built by `promptListEntries`, visually
hidden until it holds focus and rendered inside the live branch of `BrainGraphStage.tsx`, while the
canvas stays `aria-hidden` (DECISION F288 D6).
