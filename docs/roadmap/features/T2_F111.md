# T2_F111 — Diff-only repair
**Tier 2 · Depends on: F005 (schema-enforced diff output) · Later integrates: F106 session-resume repairs; F033 hunk ids replace the v1-local hunk lib · Blocks/used by: repair cost**

## Goal & Done
Repairs stop resending whole files: the repair prompt carries only the
failure-relevant hunks with minimal surrounding context, and the model
answers with a schema-enforced unified diff that is applied and verified —
with an immediate, honest full-file fallback on any apply conflict. DONE
when a fixture repair fixes a bug with a fraction of the tokens the
full-file path uses (measured, recorded), a conflicting diff falls back
cleanly, and no repair path can silently corrupt a file.

## How it fits (inspect current shape before building)
The repair loop exists inside the ping-pong machinery with bounded rounds
and its own evidence; this feature changes WHAT a repair round sends and
accepts, not when repairs happen. Structured-output validation exists —
the diff response is one more versioned schema (a wrapper carrying a
unified-diff string plus the hunks' file paths, so validation can check
paths against fences BEFORE apply). The applicator with its all-or-nothing
discipline and fence enforcement is the ONLY way changes land — the diff
path must flow through it, not around it.

## Design (suggested shape)
- Prompt side: from the failure findings (failing tests, error text,
  changed files of the round) select the relevant file regions — the
  failing hunks plus a small configurable context margin — via a small
  v1-local hunk helper (line-range extraction; a later feature replaces it
  with stable hunk ids). The prompt states explicitly that the answer must
  be a unified diff against the shown content.
- Response schema: versioned record {format: "unified_diff", diff: str,
  files: [paths]}; validation rejects diffs touching files outside the
  declared list, and the list is fence-checked before any apply.
- Apply: parse and apply the diff in-memory against the worktree state;
  ANY hunk conflict → discard entirely, record fallback_reason, and rerun
  the round in today's full-file mode — correctness beats savings, and the
  evidence says which mode ran (P6).
- Measurement: per repair round record mode (diff|full_fallback) and token
  actuals; the stats surfaces can compare later.
- Config: repair.diff_mode (default on), context margin lines.

## Task slicing
- **T001** hunk selection helper + prompt assembly + unit tests (margin
  boundaries, multi-file findings, binary files excluded).
- **T002** response schema + fence pre-check + apply-with-conflict
  fallback + tests (clean apply; conflicting hunk → full fallback, file
  byte-identical to pre-attempt state; out-of-fence path rejected before
  apply).
- **T003** wiring into the repair rounds + mode/token evidence + a
  fixture comparison test recording both modes' token counts.

## Acceptance
- Fixture bug fixed via diff mode with recorded token savings versus the
  full-file fixture run. Conflict fixture: zero partial application,
  fallback round runs, both attempts in evidence. A diff targeting a
  fence-denied path never reaches the applicator (rejected at validation).
- Diff mode off → behavior byte-identical to today (regression).

## Edge cases & assumption defaults (A9)
- Diffs with fuzzy/offset context that git-style apply would accept: v1
  requires exact context matches (strict), because the model just saw the
  exact content; fuzziness is a source of silent corruption. New-file
  creation inside a diff is allowed if the path passes fences; deletions
  require the full-file path in v1 (rare, riskier).

## Orchestrator brief
T001/T002 parallel, T003 wires. Include the strict-apply rule and the
fallback rule verbatim in orders; reject any diff-apply implementation
that shells out to `patch`/`git apply` with fuzz enabled.

## Do not touch
Repair round counts/policy, applicator semantics, session resume (later).
Suggested tests: tests/orchestration/test_diff_repair.py.

## Built State — scope amendment (DECISION F111 D1, 2026-08-13)
The repair loop this feature changes is the BOUNDED REPAIR LOOP in
`packages/orchestration/builder_bridge.py` (`run_builder_bridge_loop`), whose
cycle is build → bridge → test → repair-context → rebuild. Its bridge already
parses a `BuilderOutput` into a `StructuredPatch` and applies it through
`apply_structured_patch`, so the response-side diff channel attaches there and
flows through the existing fenced applicator exactly as "How it fits"
requires. The prompt-side hunk selection attaches to the repair context built
by `packages/orchestration/repair_context.py`.
`packages/orchestration/pingpong_loop.py` is explicitly NOT in scope: its
builder is an agentic CLI that edits the staging tree itself, `BuilderOutput`
carries no patch field on that path, and no applicator is invoked there.
Giving it a diff-shaped response would require a new provider contract and a
change to applicator semantics, both listed under Do not touch. Remedy
deliberately does not route ping-pong repairs through the diff channel in v1
for that reason.

## Built State — range source (DECISION F111 D3, 2026-08-13)
The line ranges a diff-mode repair round carries come from the PATCH THAT WAS
APPLIED, not from the `source_patch_applied` timeline event. That event's
metadata carries file LISTS only — `apply_id`, `snapshot_id`,
`snapshot_verified`, `success`, `files_modified`, `files_created`,
`error_count` (`packages/orchestration/source_apply.py`) — and
`build_repair_context` reads nothing else out of it, so no line number can be
recovered there. `run_builder_bridge_loop` already holds each cycle's
`BridgeResult`, whose `parse_result.patch` is a `StructuredPatch`; its
`unified_diffs` entries carry per-path diff text, and
`review_scope.parse_diff_line_ranges` turns that text into the
`{path: [[start, end], ...]}` shape `select_repair_hunks` consumes. A
`file_ops` patch names paths but no lines, so each of its paths maps to an
EMPTY range list and comes back as `no_ranges` — visible in the selection
result rather than silently absent. Remedy deliberately does not reconstruct
ranges by re-diffing `file_ops` content against disk in v1: that would be a
second differ next to the one `review_scope` already owns, and the full-file
repair path already covers the case.
