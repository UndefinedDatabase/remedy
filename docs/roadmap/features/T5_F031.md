## Goal & Done
Every open question in one calm place: the inbox UI renders decision
cards — type, age, blocked-subtree size — from the decision queue,
live via decision.requested/resolved events driving the badge, with
branch-only blocking semantics intact. DONE when the inbox lists
fixture decisions of every producing type with correct blocked-size
math, answering from a card round-trips through the write channel
into the same effects the CLI produces, the badge tracks live, and
sorting/urgency follows a documented rule (age × blocked size),
not vibes.

## How it fits (a storage correction versus an earlier draft)
An earlier sketch parenthesized "(SQLite)" — the decision queue is
and stays FILE-BASED (the established store with its CLI); the
inbox is a READ VIEW plus command wiring, not a migration; if scale
ever demands indexing, that is a separate, explicit decision (A6).
Everything else composes: producers already attach evidence
(plan approvals, budget stops, escalations, watchdog trips, veto
proposals, clarifications); blocked-subtree size comes from the DAG
module against the awaiting task; events ride the SSE stream
(decision.requested/resolved kinds — envelope coordination if not
yet present).

## Design (suggested shape)
- Read endpoint: decisions for the scoped project(s) with computed
  {age, blocked_count, type, job link}; the list honest about
  unreadable entries as everywhere.
- Cards per the design reference: type glyph, title, age chip,
  "blocks N tasks" chip, the producing job/node link (deep link
  into the graph focus), and the answer affordances rendered FROM
  the decision's options payload (generic renderer — producers
  define options, the inbox never hardcodes per-type forms; the
  evidence-triple feature enriches the card next).
- Ordering: urgency = f(age, blocked_count) with the formula
  documented on the sort control's tooltip; filters by type/job.
- Badge: the shell's inbox icon counts open decisions live from
  events with a snapshot-refetch fallback (the SSE hook contract).
- Answering: the existing decision-answer command through the
  channel (nonce, audit); resolved cards animate out per motion
  tokens; per-question clarification answers reuse the CLI's
  --answer semantics in form shape.

## Task slicing
- **T001** read endpoint + blocked-size computation + scoping +
  contract tests across all current producer types (fixtures per
  type).
- **T002** cards + generic options renderer + ordering/filtering +
  badge/events + component tests.
- **T003** answer wiring + clarification forms + deep links + the
  end-to-end (escalated fixture: card appears live, answer from
  the card, branch resumes, badge decrements).

## Acceptance
- Every producer type renders and answers correctly from fixtures
  (loop test — new producers must join the fixture set). Blocked
  math matches the DAG module. Badge live + fallback-correct.
  No per-type hardcoding in the renderer (a new fixture type with
  novel options renders generically — the extensibility test).

## Edge cases & assumption defaults (A9)
- Decisions from other projects: scoped out by default,
  --all-projects parity in the UI's project switcher (the
  multi-project feature completes it). Stale cards (job deleted):
  render orphaned, answerable-with-warning or dismissible —
  never a crash.

## Orchestrator brief
Gate on the write channel + SSE. The generic-renderer rule is the
architecture line (producers own semantics) — verbatim into T002.
The storage correction goes into T001's order so nobody
"helpfully" adds a database.

## Do not touch
Queue storage/format, producer payloads (the next feature raises
their bar), decision semantics. Suggested tests:
tests/ui_contract/test_decision_inbox.py.

## Design amendments (F031 R5, 2026-08-23)

> These rulings SUPERSEDE the sentences they name above. The originals are
> deliberately left in place: this file records what was planned and then what
> was ruled, in that order. Full rationale, alternatives and reversal paths are
> in `.agent/decisions.md` under DECISION F031 D1, D2 and D3.

- **D1 — the queue is a derived read view.** "How it fits" says the queue "is
  and stays FILE-BASED (the established store with its CLI)". That is true of
  the JOB RECORD, which `escalation.py` writes and `storage.py` persists, and
  not of `packages/orchestration/decision_queue.py`, which performs no I/O and
  re-derives every decision from a loaded job. T001 adds no storage; "Do not
  touch — queue storage/format" binds the escalation record shape, not the
  derivation, which may gain derived fields such as the blocked-subtree size.

- **D2 — the badge re-derives; no new event kind ships.** "Goal & Done" says
  "live via decision.requested/resolved events driving the badge", and "How it
  fits" anticipates those kinds with "envelope coordination if not yet
  present". Those kinds do not exist and no producer emits anything equivalent,
  so the badge instead RE-DERIVES its count through the same `list_decisions`
  call the read endpoint uses, refetched on the existing SSE stream. The
  snapshot-refetch path the Design section lists as the fallback becomes the
  primary one. F031 adds no kind to `event_schemas.py`.

- **D3 — the acceptance loop covers PRODUCING types.** "Acceptance" says "every
  producer type renders and answers correctly from fixtures". That set is the
  eight types a branch of `list_decisions` produces, derived from the branches
  rather than from the `DECISION_TYPES` frozenset. `worker_approval` and
  `revert_missing` have no producer, stay declared, and get no fixture; the
  extensibility test already covers a type nobody produces.

## Design amendments (F031 R11, 2026-08-26)

> These rulings SUPERSEDE the sentences they name above, on the same terms as
> the R5 section: the originals stay so this file records what was planned and
> then what was ruled. Rationale, alternatives and reversal paths are in

- **D4 — the card reuses the shipped shell.** "Design (suggested shape)" says
  "Cards per the design reference". Measured at `99d77d5c`, that reference
  carries no decision, inbox or queue COMPONENT: `component_spec.md` names none,
  the folder's only `inbox` string puts mobile inbox surfaces out of scope, and
  the one decision visual it does carry is a graph-node glyph. The card is
  therefore built from the shipped `RightLivePanel.module.css` shell and the
  `--remedy-*` properties `apps/ui/src/styles/tokens.css` defines, mounted in
  `RightLivePanel`. `NeedsAttentionCard`, which already renders a card headed
  "Needs your decision" from `workerStatus`, stays DISTINCT from the inbox in
  T002; T003 rules whether its decision branch is retired.

- **D5 — the inbox is tested at the pure layer.** "Task slicing" gives T002
  "component tests". Measured at `99d77d5c`, `apps/ui/vitest.config.ts` sets the
  environment to `node` and includes only `src/**/*.test.ts`, 0 files match
  `src/**/*.test.tsx`, and `apps/ui/package.json` names no DOM harness — so no
  component test is collected and that phrase could not be executed as written.
  T002's renderer model, ordering rule and badge count ship as pure functions
  under `apps/ui/src/api/` with `.test.ts` beside them, and the extensibility
  test runs against the model. The rendered markup is deliberately reached by no
  test until a DOM harness lands as its own feature.
