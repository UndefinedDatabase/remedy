# T12_F200 — Daemon mode (remedy serve)
**Tier 12 · Depends on: F011, F047, F048, F009 · Blocks/used by: F201 remote; M12; multi-user operation**

## Goal & Done
See ROADMAP.md F200; the Done criterion there is binding.

## Context (existing code & prior features)
Each CLI invocation spawns its own processes today; the queue (F048) already claims atomically - the foundations for a long-lived process exist.

## Design
apps/server/daemon.py: ONE supervisor per host: the scheduler loop (queue consumption F048, parallelism F049), a ui_server thread, notify/audit-export workers. The CLI becomes a client: a unix domain socket (default) or localhost HTTP with a token - detection is automatic (socket present -> client mode; else DIRECT mode exactly as today, fully supported). State ownership: in daemon mode ONLY the daemon writes job state (the CLI sends commands through the F009 gateway - the same single write door). Lifecycle: a systemd unit + a container entrypoint ship along; a restart auto-resumes running jobs (F047); the STOP file (F011) works unchanged.

## Task slicing
T001 the supervisor + the socket protocol (narrow: F009 command envelopes + status reads) + client detection + tests. T002 scheduler integration + a restart-resume test (kill -9 mid-cycle) + systemd/container artifacts. A LARGE block (A3).

## Acceptance & tests
daemon kill -> restart -> all jobs resume (F047 comparison); CLI behavior identical in both modes (the suite runs twice: direct + client); two simultaneous CLI clients never collide (nonce/queue semantics).

## Risks / anti-goals
Direct mode stays first-class (no daemon requirement for a single operator); no second write protocol (the socket transports F009 envelopes, nothing else).
