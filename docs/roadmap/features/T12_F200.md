# T12_F200 — Daemon mode (remedy serve)
**Tier 12 · Depends on: F011, F047, F048, F009 · Blocks/used by: F201 remote; M12; multi-user operation**

## Goal & Done
See ROADMAP.md F200; the Done criterion there is binding.

## Context (existing code & prior features)
Each CLI invocation spawns its own processes today; the queue (F048) already claims atomically - the foundations for a long-lived process exist.

## Design
apps/server/daemon.py: ONE supervisor per host: the scheduler loop (queue consumption F048, parallelism F049), a ui_server thread, notify/audit-export workers. The CLI becomes a client: a unix domain socket (default) or localhost HTTP with a token - detection is automatic (socket present -> client mode; else DIRECT mode exactly as today, fully supported). State ownership: in daemon mode ONLY the daemon writes job state (the CLI sends commands through the F009 gateway - the same single write door). Lifecycle: a systemd unit + a container entrypoint ship along; a restart auto-resumes running jobs (F047); the STOP file (F011) works unchanged.

## Task slicing
T001 the supervisor + the socket protocol (narrow: F009 command envelopes + status reads) + client detection + tests. T002 scheduler integration + a restart-resume test (kill -9 mid-cycle) + systemd/container artifacts. A LARGE block (A3).

## Acceptance & tests
daemon kill -> restart -> all jobs resume (F047 comparison); CLI behavior identical in both modes (the suite runs twice: direct + client); two simultaneous CLI clients never collide (nonce/queue semantics).

## Risks / anti-goals
Direct mode stays first-class (no daemon requirement for a single operator); no second write protocol (the socket transports F009 envelopes, nothing else).

## Amendment — DECISION F200 D1 (2026-10-01)
The Context, Design, Task slicing and Acceptance above were written before F261 retired the F048
queue with no heir (DECISIONs F261 D14 and D22) and before the F009 door was measured. They stay
as written, for the record; where they disagree with this section, this section governs.

**Design as amended.** `remedy serve start` runs one supervisor per data root in the foreground;
`remedy serve status` reports it and `remedy serve stop` stops it. Its files live in the durable
data-root class `serve` (`packages/orchestration/serve_paths.py`): `serve.sock`, `serve.pid`,
`serve.token` and the run registry `runs/`. The supervisor answers the unix socket with the
cockpit's own request handler, so the socket carries the F009 envelope through the same checks;
an effect that arrives over it is recorded with source `cli` and the command line's actor. When
the socket of the resolved data root answers, the command line sends each door command it shares
with the cockpit as an envelope and prints the answer exactly as its direct handler does; with no
socket every command runs direct, as today. The socket also accepts `job.run`: the supervisor runs
the job as a child process in direct mode, records it in its run registry, refuses a second run of
a job it is running, and on its next start runs again every registered job whose child is gone and
whose record still reads `running`. Not built: the scheduler loop and parallelism (the queue is
retired and F049 unbuilt), a cockpit thread inside the supervisor (F201), the notify and
audit-export workers (none exists), a localhost HTTP client channel, and a door clause for the
write commands the door does not carry (F253); those commands run direct in both modes.

**Task slicing as amended.** T001: `serve_paths` and the `serve` class; the supervisor with its
three commands and the socket; client detection; the door commands the command line shares,
forwarded. T002: `job run` through the supervisor; the restart and its kill test; the systemd unit
`scripts/serve/remedy-serve.service`, the container entrypoint `scripts/serve/container-entrypoint.sh`
and the built-state page.

**Acceptance as amended.**
- `remedy serve start` creates the socket and the token file readable by their owner only and
  writes the process id file; `remedy serve status` reports whether it runs; `remedy serve stop`
  stops it and removes the socket and the process id file.
- An envelope sent to the socket passes the cockpit door's checks and applies the same effect,
  recorded with source `cli`; a command the socket does not accept is refused as the door refuses.
- With the supervisor running, every forwarded command prints the same output, exits with the
  same code and leaves the same effect on disk as in direct mode; one test module runs each of
  them in both modes. Without a socket every command runs direct, exactly as before.
- Two clients at once never collide: two distinct nonces apply once each, a repeated nonce is
  refused as a replay, and a second `job run` of a job the supervisor runs is refused.
- Killing the supervisor and its runs with SIGKILL and starting it again runs every registered
  job that still reads `running` again, to the end F047's kill test proves: each task executed
  once and every task green.
- A STOP file (F011) stops a run the supervisor started, exactly as it stops a direct run.

**Amended by DECISION F200 D4 (2026-10-01).** Client mode covers `job.stop`, `job.pause`,
`job.unpause` and `job.run`; the other commands the cockpit's door carries run direct in both
modes, as the commands it does not carry do. "Every forwarded command" in the acceptance above
names those four.
