## Goal & Done
The disabled input under the feed comes alive: steer_task delivers a
human note into a per-task steering inbox, injected at the NEXT round
start as a binding operator note in the volatile prompt tail, the
feed shows the user's line (as in ux_design.png: "Please ensure
symlink loops are detected") — and there is no fake chat: the
builder's answer is its next action. DONE when a steering note
demonstrably lands in the following round's prompt trace at the
volatile rank, the feed renders the user line and the builder's
next humanized action as the reply, notes never interrupt in-flight
calls, and unconsumed notes surface honestly at task end.

## How it fits (inspect current shape before building)
Delivery discipline is the prompt-segment registry's volatile tail
(steering was rank 5 from day one — the slot exists, empty until
now); the inbox is a small per-task queue in job state (additive),
consumed at round start in arrival order, each note marked consumed
with the round reference (the trace-proof pattern from runtime
edits). The feed already renders event lines — a steering.sent
event kind (envelope coordination, Part E) carries the user line
into the same stream that shows the builder's subsequent actions;
the design deliberately frames the exchange as note→action, and the
UI copy must not promise conversation (the honest-tooltip era ends,
the honest-framing era begins).

## Design (suggested shape)
- Command steer_task {task_id, text: bounded length}: enqueue +
  audit + the event; notes to non-running tasks are accepted for
  the task's next run (waiting/paused) or refused on terminals with
  the state.
- Injection: round start drains the inbox into ONE operator-note
  segment ("OPERATOR NOTES (binding):" + numbered lines), rank
  steering; the trace grep proves presence; consumed markers +
  round refs in evidence.
- Unconsumed notes at task end (task finished before the next
  round): the task report lists them under "steering not consumed"
  — the human learns their note missed, instead of wondering.
- Feed/NowCard: the user line renders with the user avatar style
  per reference; no synthetic "builder says" reply is ever
  fabricated — the next humanized action IS the response
  (documented in the humanize catalog's framing).
- CLI parity `remedy job steer <id> --task Txxx "text"`.

## Task slicing
- **T001** inbox + drain-at-round-start + segment injection + trace
  proof + consumed/unconsumed evidence + unit tests.
- **T002** command + event + audit + state-gate tests (running/
  waiting/paused accept; terminals refuse).
- **T003** feed rendering + the enabled input (flag flip from the
  F021 disabled state) + framing copy + the end-to-end (steer
  mid-build → next round's trace contains it → feed shows note then
  the changed action).

## Acceptance
- Trace grep exact at the steering rank; in-flight calls never
  interrupted (call-boundary test). Ordering preserved across
  multiple notes; each consumed once. Unconsumed listing renders on
  the fast-finish fixture. No fabricated replies anywhere (copy
  audit + humanize framing test).

## Edge cases & assumption defaults (A9)
- Steering the whole job (no task): v1 targets tasks — the input
  requires a focused task context (the zoom state provides it);
  job-wide direction is the mission/decision layer's business,
  stated in the empty-focus tooltip. Prompt-injection hygiene: the
  note renders inside a clearly delimited operator block; content
  is the operator's responsibility (their job, their authority) —
  documented.

## Built State (F030, 2026-09-27)

What exists on disk at the close of F030, built in four rounds of one session on
`feature/f030-steering-messages`, cut from `main` at `15f5d384`. F264 — Steering channel — had
already built a job-wide steering message, its consumption at the start of every round, its segment
and its acknowledgement, and had enabled the feed's input; F030 builds on that channel and adds no
second one (DECISION F030 D1). Every DECISION named lives in `.agent/decisions.md`; every round's
verdict in `.agent/live_review.md` or, once rotated, its archive.

**T001 — the address, the drain, the segment and the report.** `record_steering_message` in
`packages/orchestration/steering.py` takes an optional `task_id`; the sealed record and its
`steering_message_received` event carry the key only when one is given, so every job-wide record
F264 writes is byte-identical (`note_task_id` reads it back). `consume_pending_steering`, at the one
safe point at the top of every round, consumes a note only in a round of the task it names, leaves
a note for any other task pending, never amends a mission's contract with a note, and returns the
job-wide messages alone. `consumed_task_notes` and `render_operator_notes_segment` give the task's
consumed notes, in arrival order, to `compose_builder_prompt` in
`packages/orchestration/pingpong_loop.py` as ONE segment, `builder_operator_notes`, at the steering
rank after `builder_steering` and before the directive, headed `OPERATOR NOTES (binding):` with one
numbered line per note, verbatim; every later round of that task carries it. A note whose task is
neither `pending` nor `running` and that no round took in is listed by `export_job_report` under
the task's `steering_not_consumed` key and by the text report as a `Steering not consumed:` line;
a job with no such note reports exactly as before (`_task_steering_not_consumed_map` in
`packages/orchestration/pingpong_job.py`).

**T002 — the command.** One function, `steer_task_command` in `steering.py`, answers both doors
without raising for a refusal: `invalid_message`, `job_not_steerable` for an ended job,
`unknown_task` naming the job's tasks, and `task_not_steerable` naming the status of a task outside
`STEERABLE_TASK_STATUSES` — `pending`, `running`, `blocked`, `failed` and `skipped`, the set F027's
veto already treats as able to run, pinned equal to it by a test. The command line is
`remedy job steer <job_id> "<text>" --task <task> [--json]` in
`apps/cli/commands/job_steer_cmd.py`, resolving a planned id as `job veto-task` does and exiting 2
for a wrong argument and 3 for a job or task that takes no note; the write door's command is the
same catalog id, `job.steer`, checking `task_id` and `message` before it reads the job, recording
with channel `cockpit`, and answering a refusal 409 with its code and detail (DECISION F030 D2).
`steering_overview` names the task each message was addressed to (`addressed_to`) and reads a note
whose task finished without taking it in as `not_taken_in` while the job still runs, which
`remedy chat show` prints with the task's name.

**T003 — the feed and the input.** A `steering_message_received` frame of the stream carries a
`note` of exactly four fields, message id, text, channel and task
(`_steering_note_summary_payload` in `packages/orchestration/ui_server.py`); every other kind's
frame is unchanged. `apps/ui/src/api/steeringNote.ts` reads it, `feedRowOf` gives the row
`author: "operator"` and the operator's own text as its line, and `ActivityFeedCard.tsx` draws the
row with an initial-letter disc reading "Y" and the name "You". The shell resolves its selected
graph node to the task item's id and passes it through `RightLivePanel` to the card, whose input
then sends `job.steer` for that task through `sendSteeringNote` in `steeringSend.ts`, and sends
`chat.send` job-wide, as F264 shipped it, when nothing is selected. The input's placeholder reads
"Note for task <id> — read at its next round" or "Note for the whole job — read at its next round",
and its tooltip is `STEERING_REPLY_FRAMING` in `humanizeCatalog.ts`: "Remedy never writes a reply
to a steering note: the builder's next action in this feed is the answer." The design reference's
assumption log records the placeholder and the disc (DECISION F030 D3).

**Acceptance, by the test that proves it.** The trace at the steering rank, and a call in flight
never interrupted: `TestTheCallBoundary` in `tests/orchestration/test_steering_notes.py` — a note
recorded while round 1's build call runs leaves round 1's prompt byte-identical and adds exactly
the segment to round 2's, whose trace manifest carries `builder_operator_notes` at rank 5 — and the
live proof `TestSteeringNoteTakenInLive` in `tests/ui_server/test_steering_note_e2e_live.py`,
which holds a real job's first build call in flight, posts the note through the real write door,
and reads round 1 without it and round 2 with it from the run's recorded trace. Order preserved and
each note taken in once: `TestTheNotes` in the same file. The unconsumed listing on a fast finish:
`TestTheReport`, and the live `TestSteeringNoteNotTakenInLive`, whose task passes in the round the
note arrived in and whose note then appears in the job report and in `remedy chat show` as not
taken in, never in the other task. No fabricated reply: the copy audit and the framing tests of
`tests/ui_contracts/test_steering_note_contract.py`, and the live proof's check that no stream frame
but the two steering kinds carries the note's text. The command and its state gate:
`tests/orchestration/test_steer_task.py`, `tests/cli/test_job_steer.py` and
`tests/ui_server/test_steer_task_door.py`; the frame: `tests/ui_server/test_steering_note_frame.py`.
Guards widened on purpose: `TestCommandDoorImportGuard` and `TestUiExposedCommands` in

`job.steer`; `tests/orchestration/import_reachability_allowlist.txt` gained the command's module;
and `tests/ui_contracts/test_steering_send_contract.py` pins the input's new `onSend`.

**Deliberate absences.** No second inbox and no new event name: a note is F264's steering message
with an address, and T5_F030.md's `steering.sent` is `steering_message_received` (DECISION F030
D1). No reply is ever composed; the builder's next action in the feed is the answer. The input
still steers the whole job when no task is selected, rather than refusing as the feature file's
edge case describes, because that is what F264 shipped (DECISION F030 D1). The zoom state was not
lifted into the shell: selecting a node is what focuses a task. A note never amends a mission's
contract, because it binds one task.
