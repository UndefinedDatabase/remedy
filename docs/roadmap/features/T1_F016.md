# T1_F016 — Scaling task granularity
**Tier 1 · Depends on: F014 · Blocks/used by: F144 input, self-build plan quality**

## Goal & Done
Flight-Plan tasks are right-sized automatically: oversized tasks split
into reviewable slices, trivial neighbors merged — so review happens on
small diffs, not monster patches. DONE when a fixture plan with one XL
task and three trivial tasks comes out normalized, every transformation is
recorded on the plan (nothing silently rewritten), and the heuristics are
pure functions with table tests.

## How it fits
Input and output are the Flight Plan schema; normalization runs at ONE
insertion point in plan generation, between validation and the mapping to
core tasks. No per-task-class cost history exists yet — v1 is therefore
heuristic on plan-intrinsic signals only, and the module docstring says so
instead of pretending to be data-driven (P6). Thresholds are config keys
under a planning table.

## Design (suggested shape)
Pure module `task_granularity.py`: `normalize_plan(plan, cfg)` returns the
new task list PLUS a transformations record
({kind split|merge, source_ids, result_ids, reason}) that the plan
rendering shows — the human approving the plan always sees what changed.
- Split, applied deterministically in order: a task above the configured
  max band (default: split XL) or above the acceptance-count threshold is
  split into one child per acceptance cluster (greedy grouping by shared
  files_hint tokens, else one per item); children chain their dependencies
  in original order, the first child inherits the parent's; children get
  a mid band, labeled as heuristically reassigned. A task that cannot be
  split (single acceptance item) stays and is FLAGGED unsplittable so the
  approver sees the risk.
- Merge: maximal runs of consecutive small tasks (small band, few
  acceptance items, overlapping files_hint, no external dependency on a
  middle member) merge up to a configured group size; titles join,
  acceptance concatenates, band bumps one step.
- Safety: after normalization the SAME DAG validator used by the plan
  schema runs again (import it, don't copy); any violation aborts and
  returns the original plan with an aborted-transformation record — fail
  open to the human-approved plan, never to a broken one.
- A planning config flag (default on) bypasses normalization entirely.

## Task slicing
- **T001** split rules + config + table tests (XL with three acceptance
  items → three chained children; unsplittable flag; exact threshold
  boundary).
- **T002** merge rule + dependency-safety tests (external dependency on a
  middle member blocks the merge; group cap; band bump).
- **T003** revalidation + abort path + wiring into plan generation + the
  plan.md normalization section + mixed-fixture integration + bypass test.

## Acceptance
- Mixed fixture (one XL/four-acceptance task, three consecutive trivial
  single-file tasks, one mid task) → four split children + one merged task
  + the mid task untouched; the transformation record matches a golden.
- Determinism: normalizing twice yields identical output. Disabled flag →
  byte-identical pass-through, empty record.

## Edge cases & assumption defaults (A9)
- Invalid bands can't reach this module (schema already rejected them) —
  no defensive re-checks. Overlap chains longer than the group cap: greedy
  left-to-right, remainder starts a new group.

## Orchestrator brief
One worker, sequential; the whole module is pure, so demand table-driven
tests in every order and reject diffs that add I/O. Include three or four
worked input→output examples in the T001 order text.

## Do not touch
Re-slicing of running jobs, actuals-driven estimation, review-effort
ladder (a later consumer). Suggested tests:
tests/orchestration/test_task_granularity.py.
