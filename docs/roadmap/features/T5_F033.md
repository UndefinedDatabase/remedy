## Goal & Done
Surgical consent over changes: hunks get STABLE ids (file + context
hash), approve_hunks {approved[], rejected[{id, reason}]} applies
the approved set to the branch while rejections become precise
repair feedback quoted in the next round — partial states tracked
end to end. DONE when a mixed approval on a fixture diff applies
exactly the approved hunks (worktree hash proof), rejected hunks'
reasons appear verbatim in the following repair prompt, ids survive
unrelated file edits (stability property), and every partial state
renders truthfully in viewer and report.

## How it fits (inspect current shape before building)
This feature replaces the viewer's provisional ids with content-hash
ids (file path + normalized hunk context hash — the JSON version
bumps; the viewer's contract note planned for this) and gives the
diff-repair feature its promised upgrade (the v1-local hunk lib
retires — one hunk identity across repair and approval; coordinate
the shared helper's home). Apply mechanics flow through the
applicator (fences, atomicity per approved SET — approved hunks
apply all-or-nothing together; a conflict inside the approved set
falls back to nothing-applied with the conflict named, the
established discipline). The rejection→repair loop reuses steering-
style volatile injection: rejections are findings for the next
round, quoted with their reasons.

## Design (suggested shape)
- Stable ids: hash(path + hunk old-side context normalized for
  whitespace policy) — the stability property: edits elsewhere in
  the file don't change other hunks' ids; the same logical hunk
  re-emitted next round keeps its id (tested).
- Command approve_hunks {task_id, attempt, approved[], rejected[]}:
  validation (ids exist in that attempt's diff; disjoint sets;
  reasons required on rejections — the veto lesson); effect: the
  approved subset materializes via the applicator on the job
  branch; the task's change state becomes partial with the
  ledger of hunk decisions in evidence; rejected hunks + reasons
  enqueue as repair findings for the next round.
- Partial-state truth: the viewer badges hunks
  (approved/rejected/pending), the task node shows the partial
  glyph treatment per reference, the report's task line says
  "partially approved (5/8 hunks)".
- Round interplay: the next builder round's diff maps returning
  hunks to prior decisions (same id → prior rejection reason shown
  in the viewer — the human sees the conversation).

## Edge cases & assumption defaults (A9)
- Approving nothing (all rejected): a full-rejection round — valid,
  the repair gets everything as findings. New hunks in round 2
  render pending (no inherited decisions). Whitespace-only hunks:
  normal hunks (policy is the project's formatter business, not
  the approver's).

## Amendments

**A1 (DECISION F033 D3) — T001's diff-repair consolidation is discharged as
vacuous.** The Task-slicing line for T001 and the How-it-fits paragraph both
promise that a "v1-local hunk lib" on the diff-repair side retires onto the
shared identity. No such library exists. Measured while closing T001:
`packages/orchestration/diff_repair.py` holds no hunk id, no digest and no
import of `packages/orchestration/hunk_identity.py`; its `RepairHunk` is a span
of current source lines selected for a repair prompt, with no old side to hash.
`review_scope.parse_diff_line_ranges` yields line ranges and names no hunk, and
`source_apply` digests whole files for apply proofs. `diff_parser.py` is the
only caller of the shared identity, and one caller is the design.

T001 is therefore complete on its three real deliverables — the stable
content-derived identity with its stability property tests, the parser wiring
with the `DIFF_VIEW_VERSION` bump to 2, and the client seam that stops the
viewer inventing a server-shaped id. Acceptance's "Diff-repair's suite green on
the shared helper" is read as "diff-repair's suite stays green", which it does,
untouched.

Reverse this amendment by deleting this section; the T001 clause above is
unchanged and would then read as originally written.
