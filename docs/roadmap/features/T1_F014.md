## Goal & Done
The deterministic skeleton is replaced by an LLM-generated, schema-validated
Flight Plan: ordered tasks with goals, acceptance criteria, dependencies
and token bands, carrying budgets and fences — rendered human-readably and
approved by a human before execution (P2). DONE when `remedy do` produces
a real plan on a fake provider, execution is gated behind a decision-queue
approval unless `--yes`, and the golden path's "deterministic skeleton"
label is consciously removed together with its guarding test.

## How it fits (inspect current shape before building)
The deterministic planner stays as the `--no-llm`/provider-down fallback;
this feature replaces its CALLERS' default. A planner-plan model may
already exist in the schema package — supersede it EXPLICITLY (deprecation
note pointing here), never leave two competing plan schemas undocumented.
Approval uses the existing decision queue and its CLI. Budgets and fences
are already additive job fields (earlier in STATUS order) — the plan
CARRIES them. Verify the core task model's field names before mapping
plan tasks into it.

## Design (suggested shape)
- Schemas: `PlannedTask` — id, title, goal, acceptance (min one, testable
  phrasing), depends_on, est_tokens_band S|M|L|XL (bands, not fake-precise
  numbers — honest while no per-task history exists), files_hint.
  `FlightPlan` (versioned "flight_plan_v1") — tasks (validated as a DAG:
  unknown or cyclic dependencies rejected), risks,
  clarifications_resolved (question/default/impact from intake; answers
  filled by the bundled-clarification feature), optional budgets and
  fences mirrors.
- Module `flight_plan.py`: `plan_job_llm(job, provider_call)` prompts with
  the intake JSON + the same cheap repo facts + the rendered schema;
  validates with the existing parse-retry; maps planned tasks into core
  tasks preserving order and dependency metadata; copies plan budgets/
  fences onto the job ONLY where the user set none (explicit CLI/config
  always wins — precedence test); stores the plan additively on the job;
  state planned. `render_plan_md(plan)` writes a deterministic, stably
  ordered plan.md into the job's evidence area.
- Approval gate (P2): one decision "approve flight plan", options
  approve/reject; execution entry points refuse while it is open; `--yes`
  records an auto-approval decision (audit trail, not a silent skip);
  reject leaves the job planned and suggests `--replan`, which appends a
  new plan version and keeps the old rendering.

## Task slicing
- **T001** schemas + DAG validator + tests (cycle, unknown dep, empty
  acceptance, band enum) + deprecation note on any older plan model.
- **T002** plan generation + task mapping + budget/fence precedence +
  fake-provider tests (order kept; a config-set budget survives).
- **T003** plan.md renderer (golden file) + replan versioning.
- **T004** approval gate + --yes audit + execution-refusal test + the
  label/test flip in the golden path + smoke update (init → do → approve
  → status).

## Acceptance
- Fake three-task plan → three core tasks, planned state, plan.md, one
  open decision; an execution attempt while open exits with "plan awaiting
  approval". Answering approve unblocks a fake run.
- A cyclic plan from the provider fails as parse class after the retry,
  postmortem written, job not planned. Fallback path green with providers
  stripped from PATH.

## Edge cases & assumption defaults (A9)
- More than about a dozen tasks → accepted but flagged in plan.md
  ("consider splitting the mission"); a hard validator cap (~25) rejects
  hallucinated scope. Replanning after ANY completed task is out of scope
  (guarded with a clear message) — mid-run replanning is a later feature.

## Orchestrator brief
