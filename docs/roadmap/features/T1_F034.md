## Goal & Done
All open questions are asked ONCE, bundled, at plan time — never again:
intake clarifications ride the plan-approval decision; every unanswered
question runs on its documented default; the runtime is provably incapable
of asking mid-run. DONE when an unattended `remedy do --yes` completes with
all defaults recorded in an assumption log, and a guard test fails the
build if interactive prompting ever enters the execution packages.

## How it fits
The intake schema already carries clarifications as question/default/impact
records — this feature is the consumer. The Flight Plan's approval gate
already creates exactly one decision per plan: clarifications extend THAT
entry's payload rather than adding one decision per question — one human
touchpoint is the whole point. Check the decision record's current shape;
if it has no structured payload, extend it additively.

## Design (suggested shape)
- Plan-time flow inside plan generation, after normalization: carry intake
  clarifications into the plan's clarifications_resolved with empty
  answer/answered_by; embed the questions in the approval decision's
  payload; the existing decision-answer command gains per-question answers
  (e.g. `--answer q1="use PostgreSQL"`); unanswered questions resolve to
  their defaults. On approval, answers or defaults are written back
  (answered_by human|default), the job saved, and answers become immutable
  — a late answer is rejected with a clear "already resolved".
- Assumption log: an assumptions.md in the job's evidence area, one line
  per question — question → chosen answer → source → impact — plus any
  planner-declared A9 defaults; the plan rendering links to it. This is
  the audit artifact reviewers read.
- Prompt side: the planner prompt instructs the model to RESOLVE intake
  questions into plan choices where possible and carry forward only
  genuinely ambiguous ones — target is zero questions for routine missions
  (unattended-first, P7).
- Runtime never asks — ENFORCED: a guard test (copy the repo's existing
  guard-test pattern) forbids interactive-input constructs in the
  orchestration and core packages, with an allowlist that starts empty.
  `--yes` covers approval AND clarifications (all defaults, audited);
  combined with budgets this is the sanctioned unattended mode.
- Conditional answers: a clarification answer may carry a machine-
  checkable predicate over run state (e.g. "approved provided the final
  package reports zero dirty files"). The runner evaluates the predicate
  at the consumption point with recorded evidence; unmet → the answer is
  void and the question re-escalates. Predicates are limited to a small
  registered comparator set — free-form conditions are a spec error.
  (Pattern validated 2026-07-23 in the split workflow: reviewer-authored
  conditional resolutions applied unattended once dirty==0 held.)
- CLI: `remedy job assumptions <id>` prints the log.

## Task slicing
- **T001** decision payload extension + per-question answer parsing +
  tests (answer one of two; unknown question id → clean error).
- **T002** embed → approve → write-back → immutability (late answer
  rejected) + tests.
- **T003** assumptions.md renderer (golden: one human answer, one default,
  one planner assumption) + the CLI + the plan.md link.
- **T004** the interactive-input guard test (prove it fails on an injected
  violation, then green on the real tree) + the unattended end-to-end:
  fake provider, one clarification, --yes → default recorded, zero open
  decisions, exit 0.

## Acceptance
- Two clarifications → exactly ONE open decision; a mixed answer/default
  approval persists the right answered_by values and matches the golden
  log. Zero clarifications → approval flow identical to the plain plan
  (regression). No execution path reads stdin.

## Edge cases & assumption defaults (A9)
- Defaults must be conservative: the planner prompt mandates keep/no-op
  style defaults with impact text; a fixture asserts a keep-style default
  survives the round trip. Remedy never defaults to destructive choices —
  humans can, explicitly.

## Orchestrator brief
T001 first (contract), then T002/T003 parallel, T004 last as the proving
order. Put the conservative-defaults rule verbatim into every worker
prompt that touches the planner prompt text.

## Do not touch
Mid-run advisory decisions, persona question style, notification delivery.
Suggested tests: tests/orchestration/test_bundled_clarification.py,
tests/cli/test_decision_answers.py, tests/test_no_interactive_guard.py.

## Built State (2026-07-26)

What exists, as proven by the tests named below. Nothing here claims
behavior beyond what those tests exercise.

**Contract.** `FlightPlanClarification` (schemas/models.py) gained two
additive fields: `id` and `answered_by` (`human` | `default` | `""`), both
defaulting to empty so pre-F034 `fp1` job data loads unchanged. The
persisted vocabulary is exactly those three values — a planner-declared A9
assumption keeps `answered_by=""` and is recognised by carrying an answer;
the log derives the "planner" source from that shape (rationale in
`.agent/decisions.md`).

**Plan generation.** `flight_plan.py` gained `carry_intake_clarifications`
(runs inside `plan_job_llm` after F016 granularity normalization): every
intake clarification becomes an unanswered entry with a stable id assigned
by intake order (`q1`, `q2`, …). A planner echoing an intake question back
does not close it — the intake is authoritative for what is open. Planner
entries that are not intake questions are preserved after them as
assumptions. A plan with no intake clarifications and no planner entries is
returned unchanged (identity), so the zero-clarification approval flow is
byte-for-byte the plain-plan flow.

**One decision per plan.** `open_clarification_questions` feeds the
questions into the payload of the *existing* `fp:approval` decision
(`decision_queue.py`, where `HumanDecision` gained an additive `payload`
dict). Two clarifications produce exactly one open decision, asserted by
test. No decision is created per question.

**Resolution and immutability.** `apply_clarification_answers` writes every
open question in one pass — a supplied answer with `answered_by="human"`,
an unanswered one with its `default_answer` and `answered_by="default"` —
returning new records rather than mutating the caller's. It is shared by
the interactive approval path and the unattended one, so both record
identically. `clarifications_already_resolved` backs the immutability
check: a late `--answer` against a resolved plan is rejected by name and
points at replan. Rejection leaves clarifications untouched.

**CLI.** `remedy decision resolve <job> fp:approval` takes a repeatable
`--answer q1="text"` (`ArgDef.is_repeatable`, declared per argument for the
same reason `is_flag` is). Answering a subset is valid; unknown, malformed
and duplicate ids each fail cleanly with exit 1. `remedy job assumptions
<id>` prints the log, rendered from the job's own flight plan so it is
truthful even for jobs approved before the evidence file existed.

**Assumption log.** `render_assumptions_md` / `write_assumptions_md` emit
`assumptions.md` into the job evidence area: one row per question —
id → question → answer → source → impact — with a source tally. Sources are
`human`, `default`, `planner`, `unresolved`. Table cells escape pipes and
fold newlines so free text cannot break the table. `render_plan_md` links
to the log and shows question ids.

**Unattended.** `remedy do --yes` covers approval AND clarifications: every
open question resolves to its documented default and the log is written.
The end-to-end test drives a fake provider with one clarification and
asserts the default is recorded with `answered_by="default"`, the log is on
disk, and zero flight-plan decisions remain open.

**Runtime cannot ask — enforced.** `tests/test_no_interactive_guard.py`
parses every module under `packages/orchestration`, `core`, `providers`,
`runtimes` and `verification` and fails on `input()`, `raw_input()`,
`getpass`, `click.prompt/confirm` or `sys.stdin`. The allowlist is empty and
a test keeps it empty. Detection is AST-based, not textual: a regex version
flagged prose such as "needs user input (e.g. acceptance criteria)" in
`progress_ledger.py`, and a guard with false positives gets allowlisted
into uselessness. The guard was proven red on an injected violation before
being accepted green. Scope limit worth knowing: it covers `packages/`
only — `apps/cli` stays deliberately interactive-capable.

**Planner prompt.** Instructs the model to resolve intake questions into
plan choices where the material settles them, carry forward only genuinely
ambiguous ones, and give every clarification a conservative keep/no-op
default with impact text. The conservative-defaults rule is recorded
verbatim beside the template. A fixture asserts a keep-style default
survives the round trip into the log.

**Not built.** Conditional-answer predicates (machine-checkable predicates
over run state, registered comparator set) are declared OPTIONAL by this
file's orchestrator brief and were skipped — they need a comparator
registry, a runner evaluation point and evidence plumbing, and no DONE
criterion depends on them. Recorded in `.agent/decisions.md`.
