# T3_F110 — Model routing by task class
**Tier 3 · Depends on: F103 · Blocks/used by: cost curve, F133/F156 feed it later**

## Goal & Done
One-model-for-everything ends: each call declares a task class, a router
maps classes to model tiers (cheap for format/extract/summary, mid for
standard build/review, top for architecture/mission/orchestrator), and
every routed call records the routed model WITH the reason. DONE when the
class table drives fixture calls to the right models, the written policy
document's hard rules are ENFORCED IN CODE, and promoting a cheaper model
into a class is only possible through documented benchmark thresholds —
never by editing a mapping casually.

## How it fits (inspect current shape before building)
A routing policy seed already exists as a repo document (class→tier map,
promotion rule, hard rules) — the initial mapping is SEEDED from it and
the document remains the human-readable policy; the code enforces it.
Roles already exist implicitly (builder, reviewer, orchestrator, summary,
intake/planner) — inventory every provider-call site and its role first;
routing hooks in at the single place model selection happens today (find
it; if selection is scattered, consolidating it into one resolver is the
first order). The ledger records model per call already — routing adds
the reason.

## Design (suggested shape)
- `routing.py`: resolve(task_class, context) → {model, tier, reason};
  class table from config seeded by the policy document; per-project
  overrides allowed but hard rules always win.
- Hard rules enforced in code (each a named check with a test):
  reviewer never routed weaker than its paired worker; orchestrator and
  mission-compile calls always top tier; safety-relevant classes
  (fence/DoD evaluation prompts, if any become LLM calls) never below
  mid. Violating overrides fail config validation with the rule named.
- Promotion discipline: moving a class to a cheaper tier requires a
  benchmark evidence reference (the bench feature's thresholds: multiple
  runs per fixture, documented pass bars) recorded in the config change
  — the resolver logs promoted_by evidence per run; missing evidence →
  the override is refused. Applies identically to local endpoints and
  external builders.
- Evidence: routed_model, tier, reason on every call; the report's cost
  section can group by tier.

## Task slicing
- **T001** call-site/role inventory + the single resolver seam (
  consolidation order if needed) + class declarations on all call sites.
- **T002** resolver + config schema + hard-rule checks + tests (each
  rule violated in a fixture config → named refusal).
- **T003** promotion-evidence discipline + evidence fields + goldens
  (a promotion without evidence refused; with evidence logged).

## Acceptance
- Fixture run: every call's evidence shows class, routed model, reason;
  the class table matches the policy document (a sync test diffs them).
  Each hard rule has a violating fixture that is refused with the rule
  named. Reviewer/worker pairing asserted on a real fixture round.

## Edge cases & assumption defaults (A9)
- Unknown class at a call site → route to top tier and record
  reason=unknown_class_conservative (over-spending beats under-thinking)
  plus a warning — new classes must be declared, not guessed. Model
  unavailability is the failover feature's job; routing only picks the
  intended model.

## Orchestrator brief
T001's inventory is the real work — require the full call-site list
with roles as a deliverable before T002. The policy-document sync test
keeps humans and code honest; make it an explicit acceptance line.

## Do not touch
Failover chains, local-endpoint setup, learned routing (later
features feed this). Suggested tests:
tests/orchestration/test_routing.py.
