# T3_F110 — Model routing by task class
**Tier 3 · Depends on: F103 · Blocks/used by: cost curve, F133/F156 feed it later**

## Goal & Done
See ROADMAP.md F110; the Done criterion there is binding.

## Context (existing code & prior features)
One model does everything today. A written routing seed exists in
`docs/agents/model_routing_policy.md` (class→tier map, promotion rule, hard rules).

## Design
routing.py: class -> model (format/extract/summary cheap; standard build/review mid; architecture/mission/vision top); per-project overrides; routed_model + reason in evidence. The initial mapping is seeded from `docs/agents/model_routing_policy.md`; the policy's hard rules are enforced in code: reviewer never routed weaker than the paired worker; promotion of a cheaper/local model into a task class only via the documented F082-benchmark thresholds (3 runs per fixture, ≥90% block-level / ≥75% overall), logged per run. Applies to local endpoints (F113) and external builders alike.

## Task slicing
T001 router + mapping + tests. T002 benchmark cost/PASS comparison before/after. T003 promotion gate: threshold check against F082 results + reviewer≥worker invariant test.

## Acceptance & tests
Costs drop at equal PASS (documented comparison). Additionally: a below-threshold promotion attempt is rejected with the benchmark evidence; a config routing the reviewer weaker than the worker fails validation.

## Risks / anti-goals
No silent downgrade of security-relevant roles. No promotion by vibes - only the documented benchmark path (P1).
