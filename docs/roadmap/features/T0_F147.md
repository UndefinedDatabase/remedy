# T0_F147 — Golden-path CLI
**Tier 0 · Depends on: F146 · Later integrates: F014 completes full Flight Plan rendering / plan-view behavior · Blocks/used by: the product's usability promise**

## Goal & Done
The three-command mental model works on TODAY's machinery: `remedy do
"<mission>"` creates and plans a job, `remedy status` shows where
everything stands, the existing decisions commands close the loop. DONE
when a new user in an initialized repo reaches a planned job with one
command and always sees the next step — and every output is honest about
what is deterministic scaffolding versus future LLM planning (P6).

## How it fits (inspect current shape before building)
A do-command and job commands already exist; grouped help rendering
exists. This feature is wiring and OUTPUT QUALITY, not new machinery.
Today's planner is a deterministic local skeleton (no LLM) — the golden
path must not hide that: label the plan `plan: deterministic skeleton (LLM
Flight Plan lands with F013/F014)`, with a test asserting the label so the
Flight Plan feature must consciously flip it. Every golden-path command
resolves the project first through the identity feature's shared helper
and reuses its fix-it error verbatim.

## Design (suggested shape)
- `remedy do "<mission>"`: resolve project → create the job with the
  mission stored on it (add an additive field if none exists) → plan →
  save → print: short id, project slug, state, the task list, the honest
  plan label, and `Next: remedy status`. Extend the existing do path; all
  current flags keep working (their tests stay green unmodified).
- `remedy status [--json]`: for the current project — jobs grouped by
  state, open decision count, runtime state (an unreadable state file
  degrades to "unknown" with a warning, never a crash), pending stop
  requests. Until the scoping feature lands, it shows all jobs and SAYS
  "all projects" — implement the label now, the filter later. Each section
  ends with the single most useful next command. Always exit 0 — status
  reports, it never judges.
- Help: the top layer pins do/status/decisions first, following the
  existing help-renderer structure; no help redesign.
- Exit codes: do → 0 planned, 3 unresolved project, 2 bad args.

## Task slicing
- **T001** do path: resolution + mission field + output block + label;
  tests: fresh repo init→do→planned with the skeleton tasks; missing
  project → exact fix-it text.
- **T002** status: sections + degraded values + stable json schema
  {jobs by state, decisions_open, runtime, stops_pending}; fixtures per
  section state.
- **T003** help pinning + a golden-path smoke test: init → do → status →
  stop → status shows the stopped job.

## Acceptance
- One command from mission text to a planned job with a visible task list.
- Status renders with zero jobs, mixed states, open decisions, and a
  corrupt runtime state file. All pre-existing do/job tests green
  unmodified. Empty mission → exit 2, no prompt.

## Edge cases & assumption defaults (A9)
- Very long missions are stored fully and truncated only in display.
- Jobs from other projects: visible but labeled until scoping lands —
  honesty over premature filtering.

## Orchestrator brief
T001 and T002 are independent orders; T003 gates on both plus the kill
switch. Tell workers explicitly: extend the existing do command, do not
create a parallel one (A6) — have them name the file they extended.

## Do not touch
Planner internals (the Flight Plan replaces them), decision answering,
runtime serve/stop semantics, the help taxonomy beyond pinning. Suggested
tests: tests/cli/test_golden_path.py plus extensions to existing do tests.
