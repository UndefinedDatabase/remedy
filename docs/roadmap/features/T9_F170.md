# T9_F170 — License & SBOM gate
**Tier 9 · Depends on: F017, F061 · Blocks/used by: a purchase prerequisite for many teams**

## Goal & Done
Dependency changes stop smuggling licenses in: on a dependency
delta, license resolution (Python via lockfile/metadata scan, JS
via package resolution) matches against .remedy/policy/
licenses.toml (allow/deny/review); a deny becomes a decision with
the evidence triple, review becomes a clarification item; every
job emits a CycloneDX SBOM (sbom.cdx.json) plus a delta SBOM in
the report; and a DoD block of kind licenses gates sensitive
projects. DONE when seeded dependency changes classify exactly
per policy (allow silent, deny → the decision with the license
and its source named, review → the question), the SBOM validates
against the CycloneDX schema and covers the fixture manifests,
delta SBOMs list precisely the changed components, resolution
handles the honest-unknown case (unresolvable license → review by
default, never silent allow), and generation stays dependency-
lean (stdlib parsing where feasible, any SBOM tooling optional).

## How it fits (inspect current shape before building)
Dependency-delta detection exists twice already (the ADR detector
and the permission matrix's dependency_change action parse
manifests) — consolidation finding first: ONE manifest-delta
helper (ecosystem parsers for lockfiles/manifests) serving all
three consumers. License resolution per ecosystem: Python
lockfiles/metadata carry license fields (parse; absent → the
package metadata via the local environment where installed, else
unknown), JS package.json license fields via the resolved tree —
resolution is best-effort with the honest unknown class (the
policy's review lane catches it). SBOM: CycloneDX JSON is a
documented schema — generation from the resolved dependency set
is deterministic assembly (stdlib json; a validation fixture
against the schema); no heavyweight SBOM toolchain in base
(optional extra only if an ecosystem demands it, stated).

## Design (suggested shape)
- Policy: licenses.toml {allow: [spdx ids], deny: [...],
  review: [...], unknown: review|deny (default review)};
  validation (spdx-ish id shape, no overlaps).
- The gate: manifest delta → resolve licenses per added/updated
  component → classify → deny decisions (triple: the component,
  license, source ref; expected outcome per option: keep-with-
  exception | replace | drop; downside stated), review
  clarifications (bundled at plan time when the delta is
  plan-visible, else at apply time as a decision — both paths
  tested).
- SBOM: per job, the full resolved set → sbom.cdx.json
  (components: name, version, license, purl-style ids where
  derivable) + the delta section in the report (added/updated/
  removed with licenses).
- DoD kind licenses: red on unresolved denies, warn on open
  reviews (config promotes); the sensitive-project default via
  policy packs later (noted).
- Exceptions: policy allows per-component exceptions with a
  reason (the suppression-needs-reason rule verbatim from the
  security gate).

## Task slicing
- **T001** the manifest-delta consolidation + ecosystem license
  resolution + the unknown class + table tests per ecosystem.
- **T002** policy + classification + decisions/clarifications
  (both timing paths) + exception rules + fixtures.
- **T003** SBOM generation + schema validation fixture + the
  delta report section + the DoD kind + the end-to-end (a job
  adding a GPL dependency under a deny policy → the decision;
  resolved → SBOM reflects the outcome).

## Acceptance
- Classification matrix exact incl. unknown→review. Deny
  decisions carry component+license+source with real triples.
  SBOM schema-valid, complete on fixtures; deltas precise.
  Exceptions require reasons. One manifest-delta helper (grep +
  the two prior consumers migrated, suites green).

## Edge cases & assumption defaults (A9)
- Dual-licensed components: all detected ids listed; policy
  matches on ANY deny (conservative), the decision shows the
  choice. Transitive additions: the resolved set covers them
  (that's the point); resolution failures on deep trees land in
  unknown honestly. Monorepos with multiple manifests: per-
  manifest deltas, one aggregated gate.

## Orchestrator brief
T001's consolidation protects three features — findings first.
The unknown-never-silently-allows rule and the reasoned-
exceptions rule go verbatim. SBOM stays dependency-lean; reject
toolchain imports without the ADR.

## Do not touch
ADR-detector semantics (shared helper only), matrix actions,
report structure beyond the section. Suggested tests:
tests/enterprise/test_sbom_gate.py.
