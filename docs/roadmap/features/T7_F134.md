# T7_F134 — Security gate
**Tier 7 · Depends on: F061 · Blocks/used by: safe outputs, F244 later**

## Goal & Done
Generated code passes a security bar before it ships: curated
static rules (semgrep-style), Python security lint (bandit-style)
and dependency audit (high+ severity) run on TOUCHED files,
findings enter review like any findings, sensitive orders get a
blocking DoD block, runtime stays under a minute on benchmark
repos, and false positives live under a budget with a tuning log.
DONE when seeded vulnerability fixtures fire the right rules,
tooling ships as an optional security extra with per-ecosystem
honest degradation, the curated ruleset is versioned with a
tuning log (every suppression justified), and the runtime budget
is measured and enforced.

## How it fits (a dependency-stance note + composition)
Scanners join `remedy[security]` (the extras pattern — base stays
lean); ecosystems detect per project (Python rules always in the
extra; npm audit only where a package manifest exists; absence →
the honest not-applicable/tool_unavailable rows per the DoD
rules). Scope = the job's touched files (applicator evidence) plus
dependency manifests when changed — a gate on the CHANGE, not a
repo-wide audit (that is a routine mission's job, the library can
gain one later, noted). Findings map into the review flow with
origin security_gate and the shared severity enum; the DoD block
(kind security, blocking) registers for sensitive orders — the
sensitivity trigger reuses the security LABEL vocabulary the red
review introduced (one label, two consumers).

## Design (suggested shape)
- `security_gate.py`: run configured scanners over touched scope
  → normalize findings {rule id, severity mapped to the shared
  enum, location, message, scanner} → dedupe → into the round's
  findings (origin-tagged) and the DoD rows.
- The curated ruleset: a versioned rules manifest in the repo
  (which semgrep packs/rules, which bandit tests, audit severity
  floor) + tuning.log entries {rule, decision suppress|keep,
  reason, date} — suppressions without reasons fail validation;
  the false-positive budget = suppressions reviewed per period
  (a stats line, honest).
- Runtime: per-scanner time caps summing under the minute budget
  on the benchmark fixtures (measured in CI — the budget test);
  cap hits report partial coverage honestly.
- Blocking policy: findings ≥ high block on security-labeled
  orders (the DoD block); elsewhere they enter review non-gating
  by default (config promotes).

## Task slicing
- **T001** extra packaging + ecosystem detection + the normalizer
  + shared-enum mapping + unit tests per scanner shape (fixture
  outputs, not live tools).
- **T002** touched-scope selection + the ruleset manifest +
  tuning-log validation + seeded-vuln fixtures per rule family
  (injection, secrets-in-code, dangerous call, vulnerable dep).
- **T003** review/DoD integration + the label trigger + runtime
  budget measurement in CI + the end-to-end (labeled order with a
  seeded injection → blocked → fixed → green).

## Acceptance
- Seeded matrix fires exactly (per family); unrelated files
  untouched by scope. Degradation matrix honest per ecosystem/
  extra-absence. Suppressions require reasons (validator); the
  budget stat renders. Runtime under budget on fixtures
  (numbers recorded). Blocking only on the label by default.

## Edge cases & assumption defaults (A9)
- Scanner disagreement/duplicates across tools: dedupe by
  location+category with both scanners credited. Generated/
  vendored code: the shared ignore notion applies — but
  dependency manifests always scan (that's the point of audit).

## Orchestrator brief
Gate on DoD runners + the label vocabulary. The suppressions-
need-reasons rule and the runtime budget go verbatim. T001 uses
recorded scanner outputs — no live-tool flakiness in unit tests.

## Do not touch
Repo-wide audit missions (later library entry), severity enum,
review mechanics. Suggested tests:
tests/orchestration/test_security_gate.py.
