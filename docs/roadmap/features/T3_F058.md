# T3_F058 — Model failover chain
**Tier 3 · Depends on: F001, F057 · Blocks/used by: robustness**

## Goal & Done
Availability gaps degrade gracefully within policy: each role carries a
configured failover chain, triggered ONLY by provider-unavailable after
the transport retries are exhausted — and every failover records the
configured versus the actually used model in evidence plus a mandatory
report line. DONE when an unavailable-primary fixture completes on the
fallback with full disclosure, a rate-limited provider WAITS (governor)
instead of failing over, and routing's hard rules still bind the
fallback choice.

## How it fits (inspect current shape before building)
The trigger taxonomy already exists: transport retries own timeouts and
transient errors; the rate governor owns limit waits; the
provider_unavailable classification marks the genuine gap — failover
fires on exactly that class and nothing else (failing over on a timeout
hides infrastructure problems and burns money on the wrong model).
Routing resolves the intended model; failover is a second resolution
step INSIDE the same resolver seam, and the hard rules (reviewer not
weaker than worker, core never local, orchestrator top-tier) validate
the chain at config time and the choice at runtime.

## Design (suggested shape)
- Config: per-role chains (ordered model lists); validation refuses
  chains violating hard rules ANYWHERE in the chain (a chain is only as
  safe as its last link).
- `failover.py`: on provider_unavailable for the resolved model, walk
  the chain; each attempt is a normal call with its own evidence; chain
  exhausted → the classified failure stands as today.
- Disclosure: evidence per call records intended vs used model with
  reason failover:provider_unavailable; the run report gains a
  mandatory line whenever any call in the run failed over ("N calls
  served by fallback models — see evidence"); silence is forbidden
  (P6).
- Session/resume interplay: a failed-over call never resumes a session
  from a different model (the resume feature's guard) — state that and
  test it.
- Sticky window: after a failover, subsequent calls for that role skip
  the dead primary for a config cooldown (avoid per-call thrash), with
  the governor-style honest wait/skip evidence; the cooldown expiring
  re-tries the primary.

## Task slicing
- **T001** chain config + hard-rule validation + unit tests (violating
  chains refused with the rule and link named).
- **T002** the failover walk + disclosure evidence + report line +
  fixtures (primary down → fallback serves; chain exhausted →
  unchanged failure).
- **T003** trigger discipline + sticky cooldown + interplay tests
  (timeout does NOT fail over; rate limit WAITS; resume guard holds).

## Acceptance
- Down-primary fixture completes with intended/used pairs in evidence
  and the report line present. Timeout fixture: retries then fails,
  zero failover. Limit fixture: waits, zero failover. Cooldown skips
  then re-tries the primary on expiry (injected clock).

## Edge cases & assumption defaults (A9)
- Chains crossing providers (cloud A → cloud B → local for side roles
  only): allowed where hard rules permit; cost bases differ and the
  ledger's per-model rows keep that honest. Empty chain = today's
  behavior; no implicit defaults (failover is opt-in policy).

## Orchestrator brief
Gate on routing. T003 is where discipline lives — enumerate the three
non-triggers (timeout, limit, parse) as explicit negative tests in the
order.

## Do not touch
Transport retry policy, governor pacing, routing's class table.
Suggested tests: tests/orchestration/test_failover.py.

## Amendment — DECISION F058 D1 (2026-10-12)
This section governs where the text above disagrees with it.

- **The chains** live in `remedy.toml` under the key `model_failover.chains`: one entry per role,
  each a list of links, each link a table of exactly `provider`, `model` and `tier`. A link names
  its tier because Remedy maps no model name to a tier. No chain is today's behaviour.
- **The hard rules** checked on every link are the three of
  `packages/orchestration/model_routing.py` — reviewer not weaker than worker, orchestration
  classes at the top tier, safety-relevant classes not below mid — and "core never local", which
  this feature adds as the rule `core_role_on_local_provider`: a link on the local provider
  `ollama` only for the roles whose class the shipped table routes to `cheap`.
- **A refused chain table** warns once, naming every violation, and no role fails over.
- **The module** is `packages/orchestration/model_failover.py`; the key lives in
  `packages/orchestration/config_keys_model_routing.py`, after a structural step moves the
  routing keys there out of `packages/orchestration/config.py`.

### Slices
- **T001** — the structural step, the key, the parse and the hard-rule validation, with tests
  naming the rule and the link of every refusal.
- **T002** — the failover walk where a run builds its providers, the intended and the used
  provider and model in each failed-over call's evidence with the reason
  `failover:provider_unavailable`, and the run report's line; fixtures for a primary that is down
  and a chain that is exhausted.
- **T003** — the trigger discipline (a timeout, a rate limit and a parse failure never fail
  over), the sticky cooldown on an injected clock, and the session guard: a failed-over call never
  resumes a session another model opened.

## Built State (F058, 2026-10-12)
T001 (DECISION F058 D1): the config key `model_failover.chains` is a table of roles, each a list of
links of exactly `provider`, `model` and `tier`. `parse_failover_chains` refuses a shape fault, and
`validate_failover_chains` checks every link against the three hard rules of
`docs/agents/model_routing_policy.md` and a fourth, `core_role_on_local_provider`; a refused table
raises `FailoverChainRefused` naming every violation, and `resolve_failover_chains` turns it into one
warning and no failover. The structural step that came with it moved the routing keys to
`packages/orchestration/config_keys_model_routing.py`.

T002 (DECISION F058 D2, D3): `FailoverProvider` in `packages/orchestration/model_failover.py` walks a
role's chain when `is_failover_trigger` holds, and `create_role_provider` in
`packages/orchestration/role_provider_factory.py` wraps the role's provider with it. A call the walk
reached carries a `failover` key in the run record (`packages/orchestration/pingpong_call_record.py`),
and `remedy run show` prints one `Failover:` line from it (`apps/cli/commands/run_report_cmd.py`).

T003 (DECISION F058 D4): the key `model_failover.cooldown_s` (default 300, 0 never holds) opens a
sticky window on an injected clock after a backup has served; during it the backups are tried first
and the usual provider last. The session guard offers a backup no session, resumes none for the rest
of the run once a backup has served, and `parked_session_refs` never hands a backup's session to the
usual provider on a relaunch. The three non-triggers (a timeout, a rate limit and an unreadable
answer) are proved through `run_pingpong`.
