## Why this exists
- Measured, with Luna's runner: Remedy started in a folder that is no git repository fails an
  order at its init step (`step_failed`, "is not a git repository"). Started inside repository A
  with an order whose header says `project: b`, it answered "project b selected by --project",
  filed the mission and the study under project b, and ran the job in repository A and named A in
  its apply command. The `project` key selects where records are filed and never where the work
  happens. A client that stands in the wrong folder changes the wrong repository.
- Measured: `remedy job apply <job> --approve --commit-with-history --push --json`, on a mission
  whose blocking criterion `C001` was unmet, printed `"ok": true` with `"status": "blocked"` and a
  `blocked_reason` beginning `push_refused:`, exited 0 and applied nothing. F295's page says a
  refusal answers `"ok": false` and exits non-zero.
- Measured: the page's tables are held equal to what `tests/cli/test_machine_client_contract.py`
  uses, so the page does not name what `packages/orchestration/client_digest.py` already returns
  and a client needs: a decision's `question`, `default`, `clarifications` and `age_seconds`,
  `supervisor.answers`, a project's `slug` and `cost_today`, a job's `title` and
  `result_diff_path`. It names neither `--repo`, `--project`, `--force-job`,
  `--commit-with-history` nor `--push`, nor `waiting_job_ids`, `landed` and `push` of `remedy do`,
  nor `commit_sha`, `target_branch`, `blocked_reason` and `pushed` of `remedy job apply`. A page
  written by hand and bound to one test's usage cannot be what a client builds on.
- Measured: no command declines a completed job's result. After `remedy mission abandon` the
  mission's completed job still read `waits_for_apply` true and stayed in `awaiting_apply`.
- Measured: an order of two jobs (`--force-mission`) answered `waiting_job_ids` with the second
  job and one sentence under `next` that tells a person to commit and then run it.
- Read in `apps/cli/commands/do_cmd.py`: a second `remedy do` of the same order file starts a
  second mission.
- Measured: the digest lists every job on the data root for ever. A data root with 1,001 jobs
  gave a `client` object of 717,468 bytes, and every completed job nobody applied stood in
  `awaiting_apply`.
- Measured: the job's `final_job_review.json` said `PASS` with zero acceptance criteria while the
  mission contract held `C001` unmet and refused the push; the job record's `test_passed` was null
  and its `test_command` empty. Nothing a client reads says in one place what changed, which
  checks ran, what the review said and whether Remedy would apply it, and no field carries a risk
  class.
- Measured: `contract:` accepts only `api-service`, `cli-tool`, `python-library` and `website`;
  an order that names a template for a small change to an existing repository is refused
  (`unsupported_contract_template`) before any step. `remedy init` in a repository left
  `remedy.toml` and `.remedy/` untracked there, so registering a project dirties it.
- Read in `packages/orchestration/order_file.py`: the one cap an order file may carry is
  `max-cost-usd`. The operator limits tokens and calls (ruling R1). A job record's `total_tokens`
  leaves out cache tokens, and the digest's `cost` carries no token at all.

## Task slicing
- T001 — The contract is data. One document, generated from the code and never written by hand,
  names every operation a client uses with its fields, every key the digest and the answers
  return, every job state and mission status word, every refusal token, the exit codes, the
  contract templates, the budget kinds and its own version. One command prints it with `--json`.
  The page `docs/system/machine-client-contract-v1.md` is rendered from it, and a test fails when
  the code and the document differ. Inside one major version the document only grows.
- T002 — An order runs in the repository of the project it names. An order that names a project
  runs in that project's registered repository wherever the client stands; an order whose project
  has no registered repository, or whose `--repo` is another project's repository, is refused
  before any step with its own token. One command registers a repository for a client and leaves
  its working copy clean.
- T003 — Honest refusals, and declining. Under `--approve --json` an apply that did not land
  answers `"ok": false` with one fixed error token per cause (the contract refuses the push, no
  upstream, a dirty tree, a detached HEAD, a merge conflict, protected files) and exits non-zero;
  the preview without `--approve` keeps exit 0. One command declines a completed job's result
  with a reason, recorded as the operator's decision the way the cockpit's door records one. A
  declined job, and a job of an abandoned mission, no longer waits for its apply.
- T004 — Commit, push, several jobs, and the same order twice. The second gate test drives an
  order file to `remedy job apply <job> --approve --commit-with-history --push --json` against a
  local bare upstream and reads the commit, the branch and the push from the answer; drives an
  order of two jobs to its end as a program would; and starts one order file twice. The second
  start is refused before any step and names the mission that already runs it, unless a flag asks
  for a new mission.
- T005 — What an approval card needs, from records only. Each completed job in the digest
  carries: the files it changed (a count and a bounded list), each task with its title, its
  reviewer's verdict, its repair rounds and whether a test command ran and what it answered, the
  blocking criteria of its mission's contract with status and text, one recommendation word and
  one risk word. The rules that derive the two words from recorded facts stand in the contract
  document; no word comes from a model. A job on which no check ran says so.
- T006 — Tokens and calls where a client reads a cost. Each job in the digest and each project's
  day carry the provider calls and the tokens the records hold, by kind (input, output, cache
  read, and cache creation where a provider reports it), beside the existing `cost`. The mandatory
  cap of an order may be any one of the job budgets — cost, total tokens, provider calls or
  wall-clock minutes; an order with none is refused as today. The document says exactly which
  tokens the token budget counts.
- T007 — The digest stays small, and templates. By default the digest lists every job that still
  needs something and the jobs that ended inside a window; it names the window and how many jobs
  it left out, and a flag widens it; the first round measures the operator's own data root. The
  round measures whether a small change to an existing repository needs a template of its own and
  adds one if it does.

## Acceptance
- An order with `project: b`, started in repository A or in no repository, changes only b's
  registered repository or is refused before any step; a test stands in each of the three places.
- A blocked apply under `--approve --json` exits non-zero with `"ok": false` and a token the
  document lists; no path answers `"ok": true` for an apply that did not land.
- A declined job reads `waits_for_apply` false, is not in `awaiting_apply`, and its decision is in
  the job's ownership record.
- The second gate test is green through the command line alone, with a stdin that fails the test
  on any read.
- A test fails when the code returns a key the contract document does not name, or the document
  names one the code does not return; the Markdown page is the document's rendering.
- The digest names calls and tokens by kind for a job run with a provider that reports them, and
  an order capped only by provider calls or by total tokens is accepted and stopped at its cap.
- With 1,000 settled jobs on a scratch data root the default digest stays under a size the first
  round fixes from its measurement, and names the count it left out.
- A second `remedy do` of an order file a running mission records exits 2 before any step.
- F295's gate test and its path are unchanged and green.
