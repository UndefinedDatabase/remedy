## Goal & Done
Goals that outlive one job get a first-class home: a MISSION holds the
persistent goal and links the chain of jobs that serve it; every follow-up
job starts by verifying the previous state. DONE when a two-job fixture
mission shows correct lineage, the verify-first rule provably runs before
follow-up work, and missions never auto-create — the human opts in.

## How it fits (inspect current shape before building)
Jobs, intake, checkpoints and the project registry exist; a mission is a
thin persistent record ABOVE jobs, stored like other entities (atomic
JSON per record under a project-scoped area of the data root). Intake
already produces structured output — it gains a mission-candidate hint;
the confirmation lives in the plan approval (one more payload item, same
single human touchpoint as clarifications).

## Design (suggested shape)
Module `mission_state.py`:
- Mission record: id, project id, goal text, status
  (active|paused|achieved|abandoned), ordered job links (job id, role:
  initial|follow_up, created_at), dossier reference (filled by the dossier
  feature later — reserve the field now).
- Creation: intake may set mission_candidate=true for goals that smell
  long-lived; the plan-approval payload then carries "run as mission?"
  defaulting to NO — explicit opt-in (P2). `remedy mission start <goal>`
  creates one directly.
- Follow-up: `remedy mission continue <id> "<next step>"` creates a job
  linked follow_up whose plan is REQUIRED to begin with a verify task
  (run the previous job's DoD/tests/smoke against the current state) —
  enforced structurally by injecting the verify task, not by prompt hope.
- Status transitions are explicit commands (achieve/abandon/pause) or set
  by the orchestrator loop later; nothing auto-transitions in this
  feature.
- CLI: mission start/continue/list/show (show renders the chain with each
  job's terminal state); status transitions are their own explicit
  subcommands — mission achieve/abandon/pause (R-0163 amendment,
  reviewer DECISION 2026-07-31).

## Task slicing
- **T001** record + store + link/list/show + unit tests (ordering,
  scoping, corrupt-record honesty like other listings).
- **T002** intake hint + approval payload opt-in + tests (default no; yes
  creates and links).
- **T003** continue + injected verify-first task + the two-job fixture
  end-to-end (job 1 green → continue → verify task runs first and passes
  → follow-up work runs; broken previous state → verify fails, follow-up
  never starts).

## Acceptance
- Two-job fixture lineage correct in show; verify-first ordering asserted
  from evidence; a failing verify blocks the follow-up with a clear
  message naming what broke.
- No mission is ever created without the explicit opt-in or command
  (negative test on a plain do-flow).

## Edge cases & assumption defaults (A9)
- Deleting jobs that a mission links: links render "(missing job)" —
  listings never crash. One job belongs to at most one mission (validator;
  cross-mission reuse is a later concern). Mission goals are immutable;
  changed goals are new missions (honest history).

## Orchestrator brief
T001/T002 parallel, T003 gates on checkpoints (resume interplay). Put the
verify-first enforcement rule ("injected task, not prompt instruction")
verbatim into the T003 order.

## Do not touch
The orchestrator loop (later feature), lineage UI, dossier content.

  storage._atomic_write_job; create_mission (the ONLY creation

- Verify-first (structural, not prompt): build_verify_first_task /
  inject_verify_first / assert_verify_first — the injected M000
  verify task occupies position 0, every follow-up task depends on
  it, and dag_schedule.ready_set withholds the work until the
  verification COMPLETED; run_verify_task executes the recorded
  command as argv (never a shell), outcomes passed/failed/
  unverifiable — unverifiable is named and recorded, never treated
  as passed; continue_mission + execute_mission_followup write the
  mission_verify.json evidence record (steps[0] is always the
  verification) into the job's evidence area.
- CLI (apps/cli/commands/mission_cmd.py + command_catalog.py):
  mission start/continue/list/show plus the explicit transitions

- Approval opt-in (P2): JobIntake.mission_candidate hint (additive;
  heuristic phrase list + LLM prompt rule), mission_offer rides the
  existing fp:approval payload, `remedy decision resolve --as-mission`
  creates+links only on explicit approve — a plain or auto-approved
  do-flow creates NO mission (negative tests pin it).
- Tests: tests/orchestration/test_mission_state.py (record, store,
