## Goal & Done
Remedy can be driven, end to end, by a program that never sees a terminal: Luna's runner on the
operator's workstation writes an order file, starts Remedy, polls one machine-readable digest,
answers the decisions a run raises, approves the apply, and reads the proof — through the command
line's JSON envelope alone, with no cockpit, no HTTP transport and no question on stdin. DONE when
one test drives that whole path through `apps.cli.grouped.main` with the fake builder and
reviewer, exactly as the runner will, and the contract page names every command, flag, JSON key,
exit code and file the path uses.

## Why this exists
Luna already watches Remedy's build loop through a status export and a mailbox
(`luna_operator/remedy/` in the `luna` edition reads `/srv/luna/inbox/remedy-status.json` and
writes answers to `/srv/luna/outbox/remedy-answers`). Her whole family works that way: she writes
orders into an outbox, a runner working as the operator carries them out, results come back into
an inbox; she never starts a command line herself and never reads the operator's home. To use
Remedy as her engineering department she needs the same shape for Remedy's PRODUCT: an order she
can write as a file, one digest she can read every minute, decisions she can relay and answer, an
apply that waits for the operator's approval. Most of it exists for a human — `remedy do`, the
budget flags, `--yes`, `--json` on every command, `decision list/show/resolve`, `job apply
--approve`, `change proof` — but three gaps keep a program out: `remedy do` takes only text,
although DECISION F259 D2 and DECISION amend0905-vocab D7 decided the order file; no single read
gives the state of every mission, job and open decision across jobs; and nothing documents, or
proves by a test, that a run with `--yes` and without a TTY never waits on stdin. The strategy
behind this feature, including why the HTTP API (F253) comes later and why no clock lives in
Remedy, is `docs/roadmap/design/luna-control-plane-v1.md`.

## Task slicing
- T001 — Order files. `remedy do <order.md>` reads the order from a Markdown file when its
  argument names a readable `.md` path (the decided form of DECISION F259 D2). The file carries
  the order text and an optional header block with the project, the contract template, the cost
  cap in USD and the constraints the planner must honour; a command-line flag wins over the
  header. A missing, empty or unreadable file is refused before any step with its own refusal
  code. An order read from a file that carries no cost cap — neither in the header nor as
  `--max-cost-usd` — is refused before any step: an unattended order without a budget is not
  autonomy. The format is written down on the contract page of T004.
- T002 — The digest. `remedy status --json` gains one versioned section for a machine client:
  every registered project with its missions and jobs (state, measured cost with its basis,
  evidence references), every open decision across every job (id, job, kind, the question, its
  documented default, its age), the jobs that wait for `apply`, whether a supervisor (F200)
  answers on the data root, and the cost of the day per project. Every value is read from the
  records; no word of it comes from a model. The section is cheap enough to read once a minute.
- T003 — Decisions and approvals without a terminal. Every decision a run can raise — the plan
  approval with its bundled questions, a task decision, a hunk decision, a budget raise — is
  readable and answerable with `--json`; `--yes` and the unattended path are documented in one
  place; and a test proves that a run with `--yes`, `--no-ui` and `--json` on a pipe that is not
  a TTY never reads stdin, the cost preview confirmation of F114 included.
- T004 — The contract page and the gate test. `docs/system/machine-client-contract-v1.md`,
  registered in `docs/README.md`, names every command, flag, JSON key, exit code and file a
  client uses, in the order of the four steps (read, propose, approve, apply), and what Remedy
  never does on a machine order: no apply without `--approve`, no commit or push without their
  flags, no start without a cost cap. One test drives the whole path through
  `apps.cli.grouped.main` with the fake providers: write an order file with a cap, run `remedy do
  <file> --json --no-ui --yes`, read the digest and find the mission, the job, its state, its
  cost and its evidence references there, answer one decision with `remedy decision resolve
  --json`, apply with `remedy job apply <job> --approve --json`, and read `remedy change proof
  --json`.

## Acceptance
- `remedy do` with a readable `.md` path plans and runs the order the file holds; with a path
  that is missing, empty or unreadable it exits 2 before any step, naming the path; with a file
  that carries no cost cap and no `--max-cost-usd` it exits 2 before any step, naming the rule.
- An order argument that holds whitespace is planned as text even when it names a `.md` file, as
  in `fix the heading in README.md`; only a single path without whitespace that ends in `.md` is
  read as an order file.
- `remedy status --json` carries the client section with a version field; the section lists every
  open decision across jobs with its question and default; a job that waits for `apply` is listed
  as such; the section says whether a supervisor answers.
- Every decision kind is answerable with `--json` and the answer is recorded as the cockpit's own
  door records it; a run with `--yes --no-ui --json` on a non-TTY pipe never reads stdin.
- The contract page exists, is indexed, and names every command, flag, key, exit code and file the
  gate test uses; a test fails when the page names a flag or key the test does not use or the test
  uses one the page does not name.
- The gate test runs green, end to end, through the command line alone.

## Built State (F295, 2026-10-07)

What exists on disk before the closure sequence of F295, built on
`feature/f295-machine-client-contract-v1`, cut from `main` at `9a8431ea9`. Every DECISION named
lives in `.agent/decisions.md`; every round's verdict in `.agent/live_review.md` or, once rotated,
its archive.

**T001 — order files.** `remedy do <order.md>` reads its order from a Markdown file when the
argument is one path without whitespace that ends in `.md`. An optional header between two `---`
lines names `project`, `contract`, `max-cost-usd` and any number of `constraint` lines, and a
command-line flag wins over it (DECISION F295 D2). A file that is missing, unreadable, empty or
carries a broken header, and an order from a file with no cost cap in its header or in
`--max-cost-usd`, are refused with exit code 2 before any step. The mission records the file's
path and the sha256 of the bytes Remedy read (D3).

**T002 — the digest.** Every `remedy status --json` answer carries a `client` object, version 1,
over every project on the data root: its missions with their order source; its jobs with their
state, measured cost and its basis, evidence references and whether they wait for their apply;
every open decision of every job with its question, default, options and age; the cost of the UTC
day per project; and whether a supervisor answers (D4 to D7). Every value is read from the
records.

**T003 — decisions without a terminal.** A run with `--yes --no-ui --json` on a pipe never reads
stdin, and the builder's and reviewer's child processes read end of file (D8). A budget stop
raises a decision that `remedy decision resolve` answers `extend`, with the limits it raises, or
`abandon`, which cancels the job for good (D11, D12). A job its budget stopped refuses to resume
until that decision is answered (D9) and then resumes with its own builder and reviewer (D13); a
job `remedy do` plans writes its run manifest, so its budget stop ends `stopped` (D10). Every other
kind of decision is answered with `--json`, and `remedy patch hunks` reads the hunk decisions a
client records (D14).

**T004 — the contract page and the gate test.** `docs/system/machine-client-contract-v1.md`,
linked from `docs/README.md`, names the order file, the commands, flags, JSON keys and exit codes
of the path from an order to its proof, the command that answers each kind of decision, and what
Remedy never does on a machine order. `tests/cli/test_machine_client_contract.py` drives an order
file through `remedy do`, `remedy status`, `remedy decision resolve`, `remedy job run`,
`remedy job apply --approve` and `remedy change proof` with the fake providers and a stdin that
fails the test on any read, and holds the page's tables equal to what that test uses (D16, D17).
`remedy change proof` lists the job's applies under `job_applies` (D15).

**The hardening stage.** Because the sessions ran in SLOW MODE, a fresh auditor who saw only this
file and the repository looked for a test behind every statement under Goal & Done and Acceptance
and tried to break each one (operator amendment amend0930b-slow-cap,
`.agent/f295_acceptance_audit.md`). It audited 31 statements. 28 had a test that failed when the
auditor broke the code, several of them through the command line. One, that no HTTP transport is
used, describes something this feature never builds and can only be read. Two were reported as
gaps. The first was real: nothing noticed if `remedy do --no-ui` opened the cockpit, and a test now
fails when the cockpit's launcher is called (R-1154, DECISION F295 D18). The second was not: the
reviewer showed that the docs index test fails when the contract page loses its links. The
reviewer also found that the question whether to start a follow-up mission, raised when a run
stops at its budget, stayed open after the budget was raised and the run had finished; an
`extend` now answers that question `no` in the operator's name and names it under
`closed_decisions` (R-1155, DECISION F295 D19). A repeat audit of the five statements those two
repairs touch proved all five and found no gap (`.agent/f295_acceptance_reaudit1.md`). No gap
remains open.
