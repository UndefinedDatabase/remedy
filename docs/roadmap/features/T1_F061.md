## Goal & Done
"Done" stops being vibes: user intent plus the Flight Plan compile into a
machine-checkable DoD — a list of concrete checks (tests, lint, build,
runtime flows, custom commands) with blocking flags — and a job only ends
green when all blocking checks pass. DONE when three fixture missions
compile into sensible DoDs, the job-end gate provably holds a job open on
a red blocking check, and the report shows the check matrix. This is a
deliberately LARGE block (A3).

## How it fits (inspect current shape before building)
Structured-output schemas and validation exist (the DoD is one more
versioned schema); the runtime harness can start apps and probe them (the
flow-check runner builds on it); the report renders matrices from
structured evidence. The compiler is an LLM step with the same discipline
as intake/plan: schema-enforced, parse-retried, honest fallback (no
provider → a minimal deterministic DoD from plan acceptance lines,
labeled as such).

## Design (suggested shape)
- Schema `DoD` (versioned): checks[], each {id, kind: pytest | lint |
  build | runtime_flow | custom_cmd, spec (kind-specific), blocking:
  bool, source: compiled|plan_acceptance|standard}. Kind specs stay
  declarative (e.g. a pytest selector, a command line, a flow description)
  — executable artifacts are generated from them.
- Module `dod_compiler.py`: compile(intake, plan) → DoD via provider call;
  merges three sources: compiled checks from intent, one check per plan
  acceptance line (traceability: every acceptance maps to at least one
  check), and standard checks (the product-smoke feature registers its
  block here next).
- Generated runtime-flow specs land under the job's evidence area (data
  root), not the user's repo; promoting a flow into the repo's permanent
  test suite is a human decision (P2).
- Runners: pytest/lint/build/custom execute through the existing
  subprocess discipline with per-check evidence (command, exit, output
  tail); runtime_flow drives the runtime harness (start → scripted
  interaction → stop) — v1 flows are simple declarative step lists
  (open path, expect text/status), NOT a browser-automation dependency;
  the smoke feature decides how deep to go.
- Job-end gate: the terminal-green path runs the DoD; any red blocking
  check keeps the job open with status blocked and the matrix in the
  report; non-blocking reds are reported, not gating.
- CLI: `remedy job dod <id>` shows the matrix live.

## Task slicing

- **T002** runners for pytest/lint/build/custom + per-check evidence +

- **T003** runtime_flow runner on the harness + a fixture app flow.
- **T004** the job-end gate + report matrix + end-to-end (green only when
  all blocking green; red blocking holds the job open).

## Acceptance
- Golden DoDs for three fixtures; every plan acceptance line traceable to
  a check id. Each runner kind proves red and green. Gate holds a job open
  on a red blocking check and releases after a fix. Fallback DoD is
  labeled compiled=false/deterministic.

## Edge cases & assumption defaults (A9)
- Checks that cannot run (missing tool) are red with reason
  tool_unavailable — a missing linter must not silently pass. Compiled
  nonsense checks (unrunnable specs) fail validation at compile time where
  detectable. Custom commands run inside the worktree under the fence
  rules.

## Built State (accepted 2026-08-01, F061 closure)
- **Schema** (`packages/orchestration/dod_schema.py`): `DoD` (`dod_v1`,
  registered in `SCHEMA_REGISTRY`) and the provider-facing `DoDDraft`
  (`dod_draft_v1`, deliberately unregistered — no reader ever resolves
  it; absence pinned by test). Honesty is structural: the draft cannot
  carry `source` or claim `compiled`; `compiled` must equal
  `origin == "provider"`. Compile-time validation refuses detectable
  nonsense: empty/flag-shaped selectors and tools, empty argv, cwd
  escapes, unknown keys, and (R-0165) the closed runtime_flow v1 step
  vocabulary (`open` + path + typed expectations).
- **Compiler** (`dod_compiler.py`): three merged sources — provider
  checks via `run_structured_call` (one parse retry), one generated
  check per uncovered plan acceptance line (grouped by selector), and
  the `register_standard_check_provider` seam (F062 plugs in here).
  The traceability rule (verbatim, tested against this file): every
  plan acceptance line traceable to a check id. No provider → a
  deterministic DoD from the acceptance lines, labeled
  `compiled=false`; every fallback route tested.
- **Runners** (`dod_runners.py`): pytest/lint/build/custom_cmd as
  single processes under the shared executable allowlist and worktree
  fence, each proven red and green; `runtime_flow` (T003) drives the
  F007 harness — resolve spec, start in its own session, readiness
  probe, declarative steps, stop-process-tree in a `finally`; a
  surviving process is red. Named red reasons throughout; a missing
  tool is red `tool_unavailable`, never a pass; a kind without a
  runner raises `UnsupportedCheckKindError`.
- **Gate** (`dod_gate.py` + ONE seam in
  `job_fulfillment.run_job_fulfill`): on the terminal-green path, any
  red BLOCKING check holds the job open through the existing blocked
  machinery (`dod_blocking_red:` blocker); non-blocking reds are
  reported, never gating; an unreadable stored DoD fails closed. A job
  with no stored DoD is not gated (additive; `dod_released=None`).
  End-to-end proven on the real fulfillment path: hold, then release
  after the fix on the same job. DoD + gate result live in the job's
  evidence area (`dod.json`, `dod_result.json`), never the user repo.
- **Surface**: report section "Definition of Done" with the check
  matrix (absent source renders `not recorded`); `remedy job dod <id>`
  prints the matrix read-only.
- **Boundaries (honest)**: nothing calls `compile_dod` at real job
  creation yet — F062 registers the product-smoke standard check and
  F069/F070 wire compilation into the mission/orchestrator flow; the
  flow vocabulary is v1 (`open` only) by design.
