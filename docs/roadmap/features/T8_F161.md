# T8_F161 — MCP passthrough with policy
**Tier 8 · Depends on: F009 audit, F004, F152 · Blocks/used by: F172 packs; enterprise readiness**

## Goal & Done
Workers may use MCP tools — but only the ones policy names: a
project allowlist (.remedy/policy/mcp_allowlist.toml with [[server]]
name/url and per-tool class read|write|external) drives a
worker-specific MCP configuration generated INSIDE the isolated
temp HOME, tool calls surface as run.tool_call events, a post-hoc
checker flags out-of-list calls as high review findings where
adapter-side prevention is impossible, and write/external classes
require their permission-matrix row. DONE when a worker under the
allowlist sees exactly the allowed servers/tools (the generated
config golden), an out-of-list call in recorded evidence produces
the high finding (plus the optional task-fail policy when enabled),
tool-call events render in feed/timeline, and the matrix gate
provably blocks write/external tools below the required level.

## How it fits (inspect current shape before building)
Isolation (F152) built the throwaway-HOME mechanics — the MCP
config is one more file materialized there per run (adapter
research says WHERE each tool expects it; the per-adapter ADR duty
extends to the MCP config path). The event vocabulary grows
run.tool_call {server, tool, class, args_digest} — envelope
coordination as ever; SOURCING is adapter-dependent: adapters
whose streams report tool use map it (the contract's map_stream),
others fall back to the post-hoc checker parsing recorded output
(the honesty split: prevented-vs-detected is stated per adapter in
its ADR). The permission matrix gains consumers: tool classes map
to matrix actions (write → write-class action, external →
external_call) — the matrix stays the single gate.

## Design (suggested shape)
- Policy file: [[server]] {name, url, tools = [{name, class}]};
  validation (classes closed set, names unique); absent file =
  MCP disabled entirely (closed by default — enterprise posture).
- Config generation: per run, the adapter-specific MCP client
  config containing ONLY allowlisted servers/tools, written into
  the isolated HOME; evidence records mcp_config_digest.
- Events + checker: mapped events where streams support it; the
  post-hoc checker (pure over recorded output per the adapter's
  documented tool-use markers) emits findings {server, tool,
  reason: not_allowlisted | class_gate} into the round's review;
  policy [mcp] fail_task_on_violation (default false) escalates.
- Matrix wiring: write/external tool presence in the allowlist
  requires the level rows; runtime calls consult require() with
  the instance context (the decision path for ask cells).
- CLI: `remedy policy mcp check` renders the effective allowlist
  and per-adapter prevention mode (prevented | detected).

## Task slicing

  generation into isolated HOMEs (per-adapter path via ADR) +
  goldens.
- **T002** events + the post-hoc checker + findings + the
  fail-task policy + fixtures (allowed call clean; out-of-list →
  finding; escalation on).
- **T003** matrix wiring + the CLI + docs (the prevented/detected
  honesty table) + the end-to-end on a scripted MCP-using fake.

## Acceptance
- Generated configs golden per adapter fixture; nothing outside
  the allowlist appears (grep the config). Violation fixtures
  produce the finding with server+tool named; escalation obeys
  config. Matrix blocks write/external below level (cell tests).
  Closed-by-default proven (no policy file → no MCP config
  materialized).

## Edge cases & assumption defaults (A9)
- Adapters without MCP support: the allowlist is inert for them
  (the capability matrix notes it — an entry mcp_tools).
  Args in events: digest only (args may carry secrets — the
  redaction stance; full args stay in the isolated run output
  where evidence rules govern them).
