## Goal & Done
The full suite and the round selections cost much less CPU time without losing a single assertion.
DONE when the full suite's CPU seconds, read from the test load record, are at least 40 percent
below the baseline T001 measures, OR the ranking shows that what remains cannot be made cheaper
without weakening a test, and a dated DECISION says so with the numbers.

## Why this exists
The operator's machine has 24 CPU threads and one large graphics card. For months it has run very
hot whenever tests ran, and the operator read about 740 watts at the wall during those times. That
costs real money, and he ordered the test load cut massively.

The measured facts behind the order: the full suite is 21,078 collected tests. Its last run (F044
round 13) took 213 seconds with `python3 -m pytest -n auto -q`, which started 24 workers, so about
85 CPU minutes of work arrived in one burst, once per feature. Round work ran test selections of 500
to 2,300 tests up to three times per round (the reviewer's dry run, the worker, the reviewer again),
and mutation red-proofs ran twice. `apps/ui/vitest.config.ts` set no worker limit. Headless Chrome is
started by `tests/ui_server/test_story_export_file_live.py` without `--disable-gpu`; a measurement on
2026-09-30 showed no graphics-card use from it (DECISION amend0930 D4).

A fewer-workers cap lowers the heat at any one moment but not the electricity used, because the same
work just takes longer. Electricity falls only when less work is done. This feature is the half that
does less work; the cap and the rules that stop repeated runs (DECISION amend0930 D1 to D3) are the
other half.

Baseline (amend0930-test-load, 2026-09-30): the full suite, 21,102 collected tests (21,082 passed,
20 skipped), ran under the new cap of 6 workers in 448.7 seconds of wall time and used 1,288 CPU
seconds (21.5 CPU minutes), read from the test load record. The earlier run started 24 workers and
took 213 seconds, so the cap roughly doubles the wall time; its CPU seconds were never recorded, and
the 85 CPU minutes quoted above is the upper bound of 24 workers busy for 213 seconds. During the
capped run the 24 CPU threads were on average 18.8 percent busy (highest second 95 percent) against
4.3 percent while idle. The graphics card drew 27.1 watts on average while idle and 26.6 watts during
the run (highest second 55.9 watts, utilization at most 5 percent), so the test run added nothing
measurable on the card. The CPU package's energy counter is readable only by root on this machine,
so no package watts were read. T001's baseline for the 40 percent target is therefore 1,288 CPU
seconds.

## Tasks
- **T001 — measure once and rank.** One full-suite run with `--durations=0`, written to
  `.agent/f293_inventory.md`: CPU share per test file, the 100 slowest tests, the cost of
  collection, how many tests start a child process, how many times the UI is built and Chrome is
  started, and which processes are still alive after the run.
- **T002 — cut from the top of the ranking.** Share expensive setup between the tests of one module
  (one built UI, one Chrome, one initialised project), call the command line in-process where the
  child process is not what the test is about, and merge parametrisations that repeat the same
  setup. Every changed test keeps a red-proof: a mutation of the production line it guards still
  turns it red.
- **T003 — keep it down.** Each closure's suite transcript records the run's CPU seconds; a closure
  whose suite costs more than 10 percent above the previous feature's registers a finding owned by
  the rolling findings paydown. A test run that leaves a process behind fails.
- **T004 — make it visible.** `remedy doctor core` says in one plain sentence how many test runs and
  how many CPU minutes the last 24 hours cost, read from the test load record.

## Acceptance
- T001: `.agent/f293_inventory.md` exists and holds the six readings named above from one run.
- T002: the full suite's CPU seconds in the test load record are at least 40 percent below T001's
  baseline, or a dated DECISION shows with numbers that what remains cannot be made cheaper without
  weakening a test.
- T003: a closure whose suite CPU exceeds the previous feature's by more than 10 percent registers
  a finding; a test run that leaves a process behind fails.
- T004: `remedy doctor core` prints the one sentence, from the record, and prints nothing wrong when
  the record is absent.

## Do not touch
No assertion is weakened or deleted to gain time. The rule of one full suite per feature
(amend0917-throughput). The worker cap.

## Built State (F293, 2026-09-30)

What exists on disk before the closure sequence of F293, built on `feature/f293-test-load-diet`, cut
from `main` at `8a067a3b9`. Every DECISION named lives in `.agent/decisions.md`; every round's
verdict in `.agent/live_review.md` or, once rotated, its archive.

**T001 — the inventory.** `.agent/f293_inventory.md` holds the six readings from one full-suite run
with `--durations=0`, whose whole output is committed as `.agent/authored/f293-r1-durations.txt`.
That run collected 21,102 tests and used 1,246.09 CPU seconds by the test load record; this, not the
1,288 of the amendment's own earlier run above, is the baseline the 40 percent target is read
against (DECISION F293 D1), so the target is at most 747.65 CPU seconds.

**T002 — the cuts.** Each cut was measured before and after in one tree, and each changed test kept a
red-proof. `dead_command_ids` reads a search root's files once per process and answers a repeated
question from a cache (DECISIONs F293 D2 and D4). The review manifest's metadata scan answers each
distinct text once per process (D3), and the run manifest's key check each key and use once (D5).
`tests/conftest.py` reads Remedy's own checkout identity once per test process (D6). The mission
command tests write their setup records and start their setup missions in-process, while every
mission is still read through the real command line (D10). Two provider-override tests no longer
start a real paid model process (R-1119), and one retry test no longer sleeps through a real
30-second backoff. The largest cost left is the git work of a whole job run, about 210 git
processes per `remedy do`, which is product work beyond a test diet (D10). The "after" reading is
taken by the closure's one full-suite run (D1); when it misses the target, the closure's DECISION
states the remaining cost with D10's numbers.

**T003 — keeping it down.** A test run that leaves a process behind fails, names the process and
ends it (DECISION F293 D8, R-1118). `scripts/closure_suite_cost.py` prints the closure run's CPU
seconds as one `Test load:` line for the suite transcript and exits 1 when that run cost more than
10 percent above the previous closure's; `docs/agents/integration_gate.md` step 1 and precondition 2
of `docs/roadmap/STATUS_closure_protocol.md` name the step (D9). F293's own closure is the first
transcript to carry the line, so the first comparison falls to the feature after it.

**T004 — making it visible.** `remedy doctor core` prints `test load:` and one sentence with the
runs and CPU minutes of the last 24 hours from the test load record, and its `--json` output carries
the key `test_load`; the reading is information only and never changes `ready`, and a missing or
unreadable record is said in words (DECISION F293 D7, R-1120).
