# T10_F180 — Human reviews as a gate
**Tier 10 · Depends on: F177, F033, F061 · Blocks/used by: the M11 core; F169 chains**

## Goal & Done
See ROADMAP.md F180; the Done criterion there is binding.

## Context (existing code & prior features)
The DoD knows check kinds; F033 provides the hunk UI; LLM findings flow into the repair loop. A human blocking gate is missing.

## Design
DoD check kind human_review{assignee role|user, scope full|paths[], blocking}: creates a review assignment (a decision variant with diff context via F037/F033); the verdict command human_review_verdict{approve | request_changes, findings:[{anchor, severity, text}]} - request_changes findings enter THE SAME repair flow as LLM findings (the repair request builder unchanged, A6). With blocking=true the task/job ends only after approve. A four-eyes option: min_reviewers=2; self-review by the change author is forbidden.

## Task slicing
T001 the check kind + assignment creation + the verdict command + tests. T002 repair-flow coupling + the four-eyes rule + the review UI (hunk view + finding form) + E2E fixtures for both verdict paths.

## Acceptance & tests
The blocking fixture ends only after a human approve; a rejection spawns a repair round quoting the finding verbatim (trace); self-review is blocked.

## Risks / anti-goals
No second finding format (exactly the F005 review schema); human reviews appear as review_run nodes in the graph (a reviewer=human glyph variant, a small F020 delta).
