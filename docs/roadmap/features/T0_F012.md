# T0_F012 — Deterministic runs
**Tier 0 · Depends on: F004 · Blocks/used by: F084, F140, all golden tests**

## Goal & Done
Every run records a complete, hashable INPUT manifest; a rerun can verify
"same inputs" and report drift precisely. DONE when every completed or
stopped job has one manifest, `remedy job rerun --check-manifest` classifies
a manipulated fixture correctly, and the docs say plainly what determinism
means here (P6): inputs are reproducible and verified; LLM outputs are
recorded, not promised.

## How it fits (inspect current shape before building)
The worktree layer already exposes an evidence snapshot of the checked-out
base; the config system resolves every key WITH its source (env / project
file / user file / default) — snapshot values plus sources. Prompt and call
inputs live in the per-call evidence directories the ping-pong loop
creates; hash them where they are, don't copy them. Raw stream evidence
stays untouched — the manifest references, never duplicates.

## Design (suggested shape)
Module `run_manifest.py`:
- `RunManifestV1`: manifest_v=1, job id, created_at, the Remedy repo's own
  git sha, the worktree evidence snapshot, resolved config (Remedy keys
  only, each {value, source}, secrets redacted by key-name denylist:
  token/key/secret/password), REMEDY_* environment, model ids per role,
  provider CLI versions (best effort — "unavailable" is a valid value;
  never fail a run over a version probe), an incrementally appended list of
  {call_dir, sha256} prompt hashes, python + platform strings.
- Incremental hashing hooks into the moment a call directory is finalized —
  implement ONE shared `on_call_finalized` hook that this feature and the
  postmortem writer both consume, so there is a single seam.
- `diff_manifests(a, b)` → structured diff split into blocking (base
  commit, models, prompt hashes, config values) vs informational
  (timestamps, platform, tool versions).
- CLI on the job command: `remedy job rerun <id> --check-manifest` builds a
  would-be manifest for the current environment, diffs, prints the report;
  clean exit 0, blocking drift exit 4. If actual re-execution isn't wired
  yet, the command says so honestly and the check alone satisfies F012.

## Task slicing
- **T001** record + build/write + redaction; negative test proves a config
  key named like a secret never appears in serialized output.
- **T002** the shared finalize hook + integration with a fake-provider job
  making two calls; two identical runs yield identical hashes.
- **T003** diff + CLI + a fixture quartet (identical / model drift / config
  drift / prompt drift) with expected classifications; `--json`.

## Acceptance
- Exactly one manifest per finished or stopped job (stop path writes it in
  the same code path that persists the stopped state).
- Drift quartet classified correctly; version probe failure yields
  "unavailable" and a valid manifest (PATH-stripped test).
- A docs/help grep test finds the honesty sentence ("recorded, not
  promised").

## Edge cases & assumption defaults (A9)
- Planning-only job (zero calls): valid manifest, empty hash list. Seeds:
  no RNG-critical paths exist today — record PYTHONHASHSEED if set, add no
  seed plumbing for its own sake (A6).

## Orchestrator brief
Dispatch T001 immediately (pure). Before T002, have the worker confirm
where call directories are finalized and whether the postmortem feature
already installed the shared hook — extend it, never add a second walker.

## Do not touch
Raw stream evidence format, per-call directory layout, retry logic.
Suggested tests: tests/orchestration/test_run_manifest.py,
tests/cli/test_job_rerun_manifest.py.
