## Goal & Done
Every run records a complete, hashable INPUT manifest; a rerun can verify
"same inputs" and report drift precisely. DONE when every completed or
stopped job has one manifest, `remedy job rerun --check-manifest` classifies
a manipulated fixture correctly, and the docs say plainly what determinism
means here (P6): inputs are reproducible and verified; LLM outputs are
recorded, not promised.

## How it fits (inspect current shape before building)
The worktree layer already exposes an evidence snapshot of the checked-out
base; the config system resolves every key WITH its source (env / project
file / user file / default) — snapshot values plus sources. Prompt and call
inputs live in the per-call evidence directories the ping-pong loop
creates; hash them where they are, don't copy them. Raw stream evidence
stays untouched — the manifest references, never duplicates.

## Design (suggested shape)
Module `run_manifest.py`:
- `RunManifestV1`: manifest_v=1, job id, created_at, the Remedy repo's own
  git sha, the worktree evidence snapshot, resolved config (Remedy keys
  only, each {value, source}, secrets redacted by key-name denylist:
  token/key/secret/password), REMEDY_* environment, model ids per role,
  provider CLI versions (best effort — "unavailable" is a valid value;
  never fail a run over a version probe), an incrementally appended list of
  {call_dir, sha256} prompt hashes, python + platform strings.
- Incremental hashing hooks into the moment a call directory is finalized —
  implement ONE shared `on_call_finalized` hook that this feature and the
  postmortem writer both consume, so there is a single seam.
- `diff_manifests(a, b)` → structured diff split into blocking (base
  commit, models, prompt hashes, config values) vs informational
  (timestamps, platform, tool versions).
- CLI on the job command: `remedy job rerun <id> --check-manifest` builds a
  would-be manifest for the current environment, diffs, prints the report;
  clean exit 0, blocking drift exit 4. If actual re-execution isn't wired
  yet, the command says so honestly and the check alone satisfies F012.

## Built state (2026-07-15 — implemented, `[~]`, external acceptance pending)

### What determinism means here
**Inputs are reproducible and verified; LLM outputs are recorded, not promised.** F012 records
and verifies the INPUTS a run was given. It never claims an LLM would answer the same way
again, that current provider behaviour equals recorded behaviour, or that matching manifests
make generated output deterministic. The sentence is pinned by a docs test and printed by the
CLI on every check.

### RunManifestV1 (`packages/orchestration/run_manifest.py`)
`manifest_v=1`, and: `job_id`, `created_at`, `status` (completed | stopped | planned), the
Remedy repo's own `remedy_git_sha`, the target `target_base_commit` / `worktree_head` /
`job_initial_tree`, `job_file_sha256`, a reconstructable `job_input_sha256`, `models` per role
(`provider/model`), best-effort `provider_versions`, the resolved `config` (`{key, value,
source}`, secrets redacted), the `REMEDY_*` `environment`, the recorded `calls` list
(`{call_dir, role, kind, round, sha256, artifact}`), `python_version`, `platform`, and
`pythonhashseed` when set.

### Two hashes
`record_sha256` covers the whole serialized record (creation time included) — the idempotence
key. `logical_input_sha256` covers the **comparison projection** only: no timestamps, no
python/platform, no best-effort tool versions. Two identical fake-provider jobs on different
data roots at different times share the logical hash; that is what "same inputs" means.

### Canonical serialization
UTF-8 JSON, sorted keys, sorted lists (config/env by key, calls by (round, role, kind,
dir)) — order-independent. No absolute paths (scrubbed through the shared redactor), no
temp-dir names, relative Evidence references. Published atomically through the shared
`secure_fs` primitives (the same anchoring F010's post-mortem writer and F011's control area
use): no parent may be a symlink, create-only, no temp file survives failure.

### Secret redaction
A config/env key is secret when the config registry marks it (`spec.secret`/`env_only`) OR its
name contains `token`/`key`/`secret`/`password`/`credential` (case-insensitive). Such a key
serializes its NAME and SOURCE but its value is `[REDACTED]`. A canary test proves a secret
value never appears in the manifest JSON, its hash inputs, the CLI output or the Evidence
export. Only `REMEDY_*` environment is captured — never the whole process environment.

### Provider version probes
Best-effort, bounded (5s, no shell, no network), and never a provider generation call. An
uninstalled CLI, a non-zero exit or a timeout yields `unavailable`; a PATH-stripped run still
produces a valid manifest. A version probe is never counted as a provider call in Evidence.

### The single `on_call_finalized` seam
One shared hook (`run_manifest.on_call_finalized`) fires once per finalized logical provider
call — Builder attempt, Reviewer attempt, bounded Reviewer parse retry — appending a
`FinalizedCall` to the run's `finalized_calls`. It does not fire for a call that never started
(a stop before the call), and a recovered parse retry records its input WITHOUT a failure
post-mortem (F010 unchanged). The manifest's call list is built ONLY from these records; there
is no second call-directory walker.

### Exactly-one, and integration
Completed jobs finalize the manifest after every call input is known; stopped jobs finalize it
inside the same durable transaction that persists STOPPED; a zero-call (all-skipped) job gets a
valid manifest with an empty call list. A second finalization with logically identical content
is idempotent; a conflicting one is refused. A write failure is durable
(`job.run_manifest_error`) and, via `manifest_integrity.json`, BLOCKS the final verifier — the
same mechanism as post-mortem integrity, never a text warning. Pre-F012 jobs (no manifest, no
error) are legacy/uncovered, not corrupt.

### Drift — blocking vs informational
| Blocking (a different input) | Informational (diagnostic only) |
|---|---|
| target/worktree base commit, initial tree | manifest creation time |
| Remedy code sha | Python version, platform |
| model per role | provider CLI version (best-effort) |
| resolved config value, and config source | |
| `job_input_sha256` (prompt-shaping inputs) | |
| `REMEDY_*` environment value | |
| missing / extra / reordered recorded call, per-call prompt hash | |

`diff_manifests(reference, candidate)` is pure, mutates neither, sorts its output, names exact
fields, carries redacted old/new values, and distinguishes "not available" (coverage) from
"different". An unsupported manifest version is flagged, never guessed.

### CLI
`remedy job rerun <job_id> --check-manifest [--json]` loads the stored manifest, rebuilds the
would-be manifest from the CURRENT config/git/models/env (and the reconstructable
`job_input_sha256`), diffs, and prints Blocking drift / Informational drift separately. It
mutates nothing and makes zero provider calls. **Exit 0** = same blocking inputs; **exit 4** =
blocking drift; unknown job **3**; usage **2**; missing/corrupt required manifest **1**. It is
check-only and says so: "Manifest check only — this command did not re-execute the job." — it
never prints "rerun succeeded". Per-call prompt hashes are not fabricated for the candidate
(check-only cannot reconstruct a would-be prompt without re-executing); they are compared only
when both sides carry them, and otherwise reported as `coverage: recorded_only`.

### Boundaries
No database. No LLM rerun. Raw-stream Evidence format, per-call directory layout, and
timeout/retry policy are untouched; F010 post-mortem and F011 stop semantics are unchanged. Old
jobs without manifests remain readable.

## First hardening round (external FINDINGS on `remedy-review-20260715-091841`)

The versioned-manifest foundation was useful but did not yet reliably prove "same inputs".
Twelve findings, all fixed here as one coherent block.

### Exact provider-transport fingerprints (was: hashed the pre-transform prompt)
Each provider now computes a `prepared_input` fingerprint at the moment it assembles the real
request — the exact prompt bytes it transmits, the out-of-band native schema, the model, the
mode (`api-structured` / `api-legacy` / `cli-native` / `cli-legacy` / `fake`) and material
options. The manifest records THAT, so the recorded fingerprint IS the sent request by
construction. Verified with capturing transports (a fake SDK client, a patched CLI boundary):
the structured-mode reviewer's recorded hash matches the full 1200+-byte schema-embedded
request, not the short raw prompt.

### Unique per-call identity (was: `(round, role, kind)` collapsed across tasks)
A finalized call now carries `(job_id, task_id, run_id, sequence, role, round, kind, call_id)`.
`diff_manifests` keys on this tuple, so two same-role/same-round calls in a two-task job stay
distinct; changing one, inserting, removing or reordering any call is detected; a duplicate
identity is a manifest error. `same_inputs is True` implies `logical_input_match is True`.

### Real, contained, hash-verified call artifacts (was: synthetic `streams/…` refs)
Each call's fingerprint is written to a small canonical file under
`run_manifests/<episode_id>/calls/NNNN-<role>-roundNN-<kind>.json`; the manifest references it
relatively, and manifest integrity verifies the artifact exists, is contained, and hashes to
the recorded fingerprint. Raw streams are never duplicated.

### Current-state reconstruction (was: reused historical job values)
`build_current_candidate` freshly inspects the CURRENT target repo (HEAD and a working-tree
digest that moves on an uncommitted change), resolves current config/env/models and current
Remedy identity — it does not reuse the recorded values. A new target commit or an uncommitted
change is blocking; the reconstructable `job_input_sha256` (job file + task bodies + models)
catches prompt-shaping drift.

### Honest coverage & a new exit code (was: exit 0 with `include_calls=False`)
Per-call assembled-prompt reconstruction needs a worktree replay (F140) and is a declared
capability gap. Check-only mode therefore reports INCOMPLETE call coverage and never claims
"same inputs" for a dimension it did not verify. Exit codes: **0** verification complete and no
drift; **4** confirmed blocking drift; **5** no blocking drift but coverage incomplete
(`same_inputs=null`, "Input equality could not be fully verified."); 3 unknown job; 2 usage;
1 missing/corrupt required manifest.

### Start-time input snapshot (was: re-probed at the end)
An immutable `InputSnapshot` is captured at episode start (after workspace acquisition, so the
base identity is populated) and the terminal manifest uses it — config/env/Remedy identity
(incl. a dirty-tree flag)/target base/models/provider versions as they were at start, not a
re-probe at the end.

### Episode model (was: one immutable file conflicted with stop→resume)
Each execution episode records ONE immutable manifest under
`run_manifests/<episode_id>/run_manifest.json`; `run_manifest_index.json` names every episode
and the latest; the evidence-root `run_manifest.json` mirrors the latest. A stopped episode
(id `stop-<request_id[:12]>`) is preserved; a resumed run is a NEW episode that references the
prior ones. Repeated finalization of one episode is idempotent.

### Manifest in the stop transaction (was: swallowed the failure)
The stopped episode's manifest must PUBLISH before the stop request is acknowledged. On
failure the request stays pending, the job is not falsely marked stopped, and a retry
finalizes the SAME stop episode — exactly one archive, post-mortem, event and manifest. The
manifest error never replaces the primary stop reason.

### Legacy marker (was: old completed jobs looked corrupt)
A job first run under F012 carries `run_manifest_required_v=1`. A MARKED completed/stopped job
without a manifest, or with incomplete coverage or an unresolved call artifact, is blocking; an
UNMARKED pre-F012 job is legacy/uncovered — readable, reported in integrity notes, not corrupt.

### Blocking missing coverage (was: silently written as zero calls)
A task that should have call records but whose run record is missing, a corrupt finalized-call
record, an empty fingerprint or an unresolved call artifact is a blocking manifest-integrity
failure — distinct from a genuine zero-call (all-skipped) job, which stays valid and complete.

### One shared F010/F012 call-finalization identity
`shared_call_id` is the single definition both consume: F012 records the finalized input, and
F010's post-mortem writer, on a terminal failure, describes the SAME `call_id`. There is no
second call-directory walker; F010 classification and exactly-once semantics are unchanged.

## Second hardening round (external FINDINGS on `remedy-review-20260715-104127`)

Six correctness gaps in working-tree identity, idempotency, artifact integrity, episode export
and the exact meaning of "verified". All fixed.

### Working-tree CONTENT digest (was: porcelain status only)
`target_tree()` no longer trusts `git status --porcelain` (which reads `" M a.txt"` whether a
file now says "two" or "three"). It hashes the actual bytes: `HEAD^{tree}`, the binary
`git diff` and `git diff --cached` (which encode content, renames, copies and deletions), every
untracked file's NUL-separated path + content hash (`git ls-files --others -z`), and submodule
status when present. A dirty-content-to-dirty-content change now moves the digest; a name with
spaces or newlines stays deterministic; a non-repo is `unavailable`.

### Idempotent re-finalization keeps episode/root/index consistent (was: mirror could drift)
The on-disk episode record is now the single source of truth. An idempotent re-write (same
logical content, new `created_at`) does not touch the episode file and mirrors the root and
index FROM that canonical record — so `run_manifest.json`, the episode manifest and the index
`record_sha256` can never disagree. A stale root mirror or index is repaired from the episode
on the next finalization; conflicting logical content still raises.

### Whole-artifact integrity (was: only the fingerprint field)
`FinalizedCall` carries `artifact_sha256` over the exact canonical artifact bytes. Export reads
each artifact's bytes and requires `sha256(bytes) == artifact_sha256`, and that the recorded
bytes reproduce the manifest call exactly — so tampering with `prepared_input`, `identity` or
`ok` (even while the `fingerprint` field is untouched) is blocking.

### Episode-tree export invariants (was: root mirror alone could pass)
For a marked terminal job, export requires `run_manifest_index.json`, a named latest episode
whose manifest resolves and equals the root mirror, and every indexed `manifest_ref` to
resolve. A root mirror with no episode tree, a missing indexed episode, or a root mirror that
differs from the latest episode is blocking.

### "Verified" stated precisely — two modes
1. **`--check-manifest` on a real historical job:** exit **5** when per-call coverage is
   incomplete and no blocking drift (worktree prompt replay is F140); exit **4** on blocking
   drift; exit **0** only when coverage is complete — which for an ordinary job with recorded
   calls it is NOT in check-only mode, but a genuine zero-call / planning-only job reaches. The
   public CLI does not fully reconstruct per-call prompts for ordinary jobs, and says so.
2. **Manifest-to-manifest comparison** (`diff_manifests`, used by tests and later by
   Golden/Demo/F140): proves `same_inputs=true` with complete call coverage when both sides
   carry equal calls, and blocking drift when a call differs.

### One shared finalized-call context
`finalized_call_context()` is the single constructor of the `FinalizedCallContext` that F012
records every finalized call from AND F010's post-mortem writer builds for a terminal failure
(taking the call identity from it). Code now matches the "shared finalization context" claim;
F010 classification and exactly-once semantics are unchanged. A fuller event bus for replay
remains future (F140).

## Third hardening round (external FINDINGS on `remedy-review-20260715-113936`)

Six deeper findings — the complete input, episode isolation, shared call identity, index
trust, secure Evidence reading and writer conflict handling. All fixed.

### Complete job-input definition (was: job-file hash + task body + models)
`build_job_input_definition` records EVERY material persisted input: job title, task order and
per-task title/body/acceptance hashes, isolation mode, and the full resolved execution config
(builder/reviewer/repair provider/model/effort with sources, `max_rounds`,
`repair_rounds_allowed`, test command, CLI write mode, context strategy). `job_input_sha256` is
its digest, so a `max_rounds`, test-command, effort, title, acceptance or order change is
blocking. A secret-bearing test command keeps a redacted + hashed identity — the secret is
never serialized, yet a change is still detected.

### Remedy + target CONTENT identity via one strict Git collector (was: sha + dirty bool;
fail-open; symlink-following)
`worktree_identity()` is the ONE strict collector for both Remedy and the target. It hashes the
committed tree, the binary staged/unstaged diffs, every untracked entry (regular →
bytes+mode; symlink → LINK TARGET TEXT, never followed; special/FIFO → marked, never opened),
and submodule status. A failed `git` component (nonzero, timeout, unsupported) is `incomplete`
with a distinct digest marker — NEVER an empty success that reads as clean. An incomplete or
unavailable worktree identity makes a comparison unverifiable, never "same". No absolute path
is serialized, and an untracked symlink's TARGET content is never read.

### Per-episode call ownership + episode-start workspace (was: cross-episode call bleed)
Every finalized call carries its owning `episode_id`; `_collect_calls` includes only the
current episode's calls, so a resumed completed episode contains only its own calls and a prior
stopped/completed episode keeps its calls unchanged. The snapshot records the job-workspace
tree at THIS episode's start (containing prior applied work), a material resume input.

### Per-episode timestamps (was: a global job field reused on resume)
Creation time is stored per episode in the index; a resume gets its own timestamp, a retry of
the same episode reuses it, and the job-level field mirrors the latest episode.

### One finalized-call context, created once (was: F010 re-derived it, +1 sequence)
`finalized_call_context()` builds the context once; F012 records the finalized call, and F010's
post-mortem reuses the SAME already-appended call's identity — it never advances the sequence.
F010 classification and exactly-once are unchanged.

### Strict manifest + index trust chain (was: bypassable, unverified)
`validate_run_manifest()` runs at every read/write/diff/export boundary: version, safe job and
episode ids, valid status, unique contiguous call sequence, each call's job/episode ownership,
non-empty fields and fingerprints, safe unique artifact refs, coverage-vs-problems coherence,
safe non-self prior episodes. `validate_index_and_tree()` verifies the whole chain over
ANCHORED reads: `index_v`, unique episodes, canonical refs, each indexed manifest resolves and
its dir name/job/status/created_at/record hash match the entry, exactly-one latest, root mirror
equals the latest canonical episode, no extra unindexed or missing indexed episode.

### Anchored read-only Evidence traversal (was: symlinked parents followed)
Every manifest/index/episode/artifact read on the trust path goes through `secure_fs` anchored,
symlink-refusing directory fds. A symlinked `run_manifests`, episode or calls directory is
refused — outside files are never read or copied — with no fd leaks.

### Immutable artifact conflict (was: existing artifact accepted blindly)
On an idempotent write, an existing call artifact must equal the canonical bytes exactly; a
tampered one raises `ManifestConflictError`, and no root/index update follows.

### Canonical latest-manifest loader (was: CLI trusted the root mirror alone)
`load_latest_manifest_verified()` validates the whole trust chain and returns the latest
canonical episode. The CLI uses it; an index/root/episode disagreement is an INTEGRITY ERROR
(exit 1), never mistaken for drift (4) or incomplete coverage (5).

## Hardening round 4 (external FINDINGS — 14 items)

### F1/F11 — Typed, episode-owned, MANDATORY input snapshot (was: a bare dict, silently re-probed)
The episode-start inputs are captured once as a typed, versioned `EpisodeInputSnapshotV1`
(`snapshot_v`, `episode_id`, `captured_at`, `capture_phase`, `status`, `problems`, `input`),
bound to the active episode and a named phase (`episode_start`, or `pre_work_stop` for a
pre-work stop). A capture FAILURE is recorded as `status="failed"` data, never swallowed to an
empty dict. The finalizer consumes this exact object: `build_run_manifest` REFUSES to build
without it (no terminal re-probe), and a missing/failed/foreign snapshot is a BLOCKING recording
error. A stop-retry reuses the persisted, still-bound snapshot; a resume captures a new one.

### F2 — Material invocation controls persisted + hashed (was: unhashed, invisible to drift)
`timeout_sec`, `timeout_profile`, `max_output_chars`, `stream_evidence` and `max_tasks` join
`ExecutionConfig` and `build_job_input_definition`, each with its `{value, source}` and
precedence (explicit > persisted > default). They move `job_input_sha256`, so check-mode drift
sees them. A table-driven test (F14) enumerates every material field and proves each moves the
identity.

### F3 — FD-verified untracked reader (was: an lstat→open symlink race)
Untracked files are read through held, symlink-refusing directory fds: every parent is opened
with `open_verified_dir`, the final entry is no-follow-stat'd, opened `O_NOFOLLOW`, `fstat`'d and
required to be the SAME inode — a swap between the check and the open is caught and marked, never
followed. A symlink yields its link text (never its target content); a special file is never
opened (cannot hang); a size change mid-read is a race, not silent truncation.

### F4 — Typed `dirty` tri-state (was: false for ordinary dirty trees)
`WorktreeIdentity.dirty` is `True|False|None`, computed from staged/unstaged/untracked/submodule
changes — not from "collection had problems". `remedy_dirty()` returns the typed value.
`problems` means a COLLECTION FAILURE, not dirtiness.

### F5 — Non-time episode ordinal (was: a rollback to an older episode passed)
Each episode carries a 1-based, contiguous, strictly increasing `episode_ordinal` plus
`previous_episode_id`. The latest is the MAX-ordinal episode and the root mirror mirrors it, so
re-pointing the index at an older (lower-ordinal) episode is a detected rollback. The index and
the canonical manifests must agree on ordinal and previous.

### F6 — Prior-episode DAG validation (was: cycles/unknown refs passed)
`_validate_episode_graph` proves every prior edge points at a KNOWN episode with a strictly
lower ordinal — no self, cycle, future/equal, unknown or duplicate — with a DFS that rejects a
cycle directly even under corrupt ordinals.

### F7 — Anchored call-artifact trust chain (was: artifacts outside the canonical chain)
`validate_episode_artifacts_anchored` verifies each `calls/<artifact>` through held,
symlink-refusing fds — exists, hashes to its `artifact_sha256`, equals the canonical bytes, and
no undeclared artifact remains. It is called by `validate_index_and_tree`, the latest/episode
loaders and the export (and is the single validator F084/F140 reuse).

### F8 — Fully anchored export (was: `Path` reads could follow a symlink out)
`read_manifest_tree_bytes_anchored` reads the whole tree (root mirror, index, every episode
manifest + call artifacts) as verified bytes through anchored fds only. The export copies those
bytes; it never touches the evidence tree by `Path`, so a symlinked component cannot make it read
or copy a file from outside — even when the job is BLOCKED.

### F9 — `load_episode_manifest_verified` on every production trust read (was: a raw `Path` read)
Idempotent retries, repair and export load a named episode through the anchored, whole-tree-
validated loader; a rollback / broken graph / tampered artifact is an integrity error, never a
silently-trusted read.

### F10 — F010 records against the EXACT finalized context (was: `finalized_calls[-1]` lookup)
`_finalize_call` returns the `FinalizedCallContext`; the loop threads it into
`_record_call_failure(finalized_context=ctx)`, so the post-mortem uses the precise failing call's
id instead of re-deriving it from the last-appended call.

### F12 — Git-independent review-ZIP tests (was: exit 5 with no `.git` in the bundle)
Zero-call equality tests pin Remedy's own worktree identity to a deterministic COMPLETE fixture,
so the equality being proved is about job inputs, not the harness sitting in a git checkout. A
separate test proves a genuinely no-Git Remedy identity yields honest incomplete coverage (exit
5), never a false exit 0.

### F13 — JobPlan/index episode cross-check in export
The export cross-checks the JobPlan's recorded episode state against the on-disk index (same
ids, statuses and ordinals; no index-only or job-only episode); a divergence is a BLOCKING
integrity failure, never silently reconciled.

### F14 — One table-driven material-field proof
A single parametrized test enumerates every material `ExecutionConfig`/job/task input (including
the F2 invocation controls and their `_source` companions) and proves each one moves
`job_input_sha256`, plus a guard that no `ExecutionConfig` field is missing from the hashed
definition.

## Hardening round 5 (external FINDINGS — 14 items)

### F1 — Failed mandatory snapshot HARD-BLOCKS before any provider work
`run_job` captures the episode-start snapshot, validates the wrapper immediately, and — on a
failed/invalid capture — sets a durable `input_snapshot_error`, a non-running `blocked` status,
persists, and RETURNS: zero tasks, zero provider calls, no false `completed`. The failure is
found here, never later at terminal manifest writing.

### F2 — The recorded invocation controls are the ones EXECUTED
After resolution, the canonical locals ARE the resolved values (`timeout_sec`, `timeout_profile`,
`max_output_chars`, `stream_evidence`, `max_tasks`), so the task cap, the `run_pingpong` kwargs,
the stream-evidence switch, the reports and the manifest all use one value. No second
un-resolved variable exists. `test_run_manifest_runtime_truth.py` proves runtime == JobPlan ==
manifest for every control.

### F3 — Omission-sentinel resolution
The five invocation controls default to `None` (omitted). Precedence is explicit(non-None) >
persisted > product default, so an explicit value equal to the product default still overrides a
persisted one, and an omitted flag never masquerades as an explicit default.

### F4 — The full EpisodeInputSnapshotV1 wrapper is embedded in the manifest
`RunManifestV1.episode_snapshot` carries the version, owning episode id, captured-at, phase,
status and problems — self-contained, independent of mutable JobPlan state. `snapshot` is a
read-only property. Validation requires a valid, episode-bound snapshot, and a terminal manifest
requires an `ok` one.

### F5 — Stopped manifest, snapshot and calls share ONE episode id
A stopped manifest's `episode_id` IS the active execution episode (same as its snapshot and its
calls); the stop REQUEST id is separate terminal metadata (`stop_request_id`). Call ownership is
never rewritten during collection. A pre-work stop allocates and persists one coherent episode
before the stop transaction, so a retry converges on it.

### F6 — One strict snapshot validator, used everywhere

## Hardening round 8 (external FINDINGS — 16 items)

### The final identity model (F1/F2/F16) — three distinct things

F012 now distinguishes three concepts that were previously conflated. This distinction is
BINDING: F084 (demo replay) and F140 (worktree replay) depend on it.

**1. Record / provenance identity** — `provenance_projection()` / `record_sha256()` /
`provenance_sha256()`. Proves WHICH job, episode, run and call produced this Evidence. It carries
the job id, episode id, run id, provider-generated call id, artifact refs, the terminal status,
the stop request id, the episode ordinal/history and the timestamps. It is what the index
integrity chain and the immutable episode records are about. Two identical runs legitimately
differ here.

**2. Logical input identity** — `logical_input_projection()` / `logical_input_sha256()`. Proves
whether two DIFFERENT executions were given the SAME material inputs. It contains ONLY: the
stable task id, call sequence, role, round, kind, the provider/model, the PreparedCallInput
transport fingerprint, the job-input definition hash, config/environment, and the Remedy/target/
workspace input identity. It EXCLUDES every random execution identifier (job/episode/run/call
id), artifact paths, the terminal status, the stop request id, the episode ordinal/history and
all timestamps. Two separately executed but otherwise identical runs produce the SAME
`logical_input_sha256`.

**3. Outcome / lifecycle** — completed / stopped / planned. It describes what HAPPENED; it is
never an input. It lives only in the provenance projection. A completed and a stopped record with
identical inputs have the same logical input identity.

`diff_manifests()` compares calls through the STABLE LOGICAL key
`(task_id, sequence, role, round, kind)` — `CallIdentity.logical_key()` — so differing run/call
ids can never read as `missing_call` / `extra_call` / `call_order` input drift.

### F3/F4/F5/F14 — the strict decoder is the ONLY untrusted entry point
Every permissive `from_json` on an F012 type is renamed `from_trusted_json` (in-memory canonical
data only) and is banned from persisted-data paths by a repository guard test. Persisted run
records (`_collect_calls`), persisted JobPlan snapshots (`_episode_snapshot_bound_ok`,
`_write_run_manifest_record`), root mirrors, episodes, recovery, export and `read_run_manifest`
all go through `decode_*_v1`. A malformed persisted call is a recorded COVERAGE PROBLEM, never
normalized into a valid manifest; a malformed persisted snapshot is never `is_ok` and never
reused.

### F6/F7/F8 — exact recursive schemas
`InputSnapshot` (top level, WorktreeIdentity, config/environment entries, models/provider
versions), `JobInputDefinitionV1` (top level, tasks, the complete material execution field set
with every paired source) and `PreparedCallInput` all have EXACT field sets — an unknown key at
any level is refused. This closes the canary bypass where
`{"input": {"EXTRA_SECRET": "…/home/alice"}}` rode into canonical bytes. A minimal definition
(`{tasks: [], execution: {}}`) is rejected even when its hash matches: the hash proves the bytes
were not tampered with, not that the definition is complete. A lockstep guard test compares
`ExecutionConfig`'s dataclass fields with the hashed field set, so a future material field cannot
be added without updating F012.

### F9 — the prompt byte length is BOUND
`prompt_len` is now `prompt_len_bytes`, computed from the EXACT UTF-8 bytes that `prompt_sha256`
hashes, and it is included in the transport fingerprint — tampering with it invalidates the
fingerprint instead of sitting there authoritative but unbound.

### F10 — `is_ok()` validates the nested input
`is_ok()` means FULLY valid: wrapper + strict InputSnapshot + strict JobInputDefinition + the
embedded job-input hash relation. The wrapper-only predicate is explicitly named
`wrapper_shape_is_valid()` and is never a trust decision.

### F11/F13 — raw canonical byte equality + duplicate-key rejection
The trust rule for every stored member is `raw bytes == canonical_bytes(strictly_decoded_object)`
(`require_canonical_bytes`). Decoding normalizes; that normalization may never hide raw-byte
drift. `strict_json_loads` rejects duplicate JSON keys via an `object_pairs_hook`. The root mirror
must be BYTE-FOR-BYTE equal to the latest canonical episode bytes, and noncanonical
whitespace/key order is rejected.

### F12 — writer pre-publication round-trip + aggregate limits
Before any immutable artifact exists the writer: binds artifact refs, fully validates the bound
record, serializes canonical bytes, enforces the episode byte limit, STRICTLY DECODES those exact
bytes, requires the decoded object to equal the typed object, requires re-serialization to
reproduce identical bytes, validates every artifact's final bytes and limit, and checks the
projected total tree size. No immutable episode can be created from data the canonical reader
would immediately reject.

### F15 — no name-based trust prechecks
`_open_dir_anchored_or_missing` is the existence decision for `load_index_verified`,
`episode_manifest_exists_anchored`, `_enumerate_episode_dirs_anchored`,
`read_canonical_episode_order`, the recovery loader and `read_run_manifest` — preserving the
honest missing-vs-integrity distinction without following a symlinked parent.

## Hardening round 9 (external FINDINGS — 14 items)

### F1/F14 — Published reference vs current candidate (Exit 1 vs Exit 5)
A manifest is validated in one of three explicit `ManifestValidationMode`s:

| Mode | What it is | Coverage rule |
|---|---|---|
| `prepublication` | a record being assembled, not yet stored | shape only |
| `published_reference` | a STORED terminal (completed/stopped) record | coverage MUST be `complete`, with no problems, and every call bound to its hash-verified input artifact |
| `current_candidate` | inputs reconstructed from live state by `--check-manifest` | MAY be `incomplete`, and then MUST carry at least one bounded problem |

A published terminal reference is a claim about a run that already finished, so "this run
completed" and "I do not know all of its calls" cannot both be true: that combination is
corruption. The rule lives in the **canonical loader and the writer**, not in a second
Evidence-only rule layered on top — a permissive loader compensated for elsewhere is still a
permissive loader. `write_run_manifest` refuses to publish an incomplete terminal record, and
`load_latest_manifest_verified` refuses to read one back.

This is exactly what separates the two exit codes:

* a STORED terminal manifest with incomplete coverage → **exit 1 (integrity)** — the recorded
  chain is inconsistent;
* a CURRENT CANDIDATE with incomplete coverage → **exit 5 (incomplete coverage)** — an honest
  report that the public CLI cannot reconstruct assembled prompts for ordinary jobs (that is
  worktree replay, F140).

Zero calls is `complete` only when the JobPlan/Task state proves zero calls were expected (a job
stopped before any work began). It is never "complete because nothing was found".

### F2 — The Index is canonical raw bytes
`run_manifest_index.json` is a trust anchor, so at every entry point the stored bytes must equal
`canonical_index_bytes(decode_index_v1(bytes))`: size limit BEFORE decode, strict duplicate-key
decode, exact schema, no unknown fields. Applied at `load_index_verified`,
`validate_index_and_tree`, `build_verified_manifest_tree`, the CLI loader (`read_index`), the
recovery rebuild, the export and the writer's append. A pretty-printed or reordered index parses
identically and is still refused: the bytes an operator hashes must be the bytes Remedy trusted.

### F3 — The idempotent and concurrent-create reads are strict
An already-stored episode is untrusted disk state. `_decode_existing_episode` reads it anchored
and byte-limited, strict-decodes it, requires exact canonical bytes and validates it as a
published reference. Exact same content → idempotent success (the stored record, with its
original `created_at`, stays authoritative). Malformed, noncanonical or conflicting → a
`ManifestConflictError`, never a silent repair. The concurrent-create race path gets identical
treatment, so the writer can never report success while leaving a record its own loader rejects.

### F4 — The Index append reconstructs, never preserves
`_mirror_and_index` rebuilds the derived index from the canonical episode chain on disk (anchored
enumeration + strict per-episode reads, overlaid with the episode being published) and re-emits
exact canonical bytes. Unknown or noncanonical data in a previous index cannot survive an append.

### F5 — Persisted Call lineage is VERIFIED, never normalized
The stored `sequence` is the call's position **within its own run** (each task's run numbers its
calls from 1 — the real recorded fact). `_collect_calls` verifies it there, and only a call whose
stored sequence verifies receives the manifest's **derived** job-wide contiguous position. A
tampered sequence is never renumbered into looking correct. Every call is also checked against
its containers: `job_id` = the JobPlan, `task_id` = the owning TaskEntry (declared exactly once
in the embedded JobInputDefinition), `run_id` = the containing run, non-empty `episode_id` = the
owning episode, valid role/kind/round, strict `PreparedCallInput`, no duplicate sequence or
logical key. A VALID call owned by a PRIOR episode is excluded without restamping; a malformed,
empty-episode or foreign call is still reported as a coverage problem.

### F6 — The JobInputDefinition is complete
A matching hash proves the bytes were not tampered with — it says nothing about whether the
definition covers the whole material input set. So every required fact must be present and
well-formed: non-empty valid `job_title_sha256` and `job_file_sha256`, a non-empty
`isolation_mode` from the JobPlan's real vocabulary (`worktree` | `copy`), a typed task list with
per-task content hashes, the EXACT complete `execution` block (every material field with its
paired source), no unknown fields at any level, and a test command stored only as its safe
redacted identity + hash.

### F7 — Redundant facts must agree
Where the same fact is recorded twice, the copies are crosschecked and a contradiction is an
integrity error — at most one of them can be the input that actually ran:

* the snapshot's `job_file_sha256` vs `job_input.job_file_sha256`;
* `models.<role>`'s provider part vs `job_input.execution.<role>`;
* `models.<role>`'s model part vs `job_input.execution.<role>_model` (an UNSET declared model
  means "the provider default" — there is no second fact to contradict).

### F8 — KEYS are validated, not only values
`_is_safe_key` bounds config keys, model keys, provider-version keys, environment keys and source
labels: a leading alphanumeric, then `[A-Za-z0-9_.-]`, length-bounded, no `/`, `\`, `..`, control
characters, secret-shaped names or paths. `PYTHONHASHSEED` is validated against its real bounded
vocabulary (empty, `random`, or an integer 0..4294967295) rather than accepted as free text.

### F9 — Standard JSON only
`NaN`, `Infinity` and `-Infinity` are Python extensions, not JSON. The canonical serializer sets
`allow_nan=False`, so a non-finite float is refused at write; `strict_json_loads` sets
`parse_constant` to reject those constants at read; non-finite floats are refused in records; and
invalid UTF-8 surfaces as a bounded `ManifestError`, never a raw `UnicodeDecodeError`. Everything
Remedy publishes is readable by a conforming parser with no extensions enabled.

### F10 — Every PRESENT manifest tree is validated
The F012 marker (`run_manifest_required_v`) answers exactly one question: **is a MISSING manifest
allowed?** It never decides whether an existing tree is trusted.

| | no manifest artifacts | manifest artifacts present |
|---|---|---|
| **marked** terminal job | blocking failure | full trust chain |
| **unmarked** (legacy) job | legacy/uncovered note | full trust chain |

Presence is decided by `manifest_tree_is_present` — the RAW anchored probe, not the verified
allowlist — because a tree broken badly enough that nothing survives verification (a missing
index leaves no episode declared) still exists. Unverified bytes never reach a bundle merely
because a marker is absent. **The marker changes absence semantics only.**

### F11 — No permissive raw JSON on manifest paths
`strict_json_loads` is the only `json.loads` in `run_manifest.py`, and a repository guard test
enforces it: the manifest modules (`manifest_schema.py`, `call_identity.py`, `job_rerun_cmd.py`)
call no `json.loads` at all; `job_evidence.py` may parse NON-manifest evidence (traces, token
truth) that way but never manifest bytes; and no line naming manifest/index/artifact data may use
it anywhere in the F012 production set. The one justified exception is `strict_json_loads`
itself, which must pass both hardening hooks (duplicate-key rejection and constant rejection).

### F12 — The anchored tree reader has no name-based precheck
`read_manifest_tree_bytes_anchored` decides existence with `_open_dir_anchored_or_missing` on
verified handles — it advertises anchored safety, so it makes no `Path.is_dir()`/`exists()` trust
decision of its own.

### F13 — Writer success implies canonical readability
One shared invariant matrix runs after EVERY writer and recovery path — first write, idempotent
retry, concurrent-create, Stop retry, root-mirror repair, index repair, second-episode append.
Each must IMMEDIATELY satisfy: the canonical latest loader succeeds; the verified tree has zero
problems; the mirror is byte-for-byte the latest episode record; the index bytes are canonical;
every call artifact is present, canonically named and hash-bound; and a published terminal
reference has complete coverage. A failed write raises and leaves the previous tree readable.

## Hardening round 10 (external FINDINGS — 11 items)

### F1/F2 — An append validates the COMPLETE existing canonical chain
Writer success is a claim about the whole tree, not one file. Before appending anything, the
writer runs a full preflight:

1. securely open the contained Evidence root;
2. enumerate every existing immutable Episode;
3. strictly decode each one and require its canonical bytes;
4. validate EVERY declared Call artifact of EVERY Episode (presence, canonical bytes, hash);
5. enforce the exact Episode-root allowlist (no undeclared artifact, no symlinked component);
6. validate Job ID ownership;
7. validate unique Episode IDs and unique ordinals;
8. validate contiguous ordinals `1..N`;
9. validate the exact prior history and the immediate predecessor;
10. validate no rollback / cycle / future / unknown prior;
11. validate the CANDIDATE against that chain — Episode ID not already used (unless it is an
    exact idempotent retry), ordinal exactly `N+1`, previous exactly the current latest, priors
    exactly every prior Episode in ascending order;
12. only then publish the Root Mirror and the Index.

An Index is never written first for a later Canonical Loader to discover the problem. A refused
append leaves the previous canonical state byte-for-byte intact, and leaves the broken tree
untouched for diagnosis rather than "repairing" it.

### F3/F4 — Conflict-safe Episode publication
Episodes are published from a PRIVATE staging directory (`.run_manifest_staging/<episode>.<pid>.
<random>`) that lives OUTSIDE the canonical Episode namespace:

* every Call artifact and the Episode Manifest are written and verified there;
* the complete Episode directory is published with ONE atomic `rename`;
* `rename` onto an existing published Episode fails (POSIX refuses a non-empty destination), so
  a winner is never overwritten — the loser re-reads the winner's record and settles idempotent
  (exact same content) or `ManifestConflictError` (different content);
* a losing writer leaves NOTHING in the winner's Episode, because it never had a name inside it;
* cleanup only ever removes the writer's own unpredictable staging name, so no unsafe cleanup can
  delete a winner's file;
* a crash leaves the staging tree outside the canonical namespace: no reader, allowlist or
  Evidence export ever sees it, and the next append is unaffected.

**Artifact create-race.** `write_file_atomically(create_only=True)` publishes with `os.link` and
returns `False` instead of clobbering. That Boolean is now checked: on a lost race the existing
artifact is securely re-read — identical bytes converge, different bytes raise
`ManifestConflictError`. Mirror/Index publication never happens after a conflicting artifact race.

### F5 — Only KNOWN prior Episodes may excuse a Call
"I belong to another episode" is a claim a Call makes about itself, and it used to be believed:
an unrecognised episode id made the Call vanish and the manifest still reported COMPLETE. A Call
may now be excluded as prior history ONLY when

* its Episode exists in the canonical chain (`prior_episode_ordinals`);
* its Episode's ordinal is strictly lower than this Episode's;
* it appears in THIS Episode's exact `prior_episode_ids`;
* its remaining job/task/run lineage is valid (lineage is checked BEFORE membership, so
  "it's history" can never launder a malformed record).

Unknown, future, equal-ordinal or unlisted Episode IDs are blocking coverage problems. An
excluded prior Call still occupies its position in its RUN's sequence, because the run counted it
— per-run numbering spans Episodes.

### F6 — A zero-Call reference must PROVE zero Calls were expected
"No calls recorded" means either "this job genuinely had no work" or "the evidence went missing".
The Episode Manifest now embeds a typed `CallExpectationV1`, decided at finalization while the
JobPlan and run records are still in hand, so later verification never depends on the mutable
JobPlan:

| per-task expectation | meaning | calls expected |
|---|---|---|
| `executed` | this Episode dispatched the task | ≥ 1 |
| `prior_episode` | its work happened in an earlier Episode | 0 |
| `dispatched_no_calls` | dispatched, but it died before its first finalized call | 0 |
| `skipped` | explicitly skipped | 0 |
| `not_dispatched` | never reached (pre-work stop, planning-only, max-tasks boundary) | 0 |

plus an Episode `episode_phase` of `worked` | `pre_work_stop` | `planning_only`.

BLOCKING (Exit 1): a task whose status says it ran but which has no run id, whose run record is
missing, whose run has no `finalized_calls` field, or whose run recorded no calls for this
Episode. GENUINE zero-Call references stay valid and complete, exactly as the contract says —
a pre-work stop, a **planning-only job** ("Planning-only job (zero calls): valid manifest, empty
hash list"), and an **all-skipped job** ("a genuine zero-call (all-skipped) job ... stays valid
and complete"). A current candidate that cannot reconstruct Calls remains Exit 5.

### F7 — Every Call is bound to the embedded JobInput
Each Call's `task_id` must appear EXACTLY ONCE in `episode_snapshot.input.job_input.tasks`. The
binding uses the IMMUTABLE snapshot definition, never a later mutable `job.tasks` list, and the
task's stable order comes from that definition. Finalizing is BLOCKED when the live JobPlan's
task list no longer matches the snapshot's definition (tasks added, removed, renamed or
reordered after capture) — an Episode cannot be finalized against a definition it did not run.

### F8 — ONE exact JobInput validator
`validate_job_input_definition` IS the rule set: it returns every problem,
`decode_job_input_definition_v1` applies it and raises, and `EpisodeInputSnapshotV1.is_ok()`
calls the same function. There is no weaker typed predicate beside a stricter decoder, so a
record can no longer be "valid" on the way out and invalid on the way back in. The rules: exact
top-level field set, required non-empty hashes, valid isolation mode, exact task schema, the
exact complete Execution schema with every paired source from the closed vocabulary, a safe
redacted test-command identity, bounds and vocabularies, and no unknown fields anywhere.

### F9 — Exact Builder/Reviewer/Repair agreement
`models` has an exact schema: Builder and Reviewer are required, Repair appears exactly when the
definition activates a repair provider/model, and unknown roles are refused. For every recorded
role the provider part and the pinned model must match the embedded Execution definition
(Repair's provider falls back to the Builder's provider when only a repair model is pinned —
which is what production records). Absence is symmetric and explicit: a role is recorded exactly
when the definition declares a provider for it, so a planning-only job (no resolved execution
config) declares no providers, records no models, and validates cleanly.

### F10 — One universal writer-success postcondition
Every successful writer/recovery operation — first Episode, exact idempotent retry, identical
concurrent writer, lost artifact race with identical bytes, append to a valid chain, Root-Mirror
repair, Index repair, second-Episode append, recovery after partial staging, and Stop retry after
each publication window — immediately satisfies: the canonical latest loader succeeds; the
verified tree has zero problems; all Episode/artifact bytes are canonical; Root Mirror ==
latest Episode byte-for-byte; the Index is canonical; ordinals/history are valid; published
reference coverage is complete (and a zero-Call reference carries its proof); and NO undeclared
file exists in the canonical namespace.

Every FAILED operation — conflicting concurrent writer, conflicting artifact race, duplicate
ordinal, skipped predecessor, unknown prior, tampered or missing prior artifact — leaves no new
canonical Episode, no Root/Index advancement, no contamination of an existing Episode, no staging
leftover, and a pending F011 stop still retryable.

### F11 — Authoritative Evidence contains the claimed runs
Every test count in a handoff must exist in the packaged `verification_tests.json`. A broad run
with known baseline failures is recorded with its exact failures AND the same command against a
grounded baseline — never called green, never omitted while its count is quoted.

## Hardening round 11 (external FINDINGS — 13 items)

### F1 — Per-job append serialization
The atomic directory rename only serializes writers racing for the SAME episode name. Two writers
publishing DIFFERENT ids never collide on a name: each reads the chain, each computes "the next
ordinal is N+1", and each succeeds — leaving a duplicate ordinal the canonical loader rejects.
Reproduced exactly that way.

The whole state transition now runs under ONE per-job **append claim**:

```
acquire append claim
→ load canonical chain → validate all Episodes/artifacts/allowlists
→ determine next ordinal and previous Episode → validate candidate
→ construct private stage → publish Episode
→ reload and validate the complete chain → derive Root Mirror and Index → write projections
→ enforce the writer postcondition
→ release claim
```

The claim is an `flock` on `<evidence>/.run_manifest_control/append.lock` — an anchored private
control directory OUTSIDE the canonical Manifest namespace (so it never enters an allowlist, a
verified tree or a review export), held on one fd for the whole transaction, acquired with a
bounded timeout that surfaces a wedged holder as a diagnosable error rather than a hang. The
kernel releases it when the fd closes, so an exception, a kill or a process death leaves no stale
ownership. **Readers never take it** — they validate canonical state, so a wedged writer can never
block verification.

### F2 — Every writer path validates the COMPLETE existing chain
One shared `load_verified_canonical_chain_for_write()` is used by every path: first Episode, new
append, exact idempotent retry, concurrent convergence, Stop retry, recovery and Root/Index
repair. It validates every Episode manifest (strict decode + canonical bytes), each Episode's
exact root allowlist, every declared Call artifact, no undeclared artifact, artifact hashes, Job
ownership, unique contiguous ordinals and the exact history/predecessor. Success means the same
thing on every path, because before round 11 an idempotent retry over a chain with a tampered
PRIOR artifact returned success and the loader rejected the tree immediately afterwards.

The current Episode's OWN missing artifact may be reconstructed (its canonical bytes are known —
the established idempotent contract); a conflicting current artifact blocks; any
missing/tampered/extra artifact in a PRIOR Episode blocks; nothing is published over a broken
chain.

### F3 — A lost same-Episode race verifies the COMPLETE winner
A winner may carry an identical `run_manifest.json` and have no `calls/` at all. "Its manifest
matches mine" is not "it is the episode I was about to publish". On a lost rename the winner's
WHOLE tree is verified — strict manifest decode, canonical bytes, exact root allowlist, every Call
artifact, no missing/extra/symlinked member — and only a complete, canonically equivalent winner
is idempotent success. An incomplete winner is a conflict, and this writer never repairs or adds
files into another writer's Episode.

### F4 — Post-publication chain revalidation
Preflight is not the postcondition. After publication and before the projections, the chain is
RELOADED through anchored reads, fully revalidated, and returned as a typed
`VerifiedCanonicalChain`. `_mirror_and_index()` accepts ONLY that type — a loose list of Episode
dataclasses proves nothing about how it was obtained. After writing Root/Index the writer asserts:
the canonical latest loader succeeds and the verified tree has zero problems. A successful public
Writer operation never leaves a state its own Reader rejects.

### F5 — Complete artifact create-race handling
Every create-only Call artifact write checks its Boolean: on a lost race the artifact is re-read
through the anchored reader and must equal the expected canonical bytes exactly — identical
converges, anything else (different, missing, symlinked, noncanonical) is a
`ManifestConflictError`. No Mirror/Index publication follows a conflict, on the staging path or
the existing-Episode settlement path.

### F6 — Membership is always decided
`_collect_calls()` receives the canonical prior-Episode ids, the ordinal map, the current
Episode's exact prior list and the immutable Snapshot task definition. A Call may be excluded as
history only when its Episode exists in the chain, has a strictly lower ordinal, appears in the
exact `prior_episode_ids`, and its job/task/run lineage is valid. Unknown, future, unindexed or
unrelated Episode ids are blocking problems. The owning episode is never empty — an unowned
collection would adopt whatever it found. The complete persisted per-run sequence is validated
BEFORE Episode filtering, a valid excluded prior Call still contributes its stored per-run
position, and survivors are never renumbered.

### F7 — The exact CallExpectation lifecycle matrix
`run_job` sets `completed` only when EVERY task is applied or skipped (a max-tasks boundary PAUSES
the job, and a paused job is not a finished run and gets no manifest). A stop is different by
design (F011: "the call in flight finishes, nothing new starts").

| status / phase | snapshot capture phase | allowed task expectations | calls | stop request |
|---|---|---|---|---|
| `planned` / `planning_only` | `planning_only` | `not_dispatched` | zero | forbidden |
| `stopped` / `pre_work_stop` | `pre_work_stop` | `not_dispatched` | zero | required |
| `completed` / `worked` | `episode_start` | `executed`, `prior_episode`, `skipped` | any (zero only via all-skipped/prior-episode) | forbidden |
| `stopped` / `worked` | `episode_start` | `executed`, `prior_episode`, `skipped`, `not_dispatched`, `dispatched_no_calls` | any | required |

Every other combination is refused — including `completed + planning_only`, `planned + worked`,
`completed + dispatched_no_calls`, `completed + not_dispatched`, `stopped + planning_only`, and a
`pre_work_stop` snapshot under a `worked` expectation. The phase is READ from the snapshot's own
capture phase, never inferred from the status.

### F8 — Expectation tasks match the embedded JobInput exactly
Same ids, same order, no duplicate, no missing task, no ghost — including when the definition
declares none. The source of truth is the immutable Episode Snapshot definition, and a later
mutable JobPlan task addition/removal/reorder blocks finalization.

### F9 — Exact Call counts, run binding and a ledger seal
`expected_min_calls` is gone. "At least N" plus "N found" is a tautology that can only confirm
itself. Each task expectation now carries `run_id`, an EXACT `expected_call_count`, an exact
`observed_call_count`, and `finalized_calls_sha256` — a seal over the run's COMPLETE finalized-call
ledger as read at finalization, which is what makes the count a claim about a specific ledger.
`executed`/`prior_episode`/`dispatched_no_calls` must name a run and seal its ledger; skipped and
not-dispatched must name neither; a Call recorded under a different run than its expectation names
blocks; a missing Run record, a missing `finalized_calls` field and a malformed Call all block.

### F10 — Phase-aware Snapshot identities
A WORKED episode must record every material identity — Remedy source, target, job initial
workspace, Episode-start workspace, JobInputDefinition, config/environment/models. **There is no
silent empty string**: a value the product genuinely cannot obtain (a non-git target has no tree
object) is recorded as the explicit `unavailable` marker, and an unavailable workspace identity
must carry a REASON. A pre-work stop or planning-only episode states its missing workspace the
same explicit way. Because a git tree object cannot be recomputed read-only, the snapshot carries
`episode_start_workspace_identity`: the same strict content digest every other worktree uses.

### F11 — Contained, read-only workspace inspection
Two reproductions: a persisted path whose FINAL component looked normal but whose PARENT was a
symlink to an outside repository (the check followed it and still reported complete coverage), and
`git object count 3 → 5` (the check ran `git add -A` + `git write-tree`, writing blobs and trees
into the repository it was inspecting).

The check now resolves the workspace through the canonical `worktrees_root_for()` root with
anchored no-follow traversal — every component verified, parents included — and refuses anything
outside it. The persisted path is a claim, never its own trust root. The comparison uses the
strict read-only `worktree_identity()` digest (git plumbing only): no `git add`, no
`git write-tree`, no temporary index, no object-database write. Configured clean/smudge filters
are neutralized for the inspection, so no filter side effect can fire from a read-only check.
`absent` and `escapes` are distinguished: a completed job whose worktree was intentionally cleaned
keeps the documented rerun-from-recorded-target semantics, while a resumable job's missing
workspace and any escaping path are incomplete coverage.

### F12 — One universal Writer success postcondition
The shared matrix covers: first write, exact idempotent retry, identical concurrent same-ID
writer, incomplete same-ID winner, conflicting same-ID writer, concurrent different-ID
same-ordinal writers, three parallel append writers, lost artifact race with identical bytes, lost
artifact race with conflicting bytes, append to a valid chain, append over tampered/missing/extra
prior artifacts, retry over a damaged prior chain, recovery after partial staging, and Stop retry
after every publication window. Every success immediately satisfies: canonical latest loader
succeeds; verified tree has zero problems; all Episode/artifact bytes canonical; Root Mirror ==
Latest Episode byte-for-byte; Index canonical; ordinals/history exact; published reference
coverage complete; CallExpectation lifecycle-valid; no undeclared canonical member; no stale stage.
Every failure: no new Episode, Latest does not advance, Root/Index do not advance, no winner
contamination, no outside write, and a pending F011 Stop stays retryable.

### F13 — Authoritative Evidence matches the handoff exactly
Every number in the handoff exists in the packaged verification artifact; a known-red diagnostic
is labelled and grounded against a baseline, never described as green.

## Hardening round 12 (external FINDINGS — 11 items)

### F1 — The canonical Run Call Ledger
`CallExpectationV1` carried `expected_call_count`, `observed_call_count` and a
`finalized_calls_sha256` taken over the MUTABLE Run JSON. None of those bytes were in the
canonical tree, so a stored reference could drop a call, restate both counts, put any
formally-valid 64-hex string in the hash field — and validate. A number that only agrees with
itself is not evidence.

The ledger is now an artifact like any other, at
`run_manifests/<episode>/call_ledgers/<task-id>-<run-id>.json`:

```
RunCallLedgerV1:
  ledger_v, job_id, task_id, run_id, terminal_state, complete
  entries[ per_run_sequence, call_id, episode_id, role, round, kind,
           prepared_input_fingerprint, ok ]
```

Strict exact schema, canonical bytes, bounded size/count, in the episode's exact allowlist,
hash-bound + ref-bound from `TaskCallExpectationV1`, and verified by the canonical loader,
recovery and the Evidence export. The mutable Run JSON GENERATES it at finalization; nothing
trusts that JSON afterwards.

**The bijection.** Every current-Episode Manifest call maps to EXACTLY ONE ledger entry (same
role/round/kind/fingerprint/episode); every ledger entry is either that call or a proven
prior-Episode one; no unknown, duplicate, missing or reordered entry; the per-run sequence is
contiguous 1..N. Prior-Episode calls stay IN the ledger — the run made them, and a ledger that
dropped them would disagree with the run it describes. F140's replay ("serves stream N for call
N", keyed by call sequence) consumes the same verified sequence.

### F2 — Published artifacts are immutable
Episodes publish atomically as complete directories, so a missing artifact afterwards is not a
partial write — it is corruption, tamper or storage loss. `_settle_existing_artifacts` used to
recreate it on an idempotent retry, which turned the loader green and erased the only evidence
that anything was wrong. It is gone. A private unpublished stage may be rebuilt or discarded; a
published Episode Manifest and every declared Call/Ledger artifact is VERIFIED and never
repaired — missing or altered is an integrity/conflict error, on every writer path. Recovery
rebuilds the derived Root Mirror/Index only, never an immutable member.

### F3 — Exact retry of a non-latest Episode is a no-op
`ep1`, `ep2`, then an exact retry of `ep1` failed with "ep2 references unknown prior ep1;
ordinals [2] are not contiguous": the writer excluded the candidate before validating the chain,
and excluding an OLDER episode breaks all the history built on it. The flow, under the append
claim, now asks whether the episode already exists FIRST and never excludes it: load and validate
the complete chain as it really is; compare the existing Episode's canonical bytes and every
immutable artifact/ledger; exact equality → idempotent no-op (ordinal not recomputed, Latest
unchanged, projections untouched unless they are actually stale — the documented
derived-projection recovery); conflict → `ManifestConflictError`. An unknown new episode continues
through the append flow.

### F4 — One exact task lifecycle record
`TaskCallExpectationV1` now also carries `task_status_at_finalization`, `dispatch_state`
(`never_dispatched` | `dispatched_this_episode` | `dispatched_prior_episode`), `ledger_ref` and
the ledger seal. A contradictory persisted state is REPORTED, never normalized: the run id is
never erased to make an expectation look valid, and both persisted facts stay in the record.

| persisted state | expectation | run |
|---|---|---|
| skipped | `skipped` | none (a skipped task owning a run is an integrity problem) |
| pending, never dispatched | `not_dispatched` | none |
| passed/applied/running | `executed` | valid run + sealed ledger, exact nonzero entries |
| failed/blocked before dispatch | `failed_pre_dispatch` | none |
| failed/blocked after dispatch, no finalized call | `dispatched_no_calls` | valid run + sealed zero-entry ledger |
| work happened earlier | `prior_episode` | valid run + ledger + proven canonical prior membership |

**One correction to the prompt's rule, from the committed contract:** `pending` + a Run is NOT a
contradiction. F011's mid-flight stop ("the call in flight finishes, nothing new starts")
legitimately leaves the task pending for the resume while its run holds the finalized call — the
first cut of this rule broke that suite. What is refused is an EXPECTATION claiming "never
dispatched" while a run exists: the run is the proof of dispatch, so the expectation must say what
happened.

### F5 — Pre-work Stop on a resumed job carries proven prior tasks
Episode 1 completes T001; a resume is requested; a stop is already pending before new work. The
collector correctly said `prior_episode` — and the matrix rejected it, because
`stopped/pre_work_stop` permitted only `not_dispatched`. The exact matrix now: status `stopped`,
snapshot phase `pre_work_stop`, expectation phase `pre_work_stop`, zero current-Episode calls, a
valid stop request, previously completed tasks `prior_episode` (each against a real canonical
prior Episode and verified ledger), remaining tasks `not_dispatched`, and no task executed here.

### F6 — Containment stays bound through the inspection
Verifying a path, closing the descriptors and returning an ordinary `Path` proves nothing: rename
the verified directory, drop a symlink to an outside repository in its place, and the inspection
runs against that repository — reproduced, with the outside HEAD observed.
`inspect_contained_workspace_identity(canonical_root, claimed_path)` anchors the canonical root,
no-follow traverses every component, and HOLDS the final descriptor for the whole inspection; git
runs with its cwd bound to that open description (`/proc/self/fd/N`), which no rename can
redirect; the directory's dev/inode is re-checked afterwards; and it fails CLOSED where an
fd-bound cwd cannot be guaranteed. Used by the episode-start snapshot and the current-candidate
check alike.

### F7 — Read-only means no repository code runs
`core.fsmonitor = <script>` was EXECUTED by `worktree_identity()`, which then reported
`status=ok, problems=[]`. Reading a repository must never mean running its code. Every git call in
the identity now neutralizes the repository's configured helpers — `core.fsmonitor=false`,
`filter.*.clean|smudge=cat`, `filter.*.process=false`, `filter.*.required=false`,
`diff.*.command|textconv=`, `core.hooksPath=/dev/null`, `diff.external=` — and runs with
`GIT_CONFIG_GLOBAL=/dev/null`, `GIT_CONFIG_SYSTEM=/dev/null`, `GIT_OPTIONAL_LOCKS=0` and no
askpass/SSH/protocol helper. The clean substitution keeps the identity meaningful: it digests the
RAW working-tree bytes, and both sides of every comparison are captured the same way.

### F8 — One canonical workspace identity format
The reference recorded a 40-hex git TREE OBJECT in `episode_start_workspace_tree`; the candidate
recorded a 64-hex content DIGEST in the same field; the logical projection compared it directly —
so an identical workspace produced blocking drift. Two different kinds of thing were sharing one
field name, and only one of them can be recomputed read-only. The typed
`episode_start_workspace_identity` (`status`/`head`/`digest`/`dirty`/`problems`) is now the sole
logical workspace input: the projection carries it, `diff_manifests` compares it, the candidate
captures it EXACTLY ONCE and reuses that object, and a sha256 content digest is never written into
a field whose reference holds a git tree id. `episode_start_workspace_tree` remains provenance.

### F9 — Input coverage versus Call coverage
"Every call compared" and "every material input known" are different claims. The diff reports both
(`call_status`, `input_status`, `input_problems`), and `same_inputs=true` requires BOTH complete —
an honest `unavailable` value keeps the record truthful and must never add up to determinism. A
current candidate that is short on either dimension is Exit 5; a corrupt stored reference is Exit
1. The CLI names which dimension is short, in text and in `--json`.

### F10 — The real transaction phases
The docs claimed both "the immutable Episode is the source of truth, Mirror/Index failure is
repaired from it" AND "every Writer failure leaves no new Episode". The second is false after a
successful atomic publication. The actual phases:

**Before Episode publication** — a failure leaves no canonical Episode, no Mirror/Index
advancement, and a private stage that is removed (or left as noncanonical crash debris).

**After immutable Episode publication** — a later projection or JobPlan failure may leave the
canonical immutable Episode present, the Root/Index not yet advanced, and the JobPlan/Stop not
acknowledged. The retry reconstructs the derived projections. An immutable Episode is never rolled
back.

Publication success, projection success and JobPlan acknowledgement are three separate durable
boundaries.

### F11 — Bounded safe staging cleanup
Crash debris is invisible to canonical readers, so cleanup is hygiene, not correctness — and it
fails safe: only under the append claim, only the exact staging name format, never a symlink,
never a canonical Episode name, only when the owning PID is gone AND the stage is older than
24h, bounded item count, and a cleanup failure is swallowed rather than allowed to break the
caller's real work. An active concurrent writer's stage is never removed.

## Hardening round 13 (external BLOCKED_EVIDENCE + FINDINGS — 10 items)

Round 12 made the Run Call Ledger real bytes. This round makes those bytes say something true,
closes the containment hole underneath the round-12 held-descriptor work, and settles the
operator-state policy that made the round-12 package non-authoritative.

Every finding was reproduced against the production seam before it was fixed. Two of the review's
own prescriptions turned out to contradict the committed contract and are recorded as such below —
implementing them verbatim would have refused real production records.

### F1 — A published ledger must be complete
`complete` was written and never read. A ledger could say "this is a partial account of the run"
and still be sealed into a published terminal reference, with a correctly updated hash, as if it
were the whole story. Reproduced: `complete=false` + resealed hash → published-reference
validation succeeded. A published completed/stopped Episode is the record of what happened; a
partial account of a run inside it is a contradiction, not a caveat. `MODE_PUBLISHED_REFERENCE`
now refuses it. A PRE-publication candidate may legitimately still be filling up: it says so
explicitly and reports INCOMPLETE Call coverage instead of passing as determinism.

### F2 — The terminal state comes from the Run record
The ledger describes a RUN, but its `terminal_state` was derived from the surrounding TASK's
status (`_LEDGER_STATE_OF[task_status]`, with `.get(..., "stopped")` for anything unrecognised).
That asked the wrong witness. The run's `final_status` is now strictly decoded from the persisted
run record and mapped through `RUN_FINAL_STATUS_TO_LEDGER_STATE`, which is CLOSED: an unknown
outcome is a recorded problem and an INCOMPLETE ledger, never a plausible default.

The stored half of the rule is deliberately narrow, because the reverse implication is false. A
task only reaches `passed`/`applied_to_job_workspace` AFTER its run returned a successful result,
so those two pin the ledger to `completed`. `blocked`/`failed`/`pending`/`running` pin nothing:
production reaches every one of them with a SUCCESSFUL run — the completion gate, the target-repo
guard or the workspace apply refuses the work after the run finished — and `pending` + a finished
run is F011's mid-flight stop. A rule that forbade those combinations would refuse real records.
`skipped` may own no ledger at all: skipping happens before dispatch.

### F3 — The ledger entry's result matches its call
The Manifest/Ledger bijection compared role, round, kind, fingerprint and episode — but not `ok`.
So the two accounts of one call could disagree about whether it succeeded, both sealed, both
valid. Reproduced: manifest call `ok=true`, ledger entry `ok=false`, hash resealed → accepted.
The compared field set is now named once, in `LEDGER_CALL_BIJECTION_FIELDS`, so a future
replay-material field is added deliberately rather than forgotten — F140 replays on exactly these.

### F4 — Ledger order is bound, not merely contiguous
Every entry could match its call one-for-one while the SEQUENCE said something else entirely:
swapping two entries' `per_run_sequence` left the ledger contiguous 1..N, every field still
matched, and the reference validated. But the order IS the claim ("the builder ran, then the
reviewer"), and F140's replay serves "stream N for call N" keyed by it. This episode's ledger
entries, read in recorded order, must now be exactly the manifest's calls for that run in
canonical order, and they must be the ledger's SUFFIX — a prior-episode entry can never come
after them.

### F5 — Ledger history is continuous across Episodes
A later episode's ledger could contain `call_id=ghost-prior, episode_id=ep1` — a call in no ep1
manifest, no ep1 call artifact and no ep1 ledger — and the published reference still validated,
because every existing check only ever asked "is ep1 a known prior?". History was a claim nobody
read back.

No single manifest can prove this, which is exactly why it was missed. `validate_ledger_chain()`
holds the rule: per (task, run) across the chain in ordinal order, the first ledger ESTABLISHES
the sequence; every later one is that ledger exactly or an exact EXTENSION of it; the earlier
entries are a PREFIX, field for field, in order; no prior entry may be removed, reordered,
invented or altered; every prior entry resolves to exactly one canonical call published by THAT
episode; every new suffix entry belongs to the current episode.

It lands in `_validate_episode_graph`, the one place the whole chain is in hand — so the writer
preflight, the writer postcondition, recovery, the canonical loader, the verified tree builder and
the Evidence export all get it at once instead of six times over.

A subtlety the reproduction did not show, and production did: a `call_id` is a path-shaped ref
RELATIVE TO ITS RUN (`calls/builder/round-01/attempt`), so it is unique within a run and
deliberately not across the job — every task's first builder call carries that exact string.
Keying the resolution map on the call id alone made unrelated tasks collide and refused a real
stop-then-resume. The identity that is actually unique is (task, run, call_id).

### F6 — Ledger entry identities are path- and secret-safe
Entry ids were unchecked: `call_id = "/home/alice/SUPERSECRET"` validated and its bytes entered
the canonical record. The two ids answer different questions and get the established rule for

**Recorded contract difference.** The finding specified "no separators" for `call_id`. Every real

call_id 'calls/builder/round-01/attempt' is not a safe bounded component". The committed contract

### F7 — Workspace containment rejects lexical `..` escapes

### F8 — One closed ledger contract

## Hardening round 14 (external FINDINGS — 6 items)

Round 13 made the Run Call Ledger mean something. This round closes the last trust-chain gaps:
what a *finished* run's ledger may become later, which ledgers a manifest may carry at all, how a
ledger names its artifact, and what a call ref is allowed to be.

Every finding was reproduced against the production seam before it was fixed.

### F1 — A complete terminal ledger is FINAL
Round 13 compared the entry PREFIX, so a later episode could EXTEND a run that had already
published itself as finished — and restate its outcome on the way:

```text
ep1:  run_id=rT001  terminal_state=completed  complete=true  entries=[Call 1]
ep2:  run_id=rT001  terminal_state=failed     complete=true  entries=[Call 1, Call 2]
```

Both manifests validated, both writer calls succeeded, and the canonical loader and verified tree
accepted the chain. Three separate facts forbid it: `complete=true` says the ledger is the entire
account of that run, the terminal state says the run ended, and published Evidence is immutable.
A prefix rule could only ever see the entries; the contradiction lived in the header.

**The rule, per `(task_id, run_id)`:** the first published COMPLETE ledger freezes the run's whole
ledger object. Every later episode may repeat it byte-for-byte and nothing else — no extension, no
shrink, no reordering, no terminal-state change, no `complete` change, no header change, no entry
change. `validate_ledger_chain()` therefore compares the complete Ledger object (via its canonical
sha256), not merely its entry prefix.

**Later work uses a NEW run id**, which is what production already does: `PingPongResult.run_id`
is a fresh `uuid4().hex[:16]` per execution. Verified against a real stop-then-resume:

```text
ep1  T001 run=f5962555  completed complete=True  2 entries
ep2  T001 run=f5962555  completed complete=True  2 entries   <- byte-identical repeat
ep2  T002 run=9ae434c5  completed complete=True  2 entries   <- new work, NEW run id
```

An incomplete ledger may still grow (only as an exact extension), but it can never be published:
a published reference's ledgers must be complete (F1, round 13). A non-terminal live ledger may
exist only in mutable/prepublication state.

### F2/F5 — The ledger set is exactly the expectation set
A fabricated ledger — `task_id=GHOST, run_id=ghostrun, complete=true, entries=[]` — belonging to
no embedded JobInputDefinition task, no CallExpectation and no Manifest Call was accepted by typed
validation, the writer, the canonical loader and the verified tree. Every check walked FROM the
ledgers OUTWARD ("is this ledger's expectation ok?") instead of asking whether the ledgers were
the ones the record explains. A perfectly-formed passenger is still a passenger.

`validate_ledger_set()` is one shared set-level contract, reached from typed validation, the strict
decode path, writer preflight, staged publication, existing-episode validation, the canonical
loader, recovery, the verified tree and the Evidence export:

```text
expected_ledger_keys = {(task_id, run_id) for every CallExpectation task that owns a Run}
actual_ledger_keys  == expected_ledger_keys
```

plus: every ledger's task declared exactly once in the embedded JobInputDefinition; no ledger for a
task without run ownership; no unreferenced ledger; no duplicate key; no duplicate canonical ref;
every ref recomputable from the ledger's own identity; one physical artifact per ref; no alias. A
zero-entry ledger remains legal for exactly the lifecycle state that proves a dispatched terminal
run finalized zero calls.

### F3 — Ledger artifact refs are collision-free
`call_ledgers/{task_id}-{run_id}.json` is ambiguous, because `-` is legal inside both ids:

```text
(task_id="a-b", run_id="c")   ->  call_ledgers/a-b-c.json
(task_id="a",   run_id="b-c") ->  call_ledgers/a-b-c.json
```

Both ids satisfy the safe-component schema. A crafted canonical tree carrying both declarations
and ONE physical file was accepted, because `_validate_episode_ledgers_anchored()` built a dict
keyed by filename and silently overwrote one declaration — the second ledger simply stopped
existing as far as verification was concerned.

The ref is now `call_ledgers/<sha256(canonical identity)>.json`, where the identity encoding is
canonical JSON of `{task_id, run_id}` — length-delimited by construction, so exactly one pair can
produce those bytes. It is deterministic, recomputable from the ledger's identity, and fixed-width:
69 characters whatever the ids are, far below `NAME_MAX`, so even maximum-length ids yield a legal
filename. Duplicate refs are refused BEFORE any dictionary is keyed by them, at the reader and at
the set validator. No compatibility layer is needed: F012 is unmerged.

### F4 — A closed canonical call-ref grammar
`safe_call_ref()` only asked whether a ref was DANGEROUS, so `calls//builder`, `calls/./builder`,
`calls/builder/` and `home/alice` all passed. None of them names a call. A call ref is the identity
F010's post-mortems, F012's manifests and F140's replay all use to name the SAME call, so it must
be canonical rather than merely not-absolute.

Every production call-id source was inspected and RUN first. There are exactly two shapes:

```text
calls/<role>/round-NN/<kind>          fallback / fake provider calls (shared_call_id)
streams/<role>/round-NN/<kind>-II     streamed CLI calls (_allocate_stream_call_dir,
                                      rel_prefix = f"streams/{role}"; F004/F010's layout)
```

The grammar is closed to those: relative POSIX form only, exactly four segments, no empty segment,
no `.` or `..` segment, no trailing or repeated slash, no backslash, no control character, no
absolute/home/temp path, no secret, bounded total and segment lengths, namespace in
`{calls, streams}`, role and kind closed enums, `round-NN` a real positive round, and a streamed
ref's trailing attempt index (note `parse-retry` itself contains a dash, so the index splits on the
LAST one). Because both shapes ENCODE role/round/kind, the ref must also AGREE with the
CallIdentity it belongs to — a ref naming the builder's round-1 attempt on the reviewer's parse
retry is two accounts of one call disagreeing, the same defect class F3 (round 13) closed for `ok`.

`validate_call_ref()` is the one validator, used by the CallIdentity validator and the ledger entry
validator alike. Fixtures previously emitted a synthetic `c1` production never emits — a fixture
using a shape production cannot produce is unable to prove the grammar — and now default to the
real canonical ref.

### F6 — Terminal run versus new run (the corrected contract)
Earlier rounds described a later ledger as an exact EXTENSION of the one an earlier episode
established. That is incompatible with `complete=true` plus a terminal state, and it is superseded:

* a terminal published Run Ledger is FROZEN;
* a later episode repeats it, byte-for-byte, purely as immutable prior history;
* new work uses a NEW run id;
* a later episode may therefore carry several immutable prior ledgers alongside its own new ones;
* F140 serves "stream N for call N" WITHIN one frozen Run Ledger, whose order is already bound to
  the manifest's canonical call order (F4, round 13).

### Local checkpoint commit policy (process)
The reviewed state of a round is committed locally before the next round's work begins, and each
logical repair block is committed as it goes green (targeted tests plus `git diff --check` first).
Local history is not an acceptance signal: external acceptance still governs push, PR and merge,
and F012 stays `[~]` until it arrives.

## Hardening round 15 (external FINDINGS — 7 items)

### F1 — Task lifecycle is MONOTONIC across the chain
Round 14 stopped a later episode rewriting a run it admitted to. It could still omit the ledger
entirely and claim the work never happened:

```text
ep1:  T001  expectation=executed  status=applied_to_job_workspace  run=rT001
      terminal ledger + call artifact present
ep2:  T001  expectation=skipped   run=""   no ledger   no calls
```

Both manifests validated, both writes succeeded, the canonical loader and the verified tree
accepted the chain. The finality rule never fired, because there was no second ledger to compare.
**The omission WAS the erasure.**

`validate_task_lifecycle_chain()` asks the question no single episode can answer. The terminal set
is the committed contract's, not an invention — F011: *"A task that already reached
`applied_to_job_workspace` is durable and is **never** rolled back. Nothing is converted to
`skipped`."* `run_job` proves it: the resume loop `continue`s past `applied`/`passed`/`skipped`
and the stop path refuses to roll those three back.

* **Terminal with a run** (`applied_to_job_workspace`/`passed`): every later episode must carry it

* **Non-terminal**: a stop returns the task to `pending`, and its resume legitimately starts a NEW

* **Identity**: the immutable JobInput task list cannot gain, lose or reorder a task.

It lands in `_validate_episode_graph`, so writer preflight, writer postcondition, the canonical

### F2 — Call-ref numbers have exactly one text form
Round 14 parsed the round and the attempt index with `int()`, and `int()` reads one number many
ways. `round-01`, `round-001` and `round-000001` were three names for round 1; `attempt-00` was
index 0, which is not a call. The ref is precisely the name F010's post-mortems, F012's manifests
and F140's replay must AGREE on, and an alias set breaks that the moment two of them spell it
differently.

`canonical_call_number()` / `parse_canonical_call_number()` live in `call_identity.py`, a

```text
1 -> 01     2 -> 02     9 -> 09     10 -> 10     99 -> 99     100 -> 100
```

Canonicality is decided by RECONSTRUCTION: the ref must equal what its own parts rebuild via
`canonical_call_ref()`. Rounds and indices are positive and stay inside the configured bounds. The

### F3/F5 — The review subject is typed, verified and resolved by ONE helper

`review_subject.py` owns `ReviewSubjectV1(subject_v, base_commit, head_commit, base_is_ancestor,

* the base resolves with `git rev-parse --verify <base>^{commit}` — unresolvable RAISES;
* `git merge-base --is-ancestor <base> HEAD` is required — non-ancestral RAISES;
* the environment may SUPPLY the base; the resolved full 40-char SHA becomes the durable fact;
* it is recorded in `review_subject.json`, the content proof and the ZIP manifest

* `REMEDY_REVIEW_BASE` is read in exactly one module, and a test enforces that.

Unset base remains the documented legacy path, byte-for-byte: an ordinary job whose branch carries
unrelated commits must not suddenly report them as uncovered.

### F4 — Deletions and renames are provable
The proof only hashed files that still exist, so a committed deletion sat in the subject and in no
proof set — and "no entry" is indistinguishable from "never looked". Files are now typed records

NUL-delimited git command, so a path with a space, a quote or a newline survives. A deleted path
carries a TOMBSTONE — `base_sha256`, the hash it had before removal — and the packager counts a
tombstone as authoritative coverage. A rename carries `old_path` plus both hashes.

### F6 — Authoritative coverage understands directory arguments
The round-14 package carried `missing_tests_gate=NEEDS_TESTS` for T003, listing two test files as
uncovered that had just been run green. The mapper only collected tokens ending in `.py`, so

Directory arguments now resolve to the test files under them, and `--ignore=<path>` is honoured so
an excluded file is not counted as covered. A gate that cries wolf about a test that ran teaches
operators to ignore it.

### F7 — The commit chain is an artifact, not prose
`review_commit_chain.json` records the ordered, base-exclusive ancestry path to HEAD with each
commit's parents, tree, subject, changed files and patch hash. The package builder RECOMPUTES it
from the repository and holds the artifact to it: the chain must start after the declared base,
every commit must descend from the last, it must end at the review head, and it may touch no

### F1 — `do job-flow` works again
The shared `RunInvocation` removed the local `timeout_sec`; the timeout hint still read it, so the
public `do job-flow` command died with `NameError: timeout_sec is not defined` before printing
anything. 69 of its 168 tests were red and every Evidence gate was green (see F8).

The tempting repair — resolve a default back at the call site — is exactly what `RunInvocation`
exists to prevent: an omitted control must stay `None` all the way into `run_job`, where
explicit > persisted > product-default decides. So the hint asks the JobPlan what `run_job`
RESOLVED and recorded, after the fact, and says nothing when no execution config exists rather
than inventing a number. The hint stays informational and never changes execution.

The suite's catalog test fed the parser `--stream-evidence v --no-stream-evidence v` — both halves
of a mutually exclusive pair, each given a value neither accepts. It asserted the parser would
swallow an argv nobody can type. The parser is right; the test now builds a valid argv, every
option name is also checked individually, and F15 exclusivity is pinned explicitly.

### F2 — The task-status / expectation truth table
Round 12 stored both facts deliberately — what the episode expected of a task, and what the
JobPlan recorded about it — so a contradiction would stay VISIBLE rather than be normalized away.
Nothing ever compared them. A published reference could say `expectation=skipped` while recording
`task_status_at_finalization=applied_to_job_workspace`, and all four of `skipped` + {`pending`,
`applied_to_job_workspace`, `passed`, `failed`} validated and round-tripped through the writer.

`validate_task_expectation_truth()` is the one closed table, reached from typed validation,
CallExpectation validation, the writer's preflight and postcondition, the canonical loader,
recovery and the export. It is derived from `_collect_calls`'s real behaviour:

| expectation | allowed `task_status_at_finalization` | run |
|---|---|---|
| `skipped` | `skipped` only — skipping is decided before dispatch | none |
| `not_dispatched` | `pending` | none |
| `failed_pre_dispatch` | `failed`, `blocked` | none |
| `executed` | `passed`, `applied_to_job_workspace`, `running`, `pending`, `failed`, `blocked` | required |
| `prior_episode` | same as `executed` | required |
| `dispatched_no_calls` | `failed`, `blocked`, `pending`, `running` | required |

The permissive rows are load-bearing, not laziness. `executed` + `pending` is F011's mid-flight
stop (the call in flight finishes; the task waits at pending for a resume). `executed` + `blocked`
/ `failed` is production reaching a post-run gate — the completion gate, the target guard, the
workspace apply — AFTER a successful run. Forbidding those would refuse real records.
`dispatched_no_calls` cannot be `passed`/`applied`: both are only reachable through a finalized
call. No status is ever silently normalized into a different expectation.

Two fixtures encoded the bug and were corrected rather than worked around: the shared
`_zero_call_proof` omitted the status entirely, and the lifecycle fixture hardcoded
`applied_to_job_workspace` for EVERY expectation — asserting that `skipped` + applied was a valid
published record.

### F3 — Every commit-chain field is recomputed
The chain compared `commit`, `tree`, `patch_sha256` and `parents`, and ignored `chain_v`,
`subject` and `changed_files` — the two fields a human reader actually reads were narrative that
nothing checked. Reproduced: `subject` rewritten to "FORGED SUBJECT" and `changed_files` replaced
with `["fake.py"]`, and verification returned no problems at all. Every recorded field is now
recomputed; `changed_files` must be canonically sorted and duplicate-free; an unsupported
`chain_v` blocks.

### F4 — The packager recomputes the whole review subject
`review_subject.json` is the artifact that says WHAT is under review, and the final package
trusted it — the Evidence job's own account of its own work. A forged tombstone hash, a rewritten
rename origin, or a status flipped from `added` to `modified` travelled straight into a READY
package. The subject is now resolved again from the recorded base and compared record by record:
path, old_path, status, base_sha256, current_sha256 and kind.

### F5 — Typed path kinds: inspect, never follow
Dirty paths were hashed with `read_bytes()`, which FOLLOWS symlinks: `repo/link.txt ->
/tmp/outside.txt` put the outside file's bytes into the content proof, while the ZIP collector
(`find -type f`) never packaged the link at all. The proof described a file the package did not
contain, with content read from outside the repository — and both halves were silent.

`is_file()` answers "what does this point AT"; a review needs "what IS this". Every working-tree
path is now inspected with `lstat` and typed:

| kind | proof | authoritative? |
|---|---|---|
| `regular` | sha256 of its own bytes | yes |
| `symlink` (target inside the repo) | sha256 of its literal target TEXT + recorded `link_target` | yes |
| `symlink` (absolute, `~`, or escaping) | none — the target is not part of this review and is never read | BLOCKED |
| `deleted` | its base tombstone | yes |
| `directory`, `special` (FIFO/socket/device) | none | BLOCKED |

The escape rule is LEXICAL, per F010's binding clause: `resolve()` answers where a link points,
not whether the caller was routed through one, and resolving would touch the outside filesystem

Recorded honestly: `git status -u` does not report a bare FIFO, so that door never reaches the
subject at all. The reachable special-file case is a TRACKED file replaced by one, which git
reports as a modification — that is covered and blocked.

### F6 — The review base travels explicitly; the CWD is not a credential
Round 15's resolver read `REMEDY_REVIEW_BASE` itself and then asked whether the PROCESS CWD's
repository was the one it had been handed. That aimed at a real bug — an exported base reached a
pytest subprocess and cost an unrelated job its content proof — but it made the CWD an
authorization token, and tokens cut both ways:

    REMEDY_REVIEW_BASE is set, repo_root is the intended repository, CWD is elsewhere
    -> the declaration is silently discarded -> an EMPTY legacy subject, no error

The resolver now reads no environment and consults no CWD. `read_declared_base()` is the one
top-level reader; the CLI passes the value with the repository it belongs to; and
`child_env_without_declaration()` strips it from every verification child, so an unrelated job is
never handed a base at all — the round-15 bug is closed structurally rather than by guessing. A
declared base is always honoured and always verified: a base this repository never heard of, a
non-ancestral base, or a base in a non-git directory all raise. `_same_repository` is gone.

### F7 — The package ships the patch bytes it hashes
The chain recorded `patch_sha256` and shipped nothing to hash it against, so the one field that
says what a commit DID was the one field a ZIP-only reviewer — the only kind an external review
has — could not check. A package that requires the repository is not self-contained evidence.

Every base-exclusive commit now ships `evidence/current/review_commit_patches/<full-sha>.patch`
holding exactly the bytes whose sha256 the chain records, produced by ONE helper
(`commit_patch_bytes`) so the recorded hash, the packaged file and the packager's recomputation

extra, swapped or tampered patch; the file count must equal the commit count. Patch headers are
repo-relative, so no local absolute path enters the ZIP.

### F8 — Relevant regressions are part of authoritative verification
Round 15 changed `apps/cli/commands/do_cmd.py` and shipped a broken public command while every
Missing-Tests gate said PASS. Nothing lied; nothing was asked. The gate required a task's CHANGED

A task's related tests are now its changed test files PLUS the regression suites its changed

additions show up in diffs, following F017's builtin-deny-list precedent). Coverage was already

## Hardening round 17 (external FINDINGS — 10 items)

Round 16 restored the review-subject and packaging seams; round 17 makes the ten remaining
trust-chain checks exact — task truth by episode, and every file record typed end to end into the
archive.

### F1 — Task truth depends on the episode's status and phase
The round-16 shared validator took `episode_status` and `episode_phase` and never read them, so it
judged every task by one global status set — the STOPPED/worked baseline, which is the widest an

### F2 — A prior task's terminal status is frozen
The lifecycle chain froze a completed run's id, ledger ref and ledger hash — but not the STATUS it
finished under, so a later `prior_episode` record could keep the same run and ledger while
rewriting `applied_to_job_workspace` into `failed`. The status a task completed under is part of
what completed, and is now frozen with the rest.

### F2 (files) — One lossless typed merge of committed and dirty records
A path can be both committed (base..HEAD) and dirty (HEAD..working-tree). The inline union rebuilt
a bare `ReviewFileV1(path, status, base_sha256, current_sha256, old_path)` and dropped `kind`,
`link_target`, `base_kind` and the modes, so a dirty symlink over a committed regular file came
back a regular file and the package hashed it as one. `merge_review_file_state` is the one
lossless typed merge: current side from the dirty record, base side from the committed record,
never a dropped field, and a committed deletion is not silently resurrected.

### F3 — Committed file kinds and modes come from git
`_committed_records` defaulted every record to `kind=regular`, so a committed symlink was a regular
file and a mode-only 100644→100755 change was invisible. Kinds now come from the git tree modes
reported by `git diff --raw -z`; `ReviewFileV1` carries `base_kind`, `base_mode` and `current_mode`;
and a committed symlink's target is read from its git BLOB, never followed through the working tree.

### F4 — The content-proof check is typed and no-follow
`_check_bundle_integrity` used `os.path.isfile` + `open`, both of which follow symlinks — an
allowed contained symlink was hashed as its target's bytes, and a regular file swapped for a
symlink after the proof still verified. Each path is now inspected with `lstat` and hashed by its
declared kind: a regular file its own bytes, a symlink its literal target text, never the target.

### F5 — Dirty deletions and renames carry full base proofs
A dirty deletion recorded `base_sha256: null` (no tombstone), and a dirty staged rename lost its
old path and base hash. Both are resolved against the declared HEAD with git blob reads, never the
working tree: a deletion records the HEAD blob it removed and its base kind, a rename records old
path plus both hashes and both kinds.

### F6 — `do job-flow` forwards the review base
`do job-flow` called `export_job_evidence(job_id, evidence_out)` with no base, so a clean committed
feature branch exported through the full workflow lost its committed ReviewSubject entirely — the
export reads no ambient environment (round 16), so a base not passed is a base that does not exist.
The top-level command now reads the declaration once and forwards it, exactly as `do job-evidence`
does.

### F7 — Strict external ReviewSubject schema
The packager ignored unknown fields, `subject_v`, `link_target` rules and the embedded commit list.
A packager that ignores unknown fields would ship an injected `secret`/`path` field untouched.
`validate_review_subject_schema` is exact: closed field sets, closed enums, safe relative paths,
lowercase hashes, `link_target` required for symlinks and forbidden elsewhere; and
`review_subject.commits` must equal `review_commit_chain.commits`.

### F8 — The ZIP is built from an exact path-safe model
`find -print | sort | zip -@` is newline-delimited end to end, so a filename containing a newline is
silently truncated or dropped. `packages/orchestration/review_zip.py` builds the archive with
`zipfile` from an explicit list of validated relative POSIX paths discovered NUL-safely (`find
-print0`), preserving hostile-but-legal names (newline, tab, quote, leading dash, Unicode) exactly
and refusing names that change WHERE a member lands (absolute, `..`, empty/`.` segment, backslash,
NUL, duplicate). A repository symlink is recorded as its target text, never followed.

### F9 — Containment by path components
`resolved.startswith(root)` accepts a sibling `/root/repo-evil` for root `/root/repo`. `contained`
uses `os.path.commonpath` and resolves symlinks first, so a sibling, a different tree, or a
symlinked descendant that escapes the root is refused. The packager's cwd and evidence-dir checks
use it.

### F10 — Post-build membership verification
After the archive is written it is reopened and its exact member set and per-member hashes are
verified against the typed model: no authoritative path omitted, no unlisted path present, no
duplicate.

## Hardening round 18 (external FINDINGS — 7 items)

Round 17 typed each file record; round 18 makes the whole file-to-archive boundary one typed
transaction — the ReviewSubject drives the package, and the package is verified back against it.

### F1 — One typed ArchivePlanV1 drives the package
The package was assembled from two disagreeing sources: the typed ReviewSubject, and an
independent `find -type f` list. `find -type f` does not match symlinks, so a safe authoritative
symlink was ABSENT from the archive while the Content Proof (which knew it) and the ZIP
verification (which checked only the find list) both reported PASS. `archive_plan.py` introduces
`ArchivePlanV1`: every ReviewSubject file gets exactly one disposition — a regular member, a
symlink member, a tombstone, or a BLOCK — and the repository context files ride alongside as
explicitly non-authoritative members. A changed regular path the bundle policy excludes (a
`.env`, a key, a log) BLOCKS rather than silently vanishing; a symlink is exempt from that block
because `find` always skips symlinks. Bundle discovery is now `\( -type f -o -type l \)`, so a
context symlink is packaged as a symlink member even without a subject. The shell no longer
rediscovers authoritative paths.

### F2 — File type and mode are preserved
The builder hardcoded every regular member to `0o644`, so an executable `0755` and a mode-only
change were lost. The plan carries each member's kind and mode; a regular member is written with
its real `100644→0644` / `100755→0755` permission bits and the real `S_IFREG` file-type bits, a
symlink with the canonical `S_IFLNK` mode.

### F3 — File reads are atomically no-follow
The no-follow checks were not atomic: `lstat(path)` was followed by reopening `path` by NAME, so a
regular file swapped to an external symlink in the window was followed and outside bytes were
hashed or archived. `secure_fs.read_verified_file_at` (and `read_verified_relative`) is the one
shared primitive: it lstats, opens the regular case with `O_NOFOLLOW` relative to a held anchored
parent fd, and re-`fstat`s the open descriptor's `(dev, inode)` against the pre-open lstat, so a
swap changes the inode and is refused, never read. A symlink's target is read with `readlink`
relative to the same fd. It is used by dirty-content hashing, package-time Content-Proof
verification, and every repository ZIP member read; a race that swaps the path leaves the file
unproven (which blocks) rather than laundering outside content.

### F4 — The ReviewSubject schema is exact recursively
The schema validated the top-level fields and each file's path/status/kind/hashes, but not the
embedded commit list, and not the round-17 typed file fields. So `commits: [{"EXTRA_SECRET":
"/home/alice/..."}]` and `base_kind: "SECRET-/home/alice"`, `base_mode: "999999"`, `current_mode:
"evil-mode"` were all accepted — a known field with an arbitrary string is still a leak.
`validate_review_commit_schema` validates commit subobjects exactly; the file schema closes the
git-mode and base-kind vocabularies, checks status/kind/hash coherence, and runs the established
secret/path scanners over metadata strings. `decode_review_subject_from_json` is the strict typed
entry the packager drives the plan from.

### F5 — Every file field is recomputed
The packager's recompute key omitted `link_target`, `base_kind`, `base_mode` and `current_mode`,
so a symlink retyped as a regular file (matching path/status/hash) passed. The key is now the
complete `ReviewFileV1` record.

### F6 — Post-build verification validates typed metadata
`verify_review_zip` checked names, bodies and symlink text but never the member TYPE or mode, so a
regular entry containing the correct link text passed as a symlink. It now checks the exact name
multiset, the unix file type and permission bits from `external_attr`, the deterministic
timestamp, rejects directory entries, and holds the body (hash for a regular, target text for a
symlink) — a member's declared kind and mode must match what was written.

### F7 — Full make_review_zip integration is tested
The round-17 symlink tests proved the pieces could each handle a symlink; they did not prove that
`make_review_zip.sh` drives the plan builder. `test_review_package_full_integration.py` runs the
real packaging entry point on symlinks, executables, newline/Unicode names, special files and
external symlinks, asserting the package status and the exact, typed archive membership.

### Filename-byte policy
A NUL list is decoded with `surrogateescape`, so an undecodable byte path would have raised an
uncontrolled `UnicodeEncodeError` inside `zipfile`. Such a path is now refused by name, safely and
named, at build time.

## Hardening round 19 (external FINDINGS — 12 items, the closure block)

Round 18 built the typed ArchivePlan; round 19 closes the remaining parallel truths so the ZIP is
the honest, bounded projection of ONE authority set and ONE bundle-safety policy.

### F1 — Authority is passed explicitly; it is never inferred from subject membership
The ArchivePlan marked all 21 ReviewSubject files authoritative, re-authorizing the three `.agent`
operator-state files and disagreeing with the 18-file Content-Proof authority set. `build_archive_plan`
now takes an explicit `authoritative_paths` set — exactly the Content-Proof / final-verifier /
change-provenance file set — and a member is authoritative iff its path is in it. A member also
carries a `source_class` (`repository` / `evidence` / `generated_manifest` / `operator_context`)
kept distinct from authority, so `.agent/` state is operator context, never authoritative.

### F2 — The plan and its verification report are packaged and referenced
A ZIP-only reviewer could not verify the model the members were built from. `build_review_zip.py`
now packages `evidence/current/review_archive_plan.json` and
`evidence/current/review_zip_verification.json` as verified archive members, added to the plan
BEFORE the build (they carry no self-hash), and the `.review_zip_manifest.json` names both under
`current_evidence.review_archive`. The report is derived from the plan alone and the build ABORTS
unless the reopened archive matches the plan exactly, so a packaged report
always describes a verified archive.

> **Superseded by round 20.** The round-19 `review_zip_verification.json` was a pre-build
> EXPECTATION labelled as if it were a verification result. Round 20 renames it to
> `review_zip_expectation.json`, binds it into the directed hash chain
> (`review_archive_plan.json → review_zip_expectation.json → .review_zip_manifest.json`), and makes
> the ACTUAL reopen verification govern whether the ZIP is retained. See "Hardening round 20".

### F3 — A dirty working-tree mode change is captured
A dirty chmod `0644→0755` left `current_mode=""`, so the plan mapped it back to `0644` and lost the
mode change under review. The dirty resolver now records the current git mode from the
stability-checked read's own `fstat` (`100755` when the executable bit is set, else `100644`).

### F4 — The planned mode is bound to the bytes
A plan declaring `0755` succeeded over a `0644` source because the source mode was never compared.
`read_verified_file_at` takes an `expected_mode` and refuses a member whose executability differs
from the plan — the mode is bound to the opened descriptor, not merely written into ZIP metadata.

### F5 — A regular read is a stable same-inode read
A file modified in place during a multi-chunk read returned mixed old/new bytes with no error. The
reader re-`fstat`s the OPEN descriptor after the read and discards the bytes as a torn read if
`(dev, inode)`, type, mode, size, or `mtime/ctime` nanoseconds drifted, or the byte count disagrees
with the final size.

### F6 — Symlink target and containment are one atomic fact
A context symlink passed containment as a link pointing inside, then changed target before the
secure read. The symlink's escape check and subject match now run on the EXACT bytes returned by
the stability-checked no-follow reader, never a separate earlier realpath.

### F7 — Bundle safety is one policy, decided before any read
`is_attestable_source` conflated authority with whether bytes may enter the archive, so a
policy-excluded `.log`/`.zip` was not blocked. `classify_bundle_path` is the one bundle-safety
policy, decided from the path alone before any read: a changed secret/key/log/archive/binary is
`BLOCK_SENSITIVE`, `.agent/` is `OPERATOR_CONTEXT`, a deletion is a `TOMBSTONE`, an unrepresentable
kind is `BLOCK_UNSUPPORTED`, else `INCLUDE`. No later shell regex is the primary policy.

### F8 — The Evidence inventory is typed and no-follow
Evidence discovery and staging used `find -type f` and `cp`: `find -type f` silently SKIPS a
symlink, and `cp` FOLLOWS one into outside bytes. `evidence_inventory.py` walks the tree with
anchored `O_NOFOLLOW` reads through `stage_review_evidence.py`; a symlink, FIFO, socket, device, or
symlinked directory component anywhere in the tree BLOCKS the build (never skipped, never followed),
and every regular member is staged from the exact verified bytes the archive re-hashes.

### F9 — The ReviewSubject schema is coherent, not merely field-typed
The schema closed each field in isolation but accepted self-contradictory records. A
coherence matrix now rejects a modified/added regular file with no `current_sha256`, a deletion
with no `base_sha256` tombstone, a base symlink whose `base_mode` is `100644`, a copy with no `old_path`,
and a `type_changed` record whose base and current kinds are identical.

### F10 — The subject loader fails closed
`build_review_zip.py` caught every decode error and substituted an empty ReviewSubject, so a corrupt
or forged subject produced a context-only package that still reported success. Only an ENTIRELY
ABSENT `--subject-json` yields the legacy empty subject; a supplied-but-missing, invalid-JSON, or
schema-failing subject BLOCKS.

### F11 — Symlink permission bits are verified post-build
`verify_review_zip` never checked a symlink member's permission bits, so an `S_IFLNK|0644` could
pass a planned `0777` symlink. The reopen now checks the symlink's permission bits, the Unix
`create_system`, the compression method, and rejects encrypted members.

### F12 — The archive is bounded
Nothing capped per-member bytes, aggregate bytes, member count, or expansion ratio, and the reader
read every member fully into RAM. The build and the reopen now enforce a per-member 64 MiB cap, a
2 GiB aggregate cap, a 200x expansion-ratio bomb guard (above a 1 MiB floor), and member-count
limits — every limit checked before the dangerous allocation and reported as a safe block.

## Hardening round 20 (external FINDINGS — 10 items, the root-of-trust closure)

Round 19 packaged a typed plan and a report but left the ROOT of trust reachable: the manifest,
Subject and Proof were read from the original Evidence while the ZIP packaged staged copies; a

### The single sources
* **Byte source** — the immutable private staging snapshot. Evidence is anchored, inventoried

  Authority = its `file_hashes` keys + `tombstones`, and it must EQUAL the Final-Verifier

  immutable map.

`evidence_snapshot_inventory.json` records `relative_path/kind/mode/size/sha256/source_class` for

expected hash; a staged member changed after inventory blocks.

### F4 — Directed hash chain for generated artifacts
The CoreArchivePlan carries an expected hash for every source member; the expectation carries
`review_archive_plan_sha256` and the expected model; the manifest carries the plan, expectation,
subject, proof, commit-chain and patch-set shas and the exact generated-artifact paths. Generated
bytes are passed directly into the builder; none is reopened by path, so a plan/expectation/manifest
forged on disk after generation cannot reach the archive.

### F5 — Every ArchiveMember has an expected content identity
`snapshot_plan_members` reads every source member once and binds its bytes; the finalized plan fills
`content_sha256` / `link_target` for every member (authoritative, context, operator-state,

snapshot is never packaged, and a source disagreeing with its expected hash is refused.

### F6/F7 — One bundle policy, and the manifest read no-follow
`classify_bundle_path` governs EVERY repository member including unchanged context: a `.env`, key,
certificate, log or old archive handed in as context BLOCKS through an explicit typed disposition.
The manifest is read through the anchored no-follow reader (a symlinked manifest is refused) and
packaged from in-memory bytes.

### F8 — Complete ReviewFile state matrix
Every status is closed: an `added` needs a current mode and no old_path; a `modified`/`dirty`
existing file needs its complete base side; a dirty deletion is normalized to `deleted`; a
`deleted` carries base kind/mode and no current side; a `renamed`/`copied` names a different
old_path with full base+current facts; a `type_changed` actually changes kind or mode. Every
impossible shape fails strict decode.

### F9/F10 — Inventory-time limits and an honest verification artifact
The member-count and aggregate-byte limits are enforced DURING the snapshot walk, before the whole
tree is copied; the generated artifacts are bounded by a per-generated-member cap. The in-zip

the verifier version — it does not claim an unrecorded actual result; the output ZIP is retained
only after the actual reopen verification passes. Authoritative test counts (in
`verification_tests.json`) are kept distinct from diagnostic runs.

### Accepted residual risks

The PASS_WITH_RISKS verdict acknowledges these accepted residual risks that do not block
acceptance:

1. **Verification completeness is opt-in.** `validate_evidence_candidate` accepts
   `required_verification_suites=None` by default. A caller that omits the parameter gets no
   suite coverage check. This is intentional for generic callers but means a misconfigured
   pipeline could skip completeness enforcement.

2. **ProviderTokenEvidenceV1 has optional claims.** Some PE fields are allowed but not bound
   into canonical authority (e.g. `cli_versions`, supplementary cache metadata). A future
   schema revision should either bind every allowed field or reject unused ones.

3. **Publication tests assume O_TMPFILE support.** The anonymous-inode protocol requires
   `O_TMPFILE` and `linkat(AT_EMPTY_PATH)`. On filesystems without these (certain NFS mounts,
   older kernels), tests may skip rather than fail. The capability probe detects this at
   runtime but tests do not exercise the degraded path.
