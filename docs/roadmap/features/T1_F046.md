# T1_F046 — Multi-cycle loop
**Tier 1 · Depends on: F018, F011, F006 · Blocks/used by: F047-F052, F070**

## Goal & Done
Remedy can work in bounded CYCLES instead of a single pass: plan-delta →
execute a batch of ready tasks → verify → persist, repeated until all
green, a budget hits, a deadline passes, or an operator stops it. DONE
when a five-cycle fixture run terminates with the correct terminal status
for every stop cause, each cycle leaves its own evidence, and — the
rollout rule — the DEFAULT remains one cycle until the milestone gate
(F075) passes.

## How it fits (inspect current shape before building)
Everything a cycle needs already exists as parts: the task runner executes
one task with rollback-on-failure semantics; the safe-point module answers
should-stop (operator + budgets in one check); worktrees isolate changes;
the storage layer persists jobs atomically; postmortems classify failures.
This feature is the CONDUCTOR that sequences those parts — it must not
reimplement any of them (A6). Inspect the current caller that drives
single-pass execution and grow it (or wrap it) rather than building a
parallel executor.

## Design (suggested shape)
Module `long_run_executor.py`:
- `run_cycles(job, limits, provider_call)`: loop { check should_stop →
  determine the ready task batch (linear order now; DAG scheduling refines
  the ready set later) → execute up to a configured batch size → run the
  verify step (tests) → persist job + cycle summary } until a terminal
  condition.
- Terminal statuses (write on the job + ledger event): all_green,
  stopped_by_operator, budget_exhausted, deadline_reached, blocked (every
  remaining task failed or awaits a decision). Each maps to the matching
  postmortem/stop machinery already built — no new persistence paths.
- Cycle evidence: a per-cycle summary record (cycle index, tasks
  attempted/completed/failed, verify result, tokens so far) appended under
  the job's evidence area — the report feature renders these later.
- Config: a cycles table — max_cycles (DEFAULT 1 — the rollout rule; the
  gate feature flips it via an explicit config change with an ADR),
  batch_size, and a per-cycle verify command override.
- CLI: `remedy job run <id> [--cycles N]` (flag beats config, both capped
  by the safety default until the gate) reusing the existing run/do entry
  points.

## Task slicing
- **T001** the loop skeleton + terminal-status matrix + a fake-provider
  five-cycle fixture proving each stop cause (operator stop injected,
  budget, deadline via injected clock, all-green, blocked).
- **T002** cycle evidence records + CLI flags + config keys + tests; a
  regression test proving default behavior is byte-identical to today's
  single pass when max_cycles is 1.

## Acceptance
- Each terminal status reachable and correct in tests; job state and
  ledger agree with the postmortem class where applicable.
- A cycle never starts after should_stop says stop (ordering test).
- Evidence: N cycles → exactly N summary records, monotonically indexed.
- With defaults, existing single-pass tests stay green unmodified.

## Edge cases & assumption defaults (A9)
- Zero ready tasks but job not green (all blocked) → terminal blocked,
  never a busy spin. Verify step failing repeatedly is handled by the
  self-healing feature later — here a failed verify simply ends the cycle
  with its failure recorded. Batch size larger than remaining tasks is
  fine.

## Orchestrator brief
Gate this feature on the kill switch and budgets being merged. T001 is
one substantial order — include the terminal-status table verbatim in the
worker prompt and demand one test per row before accepting.

## Do not touch
Task-level execution semantics, retry policy, checkpoint depth (next
feature), DAG readiness (later feature). Suggested tests:
tests/orchestration/test_long_run_executor.py.
