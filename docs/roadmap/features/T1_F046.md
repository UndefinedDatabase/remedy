# T1_F046 — Multi-cycle loop
**Tier 1 · Depends on: F018, F011, F006 · Blocks/used by: F047-F052, F070**

## Goal & Done
Remedy can work in bounded CYCLES instead of a single pass: plan-delta →
execute a batch of ready tasks → verify → persist, repeated until all
green, a budget hits, a deadline passes, or an operator stops it. DONE
when a five-cycle fixture run terminates with the correct terminal status
for every stop cause, each cycle leaves its own evidence, and — the
rollout rule — the DEFAULT remains one cycle until the milestone gate
(F075) passes.

## How it fits (inspect current shape before building)
Everything a cycle needs already exists as parts: the task runner executes
one task with rollback-on-failure semantics; the safe-point module answers
should-stop (operator + budgets in one check); worktrees isolate changes;
the storage layer persists jobs atomically; postmortems classify failures.
This feature is the CONDUCTOR that sequences those parts — it must not
reimplement any of them (A6). Inspect the current caller that drives
single-pass execution and grow it (or wrap it) rather than building a
parallel executor.

## Design (suggested shape)
Module `long_run_executor.py`:
- `run_cycles(job, limits, provider_call)`: loop { check should_stop →
  determine the ready task batch (linear order now; DAG scheduling refines
  the ready set later) → execute up to a configured batch size → run the
  verify step (tests) → persist job + cycle summary } until a terminal
  condition.
- Terminal statuses (write on the job + ledger event): all_green,
  stopped_by_operator, budget_exhausted, deadline_reached, blocked (every
  remaining task failed or awaits a decision). Each maps to the matching
  postmortem/stop machinery already built — no new persistence paths.
- Cycle evidence: a per-cycle summary record (cycle index, tasks
  attempted/completed/failed, verify result, tokens so far) appended under
  the job's evidence area — the report feature renders these later.
- Config: a cycles table — max_cycles (DEFAULT 1 — the rollout rule; the
  gate feature flips it via an explicit config change with an ADR),
  batch_size, and a per-cycle verify command override.
- CLI: `remedy job run <id> [--cycles N]` (flag beats config, both capped
  by the safety default until the gate) reusing the existing run/do entry
  points.

## Task slicing
- **T001** the loop skeleton + terminal-status matrix + a fake-provider
  five-cycle fixture proving each stop cause (operator stop injected,
  budget, deadline via injected clock, all-green, blocked).
- **T002** cycle evidence records + CLI flags + config keys + tests; a
  regression test proving default behavior is byte-identical to today's
  single pass when max_cycles is 1.

## Acceptance
- Each terminal status reachable and correct in tests; job state and
  ledger agree with the postmortem class where applicable.
- A cycle never starts after should_stop says stop (ordering test).
- Evidence: N cycles → exactly N summary records, monotonically indexed.
- With defaults, existing single-pass tests stay green unmodified.

## Edge cases & assumption defaults (A9)
- Zero ready tasks but job not green (all blocked) → terminal blocked,
  never a busy spin. Verify step failing repeatedly is handled by the
  self-healing feature later — here a failed verify simply ends the cycle
  with its failure recorded. Batch size larger than remaining tasks is
  fine.

## Do not touch

## Built State (2026-07-26)

What exists, as proven by the tests named below. Nothing here claims
behavior beyond what those tests exercise.

**The conductor.** `packages/orchestration/long_run_executor.py` —
`run_cycles(job, limits, provider_call)` runs bounded cycles of
`should_stop → ready batch → execute → verify → persist`. It is a conductor
only: `safe_points.should_stop` answers the safe point (operator stop and
budgets in ONE evaluation), `task_runner.run_next_task` executes a task and
keeps its own rollback semantics, `verifier.verify_task_output` +
`finalize_task` gate completion, and `storage.save_job` persists — no new
persistence path, no parallel executor. Readiness is LINEAR (PENDING tasks
in `job.tasks` order); DAG readiness stays a later feature. Nothing sleeps:
wall clock and deadline evaluation go through an injected `clock`, which is
what makes `deadline_reached` provable in a unit test.

**Seams.** `task_step`, `verify`, `clock`, `save`, `log` and
`control_root_path` are injectable and all default to the production path.
`default_task_step` is exactly the sequence `remedy job run-next` performs.

**Terminal statuses.** Five from this file's matrix plus a sixth,
`max_cycles_reached`, for the cycle budget running out with work still
pending (rationale in `.agent/decisions.md`, accepted by the round-1
verdict as a documented scope addition):

| terminal status | pingpong_job status | core RunState | trigger |
|---|---|---|---|
| `all_green` | `completed` | COMPLETED | every task COMPLETED, verify did not fail |
| `stopped_by_operator` | `stopped` | PAUSED | safe point reports an operator stop |
| `budget_exhausted` | `stopped` | PAUSED | safe point reports a budget limit hit |
| `deadline_reached` | `stopped` | PAUSED | `first_exhausted_limit == deadline` |
| `blocked` | `blocked` | PAUSED | zero ready tasks and not green — terminal, no spin |
| `max_cycles_reached` | `running` | (untouched) | cycle budget spent, work still pending |

`RunState` has no BLOCKED member, so the pingpong string is authoritative:
it is written to `job.metadata["cycle_terminal_status"]` /
`["cycle_job_status"]` and emitted as the `cycle_loop_terminal` ledger
event, alongside `cycle_completed` per cycle. `blocked` maps to PAUSED, not
FAILED — "no ready task, not green" also covers a job awaiting a decision,
which must stay resumable.

**Cycle evidence.** Each cycle writes one record (cycle index, tasks
attempted/completed/failed, verify result, verify command, tokens so far,
start/end) under the job's existing evidence area via
`pingpong_job.job_evidence_dir` — no second evidence convention. N cycles
produce exactly N monotonically indexed `cycle_NNNN.json` files. An
evidence write that fails is recorded as `cycle_evidence_error` on the job
and never aborts execution that already happened.

**Config and CLI.** `cycles.max_cycles` (DEFAULT 1), `cycles.batch_size`,
`cycles.verify_command` join the config registry and the remedy.toml doc.
`remedy job run <id> [--cycles N]` is registered in the command catalog.
The rollout cap lives in the CALLER, not the loop: `CYCLE_SAFETY_CAP = 1`
trims BOTH the flag and the config value until the F075 milestone gate
raises it, and a trimmed value is reported with its origin named rather
than silently honored — `run_cycles` itself honors `limits.max_cycles`
verbatim so the five-cycle fixture can drive it. While the resolved count
is one, the command delegates to `_cmd_run_next_task_local` verbatim, so
single-cycle CLI behavior IS today's single pass by construction.

**Honesty rules baked in.** A cycle that ran no verification records
`not_run`, never a pass; `tokens_so_far` reports only measured tokens
(unmeasured provider calls are counted as unmeasured, never as a token
total); a job with zero tasks is `blocked`, never green.

**Regression contract (stated, not implied).** With defaults
(`max_cycles=1`) `run_cycles` reproduces the single pass and adds exactly
two metadata keys plus one cycle evidence record; the regression test
asserts that this additive trace is the ONLY delta. At CLI level there is
no delta at all, because one cycle delegates to the existing entry point.

**Carried risks.** (1) The conductor writes no postmortem record itself —
stopped/budget classes derive at evidence export from the job status it
sets; revisit if F053 reporting needs per-terminal postmortems. (2) The
multi-cycle CLI branch is unreachable in production while
`CYCLE_SAFETY_CAP == 1`; it is exercised in tests with the cap raised,
simulating post-F075. (3) Full-suite nondeterminism is pre-existing and
tracked as F135/F052.

**Not built.** DAG readiness, retry policy, checkpoint depth, self-healing
verify rounds and per-cycle plan deltas — all owned by later features and
explicitly out of this file's scope.
