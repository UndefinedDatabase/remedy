# T2_F086 — Release capability
**Tier 2 · Depends on: F083 · Blocks/used by: distributability, F215 later**

## Goal & Done
Remedy ships like a normal tool: `pip install` yields the `remedy` CLI
with the UI assets bundled, `remedy --version` reports version and build
info, and a release is gated by CI plus a semver/changelog discipline.
DONE when a wheel built from a clean checkout installs into a fresh
virtualenv where the golden path and the UI serve work, the version
command matches the tag, and a release with a missing changelog entry is
refused by the gate.

## How it fits (inspect current shape before building)
Packaging metadata exists in some form (inspect the current pyproject
and entrypoint wiring); the UI is a built asset directory the serve
command already locates — the packaging question is making that lookup
work from an installed wheel as well as from a checkout (a resource-path
resolution with both modes, tested both ways). CI (previous feature) is
the gate host: the release stage extends it.

## Design (suggested shape)
- Packaging: single wheel, console entrypoint `remedy`, UI build output
  included as package data; a build step ensures the UI is built before
  the wheel (fail loudly if assets are missing — never ship a wheel with
  an empty UI directory silently).
- Version single-source: one version declaration; `remedy --version`
  prints version, git sha (embedded at build), python, platform.
- Release gate (CI stage `release`, manual trigger): full CI green +
  tag matches the version + changelog contains a section for it +
  wheel-size budget; output is the wheel artifact and a checksummed
  file list — publishing to an index stays a HUMAN command in v1 (P2;
  automation later).
- Changelog discipline: keep-a-changelog style; the gate parses only
  enough to verify the section exists and is non-empty.
- Install smoke: a scripted test creating a fresh venv, installing the
  wheel, running init + do on a fixture repo and probing the served UI.

## Task slicing
- **T001** packaging + asset bundling + dual-mode asset resolution +
  the install smoke (subprocess marker).
- **T002** version single-sourcing + build-info embedding + tests
  (checkout mode reports "dev" honestly).
- **T003** the release CI stage + changelog/tag gate + wheel budget +
  seeded-failure tests (missing changelog → refused).

## Acceptance
- Fresh-venv smoke passes: CLI on PATH, golden path works, UI serves
  from bundled assets. `remedy --version` output golden in both modes.
  The gate refuses on: red CI, tag/version mismatch, missing changelog
  section, budget breach — one test each.

## Edge cases & assumption defaults (A9)
- Source installs without the UI toolchain: the wheel always carries
  prebuilt assets; building FROM SOURCE without them degrades the serve
  command with the honest "UI assets not built" message that likely
  already exists — verify and keep. Data directory location is
  unaffected by install mode (it derives from the repo/config, not the
  package).

## Orchestrator brief
T001 is the substance; require the dual-mode resolution test in the
same order. Keep publishing manual — reject automation of the final
upload in this feature.

## Do not touch
Auto-publishing, installers beyond pip, update mechanisms, license
choice (human decision). Suggested tests: tests/test_packaging_smoke.py.

  reason to refuse a release, `scripts/release_gate_check.py` observes a real

  manual trigger. Publishing stays a human command, as the brief requires.

`.github/workflows/release.yml` has never been dispatched. Both are human
actions, and DECISION F086 D4 records the first with its measurement.
