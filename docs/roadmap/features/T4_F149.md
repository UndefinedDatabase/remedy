## Goal & Done
A brownfield repo becomes known territory in one command: `remedy
study` runs a NORMAL job (visible in the graph like any work) whose
pipeline scans structure, detects conventions, assesses test/CI
state, flags risk hotspots and inventories UI components — emitting
card CANDIDATES (origin=study, every one evidence-referenced) plus a
pre-filled dossier-card proposal, presented in the collection UI as
a staggered "card draw" reveal. DONE when a fixture brownfield repo
yields the expected candidate set with resolvable refs, everything
flows through the standard proposal gate (nothing self-activates),
--limit ranks by evidence strength, and the reveal animation follows
the design reference's restraint rule (the reveal is information,
not a slot machine).

## How it fits (inspect current shape before building)
Study is COMPOSITION as a job: the scanners are deterministic
analyzers (the context compiler's import graphs and signature
extractors, the miners' ignore conventions, churn from git history
via the existing git helper) plus bounded side-role LLM phrasing for
convention detection where pure rules end — each phase a plan task,
so progress, evidence, budgets and the graph all work for free;
candidates flow through the harvest kind (origin study). The
dossier proposal pre-fills the F122 template from the scan (stack,
structure, commands from manifests/CI files) — proposed, human-
approved, as always.

## Design (suggested shape)
- Pipeline tasks: structure_scan (modules, entry points, manifests
  → architecture/component candidates), convention_detection
  (deterministic signals first: naming distributions, layout
  patterns; one phrasing call to draft convention cards from them —
  signals cited), test_ci_state (test-file coverage per module,
  CI config presence → lesson/risk candidates for gaps),
  risk_hotspots (churn × complexity heuristic — commit-count ×
  size/AST-depth per file, thresholds config → risk cards citing
  the metric values), ui_inventory (component files per the
  frontend conventions → component candidates).
- Every candidate: typed evidence refs (file#location or
  metric-typed with the numbers) — the provenance resolver verifies
  at creation as everywhere.
- `--limit N`: rank candidates by evidence strength (metric-backed
  > multi-signal > single-signal; documented ordering) before
  proposing.
- The card draw: in the collection UI, freshly proposed study
  candidates render as a staggered reveal (250 ms stagger, the
  design reference's subtle motion tokens) in a "proposed from
  study" tray with approve/deny per tile — CLI equivalent lists
  the same ranked set (UI-optional, as ever).

## Task slicing
- **T001** the deterministic scanners (one small order each,
  fixture repos per scanner, metrics golden).
- **T002** the study job assembly (plan template, phases as tasks,
  budgets) + candidate emission through the gate + --limit ranking
  + the dossier pre-fill proposal.
- **T003** the reveal tray in the collection UI (design-conformant,
  fixture-driven) + CLI listing parity + the brownfield end-to-end
  (fixture repo → expected candidates → approve subset → cards
  active, dossier proposal pre-filled).

## Acceptance
- Per-scanner goldens on fixtures (hotspot numbers exact).
  End-to-end candidate set matches; refs resolve; nothing activates
  without approval; --limit ordering golden. The reveal renders per
  design (motion tokens only); CLI parity holds. Study on an empty
  repo degrades honestly ("little to study — N candidates").

## Edge cases & assumption defaults (A9)
- Huge repos: scanners respect scope/ignore conventions and a
  per-scanner file cap with the truncation reported in the study
  report (a normal job report — it lists what was scanned).
  Re-study: candidates duplicating ACTIVE cards suppress (the
  harvest rule); the study report says how many.
