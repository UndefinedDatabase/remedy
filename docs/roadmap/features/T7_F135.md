# T7_F135 — Flaky detector
**Tier 7 · Depends on: F061 · Blocks/used by: suite trust**

## Goal & Done
Flaky tests stop eroding trust silently: result history AT EQUAL
SHA detects alternation (same code, different verdicts), flagged
tests get a quarantine marker plus a fix idea through the queue,
and quarantined tests keep RUNNING non-blocking while staying
visible in every report. DONE when a seeded flaky fixture is
detected from history (the equal-SHA rule enforced — different-SHA
changes never count), quarantine is an explicit reviewed marker
change (never automatic mutation of the test tree), the
non-blocking-but-visible rendering appears in DoD rows and
reports, and de-quarantine requires demonstrated stability
(a documented streak).

## How it fits (inspect current shape before building)
Test results per run exist in verify evidence — the detector needs
per-test identity + verdict + the worktree SHA per run: verify
what the current test-execution evidence records (the digest work
from the regression guard already pushed toward per-test identity
— reuse/extend that record, one format). History accumulates
per project under the data root (append-only, the bench pattern).
Detection is pure: per test id, group runs by SHA; alternating
verdicts within a SHA group ≥ the threshold → flaky candidate.
Quarantine = the marker convention (a pytest marker the CI stance
already anticipated: "quarantined only via explicit marker change
in a reviewed diff") — the detector PROPOSES the diff (idea kind
test_gap sibling: flaky_fix, with the history refs), humans merge.

## Design (suggested shape)
- History: {test_id, sha, verdict, run_ref, ts} appended at verify
  completion; bounded retention (config window).
- `flaky_detector.py`: candidates = tests with mixed verdicts at
  equal SHA (threshold: ≥2 alternations across ≥3 runs, config);
  output per candidate {test_id, evidence runs, alternation
  pattern} — pure, goldenable.
- Proposal: one idea per candidate (dedup by test id via the
  queue's hash) with the proposed marker diff + the fix framing
  ("stabilize or quarantine"); approval paths: a stabilization
  job, or the quarantine marker merge.
- Quarantined behavior: the verify step runs them, records
  verdicts (history continues — recovery needs data), excludes
  them from blocking; DoD/report render a standing "quarantined:
  N tests (list)" section — visible every run, the nagging is the
  feature.
- De-quarantine: a stability streak at equal-and-then-changing
  SHAs (documented: K consecutive passes across ≥2 SHAs) → a
  removal proposal through the same path.

## Task slicing
- **T001** history recording (identity/SHA verification or the
  additive extension) + the pure detector + table tests
  (alternation at equal SHA; changes across SHAs ignored;
  thresholds).
- **T002** proposals + marker-diff drafting + queue dedup +
  fixtures.
- **T003** quarantined run semantics (non-blocking, recorded,
  rendered) + de-quarantine streak + the end-to-end (seeded flaky
  → detected → quarantine merged → visible + non-blocking →
  stabilized → removal proposed).

## Acceptance
- Detector table exact (the equal-SHA discipline proven by the
  cross-SHA negative). Nothing mutates tests without a merged
  proposal (state diff). Quarantined tests run and render every
  report (grep the section). Streak rule exact.

## Edge cases & assumption defaults (A9)
- Order-dependent flakiness (passes alone, fails in suite): the
  history records suite context where available; v1 detects
  alternation regardless of cause — diagnosis is the fix job's
  work, stated. Parametrized tests: identity includes parameters
  (the id format documented).
