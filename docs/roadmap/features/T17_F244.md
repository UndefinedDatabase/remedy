# T17_F244 — Security self-audit routine
**Tier 17 · Depends on: F045, F131, F134, F139 · Blocks/used by: permanent self-hardening**

## Goal & Done
See ROADMAP.md F244; the Done criterion there is binding.

## Context (existing code & prior features)
F134 and F131 examine JOB diffs; Remedy's own codebase gets no periodic examination.

## Design
A routine loop security_self_audit.toml (the F045 library): scope = the Remedy repo itself; steps: (1) an F134 full scan of the codebase (not just diffs) with a curated ruleset, (2) a dependency audit (pip-audit/npm audit, high+), (3) an F131 red review over the 3 most-changed core modules (F139 churn selects them), (4) config hardening checks (a doctor security section: token strength, open ports, active sandbox profiles). Output: proven findings as ideas/decisions (the F063/F066 proof duty); the history renders as an F142 tile 'self-audit'.

## Task slicing
T001 the loop definition + steps 1/2 + queue wiring + tests. T002 steps 3/4 + the tile + a fixture (an injected vulnerability in a test branch is found and correctly proven).

## Acceptance & tests
The fixture vulnerability yields exactly one proven idea with its location; the loop has proposal-only side effects (the F065 assertion pattern); the tile links its history.

## Risks / anti-goals
No auto-fixing of security findings (humans prioritize - especially here); ruleset upkeep is documented (a false-positive budget like F134).
