# T11_F191 — Migration safety
**Tier 11 · Depends on: F190, F017 · Blocks/used by: database jobs become sellable**

## Goal & Done
See ROADMAP.md F191; the Done criterion there is binding.

## Context (existing code & prior features)
F017 can fence schema_migration entirely; a proving ritual for PERMITTED migrations is missing.

## Design
Detection: migration files in the diff (alembic/prisma/raw-sql conventions per project config). The ritual in an F190 environment with fixture data: apply up -> structure + row digest comparison (tables/columns/counts, sampled hashes) -> apply down -> digest equals the start? A loss detector: an up dropping columns/tables without a documented backfill step -> a destructive_migration decision (triple: proof=the diff, downside=data loss). No down migration -> a mandatory decision.

## Task slicing
T001 detection per toolchain + the ritual runner + digest comparison + tests. T002 the loss detector + the decision path + fixtures (clean / lossy / no-down).

## Acceptance & tests
The lossy fixture blocks with a precise finding (table/column); the clean one runs frictionless; the down round-trip digest is bit-equal.

## Risks / anti-goals
Fixture data is synthetic - production data is never touched (a hard rule in docs plus an environment isolation test).
