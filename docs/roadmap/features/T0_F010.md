# T0_F010 — Automatic failure post-mortems
**Tier 0 · Depends on: none · Blocks/used by: F052, F073, F144, honest stats**

## Goal & Done
Every failed provider call, task, or run leaves a machine-readable
`postmortem.json` with a deterministic failure class, and `remedy stats
failures` aggregates them. DONE when all failure paths emit exactly one
postmortem per final failure, the classifier is a pure function (same input
→ same class), aggregation works on a fixture corpus, and the default path
makes zero LLM calls.

## How it fits (inspect current shape before building)
The raw failure signals already exist inside the provider ping-pong loop:
an error-class field for parse/config failures, retry-reason evidence from
the adaptive-timeout feature, terminal loop outcomes (provider unavailable,
tests failed, review failed), and one evidence directory per provider call.
The worktree layer raises typed conflict/lock errors; the runtime harness
reports probe failures. The event ledger is file/JSON based — do NOT
introduce a database here (a SQLite ledger arrives much later as its own
feature). Postmortems are written into the per-call evidence directories
that already exist; find the exact field names and the retry/timeout
predicate in the current code and reuse them instead of re-deriving.

## Design (suggested shape — follow existing conventions where they differ)
A new orchestration module `failure_postmortem.py`:
- `FailureClass` str-enum: provider_timeout, provider_unavailable,
  provider_nonzero_exit, parse, config, test_failed, review_failed,
  worktree_conflict, worktree_lock, runtime_probe_failed, stopped (reserved
  for the kill switch), budget_exhausted (reserved for budgets), unknown.
  The enum is extensible; later features add members instead of new enums.
- `PostmortemV1` record: postmortem_v=1, failure_class, job/task ids,
  which signal produced the class (signal_source), a truncated raw reason,
  retry evidence carried over, UTC timestamp, and relative evidence_refs
  into the call directory. Written atomically.
- `classify(...)` pure, with a documented precedence: typed exception >
  terminal loop signal > error-class field > retry reasons > unknown. The
  timeout predicate must be THE one the retry policy already uses — import
  or extract it, never copy the string match.
- Wiring: wherever a call/round is abandoned as failed, classify + write
  into that call's directory. Where a task fails terminally, write a
  task-level rollup under the job's evidence export area referencing the
  call-level files. Retried-then-recovered calls get NO postmortem.
- CLI `remedy stats failures [--since] [--job] [--json]`: histogram by
  class + top reasons; registered like the existing stats-style commands.
- Config key `postmortem.llm_summary`, default false — v1 stays fully
  deterministic (P6: no generated prose posing as analysis).

## Task slicing
- **T001** classifier + record + writer + shared timeout predicate;
  table-driven tests covering every class; unknown is returned, never
  raised.
- **T002** wiring at the failure exits + task rollup; integration test
  forcing timeout exhaustion asserts exactly one postmortem with correct
  class and evidence refs; recovered-retry negative test.
- **T003** CLI + fixture corpus + stable `--json`; empty corpus prints an
  honest "no failures recorded", not an error.

## Acceptance
- One forced failure per source (timeout, missing provider binary, invalid
  JSON against a schema, worktree lock, dead runtime probe) → correct class.
- Aggregation over the fixture corpus yields exact expected counts.
- No new dependencies, no database, no LLM call under default config.
- Runs predating this feature: stats prints a coverage line
  ("N scanned, M without postmortems") instead of failing silently.

## Edge cases & assumption defaults (A9)
- Contradictory inputs to classify → precedence order wins; signal_source
  records which. Multiple failures in one round → one postmortem per failed
  call plus one rollup. Read-only evidence dir → raise clearly, never drop.

## Orchestrator brief
Before dispatching T002, have the worker report back the actual names of
the loop's error/outcome fields and the retry predicate location; adjust
prompts to those names. Slice as listed; T001 is pure-unit and safe to run
first and in parallel with nothing.

## Do not touch
Retry POLICY (owned by the timeout feature), evidence layout, run states,
ledger schema. Suggested tests: tests/orchestration/test_failure_postmortem.py,
tests/cli/test_failure_cmd.py.

## Built state (v1 — pending external acceptance)
Status `[~]`: implemented on `feature/f010-failure-postmortems`, not yet accepted.

**Classifier precedence** (`packages/orchestration/failure_postmortem.py::classify`, pure):
typed exception → explicit terminal loop/task signal → structured `error_class` → error text
through F001's SHARED predicates → retry reasons → `unknown`. `signal_source` always names
the winning link, so contradictory inputs are explained rather than argued about. An unknown
combination is RETURNED, never raised. A reviewer verdict such as `needs_repair` is a normal
rejection and is never turned into a transport failure.

**Shared timeout predicate**: `provider_timeouts.is_timeout_error()` /
`is_nonzero_exit_error()` were extracted verbatim from the retry path; `_call_with_retry`
and the F010 classifier both import them. Timeout profiles, values, retry count, backoff
and the retryable/non-retryable policy are unchanged.

**Record** (`PostmortemV1`, `postmortem_v=1`): failure_class, signal_source, scope
(`call` | `task` | `job`), job/task/run/call ids, role, provider, terminal_status, truncated
`raw_reason` (2000 chars + marker), retries_used, retry_reasons, relative `evidence_refs`,
UTC `created_at`. Absolute paths and `..` are rejected on serialization.

**Exactly-once**: one logical provider call = one `_call_with_retry` cycle. A recovered
transport retry and a recovered reviewer parse retry write NOTHING. A call the loop
abandons writes exactly one `postmortem.json` — in the provider's existing per-call stream
directory when it has one, otherwise in `runs/<run_id>/calls/<role>/round-NN/<kind>/`.
Re-writing the identical record is idempotent; a DIFFERENT record at the same path raises
`PostmortemConflictError` and never overwrites the only account of the first failure.

**Task rollup**: the evidence export writes one `task_runs/<task_id>/postmortem.json` for a
task that ended `failed`/`blocked`, copies that run's call-level records into
`task_runs/<task_id>/call_postmortems/…` and references them relatively — so everything is
inside the bundle, the content proofs and the review ZIP without relaxing any gate.

**CLI**: `remedy stats failures [--job <ID>] [--since <ISO-8601>] [--json]` — read-only,
file-based (`failure_stats.py`), no database. JSON contract: `version`, `filters`,
`total_postmortems`, `counts_by_class`, `counts_by_scope`, bounded deterministic
`top_reasons`, `coverage` (jobs/tasks scanned, tasks without post-mortems, malformed,
unsupported version), `warnings`. The three scopes — `call`, `task` and `job` — are counted
separately, so a rollup and the calls it points at are never one number, and a job that
failed before any task ran is not filed under a task that never started. An empty corpus prints
"No failures recorded." and exits 0; an unreadable evidence root is an error, never
"no failures".

**Coverage**: pre-F010 runs are visible — "Coverage: N scanned, M without postmortems".

**Config**: `postmortem.llm_summary` (`REMEDY_POSTMORTEM_LLM_SUMMARY`, bool, default
false). v1 makes zero provider calls; no summarizer exists.

**Reserved**: `stopped` (F011) and `budget_exhausted` (F018) are classifiable and wired to
nothing.

## Hardening round (external FINDINGS on `remedy-review-20260713-214321`)
- **Streamed call records reach the bundle.** `collect_task_call_postmortems()` is the one
  collector and knows BOTH real source layouts — `pingpong_runs/<run>/calls/...` and
  `jobs/<job>/evidence/task_runs/<task>/streams/<role>/round-NN/<kind>-II/`. The export
  copies each record once into the canonical
  `task_runs/<task>/call_postmortems/<layout>/postmortem.json`, the rollup references
  exactly those, and stats counts ONLY the canonical copy (the streamed source copy is the
  same record; counting both would double every streamed failure). Duplicate layouts with
  different content raise `PostmortemConflictError` instead of one silently winning.
- **Job-scope records.** A job that fails in `_acquire_job_workspace()` — a worktree lock,
  a conflict — never reaches a task. It now writes a `scope="job"` record into the job's
  evidence directory (typed exception intact, so the class is right), the export preserves
  it at the bundle root, and stats counts it in its own scope. No pending task is blamed.
- **Write failures are durable and BLOCKING.** `postmortem_paths` (run-relative) and
  `postmortem_error` travel in the exported run JSON; the export writes
  `postmortem_integrity.json`, and a non-empty `failures` list makes the final verifier
  BLOCKED. A bundle that lost the only account of a failure cannot present clean gates.
  The original provider/task failure is never replaced by the recording failure.
- **Writer containment.** Production callers pass a trusted root; the destination must
  resolve inside it through no symlink (directory, parent component or final target).
  Publication is create-only (`os.link`), not `os.replace`: a concurrent DIFFERENT record
  conflicts instead of overwriting; an identical one is idempotent. The temp file is
  unpredictable, exclusively created, `O_NOFOLLOW`, written in full, fsynced, and removed
  on every error.
- **Read-only detection is uid-independent.** `os.access` tells root a 0o500 directory is
  writable; the writer reads the declared mode bits instead, so the contract holds on a
  root review host.
- **The real Claude timeout wording** (`claude CLI timed out after 600s`) is recognised by
  THE shared predicate, so F001 retries it and F010 classifies it as `provider_timeout`.
  Profiles, values, retry count and backoff are unchanged — only the recognition was wrong,
  and it was wrong in both places at once.
- **The target-guard exemption is strict.** Only a data root that lives strictly INSIDE the
  repository exempts anything, and only what is under it. A data root equal to the repo, an
  ancestor of it, a sibling, or a symlink out of the tree exempts nothing.

## Second hardening round (external FINDINGS on `remedy-review-20260713-220339`)
- **The writer validates before it mutates.** Nothing is created until the destination is
  proved contained: the trusted root must already exist, be a real directory and not be a
  symlink; the requested path is checked LEXICALLY (so a link the caller asked us through is
  still visible — `resolve()` answers "where does it point", not "did you ask me through a
  link"); every existing component from the root down is `lstat`-refused if it is a symlink,
  even one pointing elsewhere INSIDE the root; missing components are created one level at a
  time and re-checked immediately, so a concurrently substituted symlink is caught, not
  followed. A rejected request creates nothing, inside or outside. A write that makes no
  progress fails instead of spinning.
- **The data-root exemption is lexical AND symlink-free.** `repo/.data -> repo/src` (or an
  intermediate `repo/var -> repo/src`) exempts nothing: the configured root must be a strict
  lexical descendant of the repo, reachable without a single symlink component, and must
  resolve to itself.
- **Job-level post-mortem fields are persisted.** `job.json` carries
  `"postmortem": {"path": …, "error": …}` (evidence-relative, never absolute); older job
  files without the block load as empty. A job-level write failure therefore survives
  `_persist_job` → reload → export → `postmortem_integrity.json` → **final verifier
  BLOCKED**.
- **Retry evidence is call-local.** `CallRetryEvidence` carries only the retries of the ONE
  logical call being recorded (a reviewer call includes its single parse retry). The
  run-global `retry_reasons` / `retries_used` summary is unchanged for compatibility, but a
  builder timeout in round 1 can no longer classify a reviewer failure in round 3.
- **Deterministic redaction.** `safe_text()` runs Remedy's ESTABLISHED redactor
  (`stream_evidence.redact_text` — API keys, tokens, passwords, credentials, private-key
  material) and then converts local absolute paths into portable references
  (`[runtime-data]/pingpong_runs/<run>/…` under the data root, `[path]/<name>` otherwise).
  It is applied to `raw_reason`, every retry reason, `postmortem_error`, the job-level error
  and every `postmortem_integrity.failures[*].error`, and again on the stats histogram key.
  Classification words (`timed out`, `WorktreeLockError`, `read-only`, `postmortem.json`)
  survive; zero provider calls.
- **`postmortem_paths` are unique relative references** — `streams/<role>/round-NN/<kind>-II/postmortem.json`
  for streamed calls, `calls/<role>/round-NN/<kind>/postmortem.json` for fallback calls.
  Never the ambiguous bare basename.

**Honest limitations**
- `runtime_probe_failed` is **classifier-only / reserved integration support**: no
  production path currently performs a runtime probe inside a job/task evidence context, so
  nothing emits this class today. A standalone `remedy runtime probe` deliberately does not
  invent a fake job.
- `stats failures` covers the **evidence exports**. A job whose evidence was never exported
  is not in the corpus at all — the job registry is not scanned, and no "unscanned job"
  metric is claimed. Exported pre-F010 tasks stay visible through the coverage count.

## Third hardening round (external FINDINGS on `remedy-review-20260713-224612`)
- **The writer is anchored to open directory handles.** Validating a path with `lstat` and
  then reopening it BY NAME is check-then-use. Names are resolved exactly once, against a
  descriptor we already hold; the destination fd stays open through the mode check, the
  existing-record read, the temp creation, the full-byte write, the fsync, the create-only
  `os.link` publication, the conflict inspection and the temp cleanup.
- **Data-root addressing.** A relative `REMEDY_DATA_DIR=remedy_data` is an ordinary
  configuration; it is made absolute against the working directory exactly as every
  filesystem call in the process already interprets it. The repository may be addressed
  through a symlink, so the base is found by IDENTITY (the longest ancestor of the configured
  root that resolves to this repository), and only the components below it are walked for
  symlinks. Lexical and resolved layouts must agree. `repo/.data -> repo/src`, an
  intermediate `repo/var -> repo/src`, a root equal to the repo, an ancestor, a sibling or
  an outside path still exempt nothing. The rule is containment, not the name `.data`.
- **One path scrubber.** F007's accepted local-path/`file:`-URI sanitization moved,
  unchanged, to `packages/common/path_redaction.py`; `dev_server.py` and
  `failure_postmortem.safe_text()` both call it. `safe_text()` = established secret
  redaction → `label:/abs/path` handling (`cwd:/tmp/secret-repo` → `cwd:secret-repo`) →
  the shared scrub, with data-root paths kept as `[runtime-data]/…` references.
  `profile:`, `myfile:`, `notafile:`, `some.file:` and `x-file:` remain untouched.

## Fourth hardening round — portability (external FINDINGS on `remedy-review-20260714-101117`)
The reviewer's Linux 4.4 host **has** `O_DIRECTORY`, **has** `O_NOFOLLOW`, advertises
`dir_fd` support — and opens a directory symlink through
`O_RDONLY|O_DIRECTORY|O_NOFOLLOW` anyway. Seven writer symlink-safety tests failed there
(`177 passed, 7 failed`) while passing here. A flag the kernel accepts and ignores is not a
guarantee, and checking that the CONSTANT exists proves nothing about what it does.

- **Semantic identity verification, not flag faith.** Every directory component is now
  (1) `os.stat(name, dir_fd=…, follow_symlinks=False)` — a symlink is refused right there,
  in our code; (2) required to be a directory; (3) opened
  `O_RDONLY|O_DIRECTORY|O_NOFOLLOW`; (4) `os.fstat`'d; (5) required to have the same
  `(st_dev, st_ino)` as the entry we inspected, and to be a directory. Step 5 is the
  guarantee: on a host that follows the symlink, the opened inode is the TARGET's, not the
  one we looked at, and the write is refused. It also catches a component swapped between
  the check and the open. `O_NOFOLLOW` remains defence in depth.
- **The trusted root is verified the same way** — inspected without following symlinks,
  required to be a directory, opened, identity-compared — and never reopened by name once
  its fd is held.
- **The existing record is verified the same way** — no-follow stat, regular-file check,
  open, `fstat` identity comparison — so a symlinked `postmortem.json` is refused before a
  single byte outside the evidence directory is read.
- **The trusted root is now MANDATORY.** `root=None` used to `mkdir(parents=True)` on an
  untrusted destination, so `parent/link -> outside` had `outside/newdir/postmortem.json`
  created in it before anything was checked. There is no safe way to infer a trusted root
  from the path you are trying to validate; the caller names one, and every production call
  site already did. `root=None` now raises before any mutation.
- **Fail closed.** The capability check no longer asks whether a flag CONSTANT exists; it
  asks whether the primitives the guarantee is built from are available (directory-fd
  `stat` with `follow_symlinks=False`, `fstat`, and directory-fd `open`/`mkdir`/`link`/
  `unlink`). Without them the writer refuses to write.
- **Deterministic cross-platform coverage.** A test fixture strips `O_NOFOLLOW` from every
  directory open, reproducing the external host exactly (and asserting the seam really does
  defeat the flag). Under it the writer still refuses a destination symlink out of the
  tree, a destination symlink inside the tree, a symlinked parent, a symlinked trusted root
  and a symlinked existing record — from its own identity checks, not from an `ELOOP` the
  kernel was never going to raise.

## Accepted security boundary (v1)

External review accepted the writer with the threat model stated here, so it is stated
plainly. The writer **does** prevent path traversal out of the trusted evidence root,
pre-existing symlinks anywhere along the destination (including the root itself and an
existing `postmortem.json`), substitution of a different inode between the check and the
open, a host on which `O_NOFOLLOW` is accepted but ineffective, and the ordinary
check-then-open race — every one of those is refused by our own no-follow stat plus
`fstat` identity comparison, on every platform, and is covered by tests.

The evidence root and everything under it are private Remedy-owned control data, not a
shared or world-writable location. What v1 does **not** defend against is a malicious
concurrent process running as **the same OS user** that renames a directory Remedy has
already opened and validated. That adversary is not gaining anything it did not already
have: with the same UID it can modify or delete Remedy's evidence directly. Resisting it
would need stronger operating-system isolation — Linux `openat2` with `RESOLVE_*` scope
constraints, mount-namespace confinement, or running Remedy under a separate service
account — and that is outside F010 v1.

This boundary is narrow and it does not widen the writer: no caller-supplied path can put a
post-mortem outside the trusted root, and a symlink is never followed, ever. The residual
risk is same-UID directory relocation only.
