# T2_F082 — Self-benchmark
**Tier 2 · Depends on: F075 harness, F061 · Blocks/used by: capability regression protection, F156/F159 later**

## Goal & Done
Capability becomes a measured, versioned trend instead of a feeling: a
frozen set of benchmark orders runs on demand, producing pass rate,
cost, wall time and repair rounds per order into an append-only history,
and `remedy stats bench` shows the trend with regression warnings. DONE
when the bench runs green on fixtures, history survives across runs,
and a deliberately degraded fixture run triggers the regression warning.

## How it fits (inspect current shape before building)
The gauntlet feature built exactly the harness shape needed (run curated
orders unattended, evaluate strictly, matrix evidence) — the benchmark
REUSES that harness with a different order set and different evaluation
(metrics trend instead of flawless gate); factor shared pieces out
rather than copying (A6). Metrics come from actuals and reports; the
DoD gate defines pass.

## Design (suggested shape)
- Order set: five frozen orders probing distinct capabilities — a small
  CLI tool, an API endpoint with tests, a frontend widget (judged by
  build + the HTTP-level smoke, no browser dependency — visual judgment
  is a later tier), a bugfix on a fixture repo, a refactor with
  unchanged behavior (test-pinned). Each order file carries a rationale
  comment and a frozen version tag; changing an order starts a new
  series (comparability honesty).
- Runner `capability_bench.py` (reusing the gauntlet harness): per order
  record {order_id, series, pass, cost, wall_s, repair_rounds,
  postmortem_classes} appended to bench_history.jsonl under the data
  root's project area, plus a full evidence bundle per run.
- `remedy stats bench [--json]`: last run, trend over the series,
  regression warning when pass rate drops or cost/wall exceed the
  trailing median by a config multiplier — warnings name the order and
  the numbers.
- Model/routing context is recorded per run (which models served which
  roles) — later routing features read this to justify promotions.

## Task slicing
- **T001** harness reuse/factoring + the five orders + the record schema
  + a dry-run against recorded fixture evidence.
- **T002** history append + trend computation + regression rules +
  goldens (improving, flat, degrading fixtures).
- **T003** CLI + model-context recording + a real fake-provider bench
  run end-to-end.

## Acceptance
- Fixture series: degrading run warns with order and numbers; flat run
  doesn't. History is append-only (rerun never rewrites old rows).
  Changing an order file without bumping its version fails validation.
- The bench never runs implicitly — on demand only.

## Edge cases & assumption defaults (A9)
- Partial runs (one order crashed the harness): recorded as failed rows
  with the class, series continues — a broken bench run is data, not an
  exception. Cost comparisons use the basis labels; mixed bases are
  compared only within the same basis and the report says so.

## Orchestrator brief
Gate on the gauntlet harness. The factoring in T001 is the risky part —
require the worker to list what moved where and keep the gauntlet's
tests green unmodified.

## Do not touch
The gauntlet's pass definition, routing decisions (this feature only
records context), visual judgment. Suggested tests:
tests/orchestration/test_capability_bench.py.
