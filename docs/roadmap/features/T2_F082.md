# T2_F082 — Self-benchmark
**Tier 2 · Depends on: F075 harness, F061 · Blocks/used by: capability regression protection, F156/F159 later**

## Goal & Done
Capability becomes a measured, versioned trend instead of a feeling: a
frozen set of benchmark orders runs on demand, producing pass rate,
cost, wall time and repair rounds per order into an append-only history,
and `remedy stats bench` shows the trend with regression warnings. DONE
when the bench runs green on fixtures, history survives across runs,
and a deliberately degraded fixture run triggers the regression warning.

## How it fits (inspect current shape before building)
The gauntlet feature built exactly the harness shape needed (run curated
orders unattended, evaluate strictly, matrix evidence) — the benchmark
REUSES that harness with a different order set and different evaluation
(metrics trend instead of flawless gate); factor shared pieces out
rather than copying (A6). Metrics come from actuals and reports; the
DoD gate defines pass.

## Design (suggested shape)
- Order set: five frozen orders probing distinct capabilities — a small
  CLI tool, an API endpoint with tests, a frontend widget (judged by
  build + the HTTP-level smoke, no browser dependency — visual judgment
  is a later tier), a bugfix on a fixture repo, a refactor with
  unchanged behavior (test-pinned). Each order file carries a rationale
  comment and a frozen version tag; changing an order starts a new
  series (comparability honesty).
- Runner `capability_bench.py` (reusing the gauntlet harness): per order
  record {order_id, series, pass, cost, wall_s, repair_rounds,
  postmortem_classes} appended to bench_history.jsonl under the data
  root's project area, plus a full evidence bundle per run.
- `remedy stats bench [--json]`: last run, trend over the series,
  regression warning when pass rate drops or cost/wall exceed the
  trailing median by a config multiplier — warnings name the order and
  the numbers.
- Model/routing context is recorded per run (which models served which
  roles) — later routing features read this to justify promotions.

## Task slicing
- **T001** harness reuse/factoring + the five orders + the record schema
  + a dry-run against recorded fixture evidence.
- **T002** history append + trend computation + regression rules +
  goldens (improving, flat, degrading fixtures).
- **T003** CLI + model-context recording + a real fake-provider bench
  run end-to-end.

## Acceptance
- Fixture series: degrading run warns with order and numbers; flat run
  doesn't. History is append-only (rerun never rewrites old rows).
  Changing an order file without bumping its version fails validation.
- The bench never runs implicitly — on demand only.

## Edge cases & assumption defaults (A9)
- Partial runs (one order crashed the harness): recorded as failed rows
  with the class, series continues — a broken bench run is data, not an
  exception. Cost comparisons use the basis labels; mixed bases are
  compared only within the same basis and the report says so.

## Orchestrator brief
Gate on the gauntlet harness. The factoring in T001 is the risky part —
require the worker to list what moved where and keep the gauntlet's
tests green unmodified.

## Do not touch
The gauntlet's pass definition, routing decisions (this feature only
records context), visual judgment. Suggested tests:
tests/orchestration/test_capability_bench.py.

## Inventory — the T003b questions (R11)

Seven questions answered against the code on disk, so the build round orders
T003b against known ground instead of a guess. Nothing here changed behaviour:
every answer is a read plus a `path.py::symbol` citation of what was actually
read. R2 inventoried T001 the same way, and its two absences are why the bench
row schema is honest today.

**Q1 — role→model bindings at run time.** A live gauntlet run binds THREE roles
to a model, and no single symbol collects them. The ORCHESTRATOR is the only
explicit one: `packages/orchestration/gauntlet_runner.py::_default_move_call_fn`
passes `get_config().get("orchestrator.model")` into
`packages/orchestration/intake.py::make_structured_call_fn`. The PLANNER is
implicit — `packages/orchestration/gauntlet_runner.py::_default_plan_call_fn`
passes no model, so `packages/providers/ollama_planner/provider.py::_resolve_model`
decides it from `REMEDY_OLLAMA_PLANNER_MODEL`, `REMEDY_OLLAMA_MODEL`,
`ollama.planner.model` or the alias default. The BUILDER is implicit too:
`packages/orchestration/orchestrator_loop.py::execute_dispatched_job` constructs
`OllamaBuilder()` with no argument, so
`packages/providers/ollama_builder/provider.py::_resolve_model` decides that one.
A seven-role table does exist — `packages/orchestration/role_config.py::KNOWN_ROLES`
with `::resolve_role_config` — but its only caller is
`apps/cli/commands/do_cmd.py::_resolve_cli_role_configs`, the `remedy do` path,
so it is not reachable from a gauntlet run. So "one role is the whole truth" is
false; three roles resolve a model each, in three different modules, and not one
of the three resolutions is written down anywhere.

**Q2 — what a gauntlet `run.json` records.** No model identity of any kind. The
writer is `packages/orchestration/gauntlet_runner.py::run_order`, which
serialises the body built by `::_evidence_body` — or `::_minimal_body`, a
subset, on the crash path — and then adds `data_root_hash_after` before writing.
The keys `::_evidence_body` produces are `gauntlet_run_version`, `order_id`,
`kind`, `terminal_status`, `wall_seconds`, `operator_interventions`,
`data_root_hash_before`, `postmortems`, `open_decisions`, `era_defects`,
`injections`, `evidence_links`, `cycles_budget`, `cycles_resolved`,
`template_digest`, and then either `tokens` or `tokens_source`. The reader
`packages/orchestration/gauntlet_evidence.py::load_run` builds `::RunEvidence`
from those same fields and carries no model field either, and the finest-grained
record on this path, `packages/orchestration/orchestrator_loop.py::measure_call_cost`,
writes `calls`, `parse_retried`, `response_chars`, `schema_v`, `usage` and
`usage_source` — again no model. That absence is the T003b-shaping answer.

**Q3 — the token ledger's model, and whether a bench row could join to it.** The
column exists: `packages/orchestration/token_ledger.py::COST_GROUP_KEYS` is
`("role", "model", "day")`, and the value is filled by
`packages/orchestration/token_ledger.py::call_record_from_evidence`, which takes
`role`/`model` only where the evidence names them and states in as many words
that a configured model is not the model that ran, so it is not used. A bench
row could not join to it today, for two independent reasons. First, nothing on
the gauntlet path writes the ledger at all — the only run-time writer is
`packages/orchestration/pingpong_evidence.py::_record_finalized_call_in_ledger`
on the ping-pong job path, opt-in even there, the only other writer is the
operator-invoked `apps/cli/commands/stats_ledger_cmd.py::_cmd_stats_backfill_ledger`,
and both derive their row from `task_runs/<task_id>/provider_evidence.json`,
which no gauntlet run writes. Second, there is no key: `run.json` carries
neither `project_id` nor `job_id`, and its `evidence_links` names `data/missions`,
the mission event ledger, not `packages/orchestration/token_ledger.py::LEDGER_FILENAME`.
The nearest available join is the isolated data root itself
(`packages/orchestration/gauntlet_runner.py::ISOLATED_ROOT_DIRNAME`) — a
directory walk, not a key.

**Q4 — the smallest honest shape for model context per run.** (c), and the
recommendation is to build (c) rather than to dress (a) or (b) over an absence.
Because Q1–Q3 found no record of which model served which role, a field on
`packages/orchestration/capability_bench.py::BenchRecord` would be `None` at
every row exactly as `repair_rounds` already is, and a run-level header row in
`packages/orchestration/bench_history.py` would require `::load_bench_history`
to learn a second line shape only to carry the same absence one level up.
Recording the CONFIGURED values instead is not a way out: the comment above
`deps.run_mission` in `packages/orchestration/gauntlet_runner.py::run_order`
already refuses to name the provider there for exactly that reason (DECISION
F105 D13), and `token_ledger.py::call_record_from_evidence` states the same
rule. The smallest honest change is therefore an additive `models` key written
by `packages/orchestration/gauntlet_runner.py::_evidence_body`, fed by having
`::_default_plan_call_fn`, `::_default_move_call_fn` and the `::RunnerDeps`
execute seam surface the model each resolved. Two corrections the build round
needs: this is NOT blocked by F082's Do-not-touch list, which names the
gauntlet's pass definition, routing decisions and visual judgment and not
`gauntlet_runner.py`; but it IS an edit to a gauntlet module, which the ADDITIVE
constraint from R2 Q11 forbids by default and which DECISION F082 D1 has already
excepted once, at `::measure_tokens`, for this same class of reason. Until a
second such decision exists, T003b cannot record model context as the Design
bullet words it.

**Q5 — the fake and recorded providers this repo already runs.** Neither can
drive a gauntlet run. `packages/orchestration/pingpong_provider.py::FakeProvider`
is a deterministic double for the ping-pong Builder/Reviewer protocol
`::PingPongProvider`, whose methods are `build(prompt) -> BuilderOutput` and
`review(prompt) -> ReviewerOutput`, and it is selected by `::create_provider`
under the name `fake`; the gauntlet seam instead wants a
`call_fn(prompt, attempt) -> str` returning schema-bound JSON plus an execute
callable, so the two shapes do not meet.
`packages/orchestration/evidence_mode.py::classify_execution_mode` is not a
provider at all — it is a classifier that labels already-written evidence
`fake_provider_test` when a provider NAME contains fake, stub or mock, and its
callers are `pingpong_loop.py`, `job_evidence.py` and `final_verifier.py`, all
off the gauntlet path. The only substitution seam a bench run has is
`packages/orchestration/gauntlet_runner.py::RunnerDeps`, which is what
`tests/orchestration/test_gauntlet_runner.py` already hands doubles to.

**Q6 — what a fake-provider bench run would EXECUTE.** The entry point would be
`packages/orchestration/gauntlet_runner.py::run_campaign`, fed the
`GauntletOrder` values carried by
`packages/orchestration/bench_orders.py::load_bench_order_set`, then
`packages/orchestration/bench_dry_run.py::dry_run_rows` and
`packages/orchestration/bench_history.py::append_bench_run`. No such caller
exists today: `run_campaign`'s only caller is
`scripts/self_run_gauntlet.py::run_live`, and that one loads the GAUNTLET set
through `gauntlet_orders.load_order_set`, never the bench set. Four blockers,
named rather than assumed: (1) the missing entry point above; (2) the network —
the production `RunnerDeps` defaults reach a local Ollama through
`packages/orchestration/intake.py::make_structured_call_fn` and through the
`OllamaBuilder()` inside `orchestrator_loop.py::execute_dispatched_job`, so a
no-network run means substituting `RunnerDeps.plan_call_fn`, `::move_call_fn`
and `::execute_fn`, which those seams support; (3) the clock —
`gauntlet_runner.py::run_order` calls `time.monotonic()` around the run to fill
`wall_seconds`, so a row's `wall_s` is clock-derived even though
`capability_bench.py` and `bench_history.py` both keep clocks out of themselves;
(4) the data root — `gauntlet_runner.py::isolated_environment` confines the RUN
to `run_dir/data`, but `bench_history.py::bench_history_path_for` resolves
through `packages/orchestration/data_paths.py::projects_dir`, so an end-to-end
run must pass its own `root` or it appends into the operator's real data root.
`gauntlet_runner.py::materialise_sample_project` additionally shells out to
`git`, and is itself a `RunnerDeps` seam.

**Q7 — what the Acceptance criteria still owe.** One of the two is pinned, the
other is not. "Changing an order file without bumping its version fails
validation" IS pinned, by
`tests/orchestration/test_bench_orders.py::test_editing_an_order_without_bumping_its_version_fails_validation`,
which edits a copied order file and asserts
`packages/orchestration/bench_orders.py::BenchOrderSetError`; R-0410 records the
residual, that the freeze cannot refuse a coordinated edit which also rewrites
the digest recorded under the version the file still claims, and closure states
that threat model rather than quoting the criterion whole. "The bench never runs
implicitly" is NOT pinned by any test. It holds today only as a fact about
callers — `packages/orchestration/bench_history.py::append_bench_run` and
`packages/orchestration/bench_dry_run.py::dry_run_from_order_set` have no caller
anywhere under `apps/`, `packages/` or `scripts/` — and the nearest existing
guards, `tests/cli/test_stats_bench.py::test_the_declared_contract_says_it_only_reads`
and `::test_neither_output_mode_changes_one_byte_of_the_history`, pin the READ
VIEW as read-only rather than the bench as never-implicit. An unpinned
acceptance criterion is a closure blocker, so a later round owed a test that
asserts the absence of an implicit caller. R16 delivered it — see Built State.

## Built State — what F082 delivered

Six new modules, all ADDITIVE: no symbol moved out of any gauntlet module, and
the gauntlet's own seven test files are green UNMODIFIED. Each carries its own
test file under `tests/orchestration/`, except the CLI view, whose test sits
under `tests/cli/`.

- `packages/orchestration/capability_bench.py` — `BenchRecord` and the pure
  record builder. Carries a defaulted `models` field.
- `packages/orchestration/bench_orders.py` — `load_bench_order_set` over THREE
  frozen orders under `scripts/bench_orders/`, with the version freeze:
  editing an order without bumping its version raises `BenchOrderSetError`.
- `packages/orchestration/bench_dry_run.py` — the join from an order file to a
  row over recorded evidence.
- `packages/orchestration/bench_history.py` — the append-only history, the
  trend, and the regression rules including the `pass_drop` warning.
- `packages/orchestration/bench_run.py` — the run itself, joining the frozen
  order set to a campaign, the campaign's evidence to bench rows, and the rows
  to a history file. Its data root and history path are REQUIRED arguments, so
  a run cannot append into the operator's real data root.
- `apps/cli/commands/bench_cmd.py` — the `remedy stats bench` read view, one
  new handler key, changing no bench module.

One gauntlet module was edited, under DECISION F082 D1: `gauntlet_runner.py`
gained `measure_tokens` (R-0407) and, under D7/D8, a `models` key in
`_evidence_body` naming which model served which role.

Acceptance, measured rather than argued. The bench runs green on fixtures and a
deliberately degraded run raises the warning — both asserted at R19 by
`test_every_row_passes_on_a_clean_fixture_run` and
`test_a_deliberately_degraded_run_triggers_the_pass_drop_warning`, with a
red-proof in a disposable worktree confirming both go red when the stored gate
verdict is removed. History survives across runs. "The bench never runs
implicitly" is pinned at R16 by
`tests/orchestration/test_bench_never_runs_implicitly.py` as an enumerated
allowlist of permitted callers under DECISION F082 D9 — the allowlist holds
EXACTLY ONE name, `bench_run.py` — rather than as a total absence, because the
run that completes the feature is itself the first legitimate caller.

Four absences, stated rather than implied:

- THREE frozen orders, not the Design's five (R-0411). The shared sample project
  has no HTTP surface and no web asset, so the API-endpoint and frontend-widget
  orders have nothing to probe; they wait on a bench-owned fixture per
  DECISION F082 D3, not on an edit to the gauntlet's template.
- The version freeze holds against a file-side edit only (R-0410). A
  coordinated edit that also rewrites the digest recorded under the version the
  file still claims is not refused.
- The BUILDER's model stays unobservable (R11 Q1, Q4).
  `orchestrator_loop.py::execute_dispatched_job` constructs `OllamaBuilder()`
  where no seam can observe it, so `models` records the orchestrator and the
  planner and is honest about the third being absent.
- Every acceptance measurement was taken under DOUBLES, never under a live
  provider, and every row's `cost` is `None` under doubles while `wall_s` is
  clock-derived from the runner. Pass rate is therefore the only trend a real
  run can prove today, which is why the R19 warning property is scoped to
  `pass_drop`.
