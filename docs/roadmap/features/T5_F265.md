# T5_F265 — Teacher learning UI v1 (post-task lessons)

## Goal & Done
A learning surface as an overlay/tab over the cockpit: an index of lessons on
the left, a main area with next/previous navigation.

v1 content: after EVERY completed task the teacher produces a lesson from the
task's REAL diff — what was built, which functions and constructs were used,
what they do, why here, and whether that is best practice (with the judgement
stated as a judgement).

A second mode, "Commands", explains the CLI commands this task implemented or
touched.

Harness and model for lesson generation are selectable PER ROLE exactly as for
builder and reviewer (the `role_config` role `teacher`), with its own budget
pot. The read path stays hard read-only.

DONE when you can start a mission (`remedy do`), open the learning overlay, and — after the first
task completes — read a navigable lesson generated from the real diff.

## Why this exists
The teacher role can already narrate and answer, but the operator has no place
to READ it while a job runs. The waiting time during a build is the one moment
when a person is both idle and maximally curious about the code being written,
and today that time produces nothing. Generating from the REAL diff rather than
from the plan is the whole point: a lesson about what was INTENDED teaches the
plan, and the plan is not what shipped.

## v2 target, noted here deliberately
LIVE learning DURING the build — "you learn while you wait". v1 is post-task by
construction: it reads a finished diff. v2 is a separate feature and will be
registered separately; it is written down here so v1's post-task shape is
recognisably a first step and not an oversight.

## Design
- The overlay is a cockpit surface and takes its data from the existing event
  stream (F008/F021), not from a second polling path.
- Lesson generation is triggered by task completion, reads the task's diff, and
  runs under the `teacher` role's own harness, model and budget — the same
  role-configuration machinery builder and reviewer use, with no new mechanism.
- The read path is HARD read-only. The teacher may not write to the repository,
  and the surface may not offer an action that would.
- A lesson is an artifact with an id, keyed on the Run (one per task) and its
  Mission (DECISION amend0905-vocab D1, 2026-09-05) — never on the pre-F260 job
  record — so the index is a list of artifacts and navigation is not
  re-generation. Re-opening a lesson costs no tokens.
- The "Commands" mode reads the command catalog for the commands the diff
  touched, so it explains the SHIPPED description, never a remembered one.
- Budget exhaustion degrades honestly: no lesson, and the index says why —
  never a lesson generated from less than the real diff while presenting itself
  as complete.

## T001 — Lesson generation from the real diff
The generator, under the `teacher` role config and its own budget pot. Produces
a stored lesson artifact per completed task.

## T002 — The overlay
Index on the left, main area with next/previous. Reads stored lesson artifacts;
generates nothing itself.

## T003 — The Commands mode
The second mode, over the command catalog entries the task's diff touched.

## Acceptance
- Start a mission with `remedy do`, open the overlay, read a lesson generated from the real diff
  after the first task completes.
- The lesson names constructs that actually appear in the diff — proved by a
  fixture whose diff contains a known construct.
- The teacher's spend appears as the `teacher` role in the token ledger, under
  its own budget pot.
- The read path writes nothing to the repository, proved by a test.
- Budget exhaustion produces an honest empty state, not a partial lesson
  presented as whole.

## Do not touch
The write channel (F009) — this surface is read-only and adds no mutating
route; the builder/reviewer role configs; and the teacher's existing
`teach narrate` / `teach ask` commands, which keep working unchanged.

## Orchestrator brief
T001 is the substance and the budget risk; settle the lesson artifact's shape
before any UI exists. T002 is pure rendering over stored artifacts and is safe
to build second. T003 is small and independent of T002. The v2 live mode is NOT
in this feature — a slice that starts generating during the build has drifted.

## Built State (F265, 2026-09-24)

What exists on disk at the close of F265, built in four rounds of one session on
`feature/f265-teacher-learning-ui`, cut from `main` at `0236e3c3`. Every DECISION named lives in
`.agent/decisions.md`; every round's verdict in `.agent/live_review.md` or, once rotated, its
archive. The operator-facing description is `docs/guides/teacher-lessons-user-guide-v1.md`.

**T001 — lesson generation from the real diff.** `packages/orchestration/lessons.py` writes one
lesson per completed Run: it reads that Run's `runs/<run_id>/result.diff` and nothing else, sends
it whole under the `teacher` role's own transport and model, and stores the result create-once as
a sealed `runs/<run_id>/lesson.json` naming the Run, the job, the task, the Mission, the diff's
sha256 and the model (DECISION F265 D1). A construct is kept only when its name appears on a line
the diff adds; every other name the reply gives is listed as ungrounded. Every call is billed once
through `teacher_spend.record_teacher_question` as role `teacher`, call id
`teacher:lesson:<run_id>`, inside a per-job pot of `teacher.lesson_max_calls` (30) and
`teacher.lesson_max_tokens` (300,000) read from the ledger's `teacher` rows before the call. A Run
with no diff, a diff over 60,000 characters, no ledger, a spent pot, an unusable transport or an
unreadable reply stores an honest empty lesson whose status and reason say which, with no call
where none was made. `_teach_task_lesson` in `packages/orchestration/pingpong_job.py` writes the
lesson after every applied task while `teacher.lessons` is on — off by default, operator question
Q1 — and never changes the job's outcome. A lesson it stores is announced on the job's run log as
`task_lesson_written`, which the stream carries as a `lesson` field naming only the Run and the
status (D2).

**T002 — the overlay.** `GET /api/jobs/<job_id>/lessons` serves one row per task, the stored
lesson or the reason there is none, reading and never writing (D2). The cockpit's right panel
opens `apps/ui/src/components/lessons/LessonsOverlay.tsx`, a right-anchored dialog sheet with the
index on the left and the lesson with previous and next on the right, closed by Escape; every rule
it applies lives in the pure `apps/ui/src/api/lessons.ts`, whose decoder refuses a whole index it
cannot read rather than showing it shorter, and it reads the route again only when the stream
announces a lesson (D3). Two rows of `docs/ui/design_reference/assumption_log.md` record the
sheet's layer and missing focus trap and its entry point.

**T003 — the Commands mode.** `lessons.lesson_commands` names the commands whose handler module or
catalog line a Run's diff changed, each with its invocation and the description the command
catalog ships, computed from the stored diff whenever the route is read and never stored; the
overlay's Lesson and Commands switch shows them (D4).

**Acceptance, by the test that proves it.** A lesson from the real diff after a task completes:
`tests/orchestration/test_lessons.py::test_a_real_job_teaches_its_completed_task_from_the_runs_own_diff`,
which runs a job and compares the lesson's diff digest and prompt with the Run's own diff; the
overlay reads the stored lesson through `tests/ui_server/test_lessons_route.py`. The lesson names
constructs that appear in the diff: `test_only_constructs_on_an_added_line_are_taught` and

The read path writes nothing: `test_reading_a_lesson_writes_nothing` and
