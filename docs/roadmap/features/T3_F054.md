# T3_F054 — Auto-revert proposal
**Tier 3 · Depends on: F047, F053 · Blocks/used by: trust**

## Goal & Done
A run that leaves the test suite worse than it found it must confess
and offer the way back: a regression guard compares the suite's state
at start and end (checkpoints carry the digests), and on degradation
produces a ready-to-apply revert proposal diff plus an analysis section
in the report — NEVER applied automatically. DONE when a fixture run
that breaks a previously green test yields the proposal with a correct
revert chain, a run that only fails its own new tests does not trigger
it, and applying the proposal manually restores the start digest.

## How it fits (inspect current shape before building)
Checkpoints record a verify/test digest per cycle — confirm the digest
captures per-test identity, not just counts (extend additively if it's
count-only: the guard needs to know WHICH tests regressed). The report
renderer takes structured sections; worktree/git helpers can produce a
revert chain of the run's commits. The proposal is an artifact in
evidence; applying it is a human git action (P2), documented in the
report's next-action line when degradation is the terminal story.

## Design (suggested shape)
- `regression_guard.py`: compare(start_digest, end_digest) →
  {regressed: [test ids previously passing, now failing], newly_failing
  own tests excluded (tests introduced by this run are its own
  business), fixed: [...]} — the exclusion rule is the honesty core:
  degradation means damage to what existed.
- On regression at a terminal state: build revert_proposal.diff — the
  revert chain of this run's commits in reverse order (worktree branch
  commits are identifiable via the branch naming convention) — store in
  evidence with the regressed-test list; the report gains a
  "Regression" section leading the next-action rule table (regression
  outranks other recommendations).
- Sanity: the proposal is validated by applying it to a scratch copy
  and re-running the regressed tests (they must pass again) — a
  proposal that doesn't provably restore is labeled unvalidated with
  the reason (e.g. conflicts), never silently offered as good.

## Task slicing
- **T001** digest comparison + the own-tests exclusion + unit tests
  (regressed/fixed/new matrices).
- **T002** revert-chain construction + scratch validation + fixtures
  (clean revert validates; a conflicting history yields unvalidated
  with reason).
- **T003** terminal wiring + report section + next-action precedence +
  the end-to-end fixture (break a green test → proposal + report;
  manual apply restores digest in the test).

## Acceptance
- Break-fixture: proposal exists, validated, regressed list exact;
  applying restores. Own-new-failing-test fixture: no proposal.
  Nothing is ever auto-applied (state diff test at terminal). Report
  leads with the regression when present.

## Edge cases & assumption defaults (A9)
- Flaky tests muddy digests: a test regressed AND healed across cycles
  is listed with a flaky? flag rather than driving a proposal alone
  (threshold: regressed at terminal is what counts). Runs without a
  start digest (legacy): guard inert with an honest note.

## Orchestrator brief
Verify the digest granularity first (T001's opening deliverable). The
scratch-validation rule is non-negotiable — an unvalidated proposal
must say so; put that in the T002 order verbatim.

## Do not touch
Auto-apply of anything, checkpoint format beyond additive digest
detail, merge/PR flows. Suggested tests:
tests/orchestration/test_regression_guard.py.
