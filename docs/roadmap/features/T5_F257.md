## Goal & Done
Remedy is used on Remedy, on a schedule that cannot be skipped or forgotten.
After every feature close, the loop runs exactly ONE small curated maintenance
job from a queue file, through `remedy do job-plan` and `remedy do job-run`,
against the Remedy repository itself, and takes the result to the normal
approval gate. DONE when that step is a defined part of the loop rather than an
intention: the queue file exists, one item is consumed per feature close, and
the run's outcome reaches the approval gate like any other job.

## Why this exists
Every such run is simultaneously a PIPELINE SMOKE TEST. The dogfooding findings
this repository keeps discovering — a promotion blocked with no way forward, a
job path that records no cost — were all found by an operator running the real
commands by hand, and each one had been invisible to a green suite. A run that
exercises `job-plan`, `job-run`, the approval gate and promotion end to end
finds that class of defect on a schedule instead of by luck.

## Shape (suggested, not settled)
- **A queue file** of small, curated maintenance tasks. Curated is the load-bearing
  word: the items are chosen to be safe, bounded and genuinely useful, not
  generated. One item is consumed per feature close.
- **Exactly one item per close.** Not zero (the track must not rot) and not many
  (a maintenance sweep must never compete with feature work for a session).
- **The normal approval gate.** The result is reviewed and promoted exactly like
  any other job. No self-approval, and the scope fences of F017 apply unchanged —
  `docs/roadmap/STATUS.md` is in the builtin deny list precisely so a job can
  never check itself off.
- **Findings become operator findings.** Anything the run exposes is recorded the
  way the 2026-08-25 dogfooding findings were: as an operator finding in the
  feature file that owns the surface, so it is carried on the roadmap rather than
  in a session.

## Acceptance
- The queue file exists with at least one curated item, and its format is
  documented where a reader would look for it.
- One feature close consumes exactly one item and leaves the queue shorter.
- The run reaches the normal approval gate; nothing is promoted without it.
- A defect the run exposes lands as an operator finding in the owning feature
  file, not only in a session transcript.

## Do not touch
STATUS semantics — a job must never check itself off. The approval gate. The
scope-fence builtin deny list.

## Orchestrator brief
This is a PROCESS feature: most of its risk is in the queue's curation and in the
"exactly one" rule, not in code. Settle the queue format and the consumption
point before writing anything that runs.
