# T17_F246 — Verification gate plugin API
**Tier 17 · Depends on: F061, F162, F165, F245 · Blocks/used by: an ecosystem of checkers; niche compliance**

## Goal & Done
See ROADMAP.md F246; the Done criterion there is binding.

## Context (existing code & prior features)
F061 knows built-in check kinds; F238 defines the plugin security model for the UI - this is the CHECK counterpart.

## Design
A gate plugin = a signed bundle {manifest (name, version, publisher, required inputs), an executable entry}: the contract is STRICTLY deterministic - input: a read-only workspace mount + a DoD spec extract (json); output: findings in the F005 review schema + an exit code; runtime inside the F162 sandbox profile gate_plugin (no network; fs read-only except /out; time/memory budgets). An admission test at install: a double run on a reference fixture must produce bit-equal findings (the determinism gate) or the plugin is rejected. Registration as the DoD kind plugin:<name>.

## Task slicing
T001 the contract + the sandbox runner + the admission double-run + tests. T002 DoD integration + an example gate (a markdown linter as a plugin) + escape/nondeterminism fixtures (both must fail correctly) + third-party docs.

## Acceptance & tests
The example gate runs inside a fixture job's DoD; a nondeterministic plugin is rejected at admission; a network attempt from the sandbox fails and is logged; findings validate against the F245 schema.

## Risks / anti-goals
Plugins can only ADD checks, never replace or disable built-in gates; blocking capability requires explicit per-plugin operator approval (default: informative).
