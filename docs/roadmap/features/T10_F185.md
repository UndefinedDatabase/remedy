# T10_F185 — Per-project permissions
**Tier 10 · Depends on: F175, F148 · Blocks/used by: F210 visibility; light tenant separation**

## Goal & Done
Not everyone sees every project: an access config — per project
(.remedy/policy/access.toml) or centrally under the data root's
org area — maps user → role per project; the multi-user default is
NO access (single-user stays open and unchanged); enforcement is
server-side BEFORE the F148 filter, the project LIST itself is
filtered, cost visibility is its own flag (viewer_costs), and the
F148 leak test gains the person dimension — a property over all
GET endpoints × roles. DONE when access resolution (central +
per-project with the documented precedence) matches its table,
an unlisted user in multi-user mode sees an empty project list
and gets refusals on direct URLs (no existence leaks — the 404-
class response indistinguishable from absence, stated and
tested), roles per project cap the identity's global roles (the
intersection rule documented), viewer_costs hides cost fields
exactly where it says, the extended leak property sweeps
endpoints × roles × access states, and — the placement correction
— the central file lives under <data_root>/org/, not a home
dotfile.

## How it fits (a placement correction + the enforcement layer)
The old draft wrote ~/.remedy/org/access.toml — corrected to
<data_root>/org/access.toml (the org store's home, beside
users.toml). F148 built response filtering by audience; this
feature adds AUTHORIZATION before it: the request pipeline
resolves user (F177) → project access (this feature) → refuse or
proceed → THEN F148 filters the payload per role. Precedence:
per-project access.toml overrides central entries for that
project (locality wins; the table documented); the project list
endpoint filters by resolvable access (absence invisible).
Role capping: effective role = min(global role, project role)
per the documented order viewer < reviewer < operator (a user
can be reviewer globally but viewer on a sensitive project —
the intersection rule); the matrix consumes the EFFECTIVE role
(one resolution point feeding require()).

## Design (suggested shape)
- Config: entries {user → role} per project (central: [project.
  <id>] sections; local: the project's own file); validation
  (users exist, roles valid); `remedy access show [--user]`
  renders effective access with sources.
- Enforcement: the resolution middleware (request → project
  context → effective role | refuse); the refusal class uniform
  (existence-hiding); mutation paths already matrix-gated get
  the effective role for free (the one resolution point).
- viewer_costs: a per-project flag (default false for viewers —
  costs are sensitive); F148's cost-field filtering keyed by it
  (the filter's audience input grows the flag).
- The leak property: for every registered GET route × role ×
  access state, assert response fields ⊆ the allowed set and
  absence-indistinguishability for no-access (the F148 property
  extended — the route registry enumerates, new routes join
  automatically).
- Single-user: no access files → open (the regression sweep);
  multi-user with files → default-deny per the rule.

## Acceptance
- Precedence/intersection tables exact. No-access responses
  indistinguishable from absence (the response-class test).
  The list filters (fixture). viewer_costs hides exactly the
  cost fields (field inventory). The property sweeps green with
  a seeded leak fixture red. Single-user byte-identical.
  Central placement under the data root (grep).

## Edge cases & assumption defaults (A9)
- SSE streams: the same resolution gates subscription per
  project (events are responses too — the property includes
  stream payloads). Users gaining access mid-session: effective
  on next request (no session invalidation needed — resolution
  is per-request, stated). Operators: access still applies
  (global operators see only their projects unless listed —
  deliberate: org-wide sight is F210's explicit feature, noted).
