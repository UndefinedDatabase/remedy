## Goal & Done
An unattended job whose task ends blocked with no file changed, because the review says the work does not belong in this repository, ends at once with stop reason `not_in_this_repository` and a plain sentence naming the repository and why, so a client can hand the task back. The reviewer's verdict has a finding kind for it and its prompt asks for it. The hard time cap is checked across a restart.

## What it rests on
- Jobs 44f5ec598488464c (blocked by finding `tzbwja-wrong-repo`, no file changed) and d1a8b318952f4b04 (`waited_s` 53019 under a 120-minute cap) of 2026-10-29.

## Acceptance
- A verdict with a finding of kind `not_in_this_repository` on an empty diff of an unattended job ends the job `failed` (a state that does not wait, so a client hands the task back) with that stop reason and a sentence naming the repository.
- The same verdict on a job with changed files, or an attended job, follows the plain review path.
- Contract 1.34 names the stop reason.

## Built state (2026-10-29)
Built on branch feature/beweis. The reviewer's finding has an optional `kind` (`pingpong_provider.ReviewFinding`, the strict `schemas.models.ReviewFinding`, both parsers, the JSON shape the prompt names), the run record keeps it when set, and `review_scope_rules.REVIEWER_SCOPE_RULES` asks for the verdict blocked with one finding of kind `not_in_this_repository` naming the repository the work belongs in and why (the reviewer prompt golden's six renders gained that sentence, a declared content change). New `packages/orchestration/job_wrong_repository.py`: `end_job_not_in_this_repository` reads a blocked job after its run (`job_run_finish.stamp_blocked_job_finish`): when it runs unattended, no task has a changed file (`safe_diff_files`) and the last review of a blocked task holds such a finding, the job ends `failed` with `stop_reason` `not_in_this_repository`, the stop text (metadata `stop_text`, so `job_stop`, the story's `stop` and the order jobs' `stop_text` say it) naming the repository by name and path, the task and the review's reason, and its finish time, and is saved. An attended job, a job with a changed file and any other finding stay `blocked` on the plain review path. Contract 1.34: the "What changed from 1.33 to 1.34" block and the paragraph "A job whose work is not in its repository ends" under "Orders" of `docs/system/public-http-api-v1.md`, and the release matrix. Tests: `tests/orchestration/test_job_wrong_repository.py` (6); `tests/orchestration/test_reviewer_prompt_golden.py` updated for the declared sentence. No new dependency.

Decision: the job ends `failed`, not `blocked`, because a client (Universe's `remedy_said`) reads `blocked` as held for a person ("wartet auf dich") and `failed` as handed back; the registered acceptance said `blocked` and was corrected.

The time cap across a restart (job d1a8b318952f4b04, read only with `remedy job show`): it holds, and nothing was changed. The working clock (F310) counts the gap since the job was last active as waiting, and the cap judges the work time alone. d1a8's `waited_s` of 53019 seconds is exactly the gap from 03:32 to 18:16 UTC in which it did not run; its work time was about eleven minutes against the 120-minute cap, and it ended at its next safe point after the cancel. `tests/orchestration/test_budget_clock.py` already holds both sides (a job that waited most of nine hours is not stopped by the wall clock; one active a minute ago is). What it showed instead: a job that a dead order walk leaves `running` without a run record is neither restarted nor ended when the server starts, only a cancel ends it (`serve_runs.settle_orphaned_job_cancels`). That is reported to the orchestrator as a cause for a later number, not built here.
