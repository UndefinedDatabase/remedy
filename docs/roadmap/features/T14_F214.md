# T14_F214 — Editions & honest feature gating
**Tier 14 · Depends on: F213 · Blocks/used by: the pricing model; F218**

## Goal & Done
See ROADMAP.md F214; the Done criterion there is binding.

## Context (existing code & prior features)
Nothing exists; feature numbers (F###) are the natural gating vocabulary.

## Design
ONE file packages/product/editions.toml: [editions.core|pro|org] each lists features=[F numbers] (core = everything in Tiers 0-7 plus operations basics - generous; the tool stays excellent; pro = Tier 9 artifacts/signing/scoreboard publication; org = the team/org tiers). A central check require_edition(feature) (the F141/F157 pattern: ONE point); a gated feature shows WHAT it does + WHICH edition instead of vanishing from menus (no dark patterns, no nag modals - one calm note). The test suite runs per edition in a CI matrix.

## Task slicing
T001 editions.toml + require_edition + wiring at the tier 9/10/13 entry points + tests. T002 the UI/CLI notice rendering + the CI edition matrix.

## Acceptance & tests
Matrix enforcement is complete (a gated feature in core shows the note, never crashes); a license install applies without restart; no feature is double-listed or forgotten (a script reconciles against the roadmap numbers).

## Risks / anti-goals
Never remove a feature from core retroactively (a trust rule, anchored as a comment in the file); gating logic never leaks into feature code.
