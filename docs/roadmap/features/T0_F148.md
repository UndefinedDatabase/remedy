# T0_F148 — Project scoping everywhere
**Tier 0 · Depends on: F146 · Blocks/used by: clean data for queues, ledger, memory, ladder**

## Goal & Done
Every job and derived artifact is attributable to exactly one project, and
every listing command defaults to the current project with an explicit
`--all-projects` escape hatch. DONE when two fixture projects on one
machine never see each other's data by default, legacy data still loads
and is labeled honestly, and NO data migration is required.

## How it fits (inspect current shape before building)
Job storage is flat, file-per-job, atomic — so the scoping strategy is a
METADATA FILTER, not directory moves (moves would force a migration; a
field is additive). The registry already supports attaching jobs to
projects; this feature makes the job side authoritative. Consumers to
scope: job listings, the status view, decision listings, failure stats,
token/budget displays — all funneled through ONE shared helper.

## Design (suggested shape)
- Additive optional `project_id` on the job model, set at creation from
  the resolved project. None means legacy.
- Module `project_scope.py`: a scope selector built from the shared
  `--project`/env/cwd precedence helper plus an `--all-projects` flag; a
  `job_in_scope` predicate; and `scoped_jobs(scope)` — THE one listing
  helper every command calls, passing through the existing
  unreadable-files honesty count.
- **Legacy rule (state it prominently):** jobs without a project are in
  scope only under --all-projects OR when exactly one project exists on
  the machine — single-project users must not watch their history vanish.
- CLI: add the two flags as one shared parser fragment to job list,
  status, decision list, failure stats, token/budget displays. Derived
  stores (decisions, ledger events, actuals) stay schema-unchanged —
  scoping joins through the job's project id (A6).
- Creation without a resolvable project is only legal with an explicit
  --project; audit every job-creating entry point and wire the guard.
- Display: legacy jobs show "(unscoped)"; `remedy project adopt <job_id>`
  claims one explicitly — never automatically (P2). A job whose project
  was deleted renders "(orphaned: id)" and never crashes a listing.

## Task slicing
- **T001** model field + creation-path audit (find every job constructor
  call site, wire the project id) + backward-compat fixture (old job JSON
  loads with none).
- **T002** scope module + legacy rule + unit tests (two projects, legacy
  jobs, --all, selector, unreadable passthrough).
- **T003** CLI integration across all listed commands + adopt + a
  two-project fixture proving default isolation on every command in one
  looped test.
- **T004** docs + the status view flips its "all projects" label to the
  scoped view.

## Acceptance
- Projects A/B, two jobs each: every listed command shows only A's data
  from inside A; --all shows four; --project B works from anywhere.
- Legacy job: hidden in the two-project case, visible single-project,
  always under --all; adopt persists permanently.
- No file under the jobs area moved or renamed; decision/ledger/actuals
  unit tests run unmodified.

## Edge cases & assumption defaults (A9)
- A shared data root across machines works because scoping is data-level;
  document that slugs must then be unique per data root. Registry job
  attachment stays consistent in both directions (creation path calls it).
