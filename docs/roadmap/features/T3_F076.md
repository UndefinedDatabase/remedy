# T3_F076 — Vision-capable planner
**Tier 3 · Depends on: F013 attachments · Blocks/used by: Tier 6**

## Goal & Done
Missions can SHOW instead of only tell: image attachments (mockups,
screenshots) flow into intake and planning as real image inputs where
the configured model supports vision — and where it doesn't, a
separate vision call produces a structured description that is
honestly labeled as a description, never passed off as the image.
DONE when a fixture mockup measurably shapes the plan (design-region
hints on tasks), the capability gate routes correctly per model, and
the fallback path's labeling is visible in evidence and plan.

## How it fits (inspect current shape before building)
Intake accepts mission input via the do path — attachments need a CLI
surface (`--attach <path>`, repeatable; verify whether an attachment
notion already exists on the job/intake from the schema work and
extend additively) and storage in the job's evidence area (originals
kept, hashed into the run manifest like other inputs). Provider
adapters need a vision capability flag (the same additive
capability-surface pattern the resume feature used); routing already
picks models per class — planner/intake classes gain a
vision-required variant when attachments are present.

## Design (suggested shape)
- Attachment intake: accepted types (png/jpg, size cap config);
  stored + hashed; referenced from the intake record.
- Capability path: model supports vision → attachments go into the
  intake and plan calls as image content parts; evidence records
  images_sent (hashes). Model lacks vision → one vision call (a
  vision-capable model from config; absent → the honest degradation
  below) produces a structured VisionDescription (versioned schema:
  regions[{name, bounds_hint, elements, text_content}], overall
  layout summary) which is injected as a clearly labeled segment
  ("DESCRIPTION OF ATTACHED IMAGE (generated) — the planner did not
  see pixels"); the plan carries vision_basis: native|described|none.
- No vision anywhere configured → intake proceeds text-only with the
  label vision_basis none and a warning line — never a hard failure
  (attachments still archived for humans).
- Plan effect: planned tasks touching UI carry design_region hints
  referencing the description/regions — the DoD compiler and later
  visual checks can consume them.

## Task slicing
- **T001** attachment CLI + storage + manifest hashing + type/size
  validation + tests.
- **T002** capability flag + native path + evidence + fake
  vision-provider tests.
- **T003** the description schema + fallback call + labeled segment
  + degradation path + fixture tests proving the label appears in
  plan/evidence for described and none bases.

## Acceptance
- Fixture mockup + vision-capable fake: plan tasks reference regions;
  evidence lists image hashes. Non-vision fake + vision fallback:
  same mission yields a plan with vision_basis described and the
  label in the prompt evidence. Nothing configured: text-only run,
  warning present, attachments archived. Oversized/wrong-type
  attachments rejected at the CLI with clear messages.

## Edge cases & assumption defaults (A9)
- Multiple attachments: all processed, described individually, a
  combined layout note; per-call image count caps follow the
  provider's limits (config, conservative default). Secrets in
  screenshots are the user's responsibility — documented, not
  scanned (v1 honesty about scope).

## Orchestrator brief
T001/T002 parallel after the capability-flag pattern is confirmed;
T003's labeling rule goes verbatim into the order ("described is
never presented as seen"). Tier 6 consumers build on the
design_region vocabulary — keep it minimal and stable.

## Do not touch
Visual regression testing, screenshot capture (later tiers), routing
internals beyond the vision-required variant. Suggested tests:
tests/orchestration/test_vision_planner.py.
