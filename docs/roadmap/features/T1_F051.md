# T1_F051 — Escalate instead of block (unattended)
**Tier 1 · Depends on: F050, F046 (the backend decision queue already exists in the codebase) · Future UI integration: F031 inbox UI · Blocks/used by: long-run throughput**

## Goal & Done
An unattended run never stalls on the first human question: a task that
needs a decision pauses only its branch, the executor keeps pulling ready
tasks from disjoint branches, and open questions surface prominently so a
returning human can answer them in one place. DONE when a fixture with one
decision-blocked branch and two free branches finishes the free work,
lists the open decision in status and report, and answering it lets a
resume complete the rest.

## How it fits (inspect current shape before building)
The decision queue and its CLI already exist and are already used by plan
approval and budget stops — escalation reuses them unchanged (A6). DAG
scheduling already localizes blockage to a branch; this feature connects
"task raised a question" to "enqueue decision + mark branch
awaiting-decision" instead of ending the run. Notification delivery is a
later feature — here the surfacing is CLI/status/report only.

## Design (suggested shape)
- A task outcome "needs_decision" (additive; produced today mainly by
  review blockers and budget interplay, later by more sources): the
  executor enqueues one decision carrying task id, question, options, and
  a safe default where one exists, marks the task awaiting-decision, and
  continues with the ready set.
- Status and report render open decisions FIRST — an unattended run's
  most important output is what it needs from you.
- Answering uses the existing decision CLI; a resumed or still-running
  executor picks up answered branches at the next batch boundary
  (re-check awaiting tasks when recomputing the ready set).
- End of run with open decisions → terminal status blocked, and the final
  report's next-action line says exactly which command answers them.

## Task slicing
- **T001** the needs_decision outcome + enqueue + branch marking + unit
  tests.
- **T002** executor continuation + answered-branch pickup + the
  three-branch fixture (one blocked, two free) end-to-end.
- **T003** status/report surfacing (open decisions first, with the answer
  command) + tests.

## Acceptance
- Fixture: free branches complete, blocked branch waits, run ends blocked
  with one open decision; answer + resume completes everything; evidence
  shows the pause/resume timeline.
- No polling loops: answered decisions are noticed at batch boundaries
  (assert check count).
- A decision answered while the run still executes other branches is
  picked up without restart.

## Edge cases & assumption defaults (A9)
- Two tasks raising the same question → two decisions (deduplication is a
  human call; cross-reference them in the payload). A decision with a safe
  default is still ASKED in attended mode — defaults auto-apply only under
  --yes/unattended, and the assumption log records that (consistency with
  the bundled-clarification rules).

## Orchestrator brief
Gate on DAG scheduling. T002's fixture is the acceptance heart — spell the
three-branch topology in the order. Remind workers: extend the existing
decision queue records additively; a second queue is an automatic reject.

## Do not touch
Notification channels, inbox UI, decision auto-answering. Suggested tests:
tests/orchestration/test_escalation.py, tests/cli/test_open_decisions_view.py.
