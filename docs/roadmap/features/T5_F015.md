## Goal & Done
The human can reshape the plan before blessing it: plan_edit_*
commands (edit/delete/reorder/merge/split tasks, edit acceptance
criteria) are valid ONLY while the plan approval is open, every edit
revalidates the DAG, the full edit log lands in evidence
(user_edited_plan), and execution follows the edited plan EXACTLY —
proven by hash. DONE when each edit command round-trips through the
write channel on fixtures with correct revalidation, an approved or
running plan refuses edits with the state named, and the executed
task set hash-matches the post-edit plan.

## How it fits (inspect current shape before building)
The write channel enqueues; plan edits are its first rich payload:
the effect target is a plan-editing backend OPERATING ON THE STORED
FLIGHT PLAN through a validated transaction (load plan → apply edit
→ revalidate with the SAME DAG validator and schema the planner
used → persist + regenerate plan.md + append the edit log) — no
parallel plan representation. Merge/split reuse the granularity
module's mechanics where they fit (split by acceptance items) with
manual parameters — cite the reuse, don't reimplement. The approval
gate's openness is the edit window: consuming the approval closes
it atomically (an edit racing an approval loses cleanly with a
truthful conflict answer).

## Design (binding specifics)
- Commands (each args-schema'd in the catalog): plan_edit_task
  (title/goal/acceptance/band/files_hint fields), plan_delete_task
  (with dependency rewiring: dependents inherit the deleted task's
  depends_on — stated, tested), plan_reorder (explicit order list),
  plan_merge_tasks (ids, manual), plan_split_task (id + acceptance
  partition), plan_edit_acceptance (per-criterion add/edit/remove;
  empty acceptance stays invalid — schema holds).
- Every edit: full revalidation (cycles, orphans, unknown deps,
  schema) — failures return typed errors and change NOTHING
  (transactional); success bumps a plan revision counter, appends
  {ts, actor fingerprint, command, before/after diff} to the edit
  log, regenerates plan.md (revisioned like replans).
- Execution fidelity: at approval consumption, the plan's content
  hash is recorded; the executor asserts it at start (the belt to
  the transaction's suspenders).
- UI affordances land with the plan view (later feature) — here the
  backend + channel contract + CLI parity (`remedy plan edit ...`
  thin wrappers through the same backend) ship complete.

## Task slicing
- **T001** the editing backend (transactional apply + revalidate +
  revision + log) + per-edit-kind unit tests incl. the delete-
  rewiring rule and failed-validation atomicity.
- **T002** channel wiring (schemas, effects) + the edit-window rule
  + race-with-approval conflict tests + CLI parity wrappers.
- **T003** execution-fidelity hash + plan.md regeneration goldens +
  the end-to-end (edit, split, reorder → approve → run executes the
  edited shape, hash asserted).

## Acceptance
- Each command's fixture round-trips; invalid edits change nothing
  and name the violation. Edits after approval/start refused with
  state. The edit log reconstructs the plan evolution (replay
  test). Executed tasks hash-match. plan.md revisions golden.

## Edge cases & assumption defaults (A9)
- Editing away every task: refused (a plan needs ≥1 task — schema).
  Concurrent edits (two tabs): revision-checked — the stale edit
  gets a conflict with the current revision (no last-write-wins on
  plans). Clarification answers are NOT editable here (immutable by
  the bundled-clarification rules — the boundary named in errors).

## Orchestrator brief
Gate on the write channel. T001's transactional atomicity and the
delete-rewiring rule go verbatim into the order. The revision-
conflict discipline is what makes the later UI safe — test it
before any UI exists.

## Do not touch
Approval semantics, clarification immutability, granularity's
automatic pass, executor scheduling. Suggested tests:
tests/orchestration/test_plan_editing.py.

## Built State (F015, 2026-09-24)

What exists on disk at the close of F015, built in four rounds of one session on
`feature/f015-interactive-plan-editing`, cut from `main` at `fce49ce0`. Every DECISION named lives
in `.agent/decisions.md`; every round's verdict in `.agent/live_review.md` or, once rotated, its
archive.

**T001 — the editing backend.** `packages/orchestration/plan_editing.py`. `edit_plan(job_id,
command, args, *, expected_version, actor)` is one transaction on the job record's stored
`task_plan`: under a per-job advisory lock (`plan_edit.lock` in the job's directory) it loads the
record, refuses unless `_approval` reads `pending` and the job is `planned`, refuses a stale
`expected_version` with the current one, applies the edit, revalidates it, and writes the edited
plan, its `_version` bumped, the new `_edits` log entry and the task list `map_task_plan_to_tasks`
regenerates in ONE write of the record; `plan_v<n>.md` and `user_edited_plan.json` in the job's
evidence export follow from that write (DECISION F015 D1). The six edits are `plan_edit_task`,
`plan_delete_task` (each dependent inherits the deleted task's own dependencies in its place),
`plan_reorder`, `plan_merge_tasks` and `plan_split_task` (the granularity module's `_merge_group`,
`_split_task` and `_rewire` with the human's parameters) and `plan_edit_acceptance`.
Revalidation is the planner's own: `TaskPlan`'s schema and DAG check, then
`validate_deliverable_plan`. Every refusal raises `PlanEditRefused` with a code before anything is
written. Each log entry holds the whole task list before and after, and `replay_edits` rebuilds
the plan's evolution from the original.

**T002 — the edit window and the doors.** `consume_plan_approval` consumes a plan approval under
the same lock against the record as it stands then, so an edit landing after a door loaded the job
is approved rather than written over, and an approval that closed meanwhile is refused
`approval_closed`; both approval doors, `remedy decision resolve` and the write door's
`decision.resolve`, call it, and `resolve_task_plan_approval` runs inside it unchanged (DECISION
F015 D2). The CLI gains `remedy job plan-show` and the six `remedy job plan-*` edit commands in
`apps/cli/commands/job_plan_cmd.py`, under the `job` group because `plan` is the retired roadmap
word; each edit requires `--plan-version` and exits 2 for bad arguments, 3 for a plan or job not
ready and 1 for an edit the planner's checks refuse (D2). The write door exposes the six
`job.plan-*` ids, requires `args.expected_version`, runs each edit through `edit_plan` under the
request's token fingerprint, and answers a refusal with its status and reason (DECISION F015 D3).

**T003 — execution fidelity.** An approval records `_approved_plan_sha256`, the content hash of
the stored plan's own fields, whether a human approves through `consume_plan_approval` or
`auto_approve_task_plan` approves unattended; a rejection records none. `run_job` checks
`approved_plan_mismatch` at every start, before any workspace exists, and blocks the job with
`plan_changed_since_approval` when the plan no longer hashes to the record or the job's
plan-derived tasks are not that plan's tasks in its order. Because a job runs its tasks in plan
order, an edit may not put a task before a task it waits for. An edited revision's
`plan_v<n>.md` names each edit's version, command and editor in an `## Edits` section, and an
unedited plan renders as before (DECISION F015 D4).

**Acceptance, by the test that proves it.** Each command's fixture round-trips: the backend in
`tests/orchestration/test_plan_editing.py` (`TestEachEditRoundTrips`), the CLI in
`tests/cli/test_job_plan_cmd.py` and the write door in `tests/ui_server/test_command_dispatch.py`
(`TestPlanEditDispatchEffects`). Invalid edits change nothing and name the violation:
`TestInvalidEditsChangeNothing` reads the job record byte-identical after every refusal. Edits
after approval or start are refused with the state: `TestTheEditWindow` and
`TestTheApprovalClosesTheWindow`, and the approval race at both doors in
`TestTheCliApprovalDoor` and the plan-approval dispatch class. The edit log reconstructs the plan's
evolution: `TestTheLogReconstructsThePlan`. The executed tasks hash-match:
`tests/orchestration/test_plan_edit_execution.py`, whose end-to-end run splits, reorders and edits
a plan, approves it and runs it with the fake provider in exactly its edited sequence, and whose
refusals block a job whose plan or task list changed after approval. The `plan.md` revisions are
golden: `TestThePlanRevisionsAreGolden` over the frozen files under
`tests/orchestration/fixtures/plan_editing/golden/`. Each round's mutation proofs are its
`.agent/authored/f015-r<n>-mutations.py`.
