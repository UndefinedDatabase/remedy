## Goal & Done
The human can reshape the plan before blessing it: plan_edit_*
commands (edit/delete/reorder/merge/split tasks, edit acceptance
criteria) are valid ONLY while the plan approval is open, every edit
revalidates the DAG, the full edit log lands in evidence
(user_edited_plan), and execution follows the edited plan EXACTLY —
proven by hash. DONE when each edit command round-trips through the
write channel on fixtures with correct revalidation, an approved or
running plan refuses edits with the state named, and the executed
task set hash-matches the post-edit plan.

## How it fits (inspect current shape before building)
The write channel enqueues; plan edits are its first rich payload:
the effect target is a plan-editing backend OPERATING ON THE STORED
FLIGHT PLAN through a validated transaction (load plan → apply edit
→ revalidate with the SAME DAG validator and schema the planner
used → persist + regenerate plan.md + append the edit log) — no
parallel plan representation. Merge/split reuse the granularity
module's mechanics where they fit (split by acceptance items) with
manual parameters — cite the reuse, don't reimplement. The approval
gate's openness is the edit window: consuming the approval closes
it atomically (an edit racing an approval loses cleanly with a
truthful conflict answer).

## Design (binding specifics)
- Commands (each args-schema'd in the catalog): plan_edit_task
  (title/goal/acceptance/band/files_hint fields), plan_delete_task
  (with dependency rewiring: dependents inherit the deleted task's
  depends_on — stated, tested), plan_reorder (explicit order list),
  plan_merge_tasks (ids, manual), plan_split_task (id + acceptance
  partition), plan_edit_acceptance (per-criterion add/edit/remove;
  empty acceptance stays invalid — schema holds).
- Every edit: full revalidation (cycles, orphans, unknown deps,
  schema) — failures return typed errors and change NOTHING
  (transactional); success bumps a plan revision counter, appends
  {ts, actor fingerprint, command, before/after diff} to the edit
  log, regenerates plan.md (revisioned like replans).
- Execution fidelity: at approval consumption, the plan's content
  hash is recorded; the executor asserts it at start (the belt to
  the transaction's suspenders).
- UI affordances land with the plan view (later feature) — here the
  backend + channel contract + CLI parity (`remedy plan edit ...`
  thin wrappers through the same backend) ship complete.

## Task slicing
- **T001** the editing backend (transactional apply + revalidate +
  revision + log) + per-edit-kind unit tests incl. the delete-
  rewiring rule and failed-validation atomicity.
- **T002** channel wiring (schemas, effects) + the edit-window rule
  + race-with-approval conflict tests + CLI parity wrappers.
- **T003** execution-fidelity hash + plan.md regeneration goldens +
  the end-to-end (edit, split, reorder → approve → run executes the
  edited shape, hash asserted).

## Acceptance
- Each command's fixture round-trips; invalid edits change nothing
  and name the violation. Edits after approval/start refused with
  state. The edit log reconstructs the plan evolution (replay
  test). Executed tasks hash-match. plan.md revisions golden.

## Edge cases & assumption defaults (A9)
- Editing away every task: refused (a plan needs ≥1 task — schema).
  Concurrent edits (two tabs): revision-checked — the stale edit
  gets a conflict with the current revision (no last-write-wins on
  plans). Clarification answers are NOT editable here (immutable by
  the bundled-clarification rules — the boundary named in errors).

## Orchestrator brief
Gate on the write channel. T001's transactional atomicity and the
delete-rewiring rule go verbatim into the order. The revision-
conflict discipline is what makes the later UI safe — test it
before any UI exists.

## Do not touch
Approval semantics, clarification immutability, granularity's
automatic pass, executor scheduling. Suggested tests:
tests/orchestration/test_plan_editing.py.
