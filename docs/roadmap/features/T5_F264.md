> Registered 2026-08-31 by operator order amend0831-vocab-registrations.
> REGISTRATION ONLY — nothing in this file has been implemented.

## Goal & Done
A STEERING channel for the runs of a mission. `remedy chat <job_id>` — and the same
thing as a cockpit input field — accepts free-form user messages. The run reads
them at the NEXT SAFE POINT, works them into the next prompt, and ACKNOWLEDGES
visibly to the user WHAT it understood and FROM WHICH ROUND it takes effect.
Messages land in the event log and are certified there.

Explicitly NO talking into a running model call.

Per DECISION amend0905-vocab D9 (2026-09-05) a steering message is an
AMENDMENT to the mission's contract: it is recorded on the mission, the DoD is
recompiled, and the acknowledgement names what was understood and from which
round it applies. The data shape (`contract.amendments[]`, round of effect,
recompile) lives in F269; F264 builds only the channel — `remedy chat` and the
cockpit input — and the acknowledgement event.

DONE when a message sent during round N provably influences round N+1, and the
acknowledgement appears both in the cockpit and in the CLI.

## Why this exists
Watching a job go the wrong way and having only one button — stop — is the
expensive part of operating Remedy today. The correction the operator wants to
make is usually one sentence long, and today it costs a kill, an edit and a
restart, which throws away the rounds that were fine. A steering channel turns
that sentence into the cheapest possible intervention. The acknowledgement is
not a nicety: a steering message the run silently ignored is worse than no
channel at all, because the operator stops watching.

## Design
- The write path is F009's single write channel — authenticated, CSRF-guarded,
  rate-limited, nonce-idempotent. No second mutating route is created; a
  steering message is a command like any other.
- The read path is F008's SSE stream: the acknowledgement is an event, so the
  cockpit and the CLI render the same fact from the same source and cannot
  disagree.
- Delivery is at a SAFE POINT ONLY. A message arriving mid-call waits. This is
  a hard boundary, not a latency target.
- The acknowledgement states two things and is useless without either: the
  run's own restatement of what it understood, and the round number from which
  it applies. A bare "received" is not an acknowledgement.
- Messages are evidence. They are certified into the event log with their
  timestamp and the round they were consumed in, so a later reader can see why
  round N+1 differs from round N.

## T001 — The message channel
Accept, persist and certify a steering message over F009's write channel.
No consumption yet — this slice proves the message survives.

## T002 — Consumption at the safe point
The run picks up pending messages at its next safe point and folds them into
the next prompt. A message that arrives mid-call demonstrably waits.

## T003 — The acknowledgement
The restatement-plus-round event, rendered in both the cockpit and
`remedy chat`, from the same SSE event.

## Acceptance
- A message sent during round N provably changes round N+1 — proved by a
  fixture comparing the round N+1 prompt with and without the message.
- The acknowledgement names what was understood AND the effective round.
- A message sent mid-call is not consumed until the next safe point.
- Every message appears in the event log with its consumption round.

## Do not touch
F009's write-channel contract (this feature uses it, it does not widen it), the
approval gate, and the model call itself — nothing in this feature reaches into
a call in flight.
Interactive co-editing of a job's worktree by the human and the model at the
same time is an explicit non-goal of this feature; the operator noted on
2026-09-21 that it is possible but of uncertain demand, and it stays an idea
until he asks for it (DECISION amend0921-operator-feedback D5).

## Orchestrator brief
T001 first and alone: a persisted, certified message with no consumer is a
complete, testable thing. T002 is the risky slice — the safe-point boundary is
the property most likely to be quietly violated, so it needs a red proof that a
mid-call message WAITS. T003 is small but is the acceptance-visible half; it
cannot be dropped for budget without dropping the feature's point.

## Built State (F264, 2026-09-24)

What exists on disk at the close of F264, built in seven rounds of one session on
`feature/f264-steering-channel`, cut from `main` at `ef4cb503`. Every DECISION named lives in
`.agent/decisions.md`; every round's verdict in `.agent/live_review.md` or, once rotated, its
archive. The operator-facing description is `docs/guides/steering-user-guide-v1.md`.

**T001 — the message channel.** `packages/orchestration/steering.py` is the one place a message
is accepted. `record_steering_message` refuses an ended job, an empty message, a NUL character
and anything over `STEERING_MAX_CHARS` (2000), then writes the message create-once as a sealed
record `steering/sm-<nnnn>.json` under the job's evidence folder and only then certifies it into
the run log as a `steering_message_received` event carrying the record's seal (DECISION F264 D1).
`remedy chat send <job_id> "<message>"`, and the bare `remedy chat <job_id> "<message>"`, are its
CLI route in `apps/cli/commands/chat_cmd.py`, exiting 2 on an unusable message and 3 on an ended
or unreadable job. The cockpit's route is the catalog command `chat.send` on F009's write door,
which records and never reaches a call (D2), sent only through `apps/ui/src/api/steeringSend.ts`
from the live input at the bottom of the activity card, which answers every send with one
sentence and keeps a refused message in the field (D3).

**T002 — consumption at the safe point.** `run_pingpong` calls `consume_pending_steering` at the
top of every round, before anything of that round is composed or sent, and never from the stop
probe that also runs between retries of one call. A message is consumed exactly once, by a sealed
create-once marker `steering/consumed/<message_id>.json` naming the task and round, and every
consumed message rides in the builder prompt's `builder_steering` segment, verbatim, in every
later round of the job (D4). For a mission's job, consuming a message also amends the mission's
contract once through F269's `amend_mission_contract`, before its marker is published, and a
failed amendment stops the run loudly (D5).

**T003 — the acknowledgement.** The `steering_message_consumed` event is the acknowledgement: its
`understood` field quotes the message verbatim with the task round it applies from, and for a
mission's job the contract criterion and mission round (D6). The stream carries it as the frame's
`steering` field; `remedy chat show <job_id>` reads the same events and lists every message as
taken in, waiting, or not taken in; and the cockpit's activity feed shows it as the line
"Steering taken in at round <n>: <restatement>." through the checked reader
`apps/ui/src/api/steeringAck.ts` (D7). A message that arrives during a job's very last round is
never consumed, and `remedy chat show` says so.

**Acceptance, by the test that proves it.** Round N+1 changes and round N does not:
`tests/orchestration/test_steering_consumption.py::test_a_message_sent_during_round_one_changes_round_two_and_only_round_two`,
which compares the builder prompts with and without the message. A message sent mid-call waits
for the next safe point: `test_the_consumption_round_is_the_round_after_the_call_it_arrived_in`
in the same file. The acknowledgement names what was understood and the effective round:
`tests/orchestration/test_steering.py`, `tests/cli/test_chat_cmd.py`,
`tests/ui_server/test_sse_stream.py::TestFrameShape::test_a_steering_acknowledgement_carries_its_three_fields_and_no_other`
and `apps/ui/src/api/steeringAck.test.ts`. Every message appears in the event log with its
consumption round: the received and consumed events asserted in `tests/orchestration/test_steering.py`.
