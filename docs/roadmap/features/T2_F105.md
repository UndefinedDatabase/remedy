## Goal & Done
Prompt assembly stops being ad hoc: every prompt is composed from
REGISTERED SEGMENTS ordered by stability — stable prefixes first (system,
role conventions, dossier, cards), volatile parts last (task, steering) —
and the cache-read share per role is measured so the ordering's value is
visible in numbers. DONE when all existing prompt builders compose
through the registry, segment order is byte-stable across calls within a
role, and a stats view shows cache-read share per role from actuals.

## How it fits (inspect current shape before building)
Prompts today are assembled in several builders (intake, plan, mission,
orchestrator, worker/reviewer rounds) — inventory them first; migrating
each to the registry is the bulk of the work and must not change their
CONTENT, only their composition (golden before/after content-equality
tests per builder, modulo ordering). Cache metrics exist in the actuals
capture; the measurement view reads them — no new capture.

## Design (suggested shape)
- `prompt_segments.py`: a registry of named segments with declared
  stability ranks (system=0, conventions=1, dossier/cards=2,
  job-context=3, task=4, steering=5 — documented scale); compose(role,
  segments) sorts by rank then registration order, concatenates with
  stable delimiters, and returns both the prompt and a segment manifest
  (names, ranks, hashes) recorded into call evidence — auditability of
  what was where.
- **Canonical conventions content:** the worker/builder role loads
  `docs/agents/worker_conventions.md` and the review role
  `docs/agents/reviewer_conventions.md` verbatim as its conventions
  segment — each hard-capped at ≤800 tokens (a loader check fails loudly
  over cap). These two files become the single written source of the
  role rules that today live implicitly in code and heads; creating
  their v1 content EXISTS and is battle-tested (2026-07 split workflow,
  docs/agents/); this feature LOADS and reconciles them — it must not
  re-author policy, and any content change goes through a reviewed diff
  of those files, never through prompt-builder code. The orchestrator's conventions
  segment remains the generated protocol block from the loop feature —
  no second source. The model-routing policy document is policy input
  for a later routing feature, NOT a prompt segment.
- Volatile-tail rule: anything per-task or per-iteration ranks last;
  the dossier ranks stable because its section skeleton is stable even
  as content updates.
- Measurement: `remedy stats cache [--by role]` — cache-read share per
  role over time from actuals; the acceptance number is DIRECTIONAL
  (share should rise after migration), not a hard threshold.

- **Operator addition 2026-07-30:** the canonical conventions segments
  assembled by this feature include a distilled write-discoverable-code
  block (sourced from the AGENTS.md "Code Discoverability Conventions"
  section, compressed to fit the segment token caps) in BOTH the BUILDER
  and REVIEWER segments of Remedy's internal prompts — Remedy's own
  generated code must be navigable by the text-search-driven agents that
  will read it, including Remedy itself.

## Task slicing
- **T001** registry + compose + manifest-in-evidence + rank scale +
  unit tests (ordering stability, delimiter stability, over-cap loader
  failure).
- **T002** conventions files v1 (extracted, capped) + role loaders +
  content-equality goldens proving extraction changed no rules.
- **T003** migrate the builders one by one, each with its
  content-equality golden; the segment manifest appears in call
  evidence for every role.
- **T004** the cache stats view + a before/after comparison note in the
  feature's evidence (honest numbers, whatever they are).

## Acceptance
- Every builder composes via the registry (a guard test greps direct
  string-assembly patterns in the builder modules and fails on
  stragglers — allowlist starts empty). Same role, consecutive calls:
  identical prefix bytes up to the volatile tail (hash test).
  Conventions over 800 tokens fail the loader. Cache stats render from
  fixture actuals.

## Edge cases & assumption defaults (A9)
- Providers without cache reporting: the stats view shows "not
  reported" for those calls — never zeros pretending to be
  measurements. Segment content changes legitimately (dossier updates):
  the manifest hash trail makes cache misses explainable.

## Orchestrator brief
T001/T002 parallel; T003 as one order PER BUILDER (small reviewable
diffs, each with its golden); T004 last. The conventions extraction
order must list its sources (which prompts/files the rules came from)
for review.

## Do not touch
Model routing policy content, provider-side cache configuration, prompt
CONTENT beyond composition. Suggested tests:
tests/orchestration/test_prompt_segments.py plus per-builder goldens.

## Built State
_As built and reviewed on branch `feature/f105-cache-optimal-prompt-ordering` (T001–T004)._

- **The registry (T001)** is `packages/orchestration/prompt_segments.py`:
  `PromptSegmentRegistry` collects NAMED segments and rejects duplicates,
  `SegmentStabilityRank` is the documented 0–5 scale, and
  `compose_prompt_segments` sorts by `(rank, registration index)` — registration
  order is the tie-break, so composition is deterministic rather than dependent
  on iteration order. It joins with `PROMPT_SEGMENT_DELIMITER`, a plain blank
  line and nothing else (DECISION F105 D1), and returns `ComposedPrompt(text,
  manifest)` whose rows carry `name, rank, sha256, chars, tokens_estimated`. The
  manifest reaches evidence through `PromptTraceEntry.segment_manifest`, derived
  from the composed prompt at one seam so a manifest can never describe another
  prompt.
- **The conventions loaders (T002)** are
  `packages/orchestration/role_conventions.py`. They load
  `docs/agents/worker_conventions.md` and `docs/agents/reviewer_conventions.md`
  VERBATIM — no strip, no re-wrap, no header — and register each as the
  `CONVENTIONS`-ranked segment. `CONVENTIONS_TOKEN_CAP` is imported from
  `prompt_segments` and enforced by the registry rather than restated. Remedy
  deliberately provides no writer for either document: the rules change through
  a reviewed diff of the documents themselves.
- **Six builders migrated (T003)**, each in its own commit under its own
  content-equality golden: `compose_intake_prompt` (`intake.py`),
  `compose_flight_plan_prompt` (`flight_plan.py`), `compose_mission_prompt`
  (`mission_compiler.py`), `compose_orchestrator_prompt` /
  `compose_orchestrator_system_prompt` (`orchestrator_loop.py`), and
  `compose_builder_prompt` / `compose_reviewer_prompt` (`pingpong_loop.py`). The
  goldens freeze each pre-migration form and prove content equality modulo
  ordering; the orchestrator site was already in rank order and its golden
  asserts byte equality.
- **The measurement (T004)** is `remedy stats cache`, a read-only view over the
  ledger rows that already exist, with a `--json` mode carrying the same
  figures. It renders `unmeasured` when nobody reported the inputs and
  `undefined` when they were reported and were zero — never a `0` standing in
  for either — and prints its own per-role limit rather than passing one
  hardcoded `builder` bucket off as a breakdown.
- **The numbers live in one place:**
  [../../system/cache-optimal-prompt-ordering-v1.md](../../system/cache-optimal-prompt-ordering-v1.md)
  carries the measured before/after cacheable-prefix table, the command that
  reproduces it, and the reason the provider-side cache-read share is
  unmeasured. They are deliberately not restated here.
