# T13_F207 — Coordinated PR trains
**Tier 13 · Depends on: F205, F206, F164 · Blocks/used by: system changes become manageable; F212**

## Goal & Done
See ROADMAP.md F207; the Done criterion there is binding.

## Context (existing code & prior features)
The single-PR flow exists (worktrees + branch handover); cross-repo coordination is missing.

## Design
A train manifest train_<id>.json per multi-repo change: PRs[{pid, repo, pr_url, depends_on}], per-PR status (polled via the gh CLI per repo, budgeted). PR descriptions get generated cross-references + the train id (a Remedy-Train trailer). A status board in the cockpit (mission view): a light per PR, the recommended merge order (from the F206 topology), blockers highlighted. MERGING STAYS HUMAN - Remedy proposes the order and updates status; it never presses the button.

## Task slicing
T001 manifest + PR creation with cross-references + gh-stub tests. T002 status polling + the board UI + the order recommendation + a fixture train over 2 repos.

## Acceptance & tests
The fixture train: a consistent manifest, cross-links in both PR texts, the board reflects a status change after polling; NO merge API call exists in the code (a grep gate as a test).

## Risks / anti-goals
No 'atomic multi-repo merge' promise (it does not exist - docs are honest about the inconsistency window + mitigations via ordering/feature-flag recommendations).
