## Goal & Done
Money is visible while it burns, honestly: the MetricsBar's COST
metric renders from budget tick events {spent, limit, basis} — bar
fill against the limit, a '~' prefix plus tooltip whenever the
basis is estimated, warn color at ≥85% — and the final figure
reconciles with the ledger at terminal. DONE when the ticker
tracks a fixture stream exactly, basis changes flip the prefix/
tooltip live, the warn threshold triggers per tokens, limitless
jobs render the spent-only variant (no fake denominators), and the
terminal reconciliation displays the ledger figure with any delta
labeled.

## How it fits (inspect current shape before building)
The budget guard already evaluates spent-vs-limits at safe points
— it gains a lightweight budget.tick event emission into the
ledger stream at those same evaluations (additive event kind in
the Part E vocabulary — coordinate the envelope there; the SSE
layer carries it for free). Basis honesty flows from the counting
rules already established (actuals vs ">= N unmeasured" vs
estimated pricing) — the tick carries the basis verbatim; the UI
never computes money itself (display-only discipline: the backend
is the single arithmetic home).

## Design (binding specifics)
- budget.tick payload: {spent_usd?, spent_tokens, limit_usd?,
  limit_tokens?, basis, unmeasured_calls} — currency fields only
  when a price basis exists (no invented dollars).
- MetricsBar COST: fill = spent/limit on the strongest configured
  limit (usd preferred when both); '~' prefix + tooltip text from
  the basis ("estimated — class defaults" / "actuals with N
  unmeasured calls"); ≥85% flips to the warn token, ≥100% to the
  exceeded treatment per the design reference (the budget stop
  will land moments later — the bar tells the truth in the
  meantime); no limit → spent-only compact variant.
- Terminal reconciliation: on the terminal event, read the
  ledger's final budget tick — the last `budget.tick` in the
  job's `budget-ticks` run log, in the same whitelisted shape
  the stream already carries — and render it as the final
  value; a delta beyond rounding renders "final (ledger):
  X — live estimate was Y" (the honesty moment, small type,
  per reference). AMENDED at F022 R11 per DECISION F022 D7:
  this bullet previously named "the stats endpoint", which
  `ui_server.py` does not dispatch, and the nearest substitute
  (`token_usage`) is an estimate over a different event
  population, so a delta against it would be fabricated. The
  delta this bullet asks for is a TRANSPORT statement — what
  the client received against what the ledger holds — and
  never a second arithmetic.
- The ticker animates value changes per motion tokens (count-up,
  no spinny drama).

## Task slicing
- **T001** the tick emission at safe-point evaluations (additive
  event kind, envelope coordinated) + backend tests (cadence,
  payload honesty incl. unmeasured).
- **T002** the COST metric component on fixture streams (fill,
  prefix, tooltip, thresholds, no-limit variant) + CSS/token
  conformance.
- **T003** terminal reconciliation + delta labeling + the live
  fake-job end-to-end (estimated basis mid-run, actuals at end).

## Acceptance
- Fixture stream renders every state exactly (goldens per
  threshold and basis). No client-side money arithmetic beyond
  fill ratio (code review + a guard on price constants in the
  frontend). Reconciliation shows the ledger figure; deltas
  labeled. Limitless variant never fabricates a denominator.

## Edge cases & assumption defaults (A9)
- Ticks during rate-limit waits: spent is flat, the bar stays
  truthful (waits burn wall clock, not tokens — the wait state is
  the feed/timeline's story, not the ticker's). Multiple limits
  configured: the tooltip enumerates all with their fills; the
  bar shows the tightest.
