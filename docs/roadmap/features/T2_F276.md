## Goal & Done
Every directory class under the data root has a named owner and a reclaim rule; an
operator reclaims scratch through one preview-first command; a job refuses to start,
and an in-flight job stops at a safe point, when free disk falls below a configured
floor, in the same vocabulary as every other exhausted budget.

DONE when the Acceptance list holds.

## Why this exists
Measured on the operator's machine 2026-09-08 by `remedy brain` runs 002 and 003,
independently: `.data` 652 GB, `.data/job_workspaces` 650 GB in 2 290 `staging_*`
directories, 1 901 of them over 100 MB. A sampled one held 1 190.8 MB across 76 files
above 5 MB, its five largest being `remedy-review-*.zip` review packages that the
target repository's own `.gitignore` excludes.

Verified in code at `a5bf8949`:

- `packages/orchestration/pingpong_job.py::_create_job_workspace_copy` — the non-git
  fallback, `isolation_mode="copy"` — calls
  `staging_workspace.create_staging_workspace` and never calls `discard_staging`. The
  worktree path has a cleanup path; the copy path has none.
- `staging_workspace._copy_tree` filters directories by a fixed name set and files
  only through `_is_env_file`. It reads neither `.gitignore` nor file size.
- `shutil.disk_usage` and `os.statvfs` appear zero times under `packages/`, `apps/`
  and `scripts/`. Nothing in this repository has ever asked how much disk is left.

F166 (retention & archive export, Tier 9) governs audit evidence, preview-first and
never timer-driven. F199 (Tier 12) names a doctor disk threshold as a REPORT. Neither
reclaims scratch.

Operator ruling 2026-09-08 (DECISION amend0908-brainstorm-intake D3): non-git targets
stay supported — Remedy is for people without git — but they are not the operator's
priority, so the copy mode is REPAIRED here, not deleted.

## Design
The data root gains a class registry, two commands over it, a lifecycle repair on the
copy path, and one budget. Nothing here deletes on a timer and nothing here deletes a
path a preview did not name.

AMENDMENT, DECISION F276 D3 (2026-09-20, reviewer, round 2): T001's list of ephemeral
classes below is amended in THREE places — `workspaces`, `runs` and `job_logs` are all
DURABLE, leaving two ephemeral classes, `job_workspaces` and `review_staging.*`, and

## T001 — The class registry and `remedy data usage`
`data_paths.EPHEMERAL_CLASSES` (job workspaces, workspaces, runs, ping-pong runs, task
jobs, job logs, review staging) and `DURABLE_CLASSES`, both declared as data. An
architecture test asserts every top-level child of the data root is in exactly one of
the two, so a new class cannot be added silently. `remedy data usage` is read-only,
carries `--json`, and reports through a `footprint()` that walks the tree once and
shells out to nothing.

## T002 — `remedy data reclaim`, dry run by default
The preview lists workspace, job id, terminal state, age, bytes and total. `--apply`
deletes only the exact paths the preview named; it refuses any path that is not a
direct child of a class directory, and refuses any workspace whose job is not
terminal. A second `--apply` over the same state is a no-op. This is the command the
operator runs once against the 650 GB measured above — preview first.

AMENDMENT (2026-09-20, round 3): T002 gains `--orphans`, OFF by default; nothing above
changes. The rule above refuses a `staging_<id>` child whose job record cannot be
resolved, and on the operator's own root that refusal is where the bytes are. MEASURED
2026-09-20 ON THE OPERATOR'S DATA ROOT with the command round 2 built: 1 107 candidates
worth 284 536 286 695 bytes, against 1 886 refusals of which 1 885 are `job_unresolved`
worth 638 395 396 948 bytes — and 1 884 of those are `staging_<16-hex>` names with no
job record on disk at all (`.data/jobs/000bf7ccd9cb49f8` does not exist and asking for
that job answers "No job matches"). Those two figures sum to 922 931 683 643, which is
exactly the `job_workspaces` total the amendment above measured the same day, so the
refused bytes are 69 per cent OF `job_workspaces`'s own 922 931 683 643 — that class is
the denominator, not the whole data root, and stating which is which is the difference
between the 99.98 and 99.93 readings already in this file and in `.agent/decisions.md`,
both of which are right about different denominators. The OPERATOR STEP at the end of
this file expects `.data` under 10 GB after a reclaim, which cannot happen while those
bytes stay refused. With `--orphans` such a child
becomes a candidate once it is at least `data_reclaim.ORPHAN_MIN_AGE_DAYS` — 1.0 day —
old. THE FLOOR IS THE POINT: a job whose record is being written right now is
indistinguishable on disk from a job whose record is gone forever, the window is
seconds, and a day is cheap insurance against ever deleting live work; under the floor
the child is refused as `orphan_too_young` so the operator still sees it, and on the
default path — no flag typed — the human preview now names how many paths and bytes are
refused as `job_unresolved` and says the flag can reclaim them, so an operator is never
left to find it in the source. A record that EXISTS and will not parse is never an
orphan, and the consequence is worth saying out loud: a staging copy whose `job.json` is
present but unparseable keeps its scratch FOREVER, and no slice of this feature reaches
it. Every other rule — the `staging_` prefix, the direct-child rule, the symlink
refusal, the real path inside the root — is unchanged and still re-checked at the moment
of deletion; the orphan VERDICT is re-derived there too, so a record that appears
between the preview and the apply saves its own scratch.

## T003 — The copy-mode lifecycle
`release_staging_workspace(job_id)`, called from the same terminal-state hook the
worktree cleanup already uses. The copy gains a `.gitignore`-aware file filter — one
`git check-ignore --stdin -z` pass when the target is a git repository — plus a hard
per-file size ceiling. Excluded paths and reclaimed bytes are recorded on
`StagingWorkspace`. Red proof: the test reddens when the release call is removed.

AMENDMENT (2026-09-20, round 4): nothing above is withdrawn; five readings are made
exact, and one of them is stronger than the sentence it replaces.

RE-MEASURED AT `543863a0`. The Why-this-exists bullet reads the code at `a5bf8949`
and says `_create_job_workspace_copy` "never calls `discard_staging`". That is a
dated reading and it is true of its commit. At `543863a0` the statement is stronger:
the copy path has NO CLEANUP OF ANY KIND, and `discard_staging` DOES NOT EXIST — F273's
R-0936 paydown deleted it with the rest of the fixture fulfillment spine, and
`grep -rn "def discard_staging" packages/ apps/` returns nothing. The only
similarly-named survivor is `pingpong_loop._discard_staging`, which removes the
ping-pong loop's own `/tmp/remedy-pingpong-<run_id>` copy and never touches
`job_workspaces/`. So this slice does not repair a cleanup that stopped working; it
supplies the half that was never built.

TWO LAYERS, NOT ONE CONDITION. `release_staging_workspace` keeps its OWN floor and
refuses any job that is not terminal by `pingpong_job.JOB_TERMINAL_STATES` —
`completed`, `failed`, `cancelled`, the vocabulary `data reclaim` judges by — because
a public function that deletes must refuse on its own authority and must never free
what reclaim would refuse. THE HOOK IS STRICTER: `_finalize_job_workspace` calls the
release only under the condition it already applies to a worktree,
`job.state == JOB_COMPLETED and not job.result_diff_error`, so a failed, cancelled,
blocked, paused or stopped copy job KEEPS its staging copy exactly as such a worktree
job keeps its worktree. That is the conservative direction, it gives the operator the
same inspection window in both isolation modes, and it is what makes "the same
terminal-state hook the worktree cleanup already uses" literally true. Those copies
are not stranded: `remedy data reclaim` frees them when the operator asks. Both layers
are pinned by their own test on the same failed job — kept through the hook, released
by a direct call — and widening the hook to `job_is_terminal` reddens the first.

THE COPY'S EXISTING DIRECTORY FILTER IS WIDER THAN "a fixed name set". Measured in
`staging_workspace._should_exclude_dir`: the exclusion is the THIRTEEN names in
`_EXCLUDE_DIRS` — `.git`, `node_modules`, `venv`, `.venv`, `__pycache__`, `.data`,
`.mypy_cache`, `.pytest_cache`, `.ruff_cache`, `.tox`, `dist`, `build`, `.eggs` — AND
EVERY DOT-DIRECTORY, whatever its name. Files still pass through `_is_env_file` alone,
so a dot-FILE that is not `.env*` — `.coverage`, `.gitignore` — is copied. That rule is
unchanged by this slice; only its description here is corrected.

`excluded_bytes` IS THE BYTES OF EXACTLY TWO LISTS, `excluded_ignored` and
`excluded_oversize`, and of no other. `excluded_dirs`, `excluded_symlinks` and
`excluded_env_files` are never measured — a skipped directory is never walked — so a
total over all five would be a number no caller could interpret. The field's own
docstring says this in the same words.

THE IGNORE PASS RUNS ONLY WHEN THE TARGET HOLDS ITS OWN `.git`. A target nested inside
another repository answers `check-ignore` SUCCESSFULLY with the OUTER repository's
rules, so that one stat is what makes the pass mean the target's own ignore file. A
`.git` file rather than a directory — a git worktree checkout — counts, deliberately.
When the guard fails, or git does, the copy proceeds UNFILTERED and says so through
`StagingWorkspace.gitignore_filter` and `gitignore_detail` rather than resembling a
copy of a target with nothing to ignore.

## T004 — A disk floor that behaves like every other budget
`min_free_disk_bytes` on `JobBudgets` with a config override; a `free_disk` limit in
`budget_guard.evaluate_budget` behind an injectable probe so no test touches the real
filesystem; checked at job start and at every safe point. Exhaustion takes the STOPPED
path `remedy job stop` already uses, with post-mortem reason `disk_exhausted`.
`remedy doctor` gains a disk section.

## Acceptance
- Every top-level child of the data root resolves to exactly one class; adding an
  unclassified child reddens the architecture test (red proof).
- `remedy data usage --json` reports per-class bytes and totals from one walk.
- `remedy data reclaim` without `--apply` deletes nothing, and its preview names every
  path `--apply` would remove.
- `remedy data reclaim --apply` deletes only previewed paths; a second run is a no-op;
  a non-terminal workspace and a path outside a class directory are both refused, each
  with its own test.
- A job finishing in `isolation_mode="copy"` releases its staging workspace; removing
  the release call reddens that test (red proof).
- A copy of a target whose `.gitignore` excludes a large artifact does not copy it, and
  `StagingWorkspace` records the exclusion and the bytes not copied.
- With the injected probe below `min_free_disk_bytes`, a job start is refused and an
  in-flight job reaches STOPPED with post-mortem reason `disk_exhausted`.
- `remedy doctor` reports free disk against the floor.

## Do not touch

cleanup path for a job-owned worktree" — which already works and is not this
feature's to re-route.
