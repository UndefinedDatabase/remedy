# T2_F085 — Sandbox hardening (stage 1)
**Tier 2 · Depends on: F006, F017 · Blocks/used by: trust for foreign repos, F162 later**

## Goal & Done
Builder-spawned commands stop relying on prompted discipline: stage 1
containment gives every builder/test/DoD subprocess resource limits,
per-command timeouts, filesystem scope pinned to the worktree, and a
default-deny network posture for build/test commands — with documentation
that says EXACTLY what stage 1 does and does not prevent. DONE when the
limits provably kill a runaway fixture (fork bomb-ish loop, oversized
output, endless sleep), an off-scope write attempt fails, and the honest
limitations document exists and is linked from the README.

## How it fits (inspect current shape before building)
All subprocess execution already flows through a small number of helpers
(test runner, DoD runners, provider transport, runtime harness) —
inventory them; stage 1 wraps THOSE seams with a common execution guard
rather than scattering limits. Fences already stop the APPLICATOR from
writing outside scope; this feature extends the same worktree-scope
intent to what spawned commands themselves do. POSIX resource limits
are the stage-1 mechanism; Windows is explicitly out of scope for
stage 1 (documented), and container-grade isolation is a later feature
— never claim more than is enforced (P6).

## Design (suggested shape)
Module `exec_guard.py`:
- `run_guarded(cmd, policy)` wrapping the existing subprocess helper:
  applies rlimits (cpu seconds, address space, open files, core off) in
  the child, output-size caps (truncate + flag, never unbounded
  buffers), a hard wall timeout distinct from the provider timeouts,
  cwd pinned inside the worktree, and a scrubbed environment (an
  allowlist of variables; secrets never inherit into build/test
  commands).
- Network posture for build/test/DoD commands: default-deny via
  proxy-environment forcing where the toolchain honors it, plus an
  honest limitation note that a hostile binary can ignore proxies —
  stage 1 raises the bar, stage 2 (containers) closes it; the policy
  document lists both truthfully.
- Policies per command class (config table): builder tools, test
  commands, DoD custom commands, runtime harness (the harness NEEDS
  network on its port — its policy differs).
- Every guard trip → a classified failure (new additive postmortem
  class resource_limit) with the tripped limit in evidence.

## Task slicing
- **T001** exec_guard + rlimit/timeout/output-cap mechanics + unit
  tests with runaway fixtures (cpu, memory, output, sleep — each
  killed, each classified).
- **T002** seam migration (each subprocess helper adopts the guard, one
  order per seam, behavior-equality tests for well-behaved commands) +
  environment scrubbing with an allowlist test.
- **T003** network posture + per-class policies + the limitations
  document + README link + tests (a curl in a test command fails under
  deny; the harness still serves).

## Acceptance
- Each runaway fixture is killed by its limit and classified
  resource_limit with the limit named. Well-behaved fixture commands
  behave identically under the guard (golden equality). A secret-like
  env var set in the parent never appears in a child's environment
  dump. The limitations document exists, is linked, and names the
  non-guarantees explicitly.

## Edge cases & assumption defaults (A9)
- Limits too tight for legitimate big builds: policies are config with
  per-project overrides; the trip evidence tells the user which knob.
  macOS rlimit quirks: enforce what the platform supports, record
  unsupported limits as not-enforced in evidence — no silent claims.

## Orchestrator brief
T001 pure-ish first; T002 as one small order PER SEAM with equality
goldens; T003 last. Reject any wording — code comments included — that
overclaims containment.

## Do not touch
Container isolation (later), provider transport timeouts (owned
elsewhere), fence semantics. Suggested tests:
tests/orchestration/test_exec_guard.py.
