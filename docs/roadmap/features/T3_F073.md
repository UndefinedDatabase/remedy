# T3_F073 — Post-mortem miner -> playbook proposals
**Tier 3 · Depends on: F010, F063 · Blocks/used by: F145**

## Goal & Done
Repeated failures turn into reusable knowledge — with a human gate: a
miner detects failure PATTERNS (same class hitting the same module
family repeatedly), drafts a playbook PROPOSAL through the idea queue,
and only an approved proposal lands as a versioned playbook document.
DONE when a seeded postmortem corpus yields exactly the expected
pattern proposals with evidence references, approval materializes the
playbook file, and nothing ever writes a playbook without that gate.

## How it fits (inspect current shape before building)
Postmortems are classified records in evidence (their store and stats
already exist); the idea queue provides proposal/approve/deny with
denial memory and mandatory evidence refs — a playbook proposal is an
idea of kind playbook (additive kind on the idea schema), inheriting
the whole gate for free (A6). Approved playbooks live IN THE REPO
under `.remedy/playbooks/` — they are curated, reviewable knowledge
that should travel with the project and appear in PRs, unlike
generated mirrors (which stay under the data root); jobs may not write
there casually — the default fences deny it, and materialization goes
through the memory/knowledge CLI path only.

## Design (suggested shape)
- `postmortem_miner.py`: scan the postmortem corpus over a window;
  a pattern = same failure class + a shared module/path prefix with
  count ≥ threshold (config, default 3); emit one proposal per
  pattern: title ("Recurring <class> in <area>"), rationale with the
  counts, evidence_refs typed failure (the provenance vocabulary),
  draft playbook content (deterministic skeleton: symptom, seen-in
  list, suggested countermeasures ONLY where mechanically derivable —
  e.g. "raise timeout profile" for timeout clusters; otherwise the
  countermeasure section says "to be written on approval", honest).
- Approval hook: approving an idea of kind playbook writes
  `.remedy/playbooks/<slug>.md` (frontmatter: id, pattern, sources,
  created_from) via the gated path, and the job/PR that carries it is
  a normal reviewed change.
- Consumption preview: the planner prompt MAY include matched
  playbooks — but that wiring belongs to the distillation feature;
  here only the store, the format and the gate exist (scope
  discipline).
- Invocation: on demand (`remedy ideas mine-failures`) and as an
  optional miner in the idea-mining loop (registered with the v2
  miner interface).

## Task slicing
- **T001** pattern detection (pure, table-tested on a fixture corpus:
  threshold boundaries, prefix grouping, window edges).
- **T002** proposal emission through the idea machinery (kind, refs,
  denial memory respected) + the deterministic draft skeleton +
  goldens.
- **T003** approval materialization + fence/gate tests (a job's
  builder writing .remedy/playbooks directly is denied; the gated
  path succeeds) + the loop-miner registration.

## Acceptance
- Seeded corpus (two real patterns, one below threshold) → exactly two
  proposals with correct counts and resolvable refs; denial suppresses
  re-proposal. Approval writes the file with frontmatter; no other
  write path exists (grep + fence tests). Countermeasures are only
  ever mechanical or explicitly deferred — no invented advice (P6).

## Edge cases & assumption defaults (A9)
- Patterns spanning projects stay per-project in v1 (cross-project
  learning is a later concern). A pattern that stops recurring: the
  playbook stays (knowledge doesn't expire on silence); the hygiene
  loop may propose archiving.

## Orchestrator brief
Gate on idea provenance (typed refs). T001 pure-first. Put the
"mechanical-or-deferred countermeasures" rule verbatim into T002's
order — it is the honesty line reviewers must check.

## Do not touch
Planner prompt wiring (distillation feature), card system, postmortem
classification. Suggested tests:
tests/orchestration/test_postmortem_miner.py.
