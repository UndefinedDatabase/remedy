## Goal & Done
A task that fails on a cheaper tier is handed one tier up for its next repair round, for
reasons the evidence can name, and never for reasons that belong to failover: repeated test or
review failures, no progress across rounds, a watchdog trip. DONE when a fixture job whose
cheaper builder fails its tests twice runs its next repair round on the next tier with the
reviewer raised alongside, the call evidence carries the tier it came from, the reason and the
round, the report carries one line per escalation, the event stream carries `worker.escalated`,
the ledger carries the outcome per task class and tier, a `provider_unavailable` failure never
escalates (that is F058's), and the default stays off until a documented benchmark on the F082
corpus shows cheap-first-with-escalation at an equal PASS rate and lower cost than the class tier.

## Why this exists
F110 routes every task class to a tier and lets a class move to a cheaper tier only with
benchmark evidence; repair prompts follow the tier of the original class. F058 fails over only on
provider unavailability, after the transport retries, and its file says in as many words that
quality problems never trigger it. Between the two there is no path for the cheapest sensible
start: a cheap worker that fails twice today keeps failing on the same tier until the budget or
the round cap ends the job, or a human intervenes. Luna's strategy wants premium models to be the
escalation resource, not the default, which needs exactly this one mechanism — upward, evidence-
triggered, recorded — and the data it leaves behind is what lets F133 recommend a routing change
to a human. The routing policy itself still changes only by configuration and an ADR; this
feature changes which tier serves one repair round, never the policy.

## Task slicing
- T001 — The trigger and the step. One module names the escalation triggers as failure classes
  and thresholds read from configuration (`test_failed` or `review_failed` in N consecutive rounds,
  no progress — the same failing node set two rounds running — and a watchdog trip), decides one
  step up along `MODEL_TIERS`, raises the reviewer with the builder (F110's hard rule), refuses
  `provider_unavailable` as a trigger by name, and never steps down. Off by default behind one
  configuration key.
- T002 — The record. Every escalated call's evidence carries `escalated_from`, the reason and the
  round; the run report carries one line per escalation; the event stream carries
  `worker.escalated` (already named in ROADMAP.md Part E); the ledger carries, per task class and
  tier, the outcome, the cost, the rounds and the retries, so F133 can read them.
- T003 — The benchmark and the default. A benchmark run on the F082 corpus compares the class
  tier alone with cheap-first plus escalation, measured as PASS rate and cost per PASS; the default
  flips only when the run is documented as F110's promotion rule requires, and a feature-file
  Amendment records the numbers either way.

## Acceptance
- A fixture job whose cheaper builder fails its tests in two consecutive rounds runs round three
  on the next tier with the reviewer raised; the same job with a `provider_unavailable` failure
  does not escalate and ends as F058 or the failure classifier decides.
- Call evidence, report, event stream and ledger each carry the escalation as T002 names it.
- With the key off, no run escalates and no record changes.
- The benchmark's numbers stand in this file's Amendment before the default changes, or the
  default stays off and the Amendment says so.

## Do not touch
F058's trigger (availability after transport retries) and its disclosure; F110's seed table,
hard rules and promotion rule; the budget guards — an escalated round still spends inside the
job's budget.

## Amendment — DECISION F296 D5 (2026-10-22): T003 ran no benchmark, and the default stays off
No benchmark ran inside F296, so `model_escalation.enabled` stays `false`, as the fourth
Acceptance line allows, and this Amendment holds no numbers yet. Read at `6e4bd5788`: the F082
bench set holds five frozen orders, and `run_bench_campaign` in
`packages/orchestration/bench_run.py`, the one function that runs them, has no command that calls
it (`tests/test_no_orphan_modules.py` lists it as unwired); its rows carry tokens and no money
(`BenchRecord.cost` in `packages/orchestration/capability_bench.py`). The policy's promotion rule
runs each fixture three times, so comparing the class tier alone with cheap-first plus escalation is
thirty missions on paid models, which no round of this feature buys — the reason F307 carried
R-1351 and R-1353 as well. What such a run needs is in place: each run records its tiers and steps
as `tier_ladder` (T002b), and each task run's `tier_outcomes.json`, mirrored into the ledger's
`tier_outcomes` table, gives the outcome, rounds, retries and reported cost per task class and tier,
so two bench series — one on the class tier's models with the switch off, one starting on the cheap
tier with the switch on — compare from the rows they leave. The default changes only by a later
Amendment of this file that carries those numbers, measured as F110's promotion rule requires.
