## Binding architecture

`remedy runtime serve` is a SHORT-LIVED CLI. It must not own the dev server, or the
server dies with it. So serve starts a **persistent supervisor**:

```
remedy runtime serve (short-lived)
  └── supervisor  (own session; survives the CLI)
        ├── bounded LogPump (owns the app's stdout for its whole life)
        └── application (own process group; child of the supervisor)
```

- `packages/runtimes/runtime_supervisor.py`, invoked as
  `python -m packages.runtimes.runtime_supervisor`.
- Supervisor and application carry **separate identities** (pid, creation time,
  cmdline, cwd, fingerprint, pgid, sid) plus a random per-runtime instance id.
- Startup uses a **private atomic filesystem handshake** — never a network port.
  Bounded timeout; a failure returns a classified error, log tail and cleanup result.
- Durable states: `starting → running`, plus `probing`, `stopping`, `stop_failed`,
  `start_cleanup_failed`, `interrupted_start`, `identity_unproven`,
  `identity_mismatch`, `exited`. Only `running` may report `already_running`.
- `RuntimeSpec` is argv-only (no `shell=True`), bound to `.remedy/config.toml [runtime]`
  with vite/next/uvicorn detection; explicit config always wins; free-port fallback
  reports the EFFECTIVE port and never kills the process holding the requested one.
- Cleanup is safe: the live process group is verified before any signal, Remedy's own
  group is never signalled, and no unrelated process is ever killed.

## Acceptance & tests
Readiness timeout enforced; stop leaves no zombies; probe exit codes correct; logs
bounded and present. Tests must cross the real process boundary
(`python -m apps.cli.main runtime ...` as its own subprocess): the server keeps serving
and logging after serve exits, a separate probe leaves it running, a separate stop
removes supervisor, application and descendants.
