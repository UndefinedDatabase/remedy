# T17_F245 — Evidence schema registry & versioning
**Tier 17 · Depends on: F005, F140, F166 · Blocks/used by: a third-party tool ecosystem; long-horizon verifiability**

## Goal & Done
See ROADMAP.md F245; the Done criterion there is binding.

## Context (existing code & prior features)
schema_v exists in spots (F005 models); many artifact writers write unversioned. F202 versions DATA STORES; this versions ARTIFACT schemas.

## Design
packages/ecosystem/schema_registry.py: a central register of ALL artifact types {name, schema_v, pydantic model, since-version}; every writer obtains its model from here (a mechanical refactor). A JSON-schema export `remedy schemas export` (published with the docs site, F216) lets third parties build against it. Migrators per type (old -> new); `remedy verify` selects validation logic by schema_v; a compat suite keeps frozen fixtures of EVERY published version verifying forever in CI. Trailer/field-name registers (F164) live here too.

## Task slicing
T001 the registry + export + refactoring the top-10 writers (LARGE, A3). T002 the migrator framework + the compat suite + the remaining writers + docs publication.

## Acceptance & tests
No writer bypasses the registry (an import lint like F128); old fixtures of all versions keep verifying; the export validates (jsonschema meta).

## Risks / anti-goals
A schema change without a version bump is impossible (the registry enforces it, tested); no silent field reinterpretation (a migrator or a new field - the rule is written here).
