## Goal & Done
THE heart of self-build: the external orchestrator's working style —
read the state, decide the next order, dispatch it, evaluate the result,
write everything down — internalized as Remedy's own loop. Per mission
iteration: load the dossier and mission plan → pick or shape the next job
as a Flight Plan → run it through the multi-cycle executor → evaluate
against the milestone's DoD → update mission state and dossier → append a
decision-ledger entry. DONE when a fake-provider two-milestone mission
runs end to end unattended, every iteration leaves a ledger entry a human
can audit, and the loop provably CANNOT grant itself new goals.

## How it fits (inspect current shape before building)
Every verb the loop needs exists by this point: mission records and
plans, intake/flight-plan generation, plan approval, the multi-cycle
executor with budgets/stops/checkpoints, DoD evaluation, reports,
escalation, postmortems. The loop is a POLICY layer sequencing those
verbs — any diff that reimplements one of them is wrong (A6). The
orchestrator's provider calls use the configured top-tier model (config
key, role "orchestrator") — quality at the decision layer is the whole
point. The human-relayed split workflow (docs/agents/split_workflow.md,
run in production since 2026-07-23) is the measured prototype of this
loop — its round life cycle, fast-path bootstrap, verdict rules and
packaging order are reference behavior; where the internalized loop
deviates from that protocol, the deviation needs a documented reason in
the feature's decisions.

## Design (suggested shape)
Module `orchestrator_loop.py`:
- `run_mission(mission_id, limits)`: iterate { assemble the orchestrator
  context (dossier first — cache-stable prefix discipline; then mission
  plan state, last report, open decisions) → one orchestrator provider
  call returning a schema-validated OrchestratorMove {kind: dispatch_job
  | wait_on_decisions | declare_milestone_done | declare_mission_achieved
  | abort_with_reason, payload} → execute the move through existing verbs
  → evaluate (a dispatched job's terminal state + milestone DoD) → update
  mission/dossier → append the ledger entry {iteration, context digest,
  move, outcome, cost} } until mission terminal, limits, or stop.
- The system-prompt block for the orchestrator role is generated from a
  maintained protocol document (the loop's "job description") — keep it
  versioned in the repo so prompt changes are reviewable diffs.
- **Authority boundary (enforced, not hoped):** the move schema has NO
  kind for creating missions or editing goals; new goals travel the human
  idea/approval path. Plan approvals inside a mission follow the standard
  gate — unattended missions run under --yes semantics with the audited
  auto-approval, within budgets.
- Human overrides win instantly: stop requests and answered decisions are
  read every iteration (safe points between iterations).
- CLI: `remedy mission run <id> [--iterations N]`, `remedy mission ledger
  <id>` renders the audit trail.

## Acceptance
- End-to-end fixture reaches achieved; the ledger reconstructs every
  decision without reading code. A move attempting an undefined kind
  fails as parse-class. Stop request between iterations halts within one
  iteration. Ledger entries include cost actuals per iteration.
- Operator addition 2026-07-27: detection over the era fixture corpus is
  an acceptance criterion. The DONE proof standard for the A2 rule (the
  enforced authority boundary) extends to the corpus in the Design
  section — one test per finding class asserting the loop's evaluate
  step flags the fixture and refuses to advance.

## Edge cases & assumption defaults (A9)
- The orchestrator proposing a job for an already-done milestone → the
  evaluator refuses the move with a recorded reason and the loop
  re-prompts once with that feedback; twice → escalate to a human
  decision (never silent loops). Iteration limit default is conservative
  (config), and hitting it is a normal terminal with an honest status.
