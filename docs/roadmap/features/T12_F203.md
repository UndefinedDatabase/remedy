# T12_F203 — Structured logging & correlation
**Tier 12 · Depends on: F010, F008 · Blocks/used by: debuggability; F197 correlation; support**

## Goal & Done
See ROADMAP.md F203; the Done criterion there is binding.

## Context (existing code & prior features)
Logging is heterogeneous today; job/task/run ids exist everywhere as concepts.

## Design
packages/telemetry/logging_setup.py: ONE setup (structlog vs. stdlib+JSON formatter decided by ADR), mandatory bindings job_id/task_id/run_id via contextvars (the provider path sets them), levels per config ([logging] level, json bool), rotation under ~/.remedy/logs/. Cockpit linkage: the EvidencePanel L3 gains a 'logs' button -> a run_id-filtered view (a daemon API read). A trace_id bridge to F197 (the same ids as OTel attributes).

## Task slicing
T001 the setup + contextvar bindings + a no-print lint (ruff rule) + the mechanical migration of core paths (LARGE, A3). T002 rotation + the cockpit view + a correlation test (grep by job_id yields the gapless run).

## Acceptance & tests
grep by job_id returns the full chronological run; the lint finds no print in the core; JSON mode parses (golden).

## Risks / anti-goals
No log-level inflation (debug disciplined); logs are OPERATIONS data, never evidence (the evidence stays the truth - a docs sentence).

## Amendment — DECISION F203 D1 (2026-10-13)
This section governs where the text above disagrees with it.

- **The setup** lives in `packages/orchestration/structured_log.py`, not `packages/telemetry/`,
  on the standard library alone, not structlog: one JSON line per record with `ts`, `level`,
  `logger`, `message`, `job_id`, `task_id`, `run_id` and, when there is one, `exception`.
- **The file** is `<data root>/logs/remedy.log`, not `~/.remedy/logs/`: Remedy keeps nothing
  outside its data root. It is owner-only and rotates by size from the first round
  (`logging.max_bytes`, `logging.backup_count`).
- **The levels:** `logging.level` governs the file and defaults to `INFO`; the error stream keeps
  showing warnings as it does today. `logging.json` chooses JSON or text lines.
- **The lint** is ruff's `T20` over `packages/` only.
- **Logs are operations data, never evidence.**

### Slices
- **T001** — the module and its keys; the wiring into the command line and the serve supervisor

- **T002** — the read of one job's or run's lines on the command line, on the public API and in
  the cockpit, and the correlation test.

## Amendment — DECISION F203 D5 (2026-10-13)
The cockpit's logs view moved to F303, the feature that puts the cockpit on the public API.
T002 here is the read of one job's lines on the command line and on the public API
(`GET /api/v1/jobs/{job}/logs`), and the correlation test over a fake-provider run.

## Amendment — DECISION F203 D6 (2026-10-13)
The key that chooses JSON or text lines is `logging.json_lines` (`REMEDY_LOG_JSON_LINES`),
not `logging.json`: a key whose last part is a file extension is never checked against the
documents that name it.
