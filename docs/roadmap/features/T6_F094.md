## Goal & Done
"It looks right" grows into "it behaves right": browser flows are
GENERATED from the spec's components and the DoD (hover/click/input
per declared state), executed as DoD checks of kind playwright_flow,
and failures attach a screenshot of the failing moment. DONE when
declared component states on the fixture app generate the expected
flow steps (goldens), a seeded interaction bug fails its flow with
the moment captured, the flow kind integrates the DoD gate/report
like any check, and generation stays deterministic (flows are
reviewable artifacts, not per-run improvisation).

## How it fits (inspect current shape before building)
The DoD compiler's runtime_flow kind was deliberately HTTP-level
with browser depth deferred "to a later tier" — this is that tier:
playwright_flow is an additive check kind whose runner uses the
design extra's browser (availability-gated like capture; absent →
the check reports tool_unavailable red per the DoD's rule, honest).
Flow GENERATION is deterministic assembly from structured sources:
spec components' states (hover/click/input from
component.states[]) + DoD acceptance lines mentioning interactions
— an LLM is NOT in the generation path v1 (auditability; the flows
land as artifacts a human can read and a job can commit when
applied — the F061 apply rule for generated flows extends to these).

## Design (suggested shape)
- Flow artifact (versioned YAML/JSON per flow): {name, url/route,
  steps: [{action: goto|hover|click|fill|press, target (selector
  strategy documented: data-testid preferred, text fallback),
  value?}, {assert: visible|text|state, target, expected}]} —
  generated under the job's dod/flows/ evidence area; regeneration
  deterministic from spec+DoD (hash-stable).
- Selector honesty: generated selectors from spec component names
  need a mapping to the built DOM — the builder conventions gain
  the data-testid discipline for design jobs (a conventions-file
  addition within its cap, coordinated); unmappable targets fail
  generation with the component named (teach at compile, not at
  3 a.m.).
- Runner: per flow — harness up, execute steps, on failure capture
  the moment (screenshot + the failing step index) into the
  check's evidence; teardown always; results are DoD rows.
- Interaction sources: spec states generate the canonical
  hover/click/input probes; DoD acceptance lines with interaction
  verbs map via a small deterministic phrase table (documented,
  extensible).

## Task slicing
- **T001** flow schema + deterministic generation from
  spec+acceptance + the phrase table + goldens (hash-stable
  regeneration; unmappable → named failure).
- **T002** the runner + failing-moment capture + teardown + the
  DoD kind integration + fixtures (green flow; seeded bug → red
  with the moment).
- **T003** the data-testid conventions addition (capped,
  coordinated) + apply path notes + the end-to-end (fixture
  app with declared states → generated flows → gate holds on the
  seeded bug, releases on fix).

## Acceptance
- Generation goldens hash-stable; the phrase table covers the
  fixture acceptance lines; unmappable components fail loudly at
  compile. Seeded-bug flow red with the exact failing step's
  screenshot. Availability degradation per DoD rules. Gate/report
  integration identical to other kinds.

## Edge cases & assumption defaults (A9)
- Dynamic content breaking selectors: data-testid discipline is
  the answer; text-fallback flakiness is reported as selector
  debt in the check's evidence (a finding, not a retry storm —
  no auto-retries, the CI stance). Multi-page flows: v1 flows are
  per-route; journeys across routes are the later journey
  features' scope, noted.

## Orchestrator brief

The conventions addition is a separate small reviewed order.
