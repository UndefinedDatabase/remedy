# T4_F118 — Deterministic card attachment
**Tier 4 · Depends on: F117, F105, F112 · Blocks/used by: measurable memory**

## Goal & Done
Cards reach prompts by RULES, not vibes: for every task, a selector
picks in-scope cards deterministically — scope match, then a
role×type relevance map, then value ranking with a small exploration
quota, cut to a hard token budget — into a stable prompt slot, with
the attached set recorded in run evidence. DONE when equal state
yields byte-equal selections, every stage of the funnel is
unit-tested in isolation, the budget never splits a card mid-body,
and evidence lets anyone reconstruct WHY each card was or wasn't
attached.

## How it fits (inspect current shape before building)
The segment registry owns prompt composition — cards are ONE segment
at the stable rank the registry assigned (dossier-adjacent);
per-class input caps already constrain totals, and the card budget
(config, default ~2000 tokens) lives INSIDE the class cap (the
compiler's arithmetic must count it — verify the seam). Scope
matching uses the task's files_hint/fence closure against card
scope.paths (the same path-matching helpers fences use — reuse);
value and exploration read fields the value feature manages later
(neutral values now — the selector's mechanics don't wait for it).

## Design (suggested shape)
- `card_selection.py`, pure pipeline with each stage a named
  function: candidates = active cards → scope_filter (path overlap
  or job_kind match; empty scope = project-wide, matches all) →
  relevance_map (a table constant: role × card type → weight;
  reviewer favors decision/convention, builder favors component/
  architecture, planner favors architecture/risk — table is config-
  overridable, defaults tested) → rank by (relevance × value) with
  deterministic tie-breaks (id) → exploration slot: the LAST budget
  slice reserved for one below-cutoff card chosen by a SEEDED
  deterministic rotation (seed = job id — "exploration" without
  nondeterminism; the value feature gives it meaning) → budget cut
  whole-cards-only.
- Prompt slot: one segment, fixed heading, cards rendered
  frontmatter-lean (title, type, body) in rank order.
- Evidence: attached_cards [{id, rank, score, stage_reached}] plus
  the near-misses (top N rejected with the stage that cut them) —
  the debuggability half of the feature.
- CLI `remedy job cards <id> --task <tid>` renders the funnel from
  evidence.

## Task slicing
- **T001** the funnel stages as pure functions + per-stage table
  tests + the determinism property (same inputs, byte-equal output,
  hammered across orderings).
- **T002** budget integration inside class caps + whole-card rule +
  the segment slot + compiler-arithmetic seam test.
- **T003** evidence (attached + near-miss) + the CLI view + an
  end-to-end fixture (a project with six cards; the expected four
  attach for a builder task, a different set for its review — golden
  both).

## Acceptance
- Equal-state determinism holds (property test). The relevance
  defaults produce the fixture goldens for builder vs reviewer.
  Budget never truncates a card body; over-budget selection drops
  whole cards from the bottom. Evidence reconstructs every decision;
  the near-miss list names the cutting stage.

## Edge cases & assumption defaults (A9)
- Zero in-scope cards: empty segment omitted entirely (no header
  noise), evidence records the empty funnel. Cards larger than the
  whole budget: never attachable — flagged in near-misses as
  oversized (and the hygiene loop can propose splitting).

## Orchestrator brief
Gate on the card store + segment registry + class caps. T001 is the
soul — demand property-based determinism testing, not one example.
The relevance table's defaults go verbatim into the order.

## Do not touch
Value updates (later), embeddings pre-filter (later), UI badges.
