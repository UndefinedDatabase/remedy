# T0_F011 — Kill-Switch
**Tier 0 · Abhängigkeiten: F009 (UI-Weg) · Blockiert: F046, F033-Äquivalent im Cockpit**

## Ziel & Done
`.remedy/STOP` (Datei) + Command `stop_job` beenden jeden Lauf am nächsten sicheren
Punkt. Done: Stop wirkt ≤1 Zyklus; Zustand resumierbar.

## Design
- `packages/orchestration/kill_switch.py`: `should_stop(project_root, job_id)` prüft
  `.remedy/STOP` (global) und `.remedy/STOP.<job_id>` (gezielt); Check-Punkte: vor jedem
  Provider-Call, nach jedem Task, je Zyklus (F046). Bei Stop: Checkpoint schreiben
  (F047-Format vorwegnehmen: `job_state.json` reicht v1), Status `stopped_by_operator`.
- UI-Stop-Button → F009 `stop_job` → Konsument legt STOP.<job_id> an.
- CLI: `remedy jobs stop <id>`; `remedy jobs resume <id>` (nutzt bestehende Job-States).

## Task-Schnitt
- T001: kill_switch.py + Einbau der Checkpunkte + Tests (Stop zwischen Tasks).
- T002: CLI stop/resume + F009-Command-Konsument + UI-Button (rail).

## Akzeptanz & Tests
- Stop während Task n → Task n läuft zu Ende ODER bricht am Provider-Call-Checkpoint ab;
  resume setzt bei n bzw. n+1 fort, Endergebnis konsistent (Vergleichstest).

## Risiken / Anti-Ziele
- Kein SIGKILL auf Provider-Prozesse als Normalweg (nur harter Not-Aus mit Flag `--force`).
