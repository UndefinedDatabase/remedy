## Goal & Done
A running job can be stopped safely from a second terminal: `remedy job
stop <id>` requests it; the runner notices at the next safe point, starts
nothing new, persists a resumable state, records why it stopped, exits
cleanly. DONE when stop works mid-run against a live fake-provider job,
leaves no zombie processes, and the stopped job is inspectable.

## How it fits (inspect current shape before building)
Jobs persist atomically through the storage layer; job/task lifecycle
states live in the core models as a string enum (additive members are
backward-safe). The execution drive is: a caller loop dispatches one task
at a time into the task runner, which delegates provider rounds to the
ping-pong loop; provider failures already roll the task back to pending
and propagate — the CALLER owns persistence, so it also owns stop
handling. The runtime supervisor already uses a polled stop-request-file
pattern with atomic writes: reuse that idiom, do not invent new IPC.

## Design (suggested shape)
New shared module `safe_points.py` (budgets will extend it):
- `request_stop(job_id, reason, source)` writes a small JSON control file
  under a `control/` area of the data root (add a helper next to the
  existing data-path helpers). `stop_requested(job_id)` is a cheap
  existence check returning a StopSignal; `clear_stop` consumes it; a
  consumed request is archived, not deleted.
- Safe points — checked BEFORE starting new work, never mid-write:
  (1) caller loop before each task dispatch; (2) inside the ping-pong loop
  before each provider call, both roles; (3) between repair/parse-retry
  rounds.
- On signal: let the in-flight provider call finish; roll the current task
  back to pending exactly like the existing provider-failure path; set an
  additive STOPPED job state; save; append a job_stopped ledger event with
  the signal payload; write a postmortem with class `stopped`; archive the
  control file. Checkpoint v1 = the persisted job itself (a resume simply
  continues at the first pending task); the deep checkpoint feature builds
  on this later.
- CLI in the existing job command module: `remedy job stop <id> [--reason]`
  prints "stop requested — takes effect at the next safe point";
  `--status` shows pending/consumed; unknown job exits 3.

## Task slicing
- **T001** safe_points + control area + signal record; unit tests incl.
  malformed control file → reason "unknown", never a crash.
- **T002** STOPPED state + loop integrations + ledger event + postmortem;
  integration test: stop during call 1 → call 1 finishes, call 2 never
  starts, task back to pending, job STOPPED on disk.
- **T003** CLI + status + help text; tests for happy path and unknown job.

## Acceptance
- Live (subprocess-marker) test: 3-task fake job stopped after task 1 →
  exactly one COMPLETED, rest PENDING, STOPPED state, event + postmortem
  present, clean exit, no leftover processes.
- Stop request for a not-running job is consumed BEFORE work on next start.
- Double stop requests are idempotent. The per-call check is a file-stat,
  no config reload (assert cheapness in a test).

## Edge cases & assumption defaults (A9)
- SIGKILL of the runner is out of scope (stale-RUNNING detection is a later
  feature) — document, don't build. Stop during verify/finalize: the task
  completes; stop applies before the next one. Unwritable control area →
  loud error, never a silent no-op.

## Orchestrator brief
Have the worker first locate the caller loop and the provider-call entry
points and report the seams; then dispatch T002 with those confirmed
anchors. T001 and T003 can run as independent orders.

## Do not touch
Signal handlers, threads, daemons, retry policy, checkpoint formats beyond
the persisted job. Suggested tests: tests/orchestration/test_safe_points.py,
tests/orchestration/test_job_stop_integration.py, tests/cli/test_job_stop.py.

## Built state (2026-07-14 — implemented, `[~]`, external acceptance pending)

### The mechanism
A stop is a **fact on disk**, not a signal. `remedy job stop <id>` writes one private JSON
control file and returns immediately; the runner reads it at a safe point and stops on
purpose. **No signal handler, no thread, no daemon, no socket, no database**, and the normal
stop path never sends an OS signal to a provider process.

### Control protocol (`packages/orchestration/safe_points.py`)
- `StopSignalV1`: `stop_signal_v`, `job_id`, `request_id` (unique per REQUEST), bounded and
  redacted `reason` (≤500 chars) and `source` (≤120), UTC `requested_at`. No absolute path,
  no secret — it is copied into a ledger event, a post-mortem and an Evidence bundle.
- Layout, under a new `control/` area of the data root (`data_paths.control_dir`):
  `control/jobs/<job_id>/stop.json` and `control/jobs/<job_id>/archive/<request_id>.json`.
  0700 directories, 0600 files, atomic publication, and a job id that is not a plain path
  component is refused before it is ever joined to a path.
- `request_stop` / `stop_requested` / `consume_stop` / `clear_stop` / `stop_status`.
  A second request while one is pending returns the FIRST signal: one operator pressing the
  button twice is one episode. Consuming ARCHIVES the exact request (create-only `os.link`)
  rather than deleting it; if the archive cannot be written the request stays pending and the
  error is raised, because a stop whose history does not exist is not a stop episode.
- A malformed or unknown-version control file becomes a degraded signal with reason
  `unknown` — **never a crash**. An unwritable control area is a loud error, never a silent
  no-op.
- `stop_requested()` is a stat plus one small read. The runner binds the control root once,
  so the per-call check loads no config and scans no directory. Asserted in a test.

### Safe points — checked only BEFORE new work
1. the caller loop, before dispatching each task;
2. the ping-pong loop, at the top of each round (initial or repair);
3. immediately before each Builder provider call;
4. immediately before each Reviewer provider call (i.e. after the Builder call returned);
5. before the bounded reviewer parse retry;
6. the caller loop again, after a task is durably applied and before the next is dispatched.

A call that is already in flight **always finishes** and its evidence is kept. A stop
observed before a call means that call never starts: no `ProviderAttempt`, no prompt trace,
no repair round counted, no retry budget spent. Nothing is ever interrupted mid-write,
mid-apply or mid-state-persist.

### Task rollback rule
The incomplete task returns to `pending` (its F006 start tree kept, so the resume reviews and
diffs against the same tree). A task that already reached `applied_to_job_workspace` is
durable and is **never** rolled back. Nothing is converted to `skipped`.

### STOPPED state and resume
`JOB_STOPPED = "stopped"` is additive and distinct from `blocked`, `paused`, `failed` and
worker-queue cancellation. Old job files load unchanged; the job carries `stop.request_id`,
`reason`, `source`, `stopped_at`, `archive_ref`, `postmortem_path` and any recording error,
all backward-compatibly. **Checkpoint v1 is the persisted job itself**: a resume simply runs
the job again and continues at the first pending task, rerunning no completed work. There is
no deep checkpoint format.

### Evidence
One `job_stopped` ledger event per CONSUMED request (job id, request id, reason, source,
requested/consumed times, current task, completed/pending counts, post-mortem reference — no
paths, no secrets). One F010 post-mortem per episode, `failure_class: stopped`, scope `job`,
at `jobs/<job_id>/evidence/stop_postmortems/<request_id>/postmortem.json` and exported to
`stop_postmortems/<request_id>/postmortem.json`. Keyed by request id, so a stop → resume →
stop leaves **two** records, two archived requests and two events, and neither overwrites the
other. `remedy stats failures` counts each episode once, as job scope. A stop record that
cannot be written is durable on the job and **blocks** the package through
`postmortem_integrity.json`.

### CLI
`remedy job stop <job_id> [--reason <text>] [--source <text>] [--status] [--json]`.
Success prints `Stop requested — it will take effect at the next safe point.` `--status`
distinguishes no request, a pending request, consumed/archived requests, a stopped job and a
resumed job with stop history. Unknown job exits **3**; a malformed job id exits **2**; an
unwritable control area exits **1** and says plainly that NO stop was requested; a completed
job is refused rather than promised a stop that can never happen. It is wired to the
persisted ping-pong job — **not** to the worker-queue `pause`/`cancel` commands.

### Boundaries (documented, not built)
SIGKILL of the runner itself is out of scope: there is no stale-RUNNING recovery here. No
deep checkpoints. No budgets (F018) — `budget_exhausted` remains a reserved F010 class wired
to nothing. Retry policy, classifier precedence, Evidence layout, stats semantics and
job/task states are otherwise unchanged.

## First hardening round (external FINDINGS on `remedy-review-20260714-203106`)

The workflow worked; the plumbing under it did not. Eleven findings, all fixed here.

### Control I/O is now the SAME implementation F010 uses
The reviewed build validated only the final path, so `control -> outside` wrote
`outside/jobs/<job>/stop.json` — the very bug F010 had already fixed, reintroduced in a
weaker form. The anchored primitives now live once, in `packages/common/secure_fs.py`, and
both features call them: the trusted root is inspected no-follow, opened and identity-checked;
every component below it is inspected no-follow, opened relative to the handle above it, and
`fstat`-compared for `(st_dev, st_ino)`; `O_NOFOLLOW` is defence in depth, never the
argument; directories are created THROUGH the held fd at 0700 (never at the umask's 0755);
reads and writes are full-byte loops; every fd is closed on success and on failure; and
without the primitives the guarantee is made of, the writer **fails closed**.

Writability is judged on the DECLARED mode bits, read from the fd we hold — because
`os.access` tells root that a 0o500 directory is writable, and the review host runs as root.
A read-only control root, job directory or archive directory now raises for everybody.

### Nothing untrusted becomes a path, or evidence
A control file is attacker-controlled input. An unknown version or an unsafe `request_id`
(`../../../../escaped`) is replaced by a deterministic `malformed-<sha256[:12]>` id — the
same corrupt file is always the same episode, and nothing from it can ever be joined to a
path. The archive boundary validates the id again. `requested_at` is validated as a bounded
ISO-8601 timestamp; anything else (`API_KEY=supersecret /home/alice/private`) becomes empty
rather than travelling into the ledger, the post-mortem and the Evidence bundle.

### Concurrent requests are one episode
`stop.json` is published **create-only**. Two `remedy job stop` processes that both see
nothing pending no longer overwrite each other: the loser's `os.link` fails, it reads the
winner's request, and both return the SAME id. A valid pending request is never overwritten,
and a malformed one is honoured as the degraded episode rather than silently replaced.

### The stop finalization is a durable transaction
The pending request is the commit record, and it is removed **last**:

1. archive the request (idempotent; a different record under the same id conflicts);
2. write the stopped post-mortem (idempotent — F010's writer settles an identical record);
3. append `job_stopped`, but only if this request id has no event yet (exactly-once; the
   ledger is scanned ONLY during finalization, never at an ordinary safe point);
4. set the STOPPED state and every stop field;
5. persist the job — the durable checkpoint;
6. only now remove the pending request.

A failure anywhere in 1-5 leaves the request PENDING, starts no work, records the reason on
the job, and blocks the package through `postmortem_integrity.json`. There is no false clean
episode: an unarchived request produces no event, no post-mortem and no stopped job. A
failure at 6 leaves a durably stopped job whose request the next run acknowledges without a
second event or post-mortem. Every crash window converges to exactly one archive, one
post-mortem and one event for that request id.

### The stop check happens before ANY work
`run_job` checks for a pending stop immediately after loading the job and resolving its
config — **before** workspace acquisition, the worktree lock, the target snapshot and any
task mutation. In the reviewed build a worktree lock failure could overtake a pending stop
and leave the job `blocked` with the request still on disk. Binding the control root resolves
a path and creates nothing.

### Already-stopped is idempotent
`remedy job stop` on a job that is already `stopped` no longer writes a new request — that
was a trap that would stop the job again the moment anyone resumed it. It reports
`already_stopped` with the last stop's metadata. After a resume, a new stop is a new episode.

### The parser fix
`--status` is now declared per ARGUMENT (`ArgDef(is_flag=True)`), not special-cased by
option name in the shared grouped parser — which had turned `remedy propose list <job>
--status pending` into a usage error. `job stop --status` stays a boolean flag;
`propose list --status <value>` takes its value again.

### The run record carries the stop
A stopped run's `result.json` now contains a bounded, redacted, versioned `stop` block
(`stop_signal_v`, `request_id`, `reason`, `source`, `requested_at`). An ordinary run's JSON
is unchanged — the block is present only when the run was stopped.

## Second hardening round (external FINDINGS on `remedy-review-20260714-210839`)

The durability and control-flow fixes held. One blocker remained, and it was in the shared
helper — so it belonged to F010 as much as to F011.

### The parent of the trusted root was not verified
`secure_fs.anchor_root()` verified the root's FINAL component and then opened its parent by
raw path name (`os.open(parent, …)`). That is the same check-then-use hole, one level up.
With `real/link -> outside`:

* `request_stop(control_root_path=real/link/control)` created `outside/control/jobs/<job>/stop.json`;
* `write_postmortem(root=real/link/root)` created `outside/root/dir/postmortem.json`.

There is no trusted parent any more. `anchor_root()` now starts at the filesystem root —
which nothing can redirect — and walks every component of the absolute, normalized root path:
no-follow `stat`, reject symlink, require directory, open relative to the descriptor already
held, `fstat`, require the same `(st_dev, st_ino)` and a directory; the parent fd is closed
only once the child is held. A relative root is made absolute against the CWD first (the
semantics the callers already assumed) and then walked identically. Without the primitives
the guarantee is made of, it fails closed. F010's `write_postmortem` and every F011 control
operation (`request_stop`, `stop_requested`, `archive_stop`, `acknowledge_stop`, `clear_stop`,
`archived_signals`, `stop_status`) inherit the fix through `anchor_destination` — there is no
one-off patch anywhere.

### Nothing is created by name before validation
`_ensure_control_root()` used to call `Path.mkdir(parents=True)` on the control root's parent
BEFORE any secure anchoring ran, so an unverified chain could be materialised first.
`anchor_root(create=True)` now creates a missing component through the descriptor it holds,
at 0700, after verifying everything above it. A validation that fails leaves nothing behind —
in particular, a missing `outside/control` under a symlinked parent is never created.

### The no-leftover check is scoped
The live acceptance test asserted `psutil.Process().children(recursive=True) == []` — a claim
about the whole pytest process. On the review host that process already had an unrelated child
(`artifact_tool_rpc_daemon-bun`), so a correct runner was reported as a leak. The test now
takes a baseline snapshot of pre-existing children, tracks the runner PID, and counts a child
only if it is new AND belongs to this test (its `cwd` or command line points at the test's
`tmp_path`). Two tests police the policing: an unrelated pre-existing child must NOT count,
and a deliberately leaked test-owned child MUST still be caught.

## Accepted state (2026-07-14)

F011 is **accepted as v1** — external verdict `PASS_WITH_RISKS — ACCEPTED`, 0 open findings,
Evidence job `49955e41c49f41bc`, package
`remedy-review-20260714-223538-READY_FOR_REVIEW.zip`.

The stop mechanism is **file-polled and safe-point based**: `remedy job stop` writes one
private control file, and the runner honours it only where no work is in flight. There is
**no OS-signal stop path**, no signal handler, no thread and no daemon.

Two boundaries stay out of scope in v1, deliberately and documented rather than half-built:

- **SIGKILL of the runner itself / stale-RUNNING recovery.** If the runner is killed outright
  there is no safe point left to observe; detecting and reclaiming a job whose runner died is
  a later feature.
- **Deep checkpoints.** Checkpoint v1 is the persisted job: a resume continues at the first
  pending task. There is no finer-grained checkpoint format.
