# T0_F011 — Kill switch
**Tier 0 · Depends on: none · Future UI integration: the cockpit stop button maps to the stop_job command once F009 (Tier 5) exists · Blocks/used by: F046, F018, F200**

## Goal & Done
A running job can be stopped safely from a second terminal: `remedy job
stop <id>` requests it; the runner notices at the next safe point, starts
nothing new, persists a resumable state, records why it stopped, exits
cleanly. DONE when stop works mid-run against a live fake-provider job,
leaves no zombie processes, and the stopped job is inspectable.

## How it fits (inspect current shape before building)
Jobs persist atomically through the storage layer; job/task lifecycle
states live in the core models as a string enum (additive members are
backward-safe). The execution drive is: a caller loop dispatches one task
at a time into the task runner, which delegates provider rounds to the
ping-pong loop; provider failures already roll the task back to pending
and propagate — the CALLER owns persistence, so it also owns stop
handling. The runtime supervisor already uses a polled stop-request-file
pattern with atomic writes: reuse that idiom, do not invent new IPC.

## Design (suggested shape)
New shared module `safe_points.py` (budgets will extend it):
- `request_stop(job_id, reason, source)` writes a small JSON control file
  under a `control/` area of the data root (add a helper next to the
  existing data-path helpers). `stop_requested(job_id)` is a cheap
  existence check returning a StopSignal; `clear_stop` consumes it; a
  consumed request is archived, not deleted.
- Safe points — checked BEFORE starting new work, never mid-write:
  (1) caller loop before each task dispatch; (2) inside the ping-pong loop
  before each provider call, both roles; (3) between repair/parse-retry
  rounds.
- On signal: let the in-flight provider call finish; roll the current task
  back to pending exactly like the existing provider-failure path; set an
  additive STOPPED job state; save; append a job_stopped ledger event with
  the signal payload; write a postmortem with class `stopped`; archive the
  control file. Checkpoint v1 = the persisted job itself (a resume simply
  continues at the first pending task); the deep checkpoint feature builds
  on this later.
- CLI in the existing job command module: `remedy job stop <id> [--reason]`
  prints "stop requested — takes effect at the next safe point";
  `--status` shows pending/consumed; unknown job exits 3.

## Task slicing
- **T001** safe_points + control area + signal record; unit tests incl.
  malformed control file → reason "unknown", never a crash.
- **T002** STOPPED state + loop integrations + ledger event + postmortem;
  integration test: stop during call 1 → call 1 finishes, call 2 never
  starts, task back to pending, job STOPPED on disk.
- **T003** CLI + status + help text; tests for happy path and unknown job.

## Acceptance
- Live (subprocess-marker) test: 3-task fake job stopped after task 1 →
  exactly one COMPLETED, rest PENDING, STOPPED state, event + postmortem
  present, clean exit, no leftover processes.
- Stop request for a not-running job is consumed BEFORE work on next start.
- Double stop requests are idempotent. The per-call check is a file-stat,
  no config reload (assert cheapness in a test).

## Edge cases & assumption defaults (A9)
- SIGKILL of the runner is out of scope (stale-RUNNING detection is a later
  feature) — document, don't build. Stop during verify/finalize: the task
  completes; stop applies before the next one. Unwritable control area →
  loud error, never a silent no-op.

## Orchestrator brief
Have the worker first locate the caller loop and the provider-call entry
points and report the seams; then dispatch T002 with those confirmed
anchors. T001 and T003 can run as independent orders.

## Do not touch
Signal handlers, threads, daemons, retry policy, checkpoint formats beyond
the persisted job. Suggested tests: tests/orchestration/test_safe_points.py,
tests/orchestration/test_job_stop_integration.py, tests/cli/test_job_stop.py.
