# T1_F052 — Self-healing test rounds
**Tier 1 · Depends on: F046, F003 session ids · Blocks/used by: cycle robustness**

## Goal & Done
Trivial test breakage no longer kills unattended cycles: when a cycle's
verify step fails, up to two bounded auto-repair rounds run REUSING the
existing repair loop, and only then does the cycle fail with a classified
postmortem. DONE when a fixture with a trivially broken test heals in one
round, a stubborn break stops after exactly two rounds with an honest
trail, and repair costs are attributed to the job's budget.

## How it fits (inspect current shape before building)
A repair loop already exists in the ping-pong machinery (bounded repair
rounds with their own evidence); this feature TRIGGERS it from the cycle
verify step with the test-output digest as findings — it must not build a
second repair mechanism (A6). Budgets already count repair calls; the
postmortem classifier already has a test-failure class. Inspect how the
repair loop receives findings today and feed it the same way.

Amendment (DECISION D1, 2026-07-30): the "ping-pong machinery" named
above has no findings-injection seam and is not reachable from the
cycle executor; the EXISTING executing repair loop F052 triggers is
`builder_bridge.run_builder_bridge_loop` (findings intake via
`repair_context.build_repair_context`, `max_cycles=1` per round so
the cycle re-runs its own verify between rounds). The A6 rule stood:
no second repair mechanism was built. Details: .agent/decisions.md
and live_review D1.

## Design (suggested shape)
- After a cycle's verify fails: build a findings payload from the test
  output (failing test ids, tail of the failure text, changed files of
  this cycle as hint), invoke the existing repair path capped at a config
  key (cycles.repair_rounds, default 2), re-run verify after each round.
- Healed → the cycle completes normally, cycle evidence records
  "healed after N repair rounds" (visible in reports — silent healing
  hides risk).
- Not healed → cycle fails with the existing test-failure classification;
  the postmortem references the repair-round evidence.
- Safety: repair rounds respect fences, budgets, and stop requests exactly
  like any other provider work (they flow through the same safe points —
  assert, don't assume).

## Task slicing
- **T001** the verify→findings→repair trigger + round cap + healed path;
  fixture: a one-line assertion break heals in round one.
- **T002** the stubborn path (fixture whose break the fake provider never
  fixes) → exactly two rounds, then classified failure; budget attribution
  asserted via actuals; stop request during repair honored.

## Acceptance
- Healed fixture: cycle green, evidence line present, one repair round
  counted in actuals.
- Stubborn fixture: exactly two rounds (not one, not three), classified
  postmortem, repair evidence linked.
- A stop request between repair rounds stops cleanly (safe-point test).

## Edge cases & assumption defaults (A9)
- Verify failing for non-test reasons (command missing, config) →
  classified config/unknown, NO repair rounds (repairing a broken harness
  wastes money). Flaky tests: a heal that changed no files is suspicious —
  record "healed without changes (flaky?)" so humans see it; detection
  beyond that is a later quality feature.

## Orchestrator brief
Small feature, one worker. Before T001, have the worker report how the
existing repair loop accepts findings and cap configuration; reject any
diff that adds a new repair entry point.

## Do not touch
The repair loop's internals, flaky-test quarantine, review policies.
Suggested tests: tests/orchestration/test_self_healing_cycles.py.

## Built State
> Recorded 2026-07-30 from the committed diff of f052-r1
> (92c998c..21638c6). Statements below are limited to what that diff
> contains; the integration gate is a separate round.

- **Verify seam** — `long_run_executor.VerifyOutcome` (`result`,
  `output`, `failing_test_ids`, `changed_files`) lets a verify step
  report WHAT failed. `as_verify_outcome` normalizes the return value,
  so a step that returns a bare `VERIFY_*` string behaves exactly as
  before; both shapes are pinned by tests.
- **Verify failure classes** — `VERIFY_CONFIG_ERROR` ("config") and
  `VERIFY_UNKNOWN_ERROR` ("unknown") joined `_VERIFY_DENIES_GREEN`.
  `cycle_verify_failure_class` maps a non-passing verify through the
  EXISTING `failure_postmortem.classify` (`test_failed` / `config` /
  `unknown`; empty for passed and not_run) — no second vocabulary.
  `_VERIFY_REPAIRABLE` is `{VERIFY_FAILED}` only, so a harness failure
  is classified and never repaired (A9).
- **Round cap** — config key `cycles.repair_rounds`
  (`REMEDY_CYCLES_REPAIR_ROUNDS`, default 2) resolved by
  `limits_from_config` into `CycleLimits.repair_rounds`. The dataclass
  field itself defaults to 0, deliberately and documented on the field:
  a caller that builds its limits by hand never spends provider calls
  it did not ask for. A negative value is refused.
- **Findings payload** — `build_cycle_repair_findings` builds on the
  existing `repair_context.build_repair_context` and adds `source`
  ("cycle_verify"), `cycle_index`, `repair_round`, `failing_test_ids`,
  `failure_tail` and `changed_files` (executed task ids as fallback
  hint). No raw stdout beyond the tail the verify step bounded.
- **The repair round** — `default_repair_step` calls
  `builder_bridge.run_builder_bridge_loop(build_fn, repo_path, job=…,
  data_dir=…, max_cycles=1)`; `repo_path` comes from
  `LocalWorkspaceRuntime(job.id).workspace.root`, `data_dir` from
  `resolve_data_root()`. `build_fn` goes through the cycle's own
  counted provider seam, so a repair call lands on the job budget with
  no separate accounting. An unreachable repair loop returns
  `RepairOutcome(ran=False, error=…)` instead of raising.
- **The phase** — `_run_repair_rounds` runs at most
  `limits.repair_rounds` rounds; a round that did not run is not
  counted; the verify step re-runs after EVERY round; the phase stops
  at the first `VERIFY_PASSED`. Between rounds it evaluates the same
  `safe_points.should_stop` the cycle loop uses (operator stop and
  budgets in one call); a stop there ends the run after the cycle's
  evidence is written.
- **Evidence and reports** — ledger events `cycle_repair_round` (one
  per round that ran) and `cycle_healed`. `CycleRecord` gained
  `verify_failure_class`, `repair_rounds_used`, `healed_after_repair`,
  `healed_without_changes` and `repair_summary`, all serialized into
  the cycle record. `render_cycle_summary_line` renders one line per
  cycle and `remedy job run` prints it, e.g.
  `cycle 1: verify=passed tasks=1/1 | healed after 1 repair round`.
- **Flake suspicion (A9)** — a heal whose round changed no file sets
  `healed_without_changes` and reads
  `healed without changes (flaky?) after N repair round(s)` in the
  record, the ledger event and the rendered line.
- **Tests** — `tests/orchestration/test_self_healing_cycles.py`,
  50 tests: verify-outcome compatibility, classification, findings
  payload, cap and config, healed path, the default seam delegating to
  the existing loop, the stubborn path (exactly two rounds), budget
  attribution over the default seam, the stop between rounds, and the
  A9 edge cases.
