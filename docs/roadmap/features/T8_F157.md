# T8_F157 — Capability matrix & honest degradation
**Tier 8 · Depends on: F151 · Blocks/used by: every worker-dependent feature; law P5**

## Goal & Done
Features stop assuming capabilities and start asking: a declarative
register maps features to required capabilities (schema-features →
json_schema, image attachment → vision, resume → session_resume,
streaming evidence → streaming, ...) with ONE registered
degradation handler per entry, one central require_or_degrade at
each usage site, a per-run evidence field degraded:[...] and a UI
badge while degradation is active. DONE when the register covers
every capability-consuming feature (the inventory is the
deliverable, and new consumers must register — a guard),
degradation handlers reproduce the honest fallbacks already
scattered through features (consolidated, their tests green),
adapters lacking a capability trigger exactly the registered
fallback with the evidence entry, and a capability-consuming call
without a register entry fails loudly in CI.

## How it fits (consolidation — the fallbacks exist, scattered)
The honest fallbacks were built feature by feature: schema-in-
prompt + validation retry (when json_schema is absent), the
described-image path (no vision), full-context resend (no resume),
buffered non-streaming — each lives where its feature built it.
This feature CENTRALIZES the decision (not the implementations):
require_or_degrade(feature_key, adapter) consults capabilities()
and returns the registered strategy token; call sites branch on
the token into their existing implementations (the handlers are
REFERENCES to those paths — no logic moves, behavior equality per
consumer proven by their suites). The register makes P5 (honest
degradation) auditable: one table says what degrades how, the
evidence says when it did, the badge says it's happening.

## Design (suggested shape)
- `packages/workers/capability_matrix.py`: FEATURE_REQUIREMENTS =
  {feature_key: {requires: [caps], degradation: handler_token,
  notes}} — keys namespaced to the consuming feature (schema_gate,
  builder_vision, repair_resume, stream_evidence, ...);
  require_or_degrade returns {mode: native | degraded(token) |
  unavailable} — unavailable is legal only where the register says
  the feature may refuse (a third honest state: some features
  can't degrade, e.g. the vision PROBE itself).
- Evidence: the run/call records degraded: [feature_keys] —
  aggregated to the job (the report's degradation section lists
  them with the register's notes); the UI badge on the job chrome
  while any degradation is active (per reference's badge pattern),
  popover listing the entries.
- The CI guard: capability reads outside the matrix module fail a
  grep/import rule (consumers ask the matrix, never the adapter
  directly) — with the register-completeness test (every
  capability field has ≥1 consumer entry or a documented
  no-consumer note).
- Consolidation orders: one per existing consumer, swapping its
  local capability check for the matrix call, suite green.

## Task slicing
- **T001** the inventory (findings: every capability check in the
  tree today, its fallback, its tests) + the register drafted from
  it — reviewed.
- **T002** the module + evidence field + the guard rules + unit
  tests (native/degraded/unavailable matrix per entry).
- **T003** consolidation orders per consumer (behavior equality —
  suites green) + the report section + the UI badge + the
  end-to-end (a reduced-capability fake adapter runs a job:
  degradations exact, badge live, report lists them).

## Acceptance
- Inventory complete (review); every consumer routed through the
  matrix (import/grep guard, violation fixture red). Behavior
  equality per consolidated consumer (their suites unmodified).
  The reduced-adapter fixture's degraded list golden; badge and
  report render it. Register completeness holds.

## Edge cases & assumption defaults (A9)
- Capabilities discovered per resolved model (the contract's
  per-pair rule): the matrix call takes the pair; a mid-job
  failover changing capability → degradation state can CHANGE
  mid-job (the evidence per call carries it; the badge reflects
  the current call — truth over stability). Multiple degradations
  stacking: all listed; the register notes interactions where
  known.

## Orchestrator brief
T001's inventory is the map — review before the register
freezes. Consolidation is parallel small orders with the
equality bar verbatim. The consumers-ask-the-matrix rule is the
architecture line.

## Do not touch
Fallback implementations (referenced, not moved), adapter
capability declarations, per-feature semantics. Suggested tests:
tests/workers/test_capability_matrix.py.
