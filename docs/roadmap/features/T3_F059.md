# T3_F059 — Notifications
**Tier 3 · Depends on: F051, F053 · Blocks/used by: reaction time**

## Goal & Done
Waiting work reaches the human where they are: hooks on
decision-requested and job-finished events deliver a compact payload
(project, job, event, next command, link-style reference) to configured
channels — webhook, ntfy-style push, mail — and a delivery failure logs
loudly but never blocks or fails the run. DONE when both hook points
fire on fixtures across a fake channel, payloads match a golden, a dead
channel degrades to a logged miss with a status hint, and zero
notification code runs when nothing is configured.

## How it fits (inspect current shape before building)
The events already exist structurally: decisions are enqueued at known
seams (escalation, plan approval, budget stops, watchdog trips) and
terminal states funnel through the report writer — inventory those
seams and attach ONE dispatch call at each funnel point rather than
sprinkling sends. Configuration follows the standard config tables; the
never-block rule mirrors the ledger writer's never-fail discipline
(same pattern, cite it in the docstring).

## Design (suggested shape)
- `notify.py`: channel adapters (webhook POST json; ntfy-style simple
  POST; smtp mail) behind one send(event) with a short timeout and one
  retry, then a logged miss counted per channel; a fake channel adapter
  for tests.
- Event payload (versioned, golden-tested): {event kind, project slug,
  job id short, title/one-liner, the exact next command, timestamp} —
  compact enough for a push notification, no secrets, no file paths
  from outside the data root.
- Hook points: decision enqueue funnel (all decision kinds inherit) and
  terminal-report funnel (all terminals inherit) — two seams total;
  per-event-kind enable/disable in config (someone may want decisions
  but not finishes).
- Quiet default: no channels configured → the dispatch call is a no-op
  guarded before any I/O; `remedy notify test` sends a probe event to
  all configured channels and prints per-channel results (the setup
  UX).
- Misses surface in status ("2 notification failures this run — see
  log") — silent notification death defeats the purpose.

## Task slicing
- **T001** payload schema + goldens + the two funnel hooks + no-op
  guard + tests (every decision kind and terminal fires exactly once).
- **T002** channel adapters + timeout/retry/miss discipline + the fake
  channel + dead-channel fixtures.
- **T003** `notify test` + status surfacing + docs (config examples per
  channel).

## Acceptance
- Fixtures fire both hooks once per event with golden payloads; dead
  channel → run unaffected, miss logged and surfaced. Unconfigured →
  zero notification code paths executed (call counter). No secret-like
  config values appear in any payload (denylist test, same list as the
  manifest redaction).

## Edge cases & assumption defaults (A9)
- Notification storms (many decisions in one batch): per-run
  rate-collapse — after N sends in a window, one summary event ("k
  further decisions — see status") — documented threshold. Mail is
  fire-and-forget smtp; delivery guarantees are the channel's problem,
  stated honestly.

## Orchestrator brief
T001's funnel inventory is the substance — require the seam list as a
deliverable. Reuse the redaction denylist by import, not copy.

## Do not touch
UI/inbox rendering, chat-platform integrations (later tiers), decision
content. Suggested tests: tests/orchestration/test_notify.py.
