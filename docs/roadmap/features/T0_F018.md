# T0_F018 — Budgets & stop conditions
**Tier 0 · Depends on: F003 · Later integrates: F014 carries budgets/stop in the Flight Plan (CLI flags + config defaults until then) · Blocks/used by: F046, F104, F116**

## Goal & Done
A job carries hard limits — tokens, provider calls, wall clock, deadline —
and stops itself cleanly through the same machinery as the kill switch,
recording which limit hit and the counter evidence. DONE when a fake job
with a three-call limit stops before call four with a resumable state and
an open decision asking how to proceed, and every counter comes from
recorded actuals — never estimates presented as actuals (P6).

## How it fits (inspect current shape before building)
Token/call actuals come from the actuals feature's aggregation surface —
read that module's API first and build on it; never re-parse provider
output. Stop mechanics extend the kill switch's safe-point module: ONE
combined should-stop evaluation per safe point (stop file first, then
budgets), not two parallel checks. Budget exhaustion enqueues into the
existing human decision queue and its CLI — no new queue (A6). Flags land
on the existing do/job commands; keys go through the central config
system.

## Design (suggested shape)
- Additive optional `budgets` field on the job model: max_total_tokens,
  max_provider_calls, max_wall_clock_minutes, deadline (UTC). Precedence:
  CLI flags > `[budget]` table in project config > no limit. Persisted at
  creation so the run manifest snapshots them.
- `budget_guard.evaluate(job)` returns a status (tokens used, calls made,
  minutes elapsed, limits, first exhausted limit if any); wall clock is
  measured from the job's first running timestamp (reuse whatever exists;
  add an additive started_at only if nothing does).
- The shared safe-point check becomes should_stop(job) → signal with
  reason operator_stop | budget_exhausted:<limit> | deadline_reached.
- On budget stop: identical persistence path as the kill switch (stopped
  state, ledger event, postmortem class budget_exhausted) PLUS one
  decision-queue entry offering extend/abandon; acting on the answer is a
  later feature — document, don't build.
- Honesty: `remedy job budget <id>` prints actual counters and their
  source; calls without reported usage show as ">= N (M calls unmeasured)"
  — never silently filled estimates.

## Task slicing
- **T001** budgets field + config keys + flags + precedence matrix tests;
  invalid deadline string is a clean CLI error.
- **T002** evaluate() on actuals incl. unmeasured handling; fixtures for
  exact/partial/missing usage.
- **T003** unified should_stop + stop-on-limit integration (call limit 3 →
  stops before call 4) + decision entry asserted + postmortem class.
- **T004** budget display + docs; snapshot includes the ">=" notation.

## Acceptance
- One integration test per limit kind (wall clock via injected clock; no
  long sleeps). No limits configured → zero behavior change (existing
  do-flow tests stay green untouched).
- Budget evaluation is cached per round, not re-walked per check.
- Exactly one decision entry per exhaustion, idempotent across resume.
- Deadline already in the past at start → refuse to start, with a decision
  entry (cheaper than start-then-stop).

## Edge cases & assumption defaults (A9)
- Raising limits in config never auto-resumes a stopped job; resuming goes
  through an explicit decision answer (P2). Repair rounds count — they
  cost real money.

### T003 — safe-point seam discovery (documented, not integrated)
Integration deferred to T003 implementation. Seams identified:

1. **Safe-point hook** — `packages/orchestration/safe_points.py`:
   `stop_requested()` checks the kill-switch control file. T003 adds a
   `budget_exhausted()` call AFTER the stop-file check, same function, same
   call site. The combined predicate becomes:
   `should_stop(job) → stop_file | budget_exhausted`.

2. **Decision queue** — `packages/orchestration/decision_queue.py`:
   `DECISION_TYPES` already contains `"token_budget"`. T003 adds a
   `HumanDecision(type="token_budget", ...)` entry when a budget limit is
   exhausted, offering `extend` / `abandon` next actions. One entry per
   exhaustion, idempotent across resume.

3. **Postmortem class** — `packages/orchestration/failure_postmortem.py`:
   `FailureClass.BUDGET_EXHAUSTED` is already reserved (line 97). T003 wires
   the classifier to emit it when the stop reason is budget-related.

4. **Stop reason** — `packages/orchestration/stop_reasons.py`:
   `create_stop_reason()` produces typed stop reasons. T003 adds a
   `budget_exhausted:<limit_name>` variant.

5. **Actuals source** — `packages/orchestration/token_actuals.py`:
   `UsageActuals` (F003 surface). `BudgetCounters` in budget_guard.py
   aggregates from this — never re-parses provider output.

6. **RunManifest** — `packages/orchestration/run_manifest.py`:
   `RunManifestV1` needs a `budgets` snapshot field (additive). T003 or T004
   adds `budgets: dict | None` to the manifest at creation time.
