## Goal & Done
The '+ Add Task' button (right column of the cockpit, per
ux_design.png) is real additive control: inject_task takes the
human's task text, runs it through the PLANNER's validation — fences,
remaining budget, DAG placement with a written plan_rationale — and
inserts it into the running job's DAG; a budget shortfall becomes a
clarification decision, never a silent squeeze. DONE when an injected
task executes within the same job with full provenance
(origin=human_injected), placement respects stated dependencies or
gets a validated default, and every refusal path teaches instead of
stonewalling.

## How it fits (inspect current shape before building)
Injection is a one-task planning pass: reuse the flight-plan
machinery's task validation (schema, DAG revalidation) and the
plan-editing backend's transactional apply — an injected task is an
edit of kind add with extra ceremony: a small planner call drafts the
PlannedTask from the human text (acceptance criteria phrased
testably, band estimated, files_hint guessed) and proposes placement
(depends_on from content overlap; default: after the current frontier,
parallel-safe) — the human's confirmation of that draft rides the
same command round-trip (draft returned → confirm applies), keeping
P2 without a second approval machinery.

## Design (suggested shape)
- Command inject_task {text, after?: task_id, confirm_token?}: first
  call returns the planner's draft {task, placement, rationale,
  budget_check}; second call with the token applies transactionally.
  Budget shortfall (remaining < the draft band's calibrated cost) →
  the draft returns with a decision-seed instead of a token
  (extend budget | shrink task | drop) — the shortfall is a
  clarification, not a dead end.
- plan_rationale (why this placement) lands on the task's metadata
  and in the edit log; provenance origin=human_injected renders as
  a chip in the graph and the task list.
- The DoD traceability rule applies: the injected task's acceptance
  joins the check mapping at the next compile (the same re-sync note
  as runtime edits).
- CLI parity: `remedy job inject <id> "text" [--after Txxx] [--yes]`
  (--yes accepts the draft unseen — audited, unattended-compatible).

## Task slicing
- **T001** the draft pass (planner call, placement heuristic, budget
  check) + schemas + fake-provider tests (placement default, stated
  dependency, shortfall path).
- **T002** confirm/apply transaction + provenance + edit log + DAG

- **T003** UI: the Add Task affordance wiring, draft-confirm sheet,
  provenance chip + CLI parity + the end-to-end (inject mid-run →
  draft → confirm → executes → report shows origin).

## Acceptance
- Draft→confirm round-trip exact; unconfirmed drafts expire
  harmlessly (TTL, documented). Shortfall yields the three-option
  decision seed with real arithmetic. Injected tasks carry
  provenance end to end (graph chip, task list, report, ownership).
  --yes path audited.

## Edge cases & assumption defaults (A9)
- Injecting into a paused/blocked job: allowed (planning is safe);
  execution follows the job's state. Injection into terminal jobs:
  refused with the follow-up-job suggestion (missions continue).
  Free-text mentioning paths outside fences: the draft flags the
  fence conflict up front (teach early).

## Built State (F028, 2026-09-27)

What exists on disk at the close of F028, built in nine rounds of one session on
`feature/f028-task-injection`, cut from `main` at `ceb90b8a`. Every DECISION named lives in
`.agent/decisions.md`; every round's verdict in `.agent/live_review.md` or, once rotated, its
archive.

**T001 — the draft pass.** `packages/orchestration/task_injection.py` holds the whole injection.
`draft_task_injection` keeps the operator's text verbatim after `validate_injection_text` (blank,
over 2000 characters, control characters and secret-shaped text are refused), admits paused,
blocked, planned and running jobs and refuses a terminal one with a follow-up-job suggestion, and
drafts the task by one structured planner call over `InjectedTaskDraft` (schema tag
`task_injection_draft_v1`); no planner, or a reply still invalid after one retry, is a refusal and
never an invented draft. The id is the smallest free `INJ<k>`. Placement is computed by code, never
by the planner: the task is appended at the end of the plan, depending on the task the operator
named (basis `stated`), else on every task whose `files_hint` shares a path (basis
`content_overlap`), else on nothing (basis `frontier_default`), each with a written placement
rationale. The budget check is `predict_next_task_cost` over the draft's band (`S`, `M`, `L`, `XL`
read as `low`, `medium`, `high`, `unknown`); a predicted breach is a shortfall, whose draft carries
no confirm token and a decision seed with the three answers `extend_budget`, `shrink_task` and
`drop`, the arithmetic, the limit that would cover the task and the next smaller band. A path of
`files_hint` that meets the job's fences is flagged, never refused. The draft is a create-only file
under the job's control directory in `injection_drafts/`, expiring 900 seconds after drafting; an
expired or unknown draft is refused and nothing is deleted (DECISION F028 D1).

**T002 — the confirmation, the fold and the answers.** `confirm_task_injection` refuses a stale,
expired, foreign, unconfirmable or already confirmed draft and a full plan, and otherwise publishes
a second create-only file in `injected_tasks/`, recording `confirmed_unseen`. It never writes
`job.json`: `run_job` in `packages/orchestration/pingpong_job.py` folds every confirmed injection
through `_fold_task_injections` at four points — before the task loop, at every pre-task safe
point, after every task's post-task safe point, and once after the loop — so a task the loop has
not reached runs in the same run, and a task only the last fold appends parks the job `paused`.
`apply_injection_to_job` appends the task through the new edit kind `plan_add_task` in
`packages/orchestration/plan_editing.py`, so `replay_edits` replays an injected plan, carries
`origin` `human_injected`, `plan_rationale`, `task_rationale` and `injection_draft_id` on the task
entry's `inputs["plan"]`, bumps the plan version, re-seals an approved plan's hash, and logs one
edit whose `injection` block names the draft, the placement basis, the text, `confirmed_unseen` and
`dod_resync_pending` (DECISION F028 D2). `answer_injection_shortfall` answers a shortfall through a
create-only file in `injection_answers/`: `drop` ends the draft, `shrink_task` derives a new draft
one band smaller, and `extend_budget` derives a confirmable draft carrying the raised limit, which
the fold applies and `run_job` re-reads at once (DECISIONS F028 D3 and D4 (4)). After each fold the
run log gains one `task_injected` event, outcome `applied` or `inert`, declared in `EVENT_NAMES`
and worded in `apps/ui/src/api/humanizeCatalog.ts` (DECISION F028 D5 (2)).

**T003 — the command line, the door, the sheet and the provenance.** `remedy job inject <job>
<text> [--after <task>] [--yes] [--json]`, `remedy job inject-confirm` and `remedy job
inject-answer`, in `apps/cli/commands/job_inject_cmd.py`, draft, confirm and answer; `--yes`
confirms a draft unseen and the record says so, and never answers a shortfall, which exits 3 with
the seed (DECISION F028 D4). The write door in `packages/orchestration/ui_server.py` exposes
`job.inject`, `job.inject-confirm` and `job.inject-answer` through one `_dispatch_injection`, a
refusal answering 409 with its code and detail (DECISION F028 D5). The dashboard's task item
carries `origin`; the task-list row and the detail popover show the words "Added by you" as a pill
decided by `taskOriginChip` in `apps/ui/src/api/injectView.ts`, and the canvas chip reads "added",
or `v<n> · added` (DECISIONS F028 D6 and D7). The tasks card's "+ Add Task" row replaces the button
that copied a retired command and opens `AddTaskSheet.tsx`, a right-anchored sheet rendered through
a portal into the document's body, which drafts through `apps/ui/src/api/injectSend.ts`, shows the

**Deliberate absences.** The planner's draft call is not charged to the job's budget counters,
because it runs outside `run_job`; the draft reports its call count instead. `plan_add_task` is not
one of the edits an operator may send before approval, because a free add would bypass the draft
and its budget check. The fold does not rewrite the job's exported edit log,
`user_edited_plan.json`; the record's own edit log is the source. A shortfall answer is not an inbox
decision, and the live graph's reducer does not read `task_injected`: the injected task reaches the
canvas through the task data the chip reads. The DoD's check mapping picks up an injected task's
acceptance at the next compile, as the edit log's `dod_resync_pending` says, never inside the fold.
