## Goal & Done
The '+ Add Task' button (right column of the cockpit, per
ux_design.png) is real additive control: inject_task takes the
human's task text, runs it through the PLANNER's validation — fences,
remaining budget, DAG placement with a written plan_rationale — and
inserts it into the running job's DAG; a budget shortfall becomes a
clarification decision, never a silent squeeze. DONE when an injected
task executes within the same job with full provenance
(origin=human_injected), placement respects stated dependencies or
gets a validated default, and every refusal path teaches instead of
stonewalling.

## How it fits (inspect current shape before building)
Injection is a one-task planning pass: reuse the flight-plan
machinery's task validation (schema, DAG revalidation) and the
plan-editing backend's transactional apply — an injected task is an
edit of kind add with extra ceremony: a small planner call drafts the
PlannedTask from the human text (acceptance criteria phrased
testably, band estimated, files_hint guessed) and proposes placement
(depends_on from content overlap; default: after the current frontier,
parallel-safe) — the human's confirmation of that draft rides the
same command round-trip (draft returned → confirm applies), keeping
P2 without a second approval machinery.

## Design (suggested shape)
- Command inject_task {text, after?: task_id, confirm_token?}: first
  call returns the planner's draft {task, placement, rationale,
  budget_check}; second call with the token applies transactionally.
  Budget shortfall (remaining < the draft band's calibrated cost) →
  the draft returns with a decision-seed instead of a token
  (extend budget | shrink task | drop) — the shortfall is a
  clarification, not a dead end.
- plan_rationale (why this placement) lands on the task's metadata
  and in the edit log; provenance origin=human_injected renders as
  a chip in the graph and the task list.
- The DoD traceability rule applies: the injected task's acceptance
  joins the check mapping at the next compile (the same re-sync note
  as runtime edits).
- CLI parity: `remedy job inject <id> "text" [--after Txxx] [--yes]`
  (--yes accepts the draft unseen — audited, unattended-compatible).

## Task slicing
- **T001** the draft pass (planner call, placement heuristic, budget
  check) + schemas + fake-provider tests (placement default, stated
  dependency, shortfall path).
- **T002** confirm/apply transaction + provenance + edit log + DAG
  revalidation + tests (invalid placement refused, nothing applied).
- **T003** UI: the Add Task affordance wiring, draft-confirm sheet,
  provenance chip + CLI parity + the end-to-end (inject mid-run →
  draft → confirm → executes → report shows origin).

## Acceptance
- Draft→confirm round-trip exact; unconfirmed drafts expire
  harmlessly (TTL, documented). Shortfall yields the three-option
  decision seed with real arithmetic. Injected tasks carry
  provenance end to end (graph chip, task list, report, ownership).
  --yes path audited.

## Edge cases & assumption defaults (A9)
- Injecting into a paused/blocked job: allowed (planning is safe);
  execution follows the job's state. Injection into terminal jobs:
  refused with the follow-up-job suggestion (missions continue).
  Free-text mentioning paths outside fences: the draft flags the
  fence conflict up front (teach early).

## Orchestrator brief
