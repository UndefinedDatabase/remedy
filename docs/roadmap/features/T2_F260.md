# T2_F260 — Job/execution marriage (one job model)
**Tier 2 · Depends on: F259 (the concept model it renames into) · Blocks/used by: F261**

> Registered 2026-08-31 by operator order amend0831-vocab-registrations.
> REGISTRATION ONLY — nothing in this file has been implemented.

## Goal & Done
The two job stores are MARRIED. The Job — today `Job` in
`packages/core/models.py` — is the ADMINISTRATIVE ACT: identity, rights,
budgets, fences, decisions. Every execution run is an EVIDENCE-CASE FOLDER —
today a directory under `<data_root>/task_jobs/` — that the Job points at
through a reference list. One Job, zero or more evidence-case folders.

Outward there is ONE job-identifier world.
`packages.orchestration.data_paths.resolve_any_job_id` and the two-store special
paths that surround it disappear, because there is nothing left for them to
reconcile.

DONE when every CLI command that takes a job argument accepts the SAME
identifier, the `TWO job stores` comment in
`packages/orchestration/data_paths.py` is deleted as untrue rather than
reworded, and the glossary chapter of F259's concept model can state the new
situation in two sentences.

## Why this exists
Remedy files a job in two shapes: `<data_root>/jobs/<uuid>.json`, one file per
job, and `<data_root>/task_jobs/<16-hex>/job.json`, one directory per job. The
two mint different id shapes, so `resolve_job_id` — which returns a `UUID` —
can never resolve a task-job id. That is not a theoretical seam: it is why
`remedy teach narrate <task-job-id>` answered `no job matches prefix` for a job
whose run log was on disk the whole time (operator dogfooding, 2026-08-25), and
`resolve_any_job_id` exists solely to paper over it. Every feature that takes a
job id pays this tax again. The two stores are not two concepts; they are one
concept stored twice, and the fix is to say which of the two is the concept.

## DECISION D-A (2026-08-31, operator order amend0831-vocab-registrations)
For as long as Remedy is under development and is deployed nowhere,
CLEANLINESS COMES BEFORE BACKWARD COMPATIBILITY. Hard breaks are allowed. Old
data stores and old evidence history may become unreadable. NO migration shims
are built.

Consequence for this feature, stated plainly: existing `.data/jobs/` and
`.data/task_jobs/` content is not migrated, not read by a compatibility path,
and not converted on access. A developer with old jobs on disk deletes them.
Reverse this decision by deleting this paragraph — at which point a migration
step becomes a required slice, not an option.

## Design
- Decide which store SURVIVES before writing any code, and record the choice as
  a dated DECISION in this file. The evidence-case folder is the shape that
  already holds artifacts, so the folder is the likely survivor and the classic
  `<uuid>.json` becomes a field inside it — but that is a finding to establish
  by reading both writers, not an assumption to build on.
- One id shape, minted in one place. Both `_SHORT_HEX_RE` and the `UUID` parse
  path in `data_paths.py` cannot both survive.
- The Job carries a reference list of its runs. A run never carries the
  administrative fields; it carries evidence.
- Deletion is part of the work: `resolve_any_job_id`, the `TWO job stores`
  docstring paragraph, and every caller that branches on "which store is this"
  go away in the same round that makes them untrue.

## T001 — One identifier
Collapse the two id shapes onto one, mint it in one function, and make every
job-taking CLI command resolve through that one function. The canary
(`tests/cli/test_golden_path.py`) must stay green throughout.

## T002 — Job points at its runs
The administrative Job gains its reference list; the run folder loses whatever
administrative fields it duplicates. Per D-A this is a hard schema change with
no reader for the old shape.

## T003 — Delete the reconciliation layer
`resolve_any_job_id` and the two-store branches are removed, and the
`data_paths.py` comment is deleted. A test asserts the string `TWO job stores`
appears nowhere in `packages/`, so the claim cannot come back by copy-paste.

## Acceptance
- Every CLI command with a job argument accepts the same identifier, proved by
  a test that walks the command catalog rather than a hand-listed subset.
- `resolve_any_job_id` no longer exists, and nothing imports it.
- The `TWO job stores` comment is gone.
- F259's glossary chapter states the new situation in two sentences.

## Do not touch
The scope-fence builtin deny list (F017), the approval gate, and STATUS
semantics. No command is RENAMED here — F261 owns renames; this feature changes
what a job IS, not what it is called.

## Orchestrator brief
T001 is the risky slice and the one to settle first, because the surviving id
shape decides the rest. T002 depends on T001. T003 is a deletion round and must
come last, so the reconciliation layer is still there while T001/T002 move.
Under D-A there is no migration slice — if one appears in the plan, the plan has
drifted from this file.
