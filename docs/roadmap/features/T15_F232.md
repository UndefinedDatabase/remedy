# T15_F232 — Model upgrade playbook
**Tier 15 · Depends on: F156, F159, F133, F138 · Blocks/used by: staying current without haste**

## Goal & Done
See ROADMAP.md F232; the Done criterion there is binding.

## Context (existing code & prior features)
New models appear constantly; today every switch would be manual labor. Certification, scoreboard and ADRs are the blocks.

## Design
A routine (an F045 loop, manually triggerable: `remedy worker onboard <adapter> <model>`): (1) check/nag the price catalog entry (F158), (2) certification (F156), (3) a benchmark delta vs. the current routing (an F159 partial matrix), (4) conservative trust priors (F133), (5) generate an ADR DRAFT: a numbers appendix + a concrete routing proposal per role/class + a rollback plan. Switching happens exclusively by humans via config + ADR acceptance; afterwards an observation-window recommendation (n jobs) is anchored in the ADR.

## Task slicing
T001 the pipeline orchestration (1-4) + tests with a fixture 'new model' (a fake adapter variant). T002 the ADR draft generator + the numbers appendix + the loop packaging.

## Acceptance & tests
The fixture run produces a complete ADR draft with the scoreboard appendix + rollback plan; the routing config stays bit-identical until acceptance (an fs-diff test); the loop writes only queue entries/drafts (a side-effect assertion, F065 pattern).

## Risks / anti-goals
No auto-switching even on 'obvious' numbers (the observation window is wisdom, not bureaucracy); drafts visibly go stale when the model/prices change before acceptance (a stale marker, the F066 pattern).
