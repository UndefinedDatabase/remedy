# T2_F254 — Model alias table & dead-model doctor check
**Tier 2 · Registered by amendment round amend0805-v3 (2026-08-05; the
F232 core pulled forward — F232 itself stays in Tier 15) · Depends on:
none · Blocks/used by: F232 (model upgrade playbook), F110 (routing)**

## Goal & Done
Built-in model defaults stop rotting in place: every hardcoded default
model id moves behind ONE alias table in a single module, and
`remedy doctor` gains a check that every configured/default model id is
not on a known-dead list. DONE when doctor flags a dead id in a fixture
and no hardcoded dated model string remains outside the alias module.

## How it fits (inspect current shape before building)
As of 2026-08-05 the built-in defaults are pinned May-2025 ids —
`claude-opus-4-20250514` in packages/orchestration/role_config.py and
`claude-sonnet-4-20250514` in packages/orchestration/pingpong_provider.py
— several generations stale as of Aug 2026. The runtime already prefers
`get_config("orchestrator.model")`, so this is about the BUILT-IN
defaults and diagnosis, not the campaign path.

## Design (suggested shape)
- One alias module (single source): logical role/provider aliases →
  concrete model ids; every other module imports from it.
- Known-dead list is config-driven (a shippable data file the operator
  can extend); the doctor check compares configured AND default ids
  against it. No network call required.
- Doctor output names the offending id, where it came from
  (config vs. built-in default), and the alias to update.

## Acceptance & tests
- Doctor flags a dead id in a fixture (config-driven dead list).
- A repo scan proves no hardcoded dated model string remains outside
  the alias module.

## Non-goals
Model routing by task class (F110), the full upgrade playbook (F232),
any live provider probing.
