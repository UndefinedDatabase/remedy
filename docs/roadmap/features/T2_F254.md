# T2_F254 — Model alias table & dead-model doctor check
**Tier 2 · Registered by amendment round amend0805-v3 (2026-08-05; the
F232 core pulled forward — F232 itself stays in Tier 15) · Depends on:
none · Blocks/used by: F232 (model upgrade playbook), F110 (routing)**

## Goal & Done
Built-in model defaults stop rotting in place: every hardcoded default
model id moves behind ONE alias table in a single module, and
`remedy doctor` gains a check that every configured/default model id is
not on a known-dead list. DONE when doctor flags a dead id in a fixture
and no hardcoded dated model string remains outside the alias module.

## How it fits (inspect current shape before building)
As of 2026-08-05 the built-in defaults are pinned May-2025 ids —
`claude-opus-4-20250514` in packages/orchestration/role_config.py and
`claude-sonnet-4-20250514` in packages/orchestration/pingpong_provider.py
— several generations stale as of Aug 2026. The runtime already prefers
`get_config("orchestrator.model")`, so this is about the BUILT-IN
defaults and diagnosis, not the campaign path.

## Design (suggested shape)
- One alias module (single source): logical role/provider aliases →
  concrete model ids; every other module imports from it.
- Known-dead list is config-driven (a shippable data file the operator
  can extend); the doctor check compares configured AND default ids
  against it. No network call required.
- Doctor output names the offending id, where it came from
  (config vs. built-in default), and the alias to update.

## Acceptance & tests
- Doctor flags a dead id in a fixture (config-driven dead list).
- A repo scan proves no hardcoded dated model string remains outside
  the alias module.
- The scan covers every BUILT-IN default model id, dated or not
  (clarified 2026-08-07 during the build, DECISION D11): the Goal's
  "every hardcoded default model id" is the binding reading, so an
  undated default such as the Ollama one is in scope too. Illustrative
  ids in comments, docstrings and sample-config prose are
  documentation of a default rather than a default, and stay out of
  scope.

## Non-goals
Model routing by task class (F110), the full upgrade playbook (F232),
any live provider probing.

## Built State (built 2026-08-07, R1–R10)

Built and reviewed on branch feature/f254-model-alias-table:

- **Alias table** (packages/orchestration/model_aliases.py, R2–R3):
  `MODEL_ALIASES` maps a logical alias to the concrete id Remedy falls
  back to — `claude-flagship`, `claude-workhorse`, `ollama-default`,
  `fake`, `fixture` — with `resolve_model_alias(alias)`,
  `known_model_aliases()` and `builtin_model_ids()` as the public API.
  An unknown alias raises `KeyError` naming the known aliases; it never
  guesses, because a silent fallback would ship a model nobody chose.
  The module imports nothing from `packages.orchestration`, so any
  module can route a default through it without an import cycle. The
  ids are the strings the repo already shipped — relocating them is
  this feature, choosing NEW ones is F232.
- **Call sites routed** (R2–R3): role_config.py, pingpong_provider.py,
  the two Ollama providers (packages/providers/ollama_builder,
  packages/providers/ollama_planner) and the `ollama.model` default in
  config.py all ask the table instead of spelling an id. That is all
  eight built-in ids, dated and undated alike — the Acceptance section
  above records DECISION D11, which settled that an undated built-in
  default is in scope while an id in a comment, docstring or sample
  config is documentation of a default rather than a default.
- **Known-dead list** (packages/orchestration/dead_model_list.py +
  scripts/dead_models.json, R4): a shipped, operator-editable data file
  (`schema_version` 1, two entries) loaded by `load_dead_models()` and
  `dead_model_ids()`. The `doctor.dead_models` config key
  (`REMEDY_DOCTOR_DEAD_MODELS`) EXTENDS the shipped list and can never
  replace it, so an id Remedy ships as dead cannot be configured away.
  A missing or malformed file raises `DeadModelListError` rather than
  degrading to an empty list — "no dead models" and "I could not read
  the list" are opposite answers and must never look alike.
- **Doctor check** (apps/cli/commands/worker_facade_cmd.py, R5–R6):
  `remedy doctor core` gains one HARD check, `dead_model_list`, that
  fails only when the list cannot be READ, plus ADVISORY warnings — a
  stale id is a real defect but not a reason to call the installation
  unready, so `ready` and `blockers` are untouched by it. Each warning
  names the offending id, whether it came from config or from a
  built-in default, and the alias to repoint. Provenance is stated in
  both output modes: the text mode carries the short form ("per the
  shipped list scripts/dead_models.json — operator data, no provider
  queried") and points at `--json` for the full recorded reason. The
  count reads "N shipped + M config-only dead ids (N+M total)", a label
  that matches what it counts.
- **Acceptance pinned by tests**: a dead id in a fixture is flagged
  (tests/orchestration/test_dead_model_list.py, 23 tests;
  tests/cli/test_worker_facade_cmd.py, 63) and an `ast`-based repo scan
  proves no built-in model id is spelled outside the alias table
  (tests/orchestration/test_model_aliases.py, 24 — the scan reads
  assignments, so the comment/docstring boundary of D11 falls out of
  the mechanism rather than out of an allow-list). The reviewer
  red-proofed the scan in a disposable worktree at R6: a real
  assignment of a built-in id elsewhere turns it RED with the file,
  line and offending id; the same id in a comment leaves it green.
- **Docs**: docs/system/model-defaults-and-dead-model-check-v0.md,
  registered in the docs/README.md index (quick-find + system tables).
