# T2_F057 — Rate-limit-aware scheduler
**Tier 2 · Depends on: F004 (api_retry signals) · Later integrates: F049 parallelism throttling · Blocks/used by: stability**

## Goal & Done
Provider rate limits stop looking like failures: a per-provider governor
observes limit signals from call evidence, and when the ceiling is hit
the run WAITS visibly (a first-class waiting state with reason and
expected retry) instead of burning retries or failing the task. DONE
when a fixture provider emitting limit responses produces a paced,
successful run whose evidence shows the waits, and providers without
limit signals behave exactly as today.

## How it fits (inspect current shape before building)
Transport retry/backoff for individual calls exists in the timeout/retry
feature; rate limiting is a LONGER-horizon concern layered above it: the
governor decides whether a call may START, the existing retry policy
still owns what happens within a call. Limit signals (429-style
responses, provider-specific throttle messages) already surface in the
call evidence/retry reasons — inventory the actual signal shapes first
and normalize them in one place.

## Design (suggested shape)
Module `rate_governor.py`:
- Per-provider state (in-memory per process, persisted snapshot in the
  job area for visibility): a token-bucket or cooldown window fed by
  normalized limit signals; `acquire(provider, role)` blocks (with a
  deadline from budgets — waiting still consumes wall-clock budget,
  honestly) and records a wait event {provider, waited_s, reason} in
  cycle evidence when it had to wait.
- Integration at the single seam where provider calls start (the same
  choke point safe-point checks use — order: stop check, budget check,
  THEN governor acquire, so stops beat waits).
- Status/report surface waits ("waited 84s on provider rate limits this
  run") — the visible-waiting promise; an SSE/UI event kind is reserved
  by name but UI wiring is a later tier.
- Later parallelism throttling consumes the same governor (the acquire
  call is the throttle point) — design the interface for N concurrent
  acquirers now, implement single-flight now.
- Config: per-provider ceilings optional (requests/min) for users who
  know their tier; absent config = purely signal-reactive.

## Task slicing
- **T001** signal normalization from real evidence shapes + unit tests
  (fixture evidence per provider style).
- **T002** governor + acquire semantics + budget/stop interplay + tests
  with an injected clock (no real sleeps in unit tests).
- **T003** seam integration + wait evidence + report line + the fixture
  end-to-end (limits → paced success, waits recorded).

## Acceptance
- Limit-emitting fixture: zero failed tasks, waits in evidence, total
  wall time consistent with pacing. No-signal providers: zero behavior
  change (regression). A stop request during a wait interrupts the wait
  immediately (safe-point ordering test).

## Edge cases & assumption defaults (A9)
- Signals without retry-after hints: exponential cooldown with a
  documented cap. Deadline expiring mid-wait → the budget machinery's
  deadline stop, with the wait recorded as its last event. Multi-process
  runs share nothing in v1 (documented) — cross-process coordination is
  the scheduler tier's problem.

## Orchestrator brief
T001 needs real signal samples — have the worker extract them from
existing evidence fixtures and list them in the diff. Gate T003 on the
seam being confirmed. Reject sleeps in unit tests.

## Do not touch
Per-call retry policy, parallelism itself, provider adapters' internals.
Suggested tests: tests/orchestration/test_rate_governor.py.

## Built State
- **T001 — Signal normalization, `packages/orchestration/rate_governor.py`:**
  `RateLimitSignal` (frozen dataclass, `to_json`) plus the predicates that build
  it — `is_rate_limit_error`, `classify_rate_limit_reason`,
  `parse_retry_after_seconds`, `normalize_rate_limit_signal`. Three signal
  sources were inventoried out of real evidence shapes and are named as
  constants: `RATE_SIGNAL_SOURCE_API_RETRY` (`stream_api_retry`),
  `RATE_SIGNAL_SOURCE_PROVIDER_ERROR` (`stream_provider_error`) and
  `RATE_SIGNAL_SOURCE_RETRY_REASON` (`loop_retry_reason`). Four normalized
  reasons: `overloaded`, `rate_limited`, `quota_exceeded`, `throttled`. A
  retry-after hint is parsed and capped at `MAX_RETRY_AFTER_S`; raw signal text
  is truncated at `RATE_SIGNAL_RAW_MAX_CHARS`. `read_run_event_signals` and
  `read_retry_reason_signals` read the two existing evidence shapes. At T001 the
  module is import-only — nothing in the repo called it.
- **T002 — Governor and acquire semantics, same module:**
  `ProviderRateGovernor` with `observe(signal)`, `acquire(provider, role, ...)`,
  `cooldown_remaining_s`, `wait_events()` and `total_waited_s()`. A signal
  without a retry-after hint produces an exponential cooldown from
  `RATE_LIMIT_COOLDOWN_BASE_S` capped at `RATE_LIMIT_COOLDOWN_MAX_S`; a hint
  wins over the exponential. Waiting is sliced at `RATE_GOVERNOR_POLL_SLICE_S`
  and re-probes `stop_check` on every slice, so a stop beats a wait — the
  safe-point ordering the Acceptance section asks for. `acquire` returns a
  `RateLimitAcquireResult` carrying one of `RATE_ACQUIRE_GRANTED`,
  `RATE_ACQUIRE_STOPPED` or `RATE_ACQUIRE_DEADLINE_EXCEEDED`, and every wait is
  a `RateLimitWaitEvent`. The clock is injected, so no unit test sleeps.
- **T003 — Seam integration and report surfaces,
  `packages/orchestration/pingpong_loop.py`:** `_call_with_retry` takes a
  `rate_governor` and paces both ends of a call. Before the FIRST call it only
  WAITS and never decides not to call (DECISION F057 D3), so the acquire outcome
  is recorded rather than branched on. Before a RETRY it OBSERVES the failed
  call's own error first and then waits, so the cooldown a limit announces is
  the one that retry waits out; a non-granted acquire there returns the last
  output. A rate limit is retryable AT THIS SEAM and only when a governor is
  active (R-0373) — the precedence rule deliberately does not live in
  `provider_timeouts.py`, whose per-call transport policy this feature must not
  move. `run_pingpong` builds ONE governor per run and passes it at all three
  `_call_with_retry` call sites: the Builder call, the Reviewer call and the
  reviewer parse retry. `_record_rate_limit_wait` is the only writer of
  `PingPongResult.rate_limit_waits`, and an acquire that waited zero seconds
  records nothing. Two report surfaces: `export_pingpong_json` always carries a
  `rate_limit_waits` key — copied, never aliased, an empty list when the run was
  never paced — and the human run summary gains a
  `Rate limits: waited <total>s across <n> wait(s)` line above the `Error:`
  line, shown only when the run actually waited.
- **Behaviour for callers that never opt in:** a falsy `provider` skips the
  governor entirely (DECISION F057 D5) and `rate_governor=None` — every
  pre-F057 caller — leaves `_call_with_retry` behaving exactly as before, which
  is the "no-signal providers: zero behaviour change" half of Acceptance.
- **Known coupling, R-0378 (open, Low):** a reviewer rate limit reaches the
  governor only when its error string carries the `provider_error:` prefix,
  because `ReviewerOutput.verdict` defaults to `"blocked"` and the reject
  predicate exempts exactly that prefix. Every production reviewer error site
  emits the prefix today, so the path is safe as built; nothing pins it.
