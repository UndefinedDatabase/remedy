# T2_F057 — Rate-limit-aware scheduler
**Tier 2 · Depends on: F004 (api_retry signals) · Later integrates: F049 parallelism throttling · Blocks/used by: stability**

## Goal & Done
Provider rate limits stop looking like failures: a per-provider governor
observes limit signals from call evidence, and when the ceiling is hit
the run WAITS visibly (a first-class waiting state with reason and
expected retry) instead of burning retries or failing the task. DONE
when a fixture provider emitting limit responses produces a paced,
successful run whose evidence shows the waits, and providers without
limit signals behave exactly as today.

## How it fits (inspect current shape before building)
Transport retry/backoff for individual calls exists in the timeout/retry
feature; rate limiting is a LONGER-horizon concern layered above it: the
governor decides whether a call may START, the existing retry policy
still owns what happens within a call. Limit signals (429-style
responses, provider-specific throttle messages) already surface in the
call evidence/retry reasons — inventory the actual signal shapes first
and normalize them in one place.

## Design (suggested shape)
Module `rate_governor.py`:
- Per-provider state (in-memory per process, persisted snapshot in the
  job area for visibility): a token-bucket or cooldown window fed by
  normalized limit signals; `acquire(provider, role)` blocks (with a
  deadline from budgets — waiting still consumes wall-clock budget,
  honestly) and records a wait event {provider, waited_s, reason} in
  cycle evidence when it had to wait.
- Integration at the single seam where provider calls start (the same
  choke point safe-point checks use — order: stop check, budget check,
  THEN governor acquire, so stops beat waits).
- Status/report surface waits ("waited 84s on provider rate limits this
  run") — the visible-waiting promise; an SSE/UI event kind is reserved
  by name but UI wiring is a later tier.
- Later parallelism throttling consumes the same governor (the acquire
  call is the throttle point) — design the interface for N concurrent
  acquirers now, implement single-flight now.
- Config: per-provider ceilings optional (requests/min) for users who
  know their tier; absent config = purely signal-reactive.

## Task slicing
- **T001** signal normalization from real evidence shapes + unit tests
  (fixture evidence per provider style).
- **T002** governor + acquire semantics + budget/stop interplay + tests
  with an injected clock (no real sleeps in unit tests).
- **T003** seam integration + wait evidence + report line + the fixture
  end-to-end (limits → paced success, waits recorded).

## Acceptance
- Limit-emitting fixture: zero failed tasks, waits in evidence, total
  wall time consistent with pacing. No-signal providers: zero behavior
  change (regression). A stop request during a wait interrupts the wait
  immediately (safe-point ordering test).

## Edge cases & assumption defaults (A9)
- Signals without retry-after hints: exponential cooldown with a
  documented cap. Deadline expiring mid-wait → the budget machinery's
  deadline stop, with the wait recorded as its last event. Multi-process
  runs share nothing in v1 (documented) — cross-process coordination is
  the scheduler tier's problem.

## Orchestrator brief
T001 needs real signal samples — have the worker extract them from
existing evidence fixtures and list them in the diff. Gate T003 on the
seam being confirmed. Reject sleeps in unit tests.

## Do not touch
Per-call retry policy, parallelism itself, provider adapters' internals.
Suggested tests: tests/orchestration/test_rate_governor.py.
