## Goal & Done
The ping-pong loop calls claude-cli through the reference adapter
`ClaudeCliReferenceAdapter` (`packages/providers/adapters/claude_cli_reference.py`): the adapter
builds the invocation and maps the stream, the usage and the errors; the loop keeps transport,
timeouts, every retry, failover, rate pacing and the per-call evidence. DONE when a claude-cli
builder and reviewer call of a job runs through the adapter, the existing claude-cli goldens and
integration tests stay byte-equal and unmodified, and orchestration still imports only the contract
(the import guard of `tests/contracts/test_adapter_import_guard.py` stays green).

## Why this exists
F151 (`docs/system/worker-adapter-contract-v2.md`) built the contract, the conformance kit and the
reference adapter, and reached the adapter only from `remedy worker show`. An interface no job uses
proves nothing about the jobs; every later vendor adapter (F153, F154, F155) needs the loop to call
an adapter, and this feature makes the first one do it.

## How it fits
- The adapter is reached through a seam the wiring layer fills (the import guard forbids
  orchestration to import a concrete adapter): the loop receives a `WorkerAdapter` from the
  provider factory's caller, never imports `packages/providers/adapters/`.
- `ClaudeCliProvider` in `packages/orchestration/pingpong_provider.py` keeps its transport;
  what it builds and maps today by calling `build_claude_cli_args`, `parse_cli_result_detailed`
  and the stream functions it then asks of the adapter. `pingpong_provider.py` and the loop's
  functions are held by `docs/system/structure-ledger-v1.md`, so the change shrinks them or routes
  through a new module's door; it never grows them.
