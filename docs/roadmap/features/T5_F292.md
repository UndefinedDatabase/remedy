## Goal & Done
The cockpit can do the seven writes the write door already accepts but no screen offers: the six
edits of a plan that waits for approval (DECISION F015 D3) and the approval or rejection of a
change's hunks (F033). DONE when a plan view shows the stored plan with its version, its approval
state and, for each planned task, its dependencies and acceptance criteria, and offers each of the
six edits against the version it shows, with a version conflict told in plain words; when the diff
view lets a person approve a hunk or reject it with a reason; and when the command palette's seven
form entries open these surfaces instead of standing disabled.

## Why this exists
F015 left its edits to "the plan view, a later feature", and no feature was registered for it. F033
left hunk decisions to the command line. F044 made every write the door accepts reachable from the
palette, and measured at `5cbbe6c8` what these seven need: the browser can read no plan version, no
approval state and no dependency of a planned task, because no read route serves them, so a plan
edit cannot name the version it was made against; and although the diff envelope already carries
each hunk's id and its task run, no screen shows hunk controls. A palette is the wrong place to
merge, split or reorder planned tasks, so the palette opens these surfaces rather than holding them.

## Task slicing
- T001 — the plan read: one builder in `packages/orchestration/plan_editing.py` shared by
  `remedy job plan-show --json` and a dashboard section, serving the version, the approval, whether
  the plan is open for editing and why not, and each planned task with its entry id, dependencies
  and acceptance; the plan view that renders it.
- T002 — the six edits in the plan view, each sent with the version shown, a version conflict and a
  refused edit told in plain words, and the view read again after each accepted edit.
- T003 — hunk controls in the diff view: approve, reject with a reason, the job's own scope sent
  without a task run; the palette's seven form entries become surface entries opening these views;
  an end-to-end run.

## Acceptance
- The plan view's version, approval and tasks equal `remedy job plan-show --json` for the same job.
- Each of the six edits reaches the door with the version shown and is refused with a plain reason
  when the plan moved on.
- A hunk approved or rejected in the diff view lands in the hunk decision record exactly as
  `remedy patch approve-hunks` would record it.
- The palette lists no form entry disabled.

## Do not touch
The write door's argument checks and refusal codes; the plan's own validation; the diff view's
reading of the envelope.

## Built State (F292, 2026-10-01)

What exists on disk before the closure sequence of F292, built on
`feature/f292-plan-view-hunk-decisions`, cut from `main` at `2d138e90f`. Every DECISION named lives
in `.agent/decisions.md`; every round's verdict in `.agent/live_review.md` or, once rotated, its
archive.

**T001 — the plan read and the plan view.** One builder, `plan_view` in
`packages/orchestration/plan_editing.py`, serves the stored plan's version, its approval, whether it
is open for editing and why not, and each planned task with its dependencies, its acceptance and the
task entry that runs it; `remedy job plan-show --json` prints it and the dashboard's `plan` section
serves it, so the two read one answer (DECISION F292 D1). The cockpit's plan view,
`apps/ui/src/components/plan/PlanView.tsx`, opens from the right panel's Plan button and shows that
answer, the criteria numbered from 0, the index the edits address (D2).

**T002 — the six edits.** While the plan is open for editing, each task can be edited, deleted,
moved one place, merged with others or split into parts, and each criterion changed, removed or
added. Every edit is sent against the version the view shows through `apps/ui/src/api/planEditSend.ts`;
an accepted edit says the new version and asks the cockpit to read the dashboard again at once, a
stale version and every refusal with a reason are said in plain words, and the controls refuse
before sending what the planner would refuse (D3, D4, D5).

**T003 — hunk decisions and the palette.** The decision recorded for the attempt a diff shows is
served at `/api/jobs/<id>/hunk-decisions` and per task run (D6), and the diff panel shows, after the
diff view, one row per hunk with Approve, Reject with a reason and Undecided, starting from that
record and recording the whole decision through `patch.approve-hunks` (D7). The palette's seven form
entries now open these surfaces, the six plan edits the plan view and the hunk approval the job
diff's hunk decisions, and no palette entry is disabled for being a form (D8).
`tests/ui_server/test_plan_view_live.py` drives both through the real UI server and its write door
in headless Chrome, and reads the stored results back from disk.

**What it does not do.** The diff panel still opens below the cockpit, with the popover that opened
it above, because its layout was left to a later ruling at F037. The palette's hunk entry opens the
job's own diff; a task run's diff is opened from the task's popover. The write door withholds the
reason of a refused hunk decision on purpose, so the panel refuses beforehand everything it can see
coming and otherwise says plainly that the server refused.

**The hardening stage.** Because the session ran in SLOW MODE, a fresh auditor who saw only this file

(DECISION F292 D9).
