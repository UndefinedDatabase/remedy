# T2_F045 — Loop definitions
**Tier 2 · Depends on: F018 · Blocks/used by: F065, F067, F232**

## Goal & Done
Recurring work gets a declarative, versionable form: a LOOP defines
trigger, scope, action, budget and stop rules; `remedy loop run` executes
one as a completely normal job/mission with loop provenance in evidence.
DONE when a fixture loop validates, runs through the standard pipeline
(intake/plan/approval rules unchanged), and an invalid spec fails
validation with precise messages before anything runs.

## How it fits (deliberate simplification versus an earlier draft)
Loops are user-authored configuration, so they live where configuration
already lives: as `[[loop]]` array-of-tables INSIDE the project's config
file — one file, versionable in the repo, explainable by the config
command — instead of a new dotted directory convention (easy-to-use
beats a second config location; a split into included files can come
when someone actually has too many loops). Budgets reuse the budget
schema; actions reuse the golden path and missions; nothing here executes
work by itself.

## Design (suggested shape)
- Spec per loop: name (unique), trigger (manual now; schedule/event
  fields are parsed and VALIDATED but explicitly inert until the
  scheduler feature — running them says so honestly), scope (optional
  paths → fences, optional queue binding), action (job with a goal
  template | mission | routine reference later), budgets (the standard
  fields), stop rules, report/notify flags for later consumers.
- Module `loop_spec.py`: load + validate all loops from config (typed
  errors with the loop name and field), `run_loop(name)` → materialize a
  normal job/mission with loop_ref recorded on it and in evidence;
  approval semantics unchanged (a loop does not imply --yes; unattended
  loops set it explicitly in their spec, audited).
- CLI: `remedy loop list` (name, trigger, action, last run from
  evidence), `validate` (all specs, exit nonzero on any error), `run
  <name> [--yes]`.

## Task slicing
- **T001** spec model + config loading + validation + unit tests (unique
  names, unknown fields rejected, inert-trigger warning path).
- **T002** run materialization + loop_ref provenance + approval-semantics
  tests (no implicit --yes; explicit spec flag audited like the CLI
  flag).
- **T003** CLI + last-run display + an end-to-end fixture loop through
  the fake-provider pipeline.

## Acceptance
- Fixture loop runs as a normal job with loop_ref visible in evidence and
  report. Validation catches: duplicate names, missing action, malformed
  budget, unknown keys — each with the loop name in the message.
- Schedule-trigger loops run manually with the honest "scheduler not yet
  available; ran on demand" line.

## Edge cases & assumption defaults (A9)
- Goal templates may reference simple variables (project slug, date);
  undefined variables fail validation, not runtime. Removing a loop from
  config never touches its historical runs.

## Orchestrator brief
Small, sequential, one worker. Include the config-file placement decision
and its rationale in the T001 order so the worker doesn't "helpfully"
create a directory convention.

## Do not touch
Scheduling/cron (later), the routine library (later), notifications.
Suggested tests: tests/orchestration/test_loop_spec.py,
tests/cli/test_loop_cmd.py.
