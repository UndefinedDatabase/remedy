# T13_F211 — Card federation
**Tier 13 · Depends on: F125, F184 · Blocks/used by: knowledge scaling across projects**

## Goal & Done
See ROADMAP.md F211; the Done criterion there is binding.

## Context (existing code & prior features)
F125 knows global vs. project; F184 the curation roles. The org level and subscription are missing.

## Design
A three-level store: org (~/.remedy/org/memory/cards/) -> user-global -> project; resolution priority project > user > org on slug collision (the F125 heuristic extended). `remedy memory promote <id> --to org` (requires the reviewer role in the org scope, F184); subscribe: a project config selects org card TAGS that may be attached (opt-in per project). Value signals (F150) stay PROJECT-LOCAL; the org view shows an aggregate for information only (n projects, median rank) - no global value blending.

## Task slicing
T001 the third level in the loader + priority + promote rights + tests. T002 the subscribe mechanics + the aggregate display + a fixture (a three-level collision resolves correctly).

## Acceptance & tests
Three-level resolution tested; an org promote without the role is 403; the F150 value property stays intact (no org write path onto project-local values).

## Risks / anti-goals
No auto-subscription; subscribed org cards are usable directly but F119 shows the org origin clearly (a deliberate decision against double-approval bureaucracy, documented).
