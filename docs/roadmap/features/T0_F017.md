## Goal & Done
A job can only write inside declared path fences; violations produce a
blocking, visible artifact — never a silent skip, never a half-applied
change set. DONE when enforcement sits at the single choke point where file
changes materialize, sane defaults protect the repo with zero
configuration, and violations show up in evidence and CLI.

## How it fits (inspect current shape before building)
File changes reach the repo through one applicator path (the module that
applies builder patches/artifacts to the worktree) — enforce THERE, at one
choke point, not scattered across callers; confirm its current name and
its all-or-nothing behavior first and reuse its rollback. Worktree
containment already exists structurally; fences add path rules INSIDE the
worktree. Config keys go through the central config system so `remedy
config` can explain them.

## Design (suggested shape)
Module `fences.py`:
- `FenceSpec`: allow globs (default everything), deny globs, plus an
  always-active builtin deny covering at least the git directory, the
  project config file, the data directory, and the roadmap STATUS file
  (jobs must never check themselves off — that stays human/A4 territory).
- Precedence when loading: per-job fences (an additive optional field on
  the job model; the Flight Plan feature will populate it later) > a
  `[scope]` table in the project config > defaults.
- `check_path` is pure: deny beats allow; builtin deny beats everything;
  paths are normalized; anything resolving outside the worktree root
  (including via symlink or `..`) is denied with reason escapes_worktree.
- Enforcement: before applying a change set, check every touched path
  (renames: source AND destination); collect ALL violations, then raise a
  typed fence-violation error — atomic, nothing applied. Write a
  fence_violations.json evidence artifact; the postmortem classifier gains
  an additive `fence_violation` class.
- CLI `remedy job fences <id>` shows the effective spec with the source of
  each rule.

## Task slicing
- **T001** spec + load precedence + pure checker; exhaustive unit tests
  (glob semantics, deny-over-allow, builtin immunity, escapes, absolute
  input; case sensitivity documented as-is).
- **T002** applicator enforcement + atomicity: a set with one good and one
  violating file applies NOTHING; artifact + postmortem class asserted.
- **T003** job field (optional, default none, backward-compat fixture
  loads) + config keys + CLI display.

## Acceptance
- Unconfigured: writing a normal source file passes; writing into the git
  dir or outside the worktree is blocked with distinct reasons.
- A `[scope]` deny in a fixture config blocks exactly that subtree and the
  CLI names the source.
- Violating change set leaves the filesystem untouched (diff empty).
- Fencing a 1000-file change set stays well under a second (pure string
  work).

## Edge cases & assumption defaults (A9)
- Empty configured allow list → treated as allow-all with a logged warning
  (misconfiguration must not brick every job). Symlink targets are resolved
  before checking.

## Orchestrator brief
Have the worker confirm the applicator module and its rollback behavior
before T002; T001 is pure and dispatchable immediately. Keep the builtin
deny list a reviewable constant — reviewers must see additions in diffs.

## Operator finding (2026-08-25, dogfooding)

A protected path blocked a whole promotion with no way forward. Job
`e984ec1943bb422f` ("FizzBuzz Demo v2") produced three reviewed files. The
builder had also written a `.gitignore` into the workspace unasked, and
`.gitignore` is in `pingpong_promote._BLOCKED_EXACT`, so `remedy do job-promote`
recorded `files_planned: [fizzbuzz.py, test_fizzbuzz.py]`, `files_applied: []`
and `blocked_reason: blocked_paths: ['.gitignore: blocked_path: .gitignore']`.
Two good files were withheld because of a third the operator never asked for,
and `--approve` was already set: there is no further flag, and the blocked
output prints no next step.

THE GUARDRAIL IS CORRECT AND IS NOT THE FINDING. All-or-nothing is this
feature's Goal in its own words — "never a silent skip, never a half-applied
change set" — and a promotion that quietly dropped `.gitignore` and applied the
rest would be exactly the silent skip that rule exists to forbid. Nothing about
the blocked-path list, its enforcement or its atomicity should be weakened.
What is missing is everything AROUND the block. Three facets:

(a) **The builder should not have touched `.gitignore` at all.** A task brief
that asks for a FizzBuzz module and its tests has no business producing repo
meta-files, and a meta-file the operator never requested is the input that
turned a correct guardrail into a dead end. This is a briefing and scope
question — what a builder task is told it may create — and it sits upstream of
the fence: a fence that fires is working, but a run in which it never had to
fire is the better outcome. Nothing here proposes letting builders write
protected paths.

(b) **There is no deliberate partial promotion.** The atomic rule answers
"apply everything or nothing"; it does not answer "the operator has now SEEN
the blocked paths and decided to promote without them". That is a different
question, asked after the block, by a human who has read the list. A shape that
keeps the rule intact would name every blocked path, require the operator to
acknowledge that exact set, and then promote the remainder as its own atomic
change set — still no silent skip, still nothing half-applied, just a second
explicit decision. Deciding whether Remedy wants that, and where it lives, is a
design question this file records rather than answers.

(c) **The blocked output owes an honest next step.** `remedy do job-promote`
prints `Blocked: blocked_paths: [...]` and stops. Every other stalled surface
in Remedy ends with a `Next:` line (`remedy do`, `remedy status`, the
orchestrator's `next_safe_action`, the proof chain), and this one does not — so
the operator's only remaining move is to read the source. Even with (b)
unbuilt, the line can be honest today: name the blocked paths, and say that
removing them from the workspace and re-running is the way through.

        and `TestSkipBlockedThroughTheGroupedCLI`, 10 tests together.

**(b) Deliberate partial promotion.** `promote_job` and `_promote_from_workspace`
take `skip_blocked`, and `JobPromotionResult` carries it into the record and the
`--json` export. It changes exactly ONE decision — whether a non-empty blocked
set aborts the whole promotion — and widens nothing:

- `_is_blocked_path`, `_BLOCKED_EXACT` and `_BLOCKED_PREFIXES` are untouched.
- A blocked path is still detected by the same checks, still kept out of
  `files_planned`, and still never opened for writing.
- Every blocked path is still named in `files_blocked` and printed, so the skip
  is explicit rather than silent — the "never a silent skip" rule in this
  feature's own Goal is what the naming preserves.
- The remainder is promoted as its own atomic change set; a failure inside it
  behaves exactly as before.
- With `--skip-blocked` and NOTHING promotable left, the answer is still a block
  (`no_promotable_files`), never an empty success.

**(c) The honest next step.** `_next_step_for_promotion` gives every blocked
summary a closing `Next:` line, printed after the file lists so the operator
reads the paths before the route through them. The line names the route that
ACTUALLY applies: a protected-path block offers both removing the paths and
re-running with `--skip-blocked`; a block `--skip-blocked` cannot lift says so
in as many words instead of advertising a flag that would not help.

**Flag shape.** `--skip-blocked` is declared `is_flag=True` in
`apps/cli/command_catalog.py`. Without that it falls through to the generic
valued-option branch whose default is the STRING `"false"`, which is truthy, so
partial promotion would arm itself on every run. That shape is pinned by a test.
