## Goal & Done
DECISION amend0905-vocab D10, verbatim:

Every passed task lands as one commit on the job worktree branch `remedy/<job id>`
(message: task title + contract state). `job apply --approve` copies files as
today; `job apply --approve --with-history` merges those commits into the
operator's current branch instead. Remedy never commits on the operator's branch by
itself; `--with-history` is an operator command. Non-git targets (staging copies)
support copy only.

DONE when the Acceptance list holds.

## Why this exists
The job worktree is already a real branch: `packages/orchestration/worktrees.py`
creates it with `git worktree add -b remedy/<job id>` (`BRANCH_PREFIX = "remedy/"`,
line 34; the `add -b` call at line 355, measured 2026-09-05). But nothing commits on
it, so intermediate steps are lost at apply: the operator gets one flattened copy
and no history of how the tasks built up. One commit per passed task makes the
worktree branch the honest record, and `--commit-with-history` lets the operator keep it.

## DECISIONs
D10 binds this feature. F263's DECISION D-E (human changes are never overwritten;
on conflict the run stops and says so) governs the merge's refusal path. DECISION
amend0911-feedback D4 (2026-09-11) binds this feature: the operator's flag family
replaces `--with-history`, and the sentence "Remedy never commits on the
operator's branch by itself" becomes "never without an explicit flag or a config
key the operator set". The flag IS the operator's word; the iron rule is
unchanged.

## Design
- After a task's run passes, the job path commits the applied files on the
  worktree branch: author `Remedy <remedy@local>`, message `task <n>: <title>` plus
  a contract-state line (criteria green/red counts from F269 when present).
- `job apply --approve --commit-with-history`: verifies the operator's branch is
  clean, merges `remedy/<id>` with `--no-ff` so history reads as one block, and
  refuses on conflict under F263 D-E — human edits win, never overwrite.
- Staging mode (non-git target) → copy only; the flag is refused with one sentence.
- Snapshot guard semantics unchanged: the operator's branch is never committed to
  by Remedy on its own; `--commit-with-history` is the operator's explicit command.
- The `remedy/<id>` branch keeps existing after apply (worktrees.py already
  preserves it by design); nothing here deletes it.
- The flag family on `job apply` (and passed through by `do`), operator ruling
  2026-09-11: `--commit "<message>"` applies AND lands ONE commit on the operator's
  current branch with the operator's message; `--commit-auto` does the same with a
  message Remedy writes from the mission title, the task titles and the contract
  state; `--commit-with-history` merges the per-task commits of `remedy/<id>` with
  `--no-ff` (the former `--with-history`; the old word is deleted, never aliased,
  per D-B). Every `--commit…` flag implies `--apply`, refuses on a dirty operator
  tree, commits exactly the files apply copied, and never touches another path.
- Author and trailers: commits on the operator's branch use the operator's own git
  identity (`user.name`/`user.email` of the target repository) and carry the
  trailers `Remedy-Job: <job id>` and `Co-authored-by: Remedy <remedy@local>`;
  commits on `remedy/<id>` keep the `Remedy <remedy@local>` author above.
- Commit messages are for humans: the first line is a whole sentence in plain
  words (what changed, under 72 characters), never an id alone; the body says what
  and why in sentences; the contract state is the last body line ("contract: 3 of
  3 criteria green"). This holds for the per-task commits on `remedy/<id>` too —
  `task 2: add the contact form` is a sentence, `task 2: T002` is not.
- `--push` (only together with a `--commit…` flag; refused alone) pushes the branch
  the commit landed on to its configured upstream, never with force, never to a
  branch other than the one committed to, and only when no blocking contract
  criterion is red. Push is a MISSION-level act: `do` pushes once at the end of the
  mission, not per job. The config key `apply.push_after_mission` (default
  `false`) makes unattended runs push exactly as `--push` would; the session that
  builds it reads `packages/orchestration/config.py` and registers the key in the
  existing key registry with that default and a one-sentence help text.

## T001 — Per-task commit
The commit on the worktree branch after each passed task, with message and author
as above; a two-task fake run yields two commits.

## T002 — `--commit-with-history` merge
Clean-tree check, `--no-ff` merge onto the operator's current branch, the
operator's log shows both commits.

## T003 — Refusal paths
Dirty operator tree → refused; merge conflict → refused with the conflicting paths
and no file overwritten (D-E); staging target → copy only, flag refused.

## T004 — The commit and push flags
`--commit "<message>"`, `--commit-auto`, `--push` and the config key
`apply.push_after_mission` per the Design bullets of 2026-09-11; the message
generator for `--commit-auto` is the same one the per-task commits use; refusal
paths: `--push` without a commit flag, push with a red blocking criterion, push to
a branch with no upstream (refused with the one command that would set one).

## Acceptance
- A two-task fake run yields exactly two commits on `remedy/<id>`.
- `--commit-with-history` lands them on the operator branch; the operator's
  `git log` shows both.
- A hand edit in the target before apply is not lost (F263 D-E) — proved by a
  fixture whose edit conflicts.
- Staging targets refuse `--commit-with-history` and copy as today.
- Remedy never commits on the operator branch without an explicit `--commit…` flag
  or `apply.push_after_mission` (test).
- `--commit "Add the contact page"` on a passed fake job yields exactly one commit on
  the operator branch with that first line, the two trailers and the contract line;
  `--commit-auto` yields one commit whose first line is a sentence (a test rejects
  a first line without a verb or over 72 characters); `--push` without a commit
  flag is refused; `--push` with a red blocking criterion is refused; a fixture
  remote receives exactly one push per mission, never a force push.

## Do not touch
The apply gate's approval semantics, the snapshot guard, the worktree lifecycle
(creation, reuse, cleanup) beyond committing on it. Nothing here pushes to a
branch other than the one committed to, and nothing here pushes without the
operator's flag or config key.

**T001 — one commit per applied task.** In `run_job` (`packages/orchestration/pingpong_job.py`),
after a task of a git-target job is applied and before it is saved, the worktree's complete state
is committed on the job branch by `commit_job_worktree` in `packages/orchestration/worktrees.py`:
author and committer `Remedy <remedy@local>` whatever the operator's configuration says, no
signing, no hook, and a refusal of any branch that is not Remedy's own. The message is `task <n>:
<title>` within 72 characters, one body sentence, the contract line `contract: <met> of <total>
criteria green` or `contract: none`, and the trailers `Remedy-Job` and `Remedy-Task`. The sha is
the task's `worktree_commit` and the job's `worktree_head`; a commit an interrupted run already
made is adopted by its trailers, never repeated; a failed commit blocks the job (DECISION F270 D1;
`tests/orchestration/test_job_worktree_integration.py`). A copy-mode job commits nothing.

**T002 and T003 — `--commit-with-history`.** `remedy job apply <job> --approve
--commit-with-history` runs every existing apply gate, then, in place of the copy, `git merge
--no-ff --no-log` of the verified job-branch tip onto the operator's current branch under the
operator's identity and hooks, with the message `Merge the <n> task commits of Remedy job <id>`,
the contract line and the trailers `Remedy-Job` and `Co-authored-by: Remedy <remedy@local>`. It
refuses, changing nothing, a staging job, a target that is not a repository's top level, a
detached `HEAD`, the operator's own merge in progress, a dirty tree, `--skip-blocked`, a file the
copy would skip, and a branch that is missing, moved, or whose tree is not the reviewed
`result.diff`; a conflict or a refusing hook is aborted and named. A committed hand edit to a job
file is refused by the baseline gate before git runs (DECISIONs F270 D2 and F263 D-E;
`tests/orchestration/test_job_apply_history.py`).

**T004 — `--commit`, `--commit-auto`, `--push` and the key.** On `job apply`, `--commit
"<message>"` and `--commit-auto` land ONE commit of exactly the copied files on the operator's
branch after the copy verified and the post-test passed, under the operator's identity, with the
contract line and both trailers; `--commit-auto`'s first line starts with an imperative verb and
fits 72 characters. `--push` needs a commit flag, pushes the landed commit to the branch's
configured upstream once, never forced, and is refused before anything is written without an
upstream or while a blocking criterion of the mission is `unmet`; an `open` one is named, not held
(DECISIONs F270 D3 and D4 (6); `tests/orchestration/test_job_apply_commit.py`). `remedy do` takes
the same flags, refuses what it cannot do before any step, chains every job of the walk under a
commit flag so each is cut from its predecessor's commit, and pushes the mission once after its
last job; `apply.push_after_mission` in `packages/orchestration/config.py` makes a `do` run with a
commit flag push as `--push` would (DECISION F270 D4; `tests/cli/test_do_commit_flags.py`,
`docs/guides/do-run-v1.md`). Without a commit flag, `job apply` and `do` commit nothing on the
operator's branch, the key set or not.
