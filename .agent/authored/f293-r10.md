## DECISION F293 D7 — `remedy doctor core` reads the test load record itself and states its last 24 hours as information only (2026-09-30)

THE PROBLEM: F293 T004 orders one plain sentence in `remedy doctor core` naming how many test runs and CPU minutes the last 24 hours cost, read from the test load record, with nothing wrong printed when the record is absent. The record's path rules live in `tests/load_governor.py`, which no production module may import, and doctor core's JSON output is pinned key by key in `tests/cli/test_worker_facade_cmd.py`.

CHOSEN: `last_day_test_load(environ=None, home=None, now=None)` in `apps/cli/commands/worker_facade_cmd.py` follows the same path rules through the registered reader `env_value("REMEDY_TEST_LOAD_LOG")`: a set value names the file and a set-but-empty value means no record, otherwise `~/.remedy-loop/test_load.jsonl` when that folder exists. It counts the lines whose `utc` lies within the last 24 hours, adds their `cpu_seconds`, skips a line that does not parse, and returns `record`, `runs`, `cpu_minutes` and `sentence`. `DoctorCoreReport` gains the field `test_load` with an empty default, so the three places that build the report by keyword keep working, and `as_json()` ends with the key `test_load`; the text output prints `test load:` and the sentence directly before `dead commands:`. The reading is never a check, a warning or a blocker, so `ready` cannot change with it; a failed read says the cost is unknown. Four new tests in `TestDoctorCoreTestLoad` and the two exact-key lists in `TestDoctorCoreReportFunction`, which now name `test_load`, pin it. The reviewer's mutations in a disposable worktree at `b225adae2`: counting every line regardless of its time, adding `wall_seconds` in place of `cpu_seconds`, and dropping the two printed lines each turned the new tests red; restored, green. The doctor callers' selection read 245 passed and the canary 42 passed. Under pytest, `tests/conftest.py` sets the variable empty for the whole session, so every other doctor test sees no record.

WHAT THIS CHANGES BEHAVIOURALLY, STATED PLAINLY: `remedy doctor core` prints one more line, and its `--json` output carries one more key; nothing it decides changes. The record exists only on machines that run this repository's tests, so an operator elsewhere reads that no record was found.

ALTERNATIVES CONSIDERED: (a) a new module under `packages/orchestration/`, REJECTED because the generated import-reachability list would have to grow for one function that only doctor core calls; (b) a warning above a CPU threshold, REJECTED because T004 asks for a sentence and a threshold nobody has ruled on would be invented here.

HOW TO REVERSE: delete `last_day_test_load`, its two sentence constants, the `test_load` field and key, the two printed lines, `TestDoctorCoreTestLoad`, and `test_load` from the two exact-key lists.
