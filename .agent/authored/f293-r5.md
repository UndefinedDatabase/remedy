## DECISION F293 D3 — `_unsafe_text` in `scripts/build_review_manifest.py` caches its answer per string; the gate matrix scans each distinct text once per process (2026-09-30)

THE PROBLEM: `tests/orchestration/test_review_gate_totality.py::TestGateMatrixIsTotal::test_recursive_matrix_never_throws` was the suite's second slowest entry in T001's ranking (25.71 s), and unlike the slowest it is CPU work, not waiting. The reviewer's profile at `525c2d268` put 38 of its 44 profiled seconds under `_unsafe_text`, called about 1.08 million times over roughly 30,000 gate-matrix evaluations, each call running the secret redactor's and the path scrubber's regular expressions over one of the same few dozen field texts. The file used 29.64 CPU seconds in the test load record (`pytest tests/orchestration/test_review_gate_totality.py -q -n auto --durations=3`).

CHOSEN: `@functools.lru_cache(maxsize=4096)` on `_unsafe_text`. Its answer depends on the string alone: `_contains_secret` compares the redacted text with the input, and `_contains_local_path` compares the output of `safe_text` with the input, where every replaced path starts with `[` and so never equals a raw path, which starts with `/` or a drive letter; the data root that `safe_text` reads changes the replacement, never the yes-or-no answer. The same file then used 5.26 CPU seconds, and the matrix test's call took 2.16 s. A new test, `test_each_distinct_text_is_scanned_once` in `tests/orchestration/test_review_gate_sensitive_metadata.py`, counts the calls into `run_manifest._contains_secret`, requires one call per distinct text, and requires the cached answer for a secret to still read `a secret`. The reviewer's mutations in a disposable worktree: without the decorator the new test is red (four calls for two texts); with the decorator kept and the secret branch removed it is red again; restored, the file reads 9 passed.

WHAT THIS CHANGES BEHAVIOURALLY, STATED PLAINLY: within one process the scanner no longer re-runs for a text it has already answered. A test that swaps `run_manifest._contains_secret` or `_contains_local_path` and then expects `_unsafe_text` to re-evaluate a text scanned earlier in the same process would see the earlier answer; by `git grep` at `525c2d268` no test does that, and the one test that swaps `_contains_local_path`, in `tests/orchestration/test_review_subject_strict_schema.py`, exercises `packages/orchestration/review_subject.py`, which calls the detectors directly. The cache holds at most 4,096 strings that the process already holds in memory, and nothing is written anywhere. A review manifest build is one short process; the cache only spares it repeated scans of a text it meets again.

ALTERNATIVES CONSIDERED: (a) caching `_contains_secret` and `_contains_local_path` in `packages/orchestration/run_manifest.py`, REJECTED for this round because those two have more callers and tests that swap them, and the measured cost sits under `_unsafe_text`; (b) shrinking the matrix of wrong values in the totality test, REJECTED because it removes coverage, which the feature's Do-not-touch forbids.

HOW TO REVERSE: delete the decorator, the `import functools` line and the two docstring sentences that name this decision, and delete `test_each_distinct_text_is_scanned_once`.
