═══ ITEM 3 · C2 — the loop spec model, loading and validation ═══

DECISION F045 D1 — WHERE loops live. `[[loop]]` is a TOP-LEVEL array of
tables in remedy.toml, NOT `[[remedy.loop]]`, and NOT a new dotted directory
convention. Reason, verified on disk: `load_config` in
packages/orchestration/config.py reads only `parsed["remedy"]`
(`_extract_remedy_table`), flattens it to dotted keys, and appends
"Unknown key in <path>: <key>" to `load_report.warnings` for every key absent
from `_KEY_SPEC_MAP`. `_flatten_toml` does not recurse into lists, so
`[[remedy.loop]]` would arrive as the flat key `loop` and make every config
load emit a spurious unknown-key warning. Top-level keeps the existing config
system byte-for-byte unchanged and lets loop_spec.py own its own table.
Alternatives considered: a `[[remedy.loop]]` table (rejected — the warning
above), a `.remedy/loops/` directory (rejected — the feature file's
Orchestrator brief explicitly forbids inventing a second config location).
Reverse it by moving the table key and teaching config.py to ignore it.

DECISION F045 D2 — deadline validation is NOT imported. `LoopBudgets.deadline`
is validated in loop_spec.py by `datetime.fromisoformat` plus a REQUIRED
tzinfo, deliberately mirroring the contract of the private
`budget_resolution._parse_deadline` rather than importing a private helper or
widening budget_resolution.py, which belongs to F018/F104. Say so in the
docstring. Reverse it by promoting that helper to public API in its own round.

NEW FILE packages/orchestration/loop_spec.py. Module docstring states the
feature (F045 T001), DECISION D1 and DECISION D2 in prose. Follow the
conventions of packages/orchestration/dod_schema.py: pydantic models based on
`_Strict` from packages.orchestration.structured_base (its `extra="forbid"` IS
the "unknown fields rejected" requirement), a one-line WHY comment directly
above each public definition (AGENTS.md Code Discoverability).

Public API, exactly these names:

  LOOP_TABLE_KEY = "loop"
  INERT_TRIGGER_KINDS = frozenset({"schedule", "event"})
  INERT_TRIGGER_NOTICE = "scheduler not yet available; ran on demand"
  LOOP_TEMPLATE_VARS = frozenset({"project", "date"})

  class LoopSpecError(ValueError): attributes `loop_name: str | None` and
    `field: str | None`; str() is the full message.

  class LoopTrigger(_Strict): kind: Literal["manual","schedule","event"] =
    "manual"; schedule: str | None = None; event: str | None = None
  class LoopScope(_Strict): paths: list[str] | None = None;
    queue: str | None = None
  class LoopAction(_Strict): kind: Literal["job","mission"];
    goal_template: str | None = None; mission: str | None = None
  class LoopBudgets(_Strict): max_total_tokens: int | None,
    max_provider_calls: int | None, max_wall_clock_minutes: int | None,
    max_cost_usd: float | None, deadline: str | None — all default None, all
    field names identical to `_CONFIG_KEYS` in budget_resolution.py
  class LoopStopRules(_Strict): max_runs: int | None = None;
    stop_on_failure: bool = True
  class LoopSpec(_Strict): name: str; trigger: LoopTrigger = LoopTrigger();
    scope: LoopScope | None = None; action: LoopAction;
    budgets: LoopBudgets | None = None; stop: LoopStopRules | None = None;
    unattended: bool = False; report: bool = False; notify: bool = False
    plus a property `is_inert` -> `self.trigger.kind in INERT_TRIGGER_KINDS`

  def load_loop_specs(project_path: Path | None = None) -> tuple[LoopSpec, ...]
  def validate_loop_specs(project_path: Path | None = None) -> list[str]

Semantics:
- Default project_path is `Path("remedy.toml")`. A MISSING file is not an
  error: `load_loop_specs` returns `()` and `validate_loop_specs` returns `[]`.
- Import tomllib exactly as config.py does (tomllib on 3.11+, tomli fallback,
  None guard). Malformed TOML → LoopSpecError naming the path.
- `load_loop_specs` raises LoopSpecError on the FIRST error.
  `validate_loop_specs` returns ALL error messages in file order and never
  raises for a spec-level error.
- Message shape, every message: `loop '<name>': <detail>` when the entry has a
  usable name, else `loop #<1-based index> (no name): <detail>`. The loop name
  is in EVERY spec-level message — that is the feature's Acceptance line.
- Rules, each with its own message detail:
  * top-level `loop` present but not a list of tables →
    `<path>: 'loop' must be an array of tables`
  * missing/blank/non-string name → `name is required`
  * duplicate name → `duplicate loop name`
  * unknown key (pydantic extra=forbid) → `unknown key '<key>'`
  * missing action → `action is required`
  * action.kind == "job" without goal_template →
    `action.goal_template is required for a job action`
  * action.kind == "mission" without mission →
    `action.mission is required for a mission action`
  * trigger.kind == "schedule" without schedule → `trigger.schedule is
    required for a schedule trigger`; same shape for event/event
  * any budget int field <= 0 → `budgets.<field> must be a positive integer`;
    max_cost_usd <= 0 → `budgets.max_cost_usd must be a positive number`
  * deadline unparseable or naive → `budgets.deadline must be an ISO 8601
    timestamp with a timezone`
  * stop.max_runs <= 0 → `stop.max_runs must be a positive integer`
  * goal_template referencing a variable outside LOOP_TEMPLATE_VARS, or an
    empty `{}` → `goal_template references undefined variable '<var>'`.
    Scan with `re.findall(r"\{([^{}]*)\}", goal_template)`. This is the A9
    edge case: undefined variables fail VALIDATION, never runtime.
- An inert trigger is VALID. It is never an error, never a warning that fails
  a load; `is_inert` plus INERT_TRIGGER_NOTICE is how T002/T003 report it.
