## DECISION F293 D4 — `dead_command_ids` also caches each match answer per search root and searched words; a repeated question reads no search text (2026-09-30)

THE PROBLEM: after DECISION F293 D2, a warm call of `doctor_core_report` still cost about 0.46 CPU seconds, measured by the reviewer's profile at `b0faefe61`: 0.46 of its 0.48 profiled seconds sat in the substring test of `dead_command_ids` (`packages/orchestration/dead_command_check.py`), whose generator took 43,328 steps per call, because every call asked again, for every catalog command outside the argv-pair set, whether any search text names it. D2's alternative (b) called that matching "already cheap (under 0.01s)", which this measurement shows was wrong. `tests/cli/test_worker_facade_cmd.py` used 22.04 CPU seconds in a serial run (`pytest tests/cli/test_worker_facade_cmd.py -q -n 0 -p no:cacheprovider`, test load record).

CHOSEN: a module-level `_MATCH_CACHE` and a helper `_mentioned(root, texts, kind, words)`, keyed by the search root, the kind of test (`"text"` for the substring test, `"name"` for the whole-word test) and the frozen set of words. Both tests answer exactly what the two inline `any(...)` expressions answered, and the handler table is read at the same point as before, so a catalog entry without a handler behaves as it did. The answer depends only on the root's files, which D2 already reads once per process on the argument that they do not change while a process lives, and on the words. A command a test plants (`_plant_dead_command` in `tests/cli/test_worker_facade_cmd.py` mints its ids from a uuid and gives its handler no names) has words of its own, so it is still searched for. The same file then used 2.83 CPU seconds. A new test, `test_a_repeated_question_reads_no_search_text_again` in `tests/orchestration/test_dead_command_check.py`, replaces the cached texts with a list that refuses to be read and requires the second call to give the same answer. The reviewer's mutations in a disposable worktree: reading the cache never (`hit = None`) turned the new test red; keying the cache without the words turned four tests red, the two planted-command tests of `TestDoctorCoreDeadCommands` among them; restored, `tests/orchestration/test_dead_command_check.py` reads 6 passed.

WHAT THIS CHANGES BEHAVIOURALLY, STATED PLAINLY: within one process, `dead_command_ids` no longer re-reads the search texts for a question it has already answered for the same root; D2's limit therefore reaches the answers too, and a caller that adds a file under a root's `tests/` or `scripts/` after the first call in the same process would not see it. No caller does that (D2). `remedy doctor core` is one process per invocation and asks each question once either way.

ALTERNATIVES CONSIDERED: (a) one joined text per root in place of the per-file loop, REJECTED because a substring search reads the same bytes either way and saves only the loop's overhead; (b) caching the whole answer keyed on the catalog and the handler objects, REJECTED because a planted command would then miss the cache for every command instead of for its own.

HOW TO REVERSE: delete `_MATCH_CACHE` and `_mentioned`, put the two inline `any(...)` expressions back into `dead_command_ids`, and delete `test_a_repeated_question_reads_no_search_text_again`.
