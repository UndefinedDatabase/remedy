## DECISION F293 D5 — `_is_safe_key` in `packages/orchestration/run_manifest.py` caches its answer per string key and use; the input snapshot's key names are checked once per process (2026-09-30)

THE PROBLEM: the reviewer's profile of `tests/orchestration/test_job_task_runner.py` at `382c9cbec` found `validate_input_snapshot` called 2,266 times, and within it `_is_safe_key` called 253,811 times for about 11.4 of the run's 65 profiled seconds, almost all of it in `_contains_secret` and `_contains_local_path`, the secret redactor and path scrubber that DECISION F293 D3 already met one level up. An input snapshot carries every config key and every `REMEDY_` environment key by name, so the same key names are checked again at every validation of every run manifest.

CHOSEN: `_is_safe_key(key, *, allow_dots=True)` keeps its signature, answers False for a key that is not a string, and otherwise returns `_is_safe_str_key(key, allow_dots)`, which holds the old body under `@functools.lru_cache(maxsize=4096)`. Its answer depends on the key and `allow_dots` alone: the bounded-length limit, the character rules and the regular expression are constants, and the two detectors are pure over their input. `lru_cache` stores no answer for a call that raises, and each detector catches its own failures and answers True, so a value is never cleared by a failure. Measured in a disposable worktree at `382c9cbec`, serial runs of `tests/orchestration/test_job_task_runner.py` (`pytest ... -q -n 0 -p no:cacheprovider`, test load record) read 70.59 CPU seconds before and 54.17 after; the same file read 41.0 CPU seconds in the primary checkout at `b0faefe61`, so only readings taken in one tree are compared. Two new tests in `tests/orchestration/test_run_manifest_security.py` pin the cache: the detectors run once for a key asked twice, and a dotted key is answered apart for `allow_dots=False` and `True`, in both orders. The reviewer's mutations: without the decorator the first test is red; with the wrapper passing `True` for every use the second is red; restored, the file reads 16 passed. The selection `pytest tests/orchestration -q -n auto -k run_manifest` read 880 passed.

WHAT THIS CHANGES BEHAVIOURALLY, STATED PLAINLY: within one process a key name is checked once per use. A test that swaps `run_manifest._contains_secret` or `_contains_local_path`, or the redactor under them, and then expects `_is_safe_key` to re-check a key it checked earlier in the same process would see the earlier answer; by `git grep` at `382c9cbec` the three test files that swap a detector or the redactor (`tests/orchestration/test_run_manifest_security.py`, `tests/orchestration/test_review_subject_strict_schema.py`, `tests/orchestration/test_review_gate_sensitive_metadata.py`) call the detectors directly or through `review_subject` and the review manifest builder, never through `_is_safe_key`. The cache holds at most 4,096 key names and writes nothing.

ALTERNATIVES CONSIDERED: (a) caching `_contains_secret` itself, REJECTED because `TestSecretDetectorFailsClosed` swaps the redactor for one that raises and requires the answer True for a value an earlier test may already have checked, so a cached False would turn it red and would hide a failing redactor; (b) caching the whole `validate_input_snapshot` result, REJECTED because its input is a mutable record with no stable key short of re-serialising it, which is itself a fifth of the function's cost.

HOW TO REVERSE: fold `_is_safe_str_key` back into `_is_safe_key`, delete the decorator and the `import functools` line, and delete `TestSafeKeyAnswersPerKeyAndUse`.
