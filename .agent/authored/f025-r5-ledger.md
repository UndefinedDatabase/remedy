- R-1051 — Low, `unpause_job_command` ANSWERS `parked` FOR ANY JOB WHOSE STATE IS `paused` BEFORE IT LOOKS FOR A PENDING PAUSE, SO A PAUSE REQUESTED AGAIN ON A PARKED JOB CANNOT BE WITHDRAWN AND THE RELAUNCH IT RECOMMENDS PARKS THE JOB AGAIN. Raised by the planner and reviewer of F025's first session at round 4's gate, having searched this record and its archive for `unpause_job_command` and `parked` and found nothing. THE DEFECT, at `db496696`: without a task, `unpause_job_command` in `packages/orchestration/pause_control.py` returns outcome `parked` with the relaunch command whenever the job's state reads `paused`, and only otherwise calls `withdraw_pause`. MEASURED by the reviewer's probe against a scratch control root: a job whose state is `paused` with a pause record, given a new `request_pause`, answers `unpause_job_command` with `parked` and the new request is still pending afterwards, so `remedy job run` would serve it and park the job at once. The same answer is given for a job the task cap paused, which carries no operator pause at all. WHY LOW: a second pause on an already parked job is unusual and nothing is lost, but the command tells the operator to do something that will not do what it says. THE ROOT is DECISION F025 D2's clause (2), which states both answers without ordering them. FIX: without a task, a pending job pause is withdrawn first, outcome `withdrawn`, whatever the job's state; only when nothing is pending does a job in state `paused` WITH a non-empty pause record answer `parked`; everything else answers `not_paused`. - R-1052 — Low, THE TASK PAUSE EVENTS ARE WRITTEN ONLY WHEN THE CALL ITSELF CREATES OR RELEASES THE ENTRY, SO A `task_paused` WHOSE WRITE FAILS IS NEVER WRITTEN BY A RETRY. Raised by the planner and reviewer of F025's first session at round 4's gate, having searched this record and its archive for `task_paused` and `_write_task_paused_event` and found nothing. THE DEFECT, at `db496696`: `pause_job_command` reads whether the task was already paused, publishes the entry, and writes `task_paused` only when it was not; a failing write raises after the entry is durable, and a retry of the same pause finds the entry and writes nothing. MEASURED by the reviewer's probe against a scratch data root with the ledger writer failing once: the first call raised, the retry answered `paused`, and the job's ledger holds no `task_paused`, while the control run of a healthy release in the same root wrote its one `task_resumed`. WHY LOW: only a failing ledger write reaches it, but the timeline and the graph then never learn that the task was paused. THE ROOT is round 4's block, which ordered the event written "only when the call created, or released, the entry". FIX: `task_paused` and `task_resumed` are exactly once per task pause request id by the LEDGER, as `job_paused` is: a pause publishes the entry and then writes `task_paused` when the ledger holds none for that request id; a release writes `task_resumed` when the ledger holds none for that request id BEFORE it releases the entry, so a failed write leaves the task paused; a failed write still raises so the CLI and the door report it, and a retry of either writes the missing event exactly once.
