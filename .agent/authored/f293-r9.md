## DECISION F293 D6 — `tests/conftest.py` reads Remedy's own checkout identity once per test process, at session start (2026-09-30)

THE PROBLEM: every run's input snapshot records `remedy_worktree_identity()` (`packages/orchestration/run_manifest.py`), the git content identity of the Remedy checkout itself, and each reading runs several git processes over the whole checkout, twice per git command because `_git_bytes` first asks `git config` which helpers to neutralise. The reviewer's profile of `tests/orchestration/test_job_task_runner.py` at `382c9cbec` counted 146 such readings in one run of that file, about 15 of its wall seconds, all inside `build_input_snapshot`. Three test files (`tests/cli/test_job_rerun_manifest.py`, `tests/orchestration/test_run_manifest.py`, `tests/orchestration/test_run_manifest_logical_identity.py`) already froze the value per test, keeping the real identity, because a neighbour that writes into the shared checkout raced the digest (R-0645, R-0950).

CHOSEN: a session-scoped autouse fixture, `_one_remedy_checkout_identity_per_process`, in `tests/conftest.py`: it reads the real identity once, when a test process's session starts and before any test can patch git, and points `run_manifest.remedy_worktree_identity` at that value for the whole session, restoring the function at the end. `_remedy_repo_root()` comes from the module's own path, so the value always describes this checkout, and no test may change this checkout. A test that sets its own value with `monkeypatch` still wins inside that test, and the three freezing fixtures keep working unchanged. Child processes that a test starts, such as CLI runs, still read their own identity. Measured in one disposable worktree at `4c4be0d99`, serial runs of `tests/orchestration/test_job_task_runner.py` (`pytest ... -q -n 0 -p no:cacheprovider`, test load record) read 55.23 CPU seconds before and 12.66 after. A new test, `TestOneCheckoutIdentityPerProcess` in `tests/regression/test_test_load_governor.py`, requires two readings in one process to be the same object. The reviewer's mutations: without the fixture's reassignment the new test is red; with `remedy_worktree_identity` made to raise, the session fixture errors and the test with it, so the real reading still runs once in every test process; restored, green. With the fixture in place and before the new test was added, `pytest tests/orchestration tests/cli/test_job_rerun_manifest.py tests/regression/test_resource_safety.py tests/regression/test_test_load_governor.py tests/regression/test_data_root_guard.py tests/test_data_root_isolation.py tests/test_test_categories.py -q -n auto -k 'run_manifest or rerun or resource_safety or load_governor or data_root or categories'` read 1050 passed, and the canary 42 passed.

WHAT THIS CHANGES BEHAVIOURALLY, STATED PLAINLY: nothing in the product. Inside a test process, Remedy's own checkout identity is the one read at session start, so a test can no longer observe a neighbour's edit to the shared checkout; by `git grep` at `4c4be0d99` the one test that changes `worktree_identity` for the Remedy root, in `tests/orchestration/test_run_manifest_logical_identity.py`, already froze the identity before it, and the tests that force git failures (`tests/orchestration/test_run_manifest_integrity.py`) read temporary repositories. Every test process pays one reading at session start, including a short run of one file.

ALTERNATIVES CONSIDERED: (a) caching the identity in the product, REJECTED because a long-running Remedy process must record the checkout as it is when each job starts; (b) reading it lazily at the first call inside a test, REJECTED because a test that had patched git at that moment would leave a broken value to every later test in the process; (c) adding the per-test freeze to more files one by one, REJECTED because every in-process job run in the suite pays the same readings.

HOW TO REVERSE: delete the fixture from `tests/conftest.py` and `TestOneCheckoutIdentityPerProcess` from `tests/regression/test_test_load_governor.py`.
