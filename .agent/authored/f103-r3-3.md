## Row granularity — ruling (DECISION D16, 2026-08-08)
A ledger ROW is one FINALIZED TASK RUN, not one HTTP request, and its
`call_id` is the deterministic `"<job_id>:<task_id>"`. The Design above
says the writer consumes the same records the actuals feature produces,
and what that feature puts on disk is
`task_runs/<task_id>/provider_evidence.json` — a per-task-run record
carrying `provider_call_count` and aggregated usage counters. No
per-HTTP-request record exists on disk, so backfill has nothing finer to
read, and synthesising one row per counted call would fabricate ids,
timestamps and a usage split no file records. Remedy deliberately does
NOT do that: an unmeasured split stays unmeasured (the F075 lesson).
When a per-request evidence record exists, change
`call_id_for_task_run` and the backfill scan to read it — `call_id` is
already the primary key, so no schema migration is needed.
